HTTP/1.1 keep-alive와 pipelining 한계

한 TCP byte stream의 비용 절감과 순서 제약을 상태·queue로 추적하기 · 개념 60분 + 실습 35분

한 줄 요약
HTTP/1.1 persistent connection은 TCP/TLS 연결 비용을 여러 request가 나눠 쓰게 하지만, 하나의 순서 있는 byte stream에서는 각 message 경계를 정확히 알아야 다음 message를 읽을 수 있고 pipelined response도 request 순서를 지켜야 한다. 그래서 성능은 handshake 횟수만이 아니라 pool·framing·queue·timeout·retry 불확실성으로 결정된다.

1. 선수 용어 사전

Persistent connectionHTTP message 하나가 끝난 뒤 TCP connection을 닫지 않고 같은 origin의 다음 request/response에 재사용하는 방식. HTTP/1.1에서는 특별히 닫겠다는 신호가 없으면 persistence가 기본이다.
Keep-alive보통 persistent connection을 뜻하는 실무 표현. HTTP/1.1 persistence와 과거 HTTP/1.0의 Connection: keep-alive 관례를 구분해야 한다. Keep-Alive: timeout=... 같은 값은 모든 구현이 동일하게 보장하는 표준 계약으로 가정하면 안 된다.
Connection poolClient나 proxy가 destination별 연결을 보관·대여·반납하는 자료구조. idle/active 수, 최대 연결 수, 대기 queue, idle timeout, max age가 핵심 state다.
Pipelining앞 request의 response를 기다리지 않고 동일 HTTP/1.1 connection에 뒤 request를 연속 전송하는 기능. Server는 response를 request와 같은 순서로 보내야 하므로 앞 작업이 느리면 뒤 결과도 막힌다.
HOL blockingHead-of-line blocking. 줄 맨 앞 항목의 지연이 뒤의 독립적인 항목 진행까지 막는 현상. HTTP/1.1 response ordering의 application HOL과 TCP 손실 복구의 byte-stream HOL을 분리해 말한다.
Message framing한 message의 끝을 판정하는 규칙. Content-Length, chunked transfer coding, method/status가 content를 허용하지 않는 규칙, connection close 등이 우선순위에 따라 사용된다.
Hop-by-hop field한 transport hop에만 적용되고 proxy가 다음 hop으로 그대로 전달하면 안 되는 field. Connection과 그 값이 지목한 field가 대표적이다.
Idle timeout일정 시간 traffic이 없는 connection을 owner가 닫는 timer. Client, proxy, LB, NAT/conntrack, server가 서로 다른 timer를 가질 수 있다.
Stale socketPool에는 재사용 가능해 보이지만 peer나 middlebox는 이미 닫았거나 state를 지운 connection. 다음 write 때 EOF, RST, broken pipe 등으로 드러날 수 있다.
FIN / RSTFIN은 해당 방향의 정상 byte 전송 종료, RST는 connection state의 즉시 abort를 알리는 TCP 신호다. Application이 이를 관찰하는 시점은 실제 peer 종료 시점보다 늦을 수 있다.

2. 왜 중요한가

새 request마다 TCP와 TLS를 다시 연결하면 RTT, CPU, ephemeral port, NAT/conntrack state 비용이 늘어난다. 재사용은 이를 줄이지만 connection이 오래 살수록 양 끝과 중간 장비의 state lifetime이 어긋날 가능성도 커진다.

  • Latency: 이미 열린 connection은 handshake를 생략하고 congestion window가 유지될 수도 있어 빠르다. 다만 과도하게 오래된 connection은 path 변화나 stale state를 품을 수 있다.
  • Capacity: Connection 수를 늘리면 HTTP/1.1 동시성은 올라가지만 server fd, memory, proxy upstream slot, NAT port를 소비한다. 무제한 pool은 해결책이 아니다.
  • Correctness: 이전 response content를 끝까지 소비하지 않으면 다음 response의 시작 위치를 모른다. Pool에 반납해서는 안 된다.
  • Failure ambiguity: 재사용 socket에 request를 쓴 직후 reset되면 server가 처리 전인지, 처리 후 response만 잃었는지 client가 모를 수 있다. 비멱등 요청 blind retry는 중복 side effect를 만든다.

  1. 대여: Client는 scheme·host·port와 TLS/security 조건이 맞는 idle connection을 pool에서 가져온다. 없으면 pool limit 안에서 새 TCP를 연결하거나 queue에서 기다린다.
  2. Framing: Parser는 response A의 content 길이를 확정하고 그 byte를 모두 소비해야 B의 status line을 정확히 찾을 수 있다.
  3. Pipelining: A 응답 전 B와 C를 보낼 수 있으나 response는 A, B, C 순서다. B가 먼저 계산돼도 A 앞을 추월할 수 없어 application HOL이 생긴다.
  4. Proxy 경계: Client↔LB C1과 proxy↔origin U7은 서로 다른 connection이다. 한쪽의 keep-alive 설정이나 Connection: close를 반대편에 그대로 동일시하면 안 된다.
  5. TCP HOL: U7에서 앞 sequence byte가 손실되면 뒤에 도착한 byte도 application에는 순서대로 전달돼야 한다. 이는 HTTP response ordering과 별개 층의 blocking이다.
  6. 반납: Response content를 완전히 읽고 protocol 상태가 clean하며 close 신호가 없을 때만 pool에 idle로 반납한다.
핵심 불변식: 하나의 HTTP/1.1 connection에서 request와 final response의 대응은 순서로 결정된다. 따라서 sender와 recipient가 message length를 같은 방식으로 판정해야 하고, response N의 끝이 확정되기 전에는 response N+1의 시작도 안전하게 확정할 수 없다.

4. CS 수준 내부 동작

Persistence는 framing 위에 세워진다

Connection close만으로 body 끝을 알리는 response는 connection을 다음 message에 재사용할 수 없다. 재사용하려면 recipient가 Content-Length, 마지막 chunk, HEAD/1xx/204/304 같은 no-content 규칙, CONNECT 성공 후 tunnel 전환 등으로 현재 message 끝을 스스로 판정해야 한다. 서로 다른 parser가 Content-Length와 Transfer-Encoding 충돌을 다르게 해석하면 단순 오류를 넘어 request smuggling 보안 문제가 된다.

State owner와 성공 확정 시점

  • Client library: pool key, lease, idle eviction, response consumption, retry eligibility를 소유한다. send() 반환이나 kernel write 성공은 origin 처리 성공이 아니다.
  • Kernel: TCP sequence, ACK, retransmission, send/receive buffer를 소유한다. TCP ACK는 peer kernel byte 수신 증거다.
  • LB/NAT: flow mapping과 idle timer를 소유한다. State가 만료되어도 client socket object가 즉시 사라지지는 않는다.
  • Server: keep-alive timeout, connection당 최대 request, parser, application 처리 상태를 소유한다. 정상 drain에서는 새 요청을 제한하고 in-flight를 마친 뒤 닫는다.
  • Business system: transaction commit과 idempotency record를 소유한다. Response 유실 시 status query나 dedup state가 최종 판정 근거다.

Stale connection race의 failure window

t0에 connection이 idle pool에 들어가고, t1에 LB가 idle timeout으로 mapping을 지우며, t2에 client가 같은 socket을 대여하고, t3에 POST byte를 쓴 직후 RST를 받을 수 있다. 실패가 “쓰기 전”으로 확정되면 안전한 재연결이 쉽지만, 일부 또는 전체 request가 origin에 도달했는지 모르면 결과는 ambiguous다. TCP keepalive probe도 죽은 peer 탐지에는 도움을 주지만 모든 NAT·application 상태와 business outcome을 보증하지 않는다.

7. 35분 실습: 한 TCP에서 두 HTTP/1.1 response 읽기

사전 조건: Docker Desktop, 저장소의 labs/basic-network-observability. 실행 전 예측한다: “두 GET의 client source port가 같은가?”, “첫 response body를 읽지 않으면 왜 다음 response를 안전하게 해석할 수 없는가?”, “Server를 idle 중 종료한 뒤 같은 socket write는 어디서 실패하는가?”

0단계 · Lab 시작과 HTTP/1.1 server (5분)

cd labs/basic-network-observability
make up
docker compose exec api sh -lc 'python3 -m http.server 9005 --bind 0.0.0.0 --protocol HTTP/1.1 --directory /etc'

마지막 명령은 foreground다. 이 terminal을 A로 둔다. Python 버전이 --protocol을 지원하지 않으면 python3 -m http.server --help로 확인하고, 실습은 기존 HTTP/1.0 server의 close framing 비교로 축소한다.

1단계 · Packet과 socket 관측 (5분)

Terminal B:

docker compose exec client sh -lc "tcpdump -ni eth0 -tttt -nn -A -s 0 'host 172.28.0.20 and tcp port 9005'"

예상: 첫 요청 전에 SYN/SYN-ACK/ACK 한 번만 보이고, 뒤의 두 GET과 두 HTTP/1.1 response가 같은 5-tuple에 나타난다.

2단계 · 순차 재사용과 body 소비 (10분)

Terminal C에서 아래 명령을 실행한다. 첫 response의 read()가 message content를 끝까지 소비하므로 같은 connection을 재사용할 수 있다.

docker compose exec client python3 -c 'import http.client; c=http.client.HTTPConnection("172.28.0.20",9005,timeout=3); c.request("GET","/hostname",headers={"Host":"api.lab"}); r=c.getresponse(); print("R1",r.status,r.getheader("Content-Length"),r.read()); print("PORT1",c.sock.getsockname()[1]); c.request("GET","/hosts",headers={"Host":"api.lab"}); r=c.getresponse(); print("R2",r.status,len(r.read())); print("PORT2",c.sock.getsockname()[1]); c.close()'

예상 관찰: PORT1과 PORT2가 같고 handshake가 추가되지 않는다. Server log도 같은 client connection에서 두 GET을 순서대로 보인다.

3단계 · Raw pipelining과 순서 예측 (8분)

docker compose exec client python3 -c 'import socket,time; s=socket.create_connection(("172.28.0.20",9005),3); q=b"GET /hostname HTTP/1.1\r\nHost: api.lab\r\n\r\nGET /hosts HTTP/1.1\r\nHost: api.lab\r\nConnection: close\r\n\r\n"; s.sendall(q); time.sleep(.2); data=b""; exec("while True:\n b=s.recv(65535)\n if not b: break\n data+=b"); print(data.decode("latin1")[:1200])'

예상: request 둘은 response 대기 없이 연속 전송되지만 출력의 response는 /hostname 다음 /hosts 순서다. 이것이 “multiplexing”이 아닌 이유를 설명한다.

4단계 · 실패 주입과 cleanup (7분)

Terminal A에서 Ctrl-C로 server를 종료한 뒤 idle connection 재사용 상황을 떠올린다. 실제 client library가 FIN을 먼저 읽으면 재연결할 수 있고, race에서는 write 뒤 EOF/RST가 날 수 있다. 비멱등 POST였다면 도달 여부를 packet·server transaction log 없이 단정할 수 없다.

docker compose down -v

자주 나는 오류: port 9005 refused면 server terminal과 container IP를 확인한다. ResponseNotReady가 나면 이전 response를 완전히 읽지 않은 것이다. tcpdump 권한 오류면 lab image·capability를 docker compose config에서 확인한다. Cleanup은 임시 container/network/volume만 제거한다.

8. 놓치기 쉬운 함정

  • HTTP/1.1에서 Connection: keep-alive가 항상 필요한 것은 아니다. Persistence가 기본이며 닫으려면 보통 Connection: close를 사용한다.
  • Keep-alive는 TCP keepalive와 다르다. 전자는 HTTP connection 재사용, 후자는 kernel의 오래된 TCP peer 탐지 probe다.
  • Response 객체 close와 body 완전 소비는 library마다 다르다. Close가 drain 후 reuse인지 socket 폐기인지 공식 문서를 확인한다.
  • LB 한 개가 connection 하나를 end-to-end 유지하지 않는다. Front connection과 backend pool은 별도 5-tuple·timer·TLS state다.
  • Idle timeout만 맞추면 끝이 아니다. Max request, max age, deploy drain, DNS rotation, NAT timeout도 connection lifetime을 바꾼다.
  • Pipelining은 HTTP/2 multiplexing이 아니다. HTTP/1.1 response는 request 순서를 지키지만 HTTP/2 stream은 독립적으로 interleave된다.
  • Connection 수 증가는 공짜 병렬성이 아니다. fd, memory, TLS CPU, congestion competition, ephemeral port, upstream capacity를 함께 소비한다.
  • Parser 관대함은 호환성이 아니라 공격면일 수 있다. Front/back framing 불일치는 request smuggling으로 이어진다.
  • Slowloris 방어: header/body read timeout, header size, connection 수, request rate를 경계별로 제한하고 정상 느린 client와 trade-off를 측정한다.

9. 대기업 기술 면접 질문

  1. “HTTP/1.1 keep-alive가 성능을 높이는데도 장애를 만드는 이유를 설명하세요.”
    좋은 답변 구조: handshake·cwnd 비용 절감 → pool owner/state → message framing 불변식 → LB/NAT/server timer 불일치 → stale reuse timeline → method별 retry eligibility → bounded pool·idle/max-age·drain·metrics.
  2. “Pipelining과 HTTP/2 multiplexing의 차이는 무엇입니까?”
    좋은 답변 구조: 한 TCP ordered byte stream 공통점 → HTTP/1.1 request 순서와 ordered response HOL → HTTP/2 stream ID와 frame interleave → TCP loss HOL 잔존 → workload 수치(p50/p99·동시성) → parallel connection/HTTP/3 대안.
  3. “POST를 재사용 connection에 보낸 직후 reset됐습니다. 어떻게 처리합니까?”
    좋은 답변 구조: bytes written/ACK/business commit 성공 경계 → FIN/RST·pcap·proxy/origin log 수집 → 결과 불명확 인정 → blind retry 금지 → idempotency key·dedup/status query·reconciliation → timeout 정렬과 rollback.

10. 회상·확인 문제와 채점 기준

어제 내용 회상 3문제

  1. HTTP method의 safe와 idempotent는 어떻게 다른가?
  2. TCP ACK, HTTP 2xx, DB commit의 성공 경계를 구분하라.
  3. Content-Type, Accept, Content-Length가 각각 설명하는 것은?

짧은 정답: ① Safe는 요청한 주된 의미가 read-only, idempotent는 반복 적용의 의도된 효과가 같다는 뜻이다. ② Peer kernel byte 수신, protocol 결과, durable business state 확정으로 owner가 다르다. ③ 보낸 content media type, 원하는 response media type, HTTP/1.1 message content byte 길이다.

오늘 내용 확인 3문제

  1. HTTP/1.1 connection을 재사용하려면 response body를 왜 완전히 소비해야 하는가?
  2. Client idle timeout 90초, LB timeout 60초일 때 70초 idle 후 어떤 race가 가능한가?
  3. HTTP/1.1 pipelining의 application HOL과 TCP HOL을 각각 설명하라.

짧은 정답: ① 현재 message 끝이 확정돼야 다음 status line 시작을 판정하고 clean socket을 pool에 반납할 수 있다. ② Client는 socket을 live로 대여하지만 LB flow는 만료돼 다음 write에 EOF/RST가 나며 request 도달 여부가 불명확할 수 있다. ③ 앞 response의 순서 제약이 뒤 response 전송을 막는 것과, 앞 sequence byte 손실이 뒤 byte의 application 전달을 막는 것이다. 문항당 정의 1점, owner/flow 1점, failure·대안 1점으로 총 9점이다.
