retry eligibility, exponential backoff, jitter

“실패했으니 다시”를 eligibility·deadline·부하 예산이 있는 제어 알고리즘으로 바꾼다 · 이론 60분 + 실습 35분

한 줄 요약
Retry는 성공 확률을 높이지만 같은 요청을 추가로 만들어 장애 중인 system의 부하를 키운다. 먼저 operation이 다시 실행돼도 안전한지와 error가 transient인지 판정하고, 남은 deadline 안에서 capped exponential backoff·jitter·retry budget으로 시도 수를 제한한다.

1. 선수 용어 사전

Attempt / retryAttempt는 실제 전송 1회다. 첫 attempt 뒤 추가 attempt가 retry다. maxAttempts=3은 보통 최초 1회+retry 2회를 뜻하지만 제품 문서를 확인한다.
Retry eligibilityMethod semantics, side effect, error class, commit 가능성, 남은 deadline을 보고 재시도해도 되는지 판정하는 조건이다.
Transient / persistentTransient fault는 잠시 뒤 회복할 가능성이 있고, persistent fault는 같은 입력·설정으로 다시 해도 반복된다. 503과 일시적 connection reset은 전자 후보, 인증 실패·잘못된 요청·NXDOMAIN은 보통 후자다.
Idempotent동일 operation을 여러 번 요청해도 의도한 server effect가 한 번과 같은 성질이다. HTTP GET·PUT·DELETE는 규격상 idempotent지만 application side effect까지 자동 보장하는 것은 아니다.
BackoffRetry 사이에 기다려 server가 회복할 시간을 주는 정책이다. 즉시 반복은 queue와 connection을 더 압박한다.
Capped exponential backoffcap_n = min(maxBackoff, base × 2^(n−1))처럼 상한까지 지수적으로 대기 범위를 늘린다.
JitterBackoff에 random 분산을 넣어 다수 client의 재시도 시각을 흩뜨린다. Full jitter는 uniform(0, cap_n)에서 뽑는다.
Thundering herd동시에 실패한 client들이 같은 간격으로 다시 몰려 회복 중인 server를 재차 과부하시키는 현상이다.
Retry budget / token bucket정상 요청 대비 허용 retry 비율 또는 token 수를 제한한다. 성공 시 token을 보충하고 retry 시 소비해 장애 중 fail-fast한다.
Retry-After / pushbackServer가 다음 시도까지 기다릴 최소 시간을 알려주는 신호다. HTTP Retry-After와 protocol별 pushback을 client policy·deadline과 함께 적용한다.
Amplification factor원 요청 수 대비 실제 attempt 수다. 3개 계층이 각각 최대 3번 시도하면 최악에는 downstream attempt가 3³=27까지 늘 수 있다.
Commit pointOperation이 이미 적용됐을 수 있어 transport 실패만으로 미실행을 단정할 수 없는 경계다. gRPC는 response header 수신 뒤 RPC를 committed로 보고 더 이상 자동 retry하지 않는다.

2. 왜 중요한가

Retry는 새 부하를 만든다. 1,000 RPS가 실패하고 client가 즉시 3번 더 보내면 4,000 attempts/s가 되어 회복을 늦춘다. 반대로 모든 error를 포기하면 짧은 packet loss나 rolling restart도 사용자 실패가 된다. 핵심은 “몇 번?”보다 “어떤 operation·어떤 failure·어느 계층·어떤 budget에서?”다.

  • 정확성: 결제 POST를 blind retry하면 duplicate side effect가 생길 수 있다.
  • 가용성: 짧은 transient fault는 retry로 숨길 수 있지만 overload에는 retry가 독이 된다.
  • 공정성: Token budget이 없으면 aggressive client가 server capacity를 더 많이 차지한다.
  • Latency: Backoff 대기와 attempt timeout의 합이 전체 deadline보다 작아야 한다.
  • 면접: Status code 목록 암기보다 ambiguity, idempotency, jitter 분포, 다계층 증폭과 관측성을 설명해야 한다.

  1. Root: Retry loop 밖에서 전체 deadline과 operation ID를 만든다. Attempt마다 deadline을 새로 만들지 않는다.
  2. Attempt 1: DNS·connect·TLS·write·response 단계 중 어디서 실패했는지 기록한다. 503은 overload일 수 있어 즉시 반복하지 않는다.
  3. Eligibility: retryable error ∧ idempotent/deduplicated operation ∧ token available ∧ delay+attempt budget < remaining일 때만 진행한다.
  4. Backoff: Exponential cap이 회복 시간을 주고 jitter가 client synchronization을 푼다. Server pushback이 있으면 local minimum과 상한 정책을 적용한다.
  5. Attempt 2: Network connection은 새것이어도 logical operation ID는 같아야 server가 duplicate를 합칠 수 있다.
  6. Terminal: Success, non-retryable, committed/ambiguous, deadline exceeded, retry budget exhausted 중 정확한 이유로 끝낸다.
설계 불변식: 한 logical request의 모든 attempt와 sleep은 최초 deadline 안에 있어야 한다. Side effect가 가능한 operation은 idempotency/dedup 증거 없이는 자동 retry하지 않으며, 한 call chain에서 retry owner는 가능한 한 한 계층으로 제한한다.

4. CS 수준 내부 동작

Failure window와 ambiguity

SYN 전 실패는 server가 request를 보지 못했을 가능성이 높다. 하지만 request body 전송 뒤 response가 유실되면 server가 이미 commit했을 수 있다. Transport의 “응답 없음”과 application의 “미적용”은 다르므로 method semantics와 idempotency key가 retry safety를 결정한다.

Backoff 분포

Capped exponential 값이 800ms라면 deterministic client는 모두 800ms 뒤 몰린다. Full jitter는 0~800ms 균등분포, equal jitter는 400~800ms, decorrelated jitter는 이전 delay를 기반으로 다음 범위를 만든다. 평균 latency·burst 완화·최소 휴식의 trade-off가 다르다.

Positive feedback와 queueing

Server 처리율보다 도착률이 크면 queue가 늘고 latency가 상승해 timeout→retry→도착률 증가가 반복된다. Retry budget과 load shedding은 이 feedback loop의 gain을 낮춘다. Timeout만 늘리면 Little’s Law의 체류시간과 동시 점유가 더 커질 수 있다.

다계층 곱셈

Client, gateway, service가 각각 3 attempts를 허용하면 최하단은 최대 27번 호출될 수 있다. 그래서 가장 많은 context를 가진 edge 또는 service 한 곳을 retry owner로 정하고 다른 계층의 transparent retry까지 inventory한다.

Token bucket과 회복

Retry token은 성공 시 보충하고 추가 attempt에서 소비한다. 장애로 성공이 줄면 token이 고갈되어 fail-fast하고 server가 회복할 공간을 만든다. Tenant·resource별 bucket을 분리하지 않으면 한 noisy tenant가 다른 tenant retry를 막을 수 있다.

관측 편향

최종 성공만 기록하면 첫 실패와 추가 부하가 사라진다. Logical request latency, attempt별 latency, backoff sleep, retry success rate, amplification factor를 따로 기록하고 load test는 원래 도착률을 고정해 coordinated omission을 피한다.

7. 35분 실습: 503 burst와 full jitter 비교

사전 조건: Docker Desktop/Engine과 Compose, 저장소 root. 실행 전에 즉시 5회 retry와 jitter 5회 retry가 API log·총 소요시간에 어떤 차이를 만들지 예측한다.

0단계 · 시작과 단일 실패 (5분)

make doctor
make up
make ps
docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client curl -sS -o /dev/null -w 'code=%{http_code} total=%{time_total}\n' \
  http://proxy:8080/api/status/503

예상: API가 의도적으로 503을 반환한다. 이것이 failure injection이며 network timeout과 달리 server 응답 증거가 있다.

1단계 · Anti-pattern: 즉시 5 attempts (7분)

docker compose -f labs/basic-network-observability/docker-compose.yml exec client sh -c '
for n in 1 2 3 4 5; do
  curl -sS -o /dev/null -w "attempt=$n code=%{http_code} total=%{time_total}\n" \
    http://proxy:8080/api/status/503
done
'

예상: 5개 request가 거의 연속 도착한다. Client가 많다면 같은 burst가 겹쳐 장애 중인 server를 더 압박한다.

2단계 · Full jitter와 eligibility gate (13분)

docker compose -f labs/basic-network-observability/docker-compose.yml exec client python -c '
import random, time, urllib.error, urllib.request
url = "http://proxy:8080/api/status/503"
deadline = time.monotonic() + 4.0
base, cap, max_attempts = 0.2, 1.6, 5
for attempt in range(1, max_attempts + 1):
    try:
        urllib.request.urlopen(url, timeout=max(0.1, deadline-time.monotonic()))
        print("success", attempt); break
    except urllib.error.HTTPError as exc:
        retryable = exc.code in (429, 502, 503, 504)
        remaining = deadline - time.monotonic()
        print(f"attempt={attempt} code={exc.code} retryable={retryable} remaining={remaining:.3f}s")
        limit = min(cap, base * (2 ** (attempt - 1)))
        delay = random.uniform(0, limit)
        if not retryable or attempt == max_attempts or delay + 0.2 >= remaining:
            print("stop: eligibility/attempt/deadline gate"); break
        print(f"sleep={delay:.3f}s cap={limit:.3f}s")
        time.sleep(delay)
'

예상: Delay 상한은 0.2→0.4→0.8→1.6초로 증가하고 실제 sleep은 0부터 상한 사이에 분산된다. 남은 budget이 부족하면 5회 전에 종료할 수 있다.

3단계 · Non-retryable과 증폭 계산 (5분)

docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client curl -sS -o /dev/null -w '400 code=%{http_code}\n' \
  http://proxy:8080/api/status/400
docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client python -c 'print("3 layers × 3 attempts =", 3**3, "downstream attempts")'

예상: 400은 같은 입력을 반복해도 고쳐지지 않으므로 1회에서 멈춘다. 세 계층 retry는 최악 27 attempts로 증폭된다.

4단계 · 증거와 cleanup (5분)

docker compose -f labs/basic-network-observability/docker-compose.yml \
  logs --since=10m --timestamps api proxy
make down

자주 나는 오류: Docker가 꺼져 있으면 make doctor에서 중단한다. Random delay는 실행마다 다르다. Python command quoting이 깨지면 single quote 바깥에 문자를 붙이지 않는다. Lab의 503은 항상 실패하므로 “최종 성공”이 아니라 attempt 분산과 stop gate를 관찰한다. Cleanup은 make down만 사용한다.

8. 놓치기 쉬운 함정

  • Retryable status와 retryable operation은 별개다. 503이어도 non-idempotent commit이 가능하면 위험하다.
  • MaxAttempts와 maxRetries를 혼동하지 않는다.
  • Deadline을 attempt마다 리셋하지 않는다.
  • Exponential backoff만으로 herd가 사라지지 않는다. Jitter가 필요하다.
  • 모든 process에 같은 random seed를 쓰지 않는다.
  • Retry-After를 무시하거나 무한히 신뢰하지 않는다.
  • Proxy·SDK의 transparent retry를 inventory한다.
  • Retry budget을 tenant별로 격리하지 않으면 noisy neighbor가 생긴다.
  • 최종 성공만 기록하면 실패율·부하·latency가 가려진다.
  • Overload의 1차 처방은 capacity/admission/load shedding이지 retry 확대가 아니다.

9. 대기업 기술 면접 질문

  1. “어떤 HTTP/gRPC 실패를 자동 retry하겠습니까?”
    좋은 답변 구조: operation semantics·idempotency → failure phase·status → commit ambiguity → deadline·token → server pushback → 예외와 관측성.
  2. “Exponential backoff에 왜 jitter가 필요하고 어떤 분포를 쓰겠습니까?”
    좋은 답변 구조: synchronized clients와 herd → capped formula → full/equal/decorrelated 비교 → latency·burst trade-off → PRNG seed → metric.
  3. “3-tier system의 retry storm을 막는 설계를 제안하세요.”
    좋은 답변 구조: 3³ amplification 수치 → single owner → retry budget/token bucket → deadline gate → load shedding → canary/rollback.

10. 회상·확인 문제와 채점 기준

어제 내용 회상 3문제

  1. Child deadline이 parent보다 길어지면 안 되는 이유는?
  2. Transport cancel과 handler 종료가 같은 사건이 아닌 이유는?
  3. Commit 이후 반드시 끝낼 작업을 안전하게 분리하는 방법은?

짧은 정답: ① End-to-end budget과 자원 회수 시점이 깨진다. ② Cancellation은 협력적이라 handler·driver가 신호를 확인해야 한다. ③ Durable queue/outbox에 새 owner·deadline·retry policy로 넘긴다.

오늘 내용 확인 3문제

  1. 503을 받았는데도 retry하면 안 되는 두 조건은?
  2. Full jitter의 식과 해결하는 문제는?
  3. 각각 3 attempts인 세 계층이 만드는 최악의 downstream attempt 수는?

짧은 정답: ① Non-idempotent/commit ambiguity, deadline·retry budget 부족이다. ② uniform(0, min(cap, base×2^(n−1)))이며 synchronized herd를 분산한다. ③ 27회다. 문항당 정의 1점, 내부 흐름 1점, failure·trade-off 1점으로 총 9점이다.
