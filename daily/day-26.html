QUIC/HTTP/3, stream-level loss recovery

UDP 위 QUIC의 packet·stream·timer·queue를 장애까지 추적 · 개념 65분 + 실습 35분

한 줄 요약
QUIC은 UDP datagram 안에 암호화된 packet과 frame을 싣고, HTTP/3 request를 독립 stream으로 multiplex한다. 한 packet의 손실은 그 안의 stream offset 데이터만 새 packet number로 다시 보내므로 다른 stream의 이미 도착한 데이터 전달을 막지 않지만, 모든 stream이 공유하는 congestion window·connection flow-control·NIC/CPU queue까지 독립되는 것은 아니다.

1. 선수 용어 사전

QUIC약어를 풀어 쓰는 이름이 아니다. UDP 위에서 secure connection, reliable stream, loss recovery, congestion control, connection migration을 제공하는 transport protocol이다.
UDP datagram주소와 port가 붙은 message 단위. UDP 자체는 순서·재전송·연결 상태를 보장하지 않으며 QUIC endpoint가 user space에서 그 기능을 구현한다.
QUIC packet / framePacket은 packet number와 보호 경계를 가진 전송 단위이고, frame은 그 안의 의미 단위다. STREAM, ACK, CRYPTO, MAX_DATA, PATH_CHALLENGE 등이 frame이다.
Connection ID5-tuple이 바뀌어도 logical connection을 식별하도록 endpoint가 발급하는 byte sequence. LB routing과 migration에 쓰이지만 인증 token 자체는 아니다.
Stream ID / offsetStream ID는 독립 ordered byte stream을, offset은 그 stream 안 byte 위치를 식별한다. Receiver는 offset 기준으로 gap을 채워 application에 순서대로 전달한다.
Packet number spaceInitial, Handshake, Application Data별 ACK·loss state 영역. Packet number는 같은 space에서 증가하며 손실 packet 번호를 재사용하지 않는다.
ACK rangeReceiver가 받은 packet number 구간을 압축해 알리는 정보. ACK는 packet 수신을 뜻하며 application transaction 성공을 뜻하지 않는다.
Loss detection / PTOACK의 packet·time threshold로 손실을 추론하는 절차와, ACK가 늦을 때 probe를 보내는 Probe Timeout. PTO 만료가 반드시 특정 packet 손실 확정이라는 뜻은 아니다.
Congestion / flow control혼잡 제어는 network가 감당할 in-flight byte를 제한하고, 흐름 제어는 receiver buffer가 감당할 stream·connection byte를 제한한다. Owner와 보호 대상이 다르다.
CRYPTO frameTLS 1.3 handshake message를 운반하는 QUIC frame. QUIC은 TLS record layer를 그대로 싣지 않고 TLS와 transport key phase를 결합한다.
NAT rebinding / migrationNAT mapping이나 client network가 바뀌어 source IP/port가 달라지는 현상과, QUIC connection을 새 path에서 검증·계속하는 동작이다.
HTTP/3 · QPACKHTTP/3는 HTTP semantics를 QUIC stream/frame에 mapping한다. QPACK은 header compression이며 encoder/decoder stream과 dynamic table dependency를 관리한다.

2. 왜 중요한가

HTTP/3를 “HTTP를 UDP로 바꿔서 빠르다”라고 외우면 UDP 차단, NAT idle timeout, path MTU black hole, QPACK blocking, retry·0-RTT replay 같은 production failure를 설명할 수 없다. 핵심은 transport state의 재배치다.

  • Failure isolation: TCP byte sequence 하나를 공유하는 HTTP/2와 달리 QUIC은 stream별 offset을 복구한다. 하지만 shared congestion controller가 줄어들면 모든 stream 송신률은 함께 낮아진다.
  • Latency: Transport와 TLS handshake를 결합해 setup round trip을 줄일 수 있지만 certificate, route, CPU, loss가 사라지는 것은 아니다.
  • Operability: Kernel TCP 도구만 보던 환경에서는 encrypted user-space transport의 loss·PTO·stream state가 안 보일 수 있다. Endpoint telemetry가 필수다.
  • Correctness: Packet ACK, stream delivery, HTTP response, business commit은 서로 다른 성공 경계다. Timeout 뒤 retry할 때 이 구분이 중복 실행 여부를 결정한다.

  1. UDP path: OS는 UDP socket까지 datagram을 전달하지만 connection reliability는 QUIC endpoint가 소유한다. Firewall·NAT·LB가 UDP/443과 idle state를 별도로 지원해야 한다.
  2. Initial: Client가 선택한 destination connection ID와 TLS ClientHello를 보낸다. Initial UDP datagram은 path MTU 탐색과 amplification 방어를 위해 최소 크기 규칙을 지킨다.
  3. Validation과 handshake: Server는 client address가 검증되기 전 받은 byte의 약 3배를 넘겨 보내지 못한다. 큰 certificate chain은 Retry나 추가 client traffic 없이는 budget에 막힐 수 있다.
  4. HTTP/3 시작: 양쪽은 control stream을 하나씩 열고 SETTINGS를 교환하며 QPACK encoder/decoder stream을 둔다. 각 request-response는 보통 client-initiated bidirectional stream을 사용한다.
  5. 손실 격리: PN 42가 사라져 A에 gap이 나도 PN 43의 B bytes는 B stream offset이 연속이면 application에 전달 가능하다. TCP처럼 connection 전체 byte sequence gap을 기다리지 않는다.
  6. 복구: Sender는 PN 42 자체를 재전송하지 않는다. 잃어버린 STREAM frame의 정보가 새 packet number 47에 재구성될 수 있으며 congestion controller는 loss를 반영해 sending budget을 줄인다.
  7. Migration: Connection ID로 기존 logical connection을 찾고 새 path의 reachability를 검증한다. 새 path가 검증되기 전에 unbounded response를 보내면 reflection 공격이 된다.
핵심 불변식: 한 stream에서 application에 byte N을 전달하려면 그 stream의 0..N 범위가 연속이어야 한다. 다른 stream의 gap은 이 조건에 포함되지 않는다. 그러나 sender는 connection path의 congestion window와 receiver가 광고한 connection/stream flow-control limit를 모두 지켜야 한다.

4. CS 수준 내부 동작

Packet number와 stream offset을 분리한 이유

Packet number는 network delivery와 ACK/loss 추론을 위한 transport timeline이고, stream offset은 application byte의 위치다. 같은 STREAM range가 loss recovery 과정에서 다른 packet number에 들어갈 수 있다. 그래서 packet 중복 제거와 stream byte 중복 제거는 다른 key를 쓴다.

상태 owner핵심 state와 성공 경계
QUIC senderSent-packet map, bytes-in-flight, RTT estimator, loss timer, congestion window, stream send offset. ACK 후 packet state를 제거해도 HTTP business commit은 모른다.
QUIC receiverReceived PN ranges, stream reassembly gaps, receive windows, connection IDs, path state. Stream별 contiguous prefix만 application에 전달한다.
HTTP/3 layerControl/QPACK streams, SETTINGS, request stream state, GOAWAY. QUIC stream이 살아 있어도 malformed HTTP/3 frame이면 application error다.
ApplicationDeadline, idempotency key, authorization, database transaction. Response loss 뒤 retry가 와도 같은 operation을 한 번만 commit하도록 설계한다.

Loss detection, PTO, congestion response

ACK range와 ACK delay로 RTT sample을 갱신하고, 더 큰 packet들이 충분히 ACK되었거나 시간 threshold를 넘으면 packet을 lost로 선언할 수 있다. PTO는 smoothed RTT·RTT variation·max ACK delay 등을 바탕으로 probe 시점을 잡는다. Reordering이 큰 path에서 threshold가 너무 공격적이면 spurious retransmission, 너무 느슨하면 tail latency가 커진다.

  • ACK path: ACK frame도 loss될 수 있다. ACK가 없다고 data packet loss가 즉시 확정되는 것은 아니며 probe로 liveness를 확인한다.
  • Congestion: Loss 또는 ECN 신호를 network congestion으로 해석해 cwnd를 줄인다. Stream B가 loss-free여도 shared cwnd가 줄면 B의 새 data 전송은 늦어진다.
  • Flow control: MAX_STREAM_DATA와 MAX_DATA limit 중 먼저 닿는 곳에서 sender가 막힌다. Receiver application이 읽고 credit을 갱신하지 않으면 network가 깨끗해도 stalled 된다.
  • BDP 판단: 대략 bandwidth×RTT만큼 in-flight가 필요하다. Window가 BDP보다 지나치게 작으면 throughput을 못 채우고, 너무 크면 per-connection memory와 abusive peer 비용이 커진다.

TLS 1.3 결합과 0-RTT

Initial·Handshake·1-RTT encryption level은 key availability와 packet number space를 분리한다. Certificate path·SNI·ALPN identity 검증은 어제와 동일하게 중요하다. Resumption의 0-RTT는 handshake latency를 줄이지만 replay 가능성을 일반 1-RTT와 동일하게 취급할 수 없으므로 안전한 method와 application anti-replay 정책이 필요하다.

HTTP/3 control stream과 QPACK의 새 dependency

HTTP/3는 request stream끼리 transport-level ordered dependency를 없앴지만 header compression에는 dynamic table dependency가 생길 수 있다. Decoder가 아직 받지 못한 insertion을 참조하면 해당 header block이 blocked 된다. SETTINGS의 blocked-stream 한도와 table capacity로 memory와 latency를 제한하며, critical control/QPACK stream의 예기치 않은 종료는 connection-level error가 될 수 있다.

7. 35분 실습: H3 capability·Alt-Svc·fallback failure 분리

사전 조건: curl, grep, 인터넷 연결. RFC Editor endpoint만 사용한다. 실행 전에 “현재 curl에 HTTP/3 client가 들어 있는가?”, “서버 광고와 실제 협상은 같은가?”, “H3 실패 시 H2가 성공하는가?”를 먼저 예측한다.

0단계 · Client capability 확인 (5분)

curl -V

예상: Features에 HTTP3가 있으면 H3 시도가 가능하다. HTTP2만 있으면 서버나 network가 아니라 local curl build가 첫 blocker다. 이 Mac 기본 curl에서는 HTTP/2만 보일 수 있다.

1단계 · Server의 H3 광고와 H2 baseline (8분)

curl -sSI --http2 https://www.rfc-editor.org/ | \
	  grep -Ei '^(HTTP/|alt-svc:)'

curl -sS -o /dev/null --http2 \
  -w 'code=%{http_code} version=%{http_version} connect=%{time_connect} tls=%{time_appconnect} total=%{time_total}\n' \
  https://www.rfc-editor.org/

예상: H2 response와 alt-svc: h3=":443" 광고를 볼 수 있다. Alt-Svc는 “다음 연결에서 이 alternative를 시도할 수 있다”는 control data이지 현재 요청이 H3였다는 증거가 아니다.

2단계 · H3 only 시도와 오류 계층화 (10분)

curl --http3-only --max-time 8 -sS -o /dev/null \
  -w 'code=%{http_code} version=%{http_version} total=%{time_total}\n' \
  https://www.rfc-editor.org/

분기: Option unknown/unsupported이면 client build 문제다. HTTP/3 feature가 있는데 timeout이면 UDP path·DNS address family·firewall·server reachability를 조사한다. TLS/certificate 오류면 QUIC 도달 뒤 handshake identity 문제다. 성공하면 version이 3으로 관찰된다.

3단계 · 실패 주입과 안전한 fallback (8분)

# HTTP/3 지원 curl에서만: 예약된 TEST-NET 주소로 3초 timeout 유도
curl --http3-only --connect-timeout 3 --max-time 4 \
  --resolve www.rfc-editor.org:443:203.0.113.1 \
  https://www.rfc-editor.org/ -o /dev/null -v

# 실제 주소에서 H2 fallback 성공 확인
curl --http2 --max-time 8 -sS -o /dev/null \
  -w 'fallback code=%{http_code} version=%{http_version} total=%{time_total}\n' \
  https://www.rfc-editor.org/

첫 명령은 option 지원 환경에서만 실행하고 실패가 정상이다. 두 번째가 성공하면 application endpoint 전체 장애가 아니라 H3/client/path failure로 범위를 줄일 수 있다.

4단계 · 기록과 cleanup (4분)

Client version/features, Alt-Svc, H2/H3 result, exact error, timestamp, network를 표 한 줄로 남긴다. 파일·route·firewall을 바꾸지 않았으므로 cleanup은 없다. --resolve는 해당 process에만 적용된다.

자주 나는 오류: Corporate proxy가 UDP를 지원하지 않으면 직접 연결과 결과가 다르다. IPv4/IPv6 path도 나눠 본다. H3 option이 없는 curl을 반복 설치 없이 재시도하지 말고 capability blocker로 기록한다. Alt-Svc cache가 결과에 영향을 주면 fresh client profile 여부를 명시한다.

8. 놓치기 쉬운 함정

  • QUIC은 raw HTTP over UDP가 아니다. Reliable stream, TLS 1.3, loss recovery, flow/congestion control을 endpoint가 구현한다.
  • Packet을 그대로 재전송하지 않는다. Lost packet의 frame 정보가 새 packet number로 다시 packetize된다.
  • Stream-level HOL 제거가 무한 병렬성은 아니다. cwnd, connection window, CPU, NIC, QPACK control dependency는 공유된다.
  • ACK는 application 성공이 아니다. Peer QUIC stack 수신과 database commit 사이에는 parser, authorization, queue, transaction이 남아 있다.
  • UDP라서 timeout이 없지 않다. QUIC idle timer, PTO, application deadline, NAT/LB UDP state timeout이 모두 있다.
  • Connection migration은 모든 network change에서 무조건 성공하지 않는다. Peer policy, CID routing, path validation, address family, enterprise firewall이 막을 수 있다.
  • Alt-Svc가 보인다고 현재 H3가 아니다. Client capability와 실제 negotiated protocol을 별도 증거로 수집한다.
  • 큰 Initial을 IP fragmentation에 맡기지 않는다. Tunnel/VPN을 포함한 path MTU와 probe 결과를 본다.
  • 0-RTT는 0ms도, exactly-once도 아니다. Replay와 rejection을 application semantics로 다룬다.

9. 대기업 기술 면접 질문

  1. “HTTP/2의 TCP HOL과 HTTP/3의 stream-level loss recovery를 packet 예시로 비교하세요.”
    좋은 답변 구조: H2 streams→TCP 단일 byte sequence gap→모두 kernel delivery 대기 → QUIC packet number와 stream offset 분리 → A loss/B delivery → 새 PN에 A frame 정보 재전송 → shared cwnd·flow window라는 남은 coupling.
  2. “모바일에서 H3 p99가 급증했지만 H2는 정상입니다. 어떻게 진단·완화합니까?”
    좋은 답변 구조: client/ISP/region 분할 → capability·Alt-Svc·negotiation → UDP/443, Initial/Retry, MTU, NAT idle, PTO/loss/CID migration 증거 → h2 fallback 확인 → cohort Alt-Svc 축소/canary rollback → 재확대 기준.
  3. “QUIC connection을 L4 LB 뒤에서 운영할 때 상태와 보안 경계를 설계하세요.”
    좋은 답변 구조: 5-tuple 변화 요구사항 → CID encoding/routing owner → key·rotation·retirement/stateless reset → anti-amplification/path validation → per-connection memory/stream limit → drain/failover → CID privacy와 observability trade-off.

10. 회상·확인 문제와 채점 기준

어제 내용 회상 3문제

  2. CertificateVerify와 Finished가 보장하는 것은 어떻게 다른가?
  3. TCP connect 성공과 TLS·HTTP 성공을 왜 분리해야 하는가?

짧은 정답: ① ClientHello SNI는 server 설정/cert 선택, client는 SAN과 intended hostname 비교, ALPN은 상위 protocol 협상에 쓴다. ② CertificateVerify는 private-key possession과 transcript signature, Finished는 handshake secret과 transcript의 key confirmation/integrity를 확인한다. ③ Route/transport, identity/encryption, application parser/transaction의 owner와 failure가 다르기 때문이다.

오늘 내용 확인 3문제

  1. PN 42의 STREAM A frame이 손실될 때 B가 전달될 수 있는 조건과 B도 느려질 수 있는 조건을 설명하라.
  2. QUIC packet 재전송이 아니라 “정보 재전송”이라고 말하는 이유는?
  3. H3 timeout의 client·network·server 가설을 분리할 최소 증거를 제시하라.

짧은 정답: ① B stream의 필요한 offset이 연속이면 전달 가능하지만 shared cwnd·connection window·CPU queue가 막히면 B의 새 전송도 늦다. ② Packet number는 재사용하지 않고 lost frame의 STREAM range 등을 새 packet number에 다시 싣기 때문이다. ③ Curl/engine HTTP3 capability, Alt-Svc/negotiated version, UDP path·IP family, Initial/Retry/handshake timestamp, ACK/PTO/loss/MTU, LB/CID와 H2 fallback. 문항당 정의 1점, state/flow 1점, failure·trade-off 1점으로 총 9점이다.
