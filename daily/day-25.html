HTTP · TLS · QUIC · WEEK 4 / DAY 25

TLS certificate chain, SNI, ALPN, handshake

암호화 연결을 신원·key agreement·protocol 선택의 상태기계로 읽기 · 개념 65분 + 실습 35분

한 줄 요약
TLS handshake는 “자물쇠를 켠다”가 아니라 ClientHello의 SNI·ALPN·key share에서 시작해 server certificate chain과 hostname을 검증하고, ephemeral key agreement로 traffic key를 만들며, transcript에 대한 CertificateVerify·Finished를 확인하는 분산 상태 전이다. TCP 연결, TLS 암호화, server identity, HTTP 성공은 서로 다른 성공 경계다.

1. 선수 용어 사전

TLSTransport Layer Security. Reliable byte stream 위에서 peer 인증, 기밀성, 무결성을 제공하는 protocol. TCP 자체의 delivery reliability와 역할이 다르다.
CertificatePublic key와 subject/SAN, validity, issuer, usage 같은 identity metadata를 CA가 서명한 X.509 문서. Private key는 certificate 안에 들어 있지 않는다.
Leaf / Intermediate / RootLeaf는 실제 service certificate, intermediate CA는 leaf를 발급·서명, root CA는 local trust store의 trust anchor다. Server는 보통 leaf와 필요한 intermediate를 보내고 root는 보내지 않아도 된다.
Trust storeClient OS/runtime가 신뢰하도록 설치한 root CA 집합과 정책. 같은 server도 host, container, JVM의 trust store 차이로 결과가 달라질 수 있다.
SANSubject Alternative Name. Certificate가 유효한 DNS name/IP identity 목록. Client가 요청한 hostname과 SAN을 규칙에 따라 비교한다.
SNIServer Name Indication. ClientHello에서 접속하려는 hostname을 server에 알려 shared IP/LB가 알맞은 certificate와 virtual host를 선택하게 하는 TLS extension.
ALPNApplication-Layer Protocol Negotiation. TLS 안에서 h2, http/1.1 같은 상위 protocol을 협상한다. Server가 client 목록 중 하나를 선택한다.
(EC)DHE key shareEphemeral Diffie-Hellman key agreement용 공개 값. 양쪽이 network에 shared secret을 직접 보내지 않고 같은 secret을 계산한다.
Forward secrecy훗날 server 장기 private key가 유출돼도 과거 ephemeral session traffic을 복호화하기 어렵게 하는 성질.
Transcript hash현재까지 handshake message를 순서대로 hash한 값. Negotiation 변조를 탐지하고 CertificateVerify·Finished가 같은 handshake를 봤는지 묶는다.
AEADAuthenticated Encryption with Associated Data. TLS record payload를 암호화하면서 위·변조도 검출한다. TLS 1.3 cipher suite는 AEAD와 hash를 선택한다.
mTLSMutual TLS. Server뿐 아니라 client도 certificate로 인증하는 방식. Identity 발급·rotation·authorization 연결이 추가로 필요하다.

2. 왜 중요한가

TLS 오류를 “인증서 문제”로 묶으면 DNS·시간·SNI routing·trust store·protocol negotiation·cipher policy를 구분하지 못한다. 반대로 -k로 검증을 끄고 연결되었다고 해결하면 암호화된 공격자에게 연결될 수 있다.

  • Identity: Chain 서명이 맞아도 요청 hostname이 SAN에 없거나 certificate가 만료됐으면 그 service identity로 신뢰할 수 없다.
  • Routing: SNI가 없거나 틀리면 같은 IP의 default certificate, TLS alert, 엉뚱한 tenant로 갈 수 있다.
  • Protocol: ALPN이 h2를 선택했는데 peer가 HTTP/1.1 text를 보내면 TLS는 성공했어도 application protocol은 실패한다.
  • Failure cost: TLS handshake는 RTT와 asymmetric crypto CPU를 쓰며, retry storm·짧은 connection lifetime·certificate rotation 오류가 LB capacity를 압박한다.

Front/back 보안 경계 분리
  1. 주소와 transport: DNS answer와 route가 peer IP를 정하고 TCP 연결이 성공해도 hostname identity는 아직 검증되지 않았다.
  2. ClientHello: Client는 지원 version·algorithm·key share와 SNI/ALPN preference를 보낸다. 전통적 SNI는 ClientHello 관측자에게 노출될 수 있어 TLS가 IP·traffic metadata 전체를 숨기는 것은 아니다.
  3. Key exchange: ServerHello의 key share와 client ephemeral private state로 shared secret을 계산하고 HKDF key schedule로 handshake traffic secret을 만든다. TLS 1.3은 ServerHello 뒤 handshake message를 보호한다.
  4. Authentication: CertificateVerify는 server가 certificate public key에 대응하는 private key를 소유하며 transcript에 서명했음을 보인다. Chain validation과 hostname match는 client policy가 수행한다.
  5. Key confirmation: Finished는 handshake secret과 transcript에 기반해 양쪽이 같은 handshake와 key를 공유함을 확인한다. 이 뒤 application traffic protection이 시작된다.
  6. Termination: Edge LB에서 TLS를 terminate하면 client↔LB와 LB↔origin은 서로 다른 certificate, key, cipher, socket, timeout을 가진다. “end-to-end TLS” 여부를 architecture에서 명시한다.
핵심 불변식: Client가 의도한 hostname과 검증한 certificate identity가 일치하고, certificate path가 local trust policy에서 유효하며, CertificateVerify와 Finished가 현재 transcript에 맞아야만 authenticated channel이다. 암호화 key가 만들어졌다는 사실만으로 올바른 server와 연결됐다고 결론 내릴 수 없다.

TLS 1.3 key schedule과 성공 시점

Client와 server는 (EC)DHE shared secret을 그대로 traffic key로 쓰지 않는다. HKDF-Extract/Expand 기반 key schedule이 early, handshake, master secret 단계와 client/server 방향별 traffic secret을 분리한다. Nonce는 record sequence와 key material로 만들며 같은 key/nonce 재사용은 AEAD 안전성을 깨뜨린다.

  • ServerHello 수신: Version·cipher·key share 선택과 handshake key derivation 가능. 아직 server certificate 검증 완료가 아니다.
  • CertificateVerify 성공: Server private-key possession과 transcript signature 확인. Path/hostname policy도 통과해야 identity가 완성된다.
  • Server Finished 성공: Server 쪽 handshake integrity와 key confirmation. Client는 자신의 Finished 전송 뒤 normal application traffic 단계로 간다.
  • HTTP response: TLS record가 정상 복호화돼도 application authorization·transaction 성공과는 별도다.

SNI와 ALPN은 routing/control data다

SNI는 shared listener가 certificate/tenant 설정을 선택하게 하고 ALPN은 같은 443 port에서 HTTP/2와 HTTP/1.1 같은 protocol parser를 선택하게 한다. 둘 다 “application content”가 아니라 handshake control path지만, 선택 결과가 이후 data path를 바꾼다. Proxy가 front TLS를 terminate하면 backend SNI와 ALPN은 새 ClientHello에서 다시 정해진다.

Session resumption과 0-RTT trade-off

TLS 1.3 resumption은 PSK ticket으로 full certificate handshake 비용을 줄일 수 있다. 0-RTT early data는 한 RTT를 더 줄이지만 replay protection이 일반 1-RTT application data와 같지 않다. 결제·생성 같은 비멱등 요청을 protocol 지원만 보고 0-RTT로 보내면 안 되며 application-level anti-replay/idempotency 정책이 필요하다.

7. 35분 실습: SNI·ALPN·chain·hostname 실패 추적

사전 조건: curl, openssl, Python 3, 인터넷 연결. RFC Editor만 사용한다. 실행 전 “TCP 연결과 TLS 검증 중 어느 단계에서 실패하는가?”, “SNI와 hostname validation은 같은가?”, “ALPN 선택 뒤 어떤 parser가 필요한가?”를 답한다.

0단계 · End-to-end timing (5분)

curl -sS -o /dev/null --http2 \
  -w 'dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} first=%{time_starttransfer} total=%{time_total} http=%{http_version}\n' \
  https://www.rfc-editor.org/

tls - tcp는 대략 TLS 구간을 포함하지만 scheduling·reuse 영향을 받는다. 새 연결 여부와 proxy를 함께 확인하고 단일 표본을 SLO로 일반화하지 않는다.

1단계 · SNI와 ALPN 관찰 (8분)

printf '' | openssl s_client \
  -connect www.rfc-editor.org:443 \
  -servername www.rfc-editor.org \
  -alpn h2,http/1.1 -tls1_3 -showcerts 2>&1 | \
  grep -E 'Protocol|Cipher|ALPN|subject=|issuer=|Verify return code'

예상: TLS 1.3 또는 local engine이 협상한 version, selected ALPN h2, leaf subject/issuer, verify 결과가 보인다. LibreSSL/OpenSSL 출력 형식은 다를 수 있다.

2단계 · Leaf identity와 기간 읽기 (8분)

printf '' | openssl s_client \
  -connect www.rfc-editor.org:443 \
  -servername www.rfc-editor.org 2>/dev/null | \
  openssl x509 -noout -subject -issuer -dates -fingerprint

예상: Leaf subject, issuer, notBefore/notAfter, fingerprint가 나온다. 이 명령은 첫 certificate의 metadata 관찰이며 system trust·hostname policy 전체를 독립적으로 재구현하는 명령은 아니다.

3단계 · 실패 주입: hostname mismatch (10분)

python3 -c 'import socket,ssl; c=ssl.create_default_context(); s=c.wrap_socket(socket.create_connection(("www.rfc-editor.org",443),3),server_hostname="www.rfc-editor.org"); cert=s.getpeercert(); print("TLS",s.version(),"ALPN",s.selected_alpn_protocol()); print("SAN",cert.get("subjectAltName")); ssl.match_hostname(cert,"wrong.example")'

예상: TLS connection과 trust validation은 먼저 성공하지만 마지막 hostname 비교가 CertificateError를 낸다. 이로써 “certificate 서명 유효”와 “요청 identity 일치”가 다른 검증임을 확인한다. Python version에 따라 match_hostname deprecation warning은 날 수 있다.

4단계 · SNI failure와 cleanup (4분)

curl --connect-to wrong.example:443:www.rfc-editor.org:443 \
  https://wrong.example/ -v -o /dev/null

환경에 따라 TLS alert, wrong certificate/hostname 오류가 난다. shared edge의 default policy가 다를 수 있어 exact error text보다 ClientHello SNI와 failure phase를 본다. 파일이나 key를 만들지 않았으므로 cleanup은 없고 terminal에 secret이 출력되지 않았는지 확인한다.

자주 나는 오류: -tls1_3 미지원이면 local TLS engine version을 확인하고 option을 빼서 negotiated version을 관찰한다. Corporate proxy가 있으면 peer certificate issuer와 remote IP가 달라질 수 있으므로 proxy 경계를 기록한다. DNS 실패는 TLS 전에 해결한다.

8. 놓치기 쉬운 함정

  • TLS certificate는 data 암호화 key가 아니다. TLS 1.3 traffic key는 ephemeral shared secret과 transcript에서 파생된다.
  • SNI와 Host/:authority는 계층·시점이 다르다. SNI는 HTTP 전에 certificate/tenant 선택, Host는 TLS 뒤 HTTP routing에 쓰인다.
  • Certificate chain valid와 hostname valid는 다르다. 둘 중 하나라도 실패하면 intended server identity 검증 실패다.
  • Root certificate는 server가 보내야 하는 chain의 마지막이라는 뜻이 아니다. Trust anchor는 보통 client trust store에 있다.
  • 인증서 갱신은 새 connection부터 보인다. 기존 TLS connection은 예전 handshake state를 유지하므로 connection drain과 rollout 관측이 필요하다.
  • TLS termination 지점 뒤 traffic이 자동으로 보호되는 것은 아니다. LB→origin re-encryption/mTLS와 trust owner를 별도 설계한다.
  • ALPN은 protocol을 선택할 뿐 구현 정상성을 보증하지 않는다. 선택한 parser와 actual bytes가 맞아야 한다.
  • 0-RTT는 일반 request와 같은 replay 보장이 아니다. Non-idempotent operation을 기본 허용하지 않는다.
  • Packet capture만으로 TLS 1.3 certificate를 평문 확인할 수 없을 수 있다. ServerHello 뒤 handshake가 암호화되므로 endpoint logs와 안전한 key-log 정책이 필요하다.

9. 대기업 기술 면접 질문

  1. “TLS 1.3 full handshake를 packet 순서와 성공 경계로 설명하세요.”
    좋은 답변 구조: DNS/TCP 선행 → ClientHello(SNI·ALPN·key share) → ServerHello/shared secret/HKDF → encrypted certificate·CertificateVerify → path/SAN/time 검증 → Finished/transcript → application key/data → TCP/TLS/HTTP 성공 분리.
  2. “Certificate chain 서명은 유효한데 hostname mismatch가 발생했습니다. 왜이며 어떻게 복구합니까?”
    좋은 답변 구조: CA path와 service identity 분리 → requested hostname/SNI/SAN 증거 → default cert·LB route·wrong endpoint 가설 → 정상 cert/config canary → 검증 우회 금지 → fingerprint/edge 전체 확인.
  3. “대규모 서비스의 certificate rotation을 무중단으로 설계하세요.”
    좋은 답변 구조: termination/key owner → expiry SLO와 자동 issuance → old/new overlap → multi-region propagation → served-chain external probe → connection reuse/drain → canary·rollback → key compromise/revocation runbook.

10. 회상·확인 문제와 채점 기준

어제 내용 회상 3문제

  1. HTTP/2 stream window와 connection window가 동시에 필요한 이유는?
  2. HTTP/2가 해결한 HOL과 해결하지 못한 HOL은?
  3. RST_STREAM과 GOAWAY의 영향 범위 차이는?

짧은 정답: ① 개별 consumer와 전체 connection buffer를 각각 보호한다. ② HTTP/1.1 ordered response HOL은 줄이지만 TCP sequence loss HOL은 남는다. ③ RST_STREAM은 한 stream, GOAWAY는 connection drain과 last-stream-id 처리 범위를 알린다.

오늘 내용 확인 3문제

  1. SNI, SAN hostname validation, ALPN의 owner와 시점을 각각 설명하라.
  2. CertificateVerify와 Finished는 무엇을 각각 증명하는가?
  3. TCP connect 성공 뒤 TLS handshake가 실패할 수 있는 가설을 네 가지 제시하라.

짧은 정답: ① Client가 ClientHello SNI로 server 설정 선택을 돕고, client verifier가 served certificate SAN과 intended hostname을 비교하며, client offer/server selection으로 상위 protocol을 정한다. ② 전자는 certificate private-key possession과 transcript signature, 후자는 handshake secret과 transcript의 key confirmation·integrity다. ③ Chain/trust, hostname/SNI, time/expiry, version/cipher/signature overlap, ALPN/policy, key mismatch 중 네 가지. 문항당 정의 1점, state/flow 1점, failure·trade-off 1점으로 총 9점이다.
