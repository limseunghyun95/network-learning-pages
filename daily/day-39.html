RESILIENCE PATTERN · WEEK 6 / DAY 39

idempotency key와 duplicate side effect

여러 network attempt를 하나의 logical operation으로 수렴시키는 저장·경쟁·TTL 설계 · 이론 65분 + 실습 35분

한 줄 요약
Idempotency key는 “중복 요청을 무시하는 문자열”이 아니다. Client가 logical operation identity를 만들고, server가 tenant·operation·key와 canonical request fingerprint를 원자적으로 저장하며, 동시 요청·commit 후 response 유실·TTL 만료를 일관된 상태기계로 처리해야 duplicate charge·order·event를 막을 수 있다.

1. 선수 용어 사전

Idempotent같은 의도의 operation을 한 번 또는 여러 번 실행해도 외부에서 약속한 최종 효과가 같은 성질이다. “함수가 한 번만 실행됨”이나 “응답 byte가 항상 같음”과는 다르다.
Idempotency keyClient가 한 logical operation의 모든 retry에 동일하게 보내는 opaque identifier다. 새 사용자 행동에는 새 key를 쓴다.
Duplicate side effect같은 의도가 둘 이상의 결제 승인·주문·쿠폰 차감·메일·Kafka event로 반영되는 현상이다.
Logical operation / attemptOperation은 사용자가 원하는 1개의 업무 결과이고 attempt는 network 전송 1회다. 여러 attempt가 하나의 operation을 가리킬 수 있다.
FingerprintMethod·resource·tenant·canonicalized payload 등 의미 있는 입력으로 만든 digest다. 같은 key를 다른 payload에 재사용하는 사고를 막는다.
Atomicity여러 상태 변경이 전부 반영되거나 전부 반영되지 않는 성질이다. “key 선점”과 business write 사이 원자 경계가 핵심이다.
Unique constraint / compare-and-set동시 요청 중 하나만 key를 선점하게 하는 DB 제약 또는 조건부 쓰기다. Application의 check-then-insert만으로는 race를 막지 못한다.
Commit pointBusiness effect가 durable해져 transport 실패 뒤에도 이미 성공했을 수 있는 경계다.
Outbox patternBusiness row와 “보낼 event”를 같은 DB transaction에 기록하고 별도 publisher가 전달하는 방법이다. DB commit과 message publish 사이 dual-write gap을 줄인다.
TTL / replay windowDedup record를 보존하는 시간이다. Client retry 가능 시간보다 짧으면 늦은 retry가 새 operation으로 실행될 수 있다.
Exactly-once effectEnd-to-end side effect가 업무적으로 한 번만 보이게 만드는 목표다. Network 자체는 packet·request를 중복 전달할 수 있어 application state와 unique identity로 수렴시킨다.

2. 왜 중요한가

Client가 POST /payments를 보내고 server가 결제를 commit한 직후 response packet이 사라졌다고 하자. Client가 본 것은 timeout이지만 server state는 성공이다. Retry를 하지 않으면 사용자는 결과를 모른 채 실패로 보며, 새 요청으로 다시 보내면 두 번 결제될 수 있다. 이 구간이 distributed system의 ambiguous completion이다.

  • Transport ACK ≠ business commit: TCP ACK는 byte 수신 증거일 뿐 결제 transaction 완료 증거가 아니다.
  • HTTP 200 유실: Server는 성공했지만 client는 response를 받지 못할 수 있다.
  • At-least-once delivery: Queue·webhook·consumer 재시작은 동일 message를 다시 전달할 수 있다.
  • Human retry: 사용자가 버튼을 두 번 누르거나 새로고침해도 duplicate가 생긴다.
  • 면접 포인트: “key를 Redis에 저장”으로 끝내지 말고 identity scope, atomicity, state transition, payload mismatch, TTL, downstream effect까지 방어해야 한다.

  1. Identity: Client는 화면 click이 아니라 logical operation lifecycle 동안 key를 보존한다. 앱 restart 뒤에도 retry해야 한다면 durable storage가 필요하다.
  2. Scope: Key만 global lookup하지 않는다. Tenant와 operation type을 함께 묶어 다른 고객의 result가 노출되는 것을 막는다.
  3. Claim: SELECT 후 INSERT가 아니라 unique constraint/conditional put으로 한 request만 owner가 되게 한다.
  4. Commit: Business effect, dedup outcome, outbox record를 가능한 한 같은 transaction boundary에 둔다.
  5. Ambiguity: Response 유실은 success와 failure를 구분하지 못하게 한다. 새 key가 아닌 같은 key retry로 server state를 조회한다.
  6. Replay: 완료 record라면 effect를 재실행하지 않고 저장된 status/body/resource ID를 반환한다.
핵심 불변식: 같은 scope·key·fingerprint에는 business effect가 최대 한 번 commit된다. 같은 scope·key에 다른 fingerprint는 거부한다. 완료 response가 유실돼도 retry는 동일한 durable outcome으로 수렴한다.

4. CS 수준 내부 동작

상태기계와 선형화 지점

최소 상태는 ABSENT → IN_PROGRESS → SUCCEEDED|FAILED_FINAL이다. 첫 atomic insert가 owner를 정하는 선형화 지점(linearization point)이다. 동시 duplicate가 IN_PROGRESS를 보면 무한 대기하지 말고 409/202+status URI 또는 짧은 bounded wait 정책을 따른다. Owner crash를 처리하려면 lease/heartbeat나 transaction rollback 규칙이 필요하다.

Check-then-act race

두 thread가 동시에 “key 없음”을 읽고 각각 결제하면 이미 늦다. Process mutex는 한 instance에만 유효하다. DB unique composite key, serializable transaction, conditional write처럼 모든 instance가 공유하는 원자 primitive가 필요하다.

Fingerprint canonicalization

JSON raw byte를 그대로 hash하면 field order·공백·숫자 표현 차이로 같은 의미가 다르게 보일 수 있다. 반대로 중요한 field를 빼면 다른 요청이 같아진다. API가 정의한 stable semantic fields를 canonical form으로 만들고 hash algorithm/version을 record한다. Secret·PII 원문을 key나 log에 넣지 않는다.

Transaction 경계와 dual write

Dedup record를 별도 Redis에 먼저 DONE으로 쓰고 DB commit이 실패하면 phantom success가 된다. 반대로 DB commit 후 dedup 저장 전 crash하면 retry가 effect를 반복한다. 같은 DB transaction에 둘 수 없다면 domain unique constraint, transactional outbox, reconciliation을 결합해야 한다.

Exactly-once라는 표현의 경계

Network delivery를 정확히 한 번으로 만들 수 있는 것이 아니라, duplicate delivery를 허용하고 durable identity·dedup·idempotent consumer로 observable effect를 한 번으로 수렴시킨다. Email처럼 외부 provider가 idempotency를 제공하지 않으면 provider message ID 저장, send-before-mark crash window, 보상 절차가 남는다.

TTL과 안전성

retention ≥ 최대 client retry window + 최대 queue redelivery delay + clock skew + incident recovery margin이어야 한다. TTL 뒤 같은 key를 새 요청으로 허용할지 영구 tombstone을 둘지는 업무 위험·storage cost·규제 보존 기간의 trade-off다.

HTTP method semantics

RFC 9110의 idempotent는 동일 request 여러 번의 “의도된 server effect”가 한 번과 같다는 뜻이다. PUT/DELETE는 method semantics상 idempotent지만 audit log·notification 같은 부수 효과는 별도 방어가 필요하다. POST도 application contract와 key로 idempotent하게 만들 수 있다. Idempotency-Key IETF 문서는 2026-04-18 만료된 Internet-Draft이므로 현재 RFC 표준이라고 단정하지 말고 API contract를 확인한다.

5. 실무 설계 판단과 best practice

판단권장 기준과 이유
Key 생성·scope충분한 entropy의 UUID 계열을 client에서 만들고 (tenant_id, operation, key)에 unique constraint를 둔다. Key를 authorization 대신 쓰지 않는다.
Payload mismatch같은 key·다른 fingerprint는 409 또는 422 등 문서화한 error로 거부한다. 기존 result를 조용히 반환하면 잘못된 요청을 숨긴다.
동시 duplicateIN_PROGRESS면 409, 202+poll, bounded wait 중 하나를 명시한다. Request thread를 lease 만료까지 붙잡지 않는다.
결과 저장Resource ID, outcome class, stable response fields, fingerprint, created/expiry time을 저장한다. 거대한 body·민감정보는 최소화하고 schema version을 둔다.
Failure 저장 정책Validation처럼 실행 전 실패는 수정 후 새 요청을 허용할 수 있다. Commit 뒤 business decline처럼 최종 결과는 같은 key에 고정해야 한다. 500을 무조건 cache할지 말지는 commit 가능성과 contract로 정한다.
TransactionBusiness row·dedup outcome·outbox를 같은 transaction에 둔다. 불가능하면 각 system의 domain key와 reconciliation job을 둔다.
TTLSDK retry, offline app replay, webhook/queue redelivery의 최장 시간을 측정해 retention을 정하고 client contract에 공개한다.
Hot key·DoSKey 길이·형식을 제한하고 tenant rate limit, record size cap, auth check를 먼저 적용한다. 공격자가 다른 tenant result를 probing하지 못하게 scope한다.
ObservabilityKey 원문 대신 hash/tag를 기록하고 new|replay|in_progress|mismatch|expired, age, owner, commit/result ID를 trace에 남긴다.
Engine 차이: RDBMS unique constraint/transaction은 business row와 강한 원자 경계를 만들기 쉽다. Redis SET NX는 빠르지만 DB effect와 원자 transaction이 아니며 eviction·failover·TTL을 검토해야 한다. DynamoDB류 conditional put은 key 선점에 유용하지만 다른 store와의 side effect에는 saga/outbox가 필요하다. Stripe·EC2처럼 API별 replay window, parameter mismatch, regional/zonal scope가 다르므로 공식 contract를 따른다.

7. 35분 실습: 원자적 idempotency state machine

사전 조건: Python 3 표준 라이브러리와 임시 디렉터리를 만들 수 있는 shell. 실행 전에 같은 key 10개 thread가 동시에 요청할 때 effect count가 몇이어야 하는지, 다른 payload 재사용은 어떤 error여야 하는지 예측한다.

0단계 · 임시 실습 파일 생성 (5분)

LAB_DIR="$(mktemp -d)"
export LAB_DIR
python3 - <<'PY'
import os, pathlib
p = pathlib.Path(os.environ["LAB_DIR"]) / "idem.py"
p.write_text(r'''
import hashlib, json, sqlite3, sys, threading, time
db = sys.argv[1]
def fp(payload):
    raw = json.dumps(payload, sort_keys=True, separators=(",", ":"))
    return hashlib.sha256(raw.encode()).hexdigest()
def call(key, payload):
    con = sqlite3.connect(db, timeout=5, isolation_level=None)
    f = fp(payload)
    try:
        con.execute("BEGIN IMMEDIATE")
        row = con.execute("SELECT fingerprint,state,result FROM idem WHERE tenant=? AND op=? AND key=?",
                          ("t1","charge",key)).fetchone()
        if row:
            if row[0] != f: con.execute("ROLLBACK"); return "MISMATCH"
            con.execute("COMMIT"); return "REPLAY:" + row[2]
        con.execute("INSERT INTO idem VALUES (?,?,?,?,?,?)", ("t1","charge",key,f,"IN_PROGRESS",None))
        con.execute("INSERT INTO effects(idem_key,amount) VALUES (?,?)", (key,payload["amount"]))
        result = "charge:" + str(con.execute("SELECT last_insert_rowid()").fetchone()[0])
        con.execute("UPDATE idem SET state='SUCCEEDED',result=? WHERE tenant='t1' AND op='charge' AND key=?", (result,key))
        con.execute("COMMIT"); return "NEW:" + result
    except Exception:
        try: con.execute("ROLLBACK")
        except Exception: pass
        raise
    finally: con.close()
def main():
    con=sqlite3.connect(db); con.executescript("""
    CREATE TABLE IF NOT EXISTS idem(tenant TEXT,op TEXT,key TEXT,fingerprint TEXT,state TEXT,result TEXT,PRIMARY KEY(tenant,op,key));
    CREATE TABLE IF NOT EXISTS effects(id INTEGER PRIMARY KEY,idem_key TEXT UNIQUE,amount INTEGER);
    """); con.commit(); con.close()
    out=[]
    ts=[threading.Thread(target=lambda: out.append(call("pay-001", {"amount":1000}))) for _ in range(10)]
    [t.start() for t in ts]; [t.join() for t in ts]
    print("results", sorted(out)); print("mismatch", call("pay-001", {"amount":2000}))
    con=sqlite3.connect(db); print("effect_count", con.execute("SELECT count(*) FROM effects").fetchone()[0]); print("rows", con.execute("SELECT key,state,result FROM idem").fetchall())
if __name__ == "__main__": main()
''')
print(p)

2단계 · Anti-pattern 예측 (8분)

코드를 실행하기 전에 아래 변경의 결과를 말한다.

  • BEGIN IMMEDIATE를 제거하고 조회 뒤 100ms sleep 후 insert한다 → 두 thread가 모두 ABSENT를 볼 수 있다. Unique constraint가 없으면 effect가 중복된다.
  • effects.idem_key UNIQUE를 제거한다 → idempotency layer가 깨졌을 때 domain invariant도 사라진다.
  • Business commit 뒤 별도 connection에서 dedup result를 저장한다 → 그 사이 crash가 나면 retry가 중복 effect를 만들 수 있다.

8. 놓치기 쉬운 함정

  • Retry마다 새 key를 만들면 dedup이 불가능하다.
  • 같은 key를 영구 재사용하면 새로운 사용자 의도까지 막는다.
  • Key만 비교하고 payload를 비교하지 않으면 잘못된 result를 반환한다.
  • Application-level SELECT 후 INSERT는 원자적이지 않다.
  • Process lock은 multi-instance·multi-region race를 막지 못한다.
  • Redis NX와 DB commit은 하나의 transaction이 아니다.
  • Success만 저장하고 final failure를 저장하지 않으면 같은 operation이 다른 결과를 낼 수 있다.
  • Response 전체를 무기한 저장하면 PII·storage·schema migration 문제가 생긴다.
  • TTL은 cache tuning 값이 아니라 correctness window다.
  • Producer dedup만으로 downstream consumer side effect가 안전해지지 않는다. Consumer도 message/business key를 저장해야 한다.
  • Idempotency key는 authentication·authorization을 대체하지 않는다.
  • “Exactly once”라는 마케팅 용어보다 failure window와 durable invariant를 묻는다.

9. 대기업 기술 면접 질문

  1. “결제 API의 idempotency를 설계하세요.”
    좋은 답변 구조: 요구사항·replay window → key owner/scope → fingerprint → atomic state machine → payment/outbox transaction → concurrent duplicate → response loss → TTL·보안·metric → multi-region trade-off.
  2. “Redis SET NX만으로 충분하지 않은 이유는?”
    좋은 답변 구조: Redis claim과 DB effect의 dual-write gap → crash windows → eviction/failover/TTL → domain unique constraint·outbox·reconciliation → latency와 availability trade-off.
  3. “Exactly-once delivery를 보장할 수 있나요?”
    좋은 답변 구조: network duplicate/ambiguity → delivery와 effect 분리 → at-least-once + durable dedup → producer/outbox/consumer invariant → 외부 side effect 한계 → 보상과 관측성.
