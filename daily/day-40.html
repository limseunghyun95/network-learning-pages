RESILIENCE PATTERN · WEEK 6 / DAY 40

pool, queue, bulkhead, circuit breaker, rate limit

제한된 capacity를 숫자로 모델링하고 overload를 admission 단계에서 끊는 설계 · 이론 70분 + 실습 35분

한 줄 요약
Pool은 재사용할 자원의 동시성 상한, queue는 잠시 기다릴 작업의 유한 buffer, bulkhead는 실패 범위의 격리, circuit breaker는 실패하는 dependency 호출의 임시 차단, rate limit은 유입량의 admission 정책이다. 이들을 무한 대기열이나 큰 pool로 대체하지 말고 deadline·capacity·공정성에 맞춰 함께 설계한다.

1. 선수 용어 사전

CapacitySystem이 목표 latency와 오류율 안에서 처리할 수 있는 작업량이다. CPU, DB connection, downstream concurrency, bandwidth 중 가장 작은 병목이 상한을 만든다.
Concurrency동시에 진행 중인 작업 수다. 같은 RPS라도 service time이 길어지면 필요한 concurrency가 증가한다.
PoolConnection·thread·worker처럼 생성 비용이 큰 자원을 재사용하는 집합이다. Pool size는 dependency가 감당할 수 있는 동시성 budget이어야 한다.
Queue즉시 실행하지 못한 작업이 기다리는 buffer다. 메모리만 있으면 되는 무료 capacity가 아니라 deadline을 소비하는 숨은 latency다.
BackpressureConsumer가 느릴 때 producer의 속도를 늦추거나 거부해 work-in-progress가 무한히 늘지 않게 하는 feedback이다.
Bulkhead선박의 격벽처럼 자원을 dependency·tenant·priority별로 분리해 한 구역의 고갈이 전체를 삼키지 않게 하는 패턴이다.
Circuit breaker최근 실패·지연이 임계치를 넘으면 remote call을 잠시 차단하고, 제한된 probe로 회복을 확인하는 상태기계다.
Rate limit / quota시간 단위 허용 요청량 또는 tenant별 사용 한도다. 지속률과 순간 burst를 구분해야 한다.
Token bucket일정 rate로 token을 보충하고 요청마다 소비한다. Bucket 크기만큼 burst를 허용하면서 장기 평균률을 제한한다.
Load shedding이미 처리 능력을 넘은 low-value/late work를 빨리 거부해 남은 요청의 성공률과 recovery space를 지키는 정책이다.
Little’s LawL = λ × W. 안정 상태에서 system 안 평균 작업 수 L은 arrival rate λ와 평균 체류시간 W의 곱이다.

2. 왜 중요한가

정상 100 RPS, service time 100ms인 dependency는 평균 concurrency가 약 10이다. 같은 유입에서 service time이 2초로 늘면 concurrency는 200이 된다. Pool이 50이라면 150개가 queue에서 기다리고, timeout 뒤 retry까지 들어오면 도착률이 증가한다. “응답이 느려서 queue를 늘린다”는 처방은 실패를 늦게 보여줄 뿐 recovery를 어렵게 할 수 있다.

  • Pool: Connection 생성 비용은 줄이지만 downstream CPU·lock·IO capacity를 만들지는 않는다.
  • Queue: 짧은 burst를 흡수하지만 지속 overload에서는 stale work와 memory를 쌓는다.
  • Bulkhead: 중요 traffic과 느린 dependency를 격리해 blast radius를 제한한다.
  • Circuit breaker: 실패가 지속될 때 timeout까지 자원을 점유하는 call을 fail-fast한다.
  • Rate limit/load shedding: 비싼 work가 시작되기 전에 admission을 제어한다.

↖ overflow/late work는 앞단에서 빠르게 거부

  1. Rate gate: Identity/tenant/endpoint별 token을 확인한다. 거부할 work를 TLS 종료·JSON parse·DB query 뒤에 판단하면 이미 capacity를 썼다.
  2. Bulkhead: Critical과 batch, dependency A와 B가 같은 semaphore·thread·pool을 공유하지 않게 한다.
  3. Queue: Queue capacity와 최대 age를 둔다. 예상 queue wait가 remaining deadline을 넘으면 enqueue하지 않는다.
  4. Circuit gate: OPEN이면 pool을 획득하지 않고 즉시 degrade한다. Rate limit과 달리 dependency health signal에 반응한다.
  5. Pool: Permit을 얻은 요청만 connection/stream을 사용한다. HTTP/2는 connection 수와 stream concurrency를 따로 본다.
  6. Recovery: HALF_OPEN probe 수를 제한해 회복 중인 dependency를 재차 flood하지 않는다.
설계 불변식: 모든 대기열은 유한하고 deadline-aware다. 동시성 상한은 downstream capacity 이하다. 한 bulkhead의 포화가 다른 중요 경로의 permit을 소비하지 않는다. OPEN breaker는 retryable error가 아니라 admission 거부 신호로 취급한다.

4. CS 수준 내부 동작

Queueing과 tail latency

Utilization이 100%에 가까워질수록 작은 service-time 변동도 queue wait를 크게 늘린다. 200 RPS에서 평균 50ms면 in-flight 평균은 10이지만 p99 500ms 동안 순간 concurrency는 100까지 필요할 수 있다. 평균만으로 pool을 정하지 말고 tail·burst·deadline을 함께 측정한다.

Pool sizing은 capacity allocation

DB max connection이 200이고 application instance가 20개면 instance당 pool 20은 총 400으로 이미 초과한다. Migration·admin·failover 여유를 남긴 뒤 per-instance budget ≤ usable downstream connections / max instances로 시작한다. Pool 대기시간과 query 시간을 분리한다.

Bounded queue와 stale work

Queue가 1,000이고 worker 10개가 각 100ms라면 drain rate는 이상적으로 100/s다. 가득 찬 queue 끝의 작업은 약 10초 뒤 시작한다. Deadline 2초라면 8초 전에 이미 가치가 없는 work다. Queue length보다 oldest age와 deadline slack이 더 직접적인 증거다.

Bulkhead의 비용

격리는 blast radius를 줄이지만 idle capacity fragmentation을 만든다. Hard partition, reserved+borrowable capacity, priority queue 중 요구사항을 선택한다. Borrowing을 허용하면 overload 시 reserve를 즉시 회수할 수 있어야 한다.

Circuit breaker 상태기계

CLOSED는 call을 통과시키며 sliding window를 관측한다. Failure/slow-call 비율과 최소 sample 수를 만족하면 OPEN으로 전이한다. Cooldown 후 HALF_OPEN에서 제한된 probe만 통과시켜 충분히 성공하면 CLOSED, 하나라도 치명적으로 실패하면 OPEN으로 돌아간다. 전 process에 동일한 global breaker를 두면 coordination 비용과 false sharing이 생긴다.

Rate limit 알고리즘

Fixed window는 경계에서 2배 burst가 가능하다. Sliding window는 더 정확하지만 상태 비용이 크다. Token bucket은 refill rate r과 bucket size b로 장기률과 burst를 제어한다. Concurrency limiter는 RPS가 아니라 진행 중 work를 제한해 latency 증가에 더 직접 반응한다.

Control plane과 data plane

Threshold·quota·routing은 control plane 설정이고 각 request의 token/permit/circuit 판정은 data plane이다. 중앙 limiter 장애 때 fail-open/fail-closed 정책, local cache 오차, shard hot spot을 미리 정한다. Distributed limiter는 완벽한 전역 정확도와 low latency·availability 사이 trade-off가 있다.

7. 35분 실습: slow dependency에서 queue와 admission 비교

사전 조건: Docker Desktop/Engine, Compose, 저장소 root. 실행 전 20개 요청을 5개 worker로 2초 slow endpoint에 보낼 때 마지막 요청의 최소 시작 지연을 예측한다.

0단계 · Lab 시작과 단일 latency 확인 (5분)

make doctor
make up
docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client curl -sS -o /dev/null \
  -w 'code=%{http_code} total=%{time_total}\n' \
  'http://proxy:8080/api/slow?seconds=2'

예상: HTTP 200이지만 약 2초가 걸린다. Error rate만 보는 breaker는 slow dependency를 놓칠 수 있다.

1단계 · Anti-pattern: worker 뒤 긴 queue (10분)

docker compose -f labs/basic-network-observability/docker-compose.yml exec client python -c '
import concurrent.futures,time,urllib.request
url="http://proxy:8080/api/slow?seconds=2"
t0=time.monotonic()
def one(i):
    start=time.monotonic()-t0
    urllib.request.urlopen(url,timeout=12).read()
    return i,start,time.monotonic()-t0
with concurrent.futures.ThreadPoolExecutor(max_workers=5) as ex:
    for row in ex.map(one,range(20)): print("id=%02d start=%.2f done=%.2f"%row)
'

예상: 5개씩 네 wave가 실행되고 마지막 wave는 약 6초 뒤 시작해 8초쯤 끝난다. Request timeout이 3초라면 queue의 뒤쪽 work는 시작 전부터 성공 불가능하다.

2단계 · Bounded admission과 bulkhead (12분)

docker compose -f labs/basic-network-observability/docker-compose.yml exec client python -c '
import concurrent.futures,threading,time,urllib.request
url="http://proxy:8080/api/slow?seconds=2"; permits=threading.BoundedSemaphore(5); t0=time.monotonic()
def one(i):
    if not permits.acquire(timeout=0.05): return i,"SHED",time.monotonic()-t0
    try:
        urllib.request.urlopen(url,timeout=3).read(); return i,"OK",time.monotonic()-t0
    finally: permits.release()
with concurrent.futures.ThreadPoolExecutor(max_workers=20) as ex:
    rows=list(ex.map(one,range(20)))
print("ok",sum(r[1]=="OK" for r in rows),"shed",sum(r[1]=="SHED" for r in rows))
print(rows)
'

예상: 약 5개만 downstream에 들어가고 나머지는 50ms 안에 SHED된다. 총 성공 수는 적어 보이지만 accepted request의 latency와 downstream 회복 공간을 지킨다. Critical traffic에는 별도 semaphore를 두는 것이 bulkhead다.

3단계 · 증거·계산·cleanup (8분)

docker compose -f labs/basic-network-observability/docker-compose.yml \
  logs --since=10m --timestamps api proxy
python3 -c 'print("Little Law: 100 RPS × 0.1s =",100*0.1,"in-flight; slow 2s =",100*2,"in-flight")'
make down

자주 나는 오류와 해결: Docker가 꺼졌으면 make doctor에서 멈춘다. make up 직후 connection refused가 나면 proxy가 아직 listen 전이므로 make ps와 log를 확인하고 readiness 뒤 다시 실행한다. Timeout은 환경 부하에 따라 달라질 수 있다. Lab server 구현이 single-thread라면 실제 처리율이 더 낮아지는 것도 관측 대상이다. 429/503을 직접 내는 production limiter와 달리 실습의 SHED는 client-side 문자열이다. Cleanup은 make down만 사용한다.

8. 놓치기 쉬운 함정

  • Pool을 키우면 capacity가 생긴다고 믿지 않는다. Downstream bottleneck과 총 instance 수를 본다.
  • Queue depth 0이 항상 좋은 것은 아니다. Pool 과대·직접 overload일 수 있다.
  • Queue length만 보지 말고 oldest age와 deadline slack을 본다.
  • Bulkhead를 같은 thread pool 위 label만 나눠 구현하지 않는다.
  • Circuit breaker와 rate limiter를 혼동하지 않는다. 전자는 health, 후자는 admission/fairness다.
  • Breaker의 최소 sample 없이 낮은 비율 threshold를 쓰면 저트래픽에서 오작동한다.
  • HALF_OPEN에 모든 대기 요청을 풀지 않는다.
  • 429에 retry-after·jitter·budget 없이 즉시 retry하지 않는다.
  • Global limiter만 두면 hot tenant와 critical traffic을 구분하지 못한다.
  • Autoscaling은 즉시 반응하지 않는다. Boot/warm-up 동안 admission control이 필요하다.
  • Fallback도 dependency와 capacity를 가진다. 검증되지 않은 fallback은 새 cascade를 만든다.
  • Rejected work를 숨기지 않는다. 보호 성공과 사용자 영향 모두 metric에 남긴다.

9. 대기업 기술 면접 질문

  1. “DB pool을 몇 개로 설정하겠습니까?”
    좋은 답변 구조: DB usable max·instance max·failover reserve → query service time·target RPS → Little’s Law → per-instance budget → acquire timeout·queue bound → load test·metric·rollback.
  2. “Circuit breaker와 rate limiter의 차이와 결합 순서는?”
    좋은 답변 구조: health-driven state machine vs identity/time quota → cheap admission first → bulkhead/queue → circuit/pool → 429/503 semantics → retry interaction → distributed state trade-off.
  3. “Overload 시 queue를 늘릴까요, fail-fast할까요?”
    좋은 답변 구조: burst인지 지속 overload인지 → drain rate·oldest age·deadline 계산 → value/priority → bounded queue → load shedding → recovery/canary → 사용자 경험과 cost.

10. 회상·확인 문제와 채점 기준

어제 내용 회상 3문제

  1. 같은 idempotency key에 다른 payload를 왜 거부하는가?
  2. Check-then-insert가 동시 duplicate를 막지 못하는 이유는?
  3. Dedup TTL이 client retry window보다 짧으면 어떤 failure가 생기는가?

짧은 정답: ① 다른 의도를 기존 operation으로 오인하지 않기 위해서다. ② 두 request가 동시에 ABSENT를 읽을 수 있어 unique/conditional write가 필요하다. ③ 늦은 retry가 새 operation으로 실행돼 duplicate effect가 생긴다.

오늘 내용 확인 3문제

  1. 100 RPS, 평균 service time 200ms의 평균 in-flight는?
  2. Queue length보다 oldest age가 중요한 이유는?
  3. OPEN breaker가 HALF_OPEN으로 갈 때 probe를 제한하는 이유는?

짧은 정답: ① Little’s Law로 100×0.2=20이다. ② Deadline을 이미 소진한 stale work인지 직접 보여주기 때문이다. ③ 회복 중인 dependency를 대기 요청이 다시 flood하지 않게 하기 위해서다. 문항당 정의 1점, 수치·내부 흐름 1점, failure·trade-off 1점으로 총 9점이다.
