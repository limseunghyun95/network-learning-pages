COMPUTER NETWORKING · WEEK 2 / DAY 08

stub / recursive / authoritative resolver

하나의 hostname이 answer가 되기까지 · 예상 학습 40분 + 실습 30분

한 줄 요약
Application 가까이의 stub resolver는 질문을 만들고, recursive resolver는 cache가 없으면 root부터 delegation을 따라 최종 답을 찾아오며, authoritative server는 자신이 맡은 zone의 원본 데이터로 답한다. 세 이름은 제품명이 아니라 요청마다 수행하는 역할이다.

1. 선수 용어 사전

Domain name / labelapi.example.com.처럼 계층을 나타내는 이름. 점으로 나뉜 api, example, com 각각을 label이라 한다. 끝의 점은 root까지 포함한 절대 이름임을 나타낸다.
QNAME / QTYPE질문할 이름(Query Name)과 원하는 record type. 예: QNAME=api.example.com., QTYPE=A.
RR / RRsetRR(Resource Record)은 DNS 데이터 한 행이다. 같은 owner name·type·class를 가진 RR 묶음이 RRset이며 cache와 DNSSEC 판단의 기본 단위다.
Stub resolverApplication 대신 DNS query를 만들지만 전체 계층을 직접 순회하지 않는 작은 resolver. 보통 OS library가 설정된 recursive resolver에 일을 위임한다.
Recursive resolverClient에 최종 answer 또는 error를 돌려줄 책임을 맡는 resolver. Cache miss면 다른 DNS server들에 query를 보내 resolution을 수행한다.
Authoritative server자신이 맡은 DNS zone의 내용을 local knowledge로 알고 답하는 server. 해당 zone의 authoritative answer에는 보통 AA bit가 설정된다.
Zone / delegationZone은 한 관리 주체가 authoritative하게 제공하는 DNS tree 구간이다. Delegation은 child zone의 책임을 NS record로 다른 authoritative server에 넘기는 경계다.
Referral / glueReferral은 “나는 최종 답 대신 더 가까운 NS를 알려준다”는 응답이다. Glue는 그 NS 이름을 찾아가기 위해 parent가 함께 주는 주소 record다.
RD / RA / AARD는 Recursion Desired, RA는 Recursion Available, AA는 Authoritative Answer header bit다. Bit 하나를 역할 전체의 성공으로 과대해석하지 않는다.
RCODEDNS 처리 결과 코드. NOERROR, SERVFAIL, NXDOMAIN, REFUSED 등이 있으며 HTTP status와 다른 protocol 계층의 상태다.

2. 왜 중요한가

“DNS가 느리다”는 한 문장 안에는 application의 resolver 설정, local search rule, recursive cache, upstream delegation, authoritative zone, network loss가 섞여 있다. 역할을 나누지 않으면 cache를 지우거나 authoritative server를 재시작하는 위험한 조치부터 하게 된다.

  • 소유자가 다르다. Stub 설정은 host/container, recursive cache는 platform·ISP·사내 DNS, zone 원본은 authoritative operator가 소유한다.
  • 성공 시점이 다르다. DNS answer를 받았다는 것은 이름→데이터 해석이 끝났다는 뜻이지, 그 IP의 TCP port·TLS·application이 정상이라는 뜻은 아니다.
  • 같은 질문도 cache 상태에 따라 path가 다르다. Warm cache는 한 번의 왕복, cold cache는 root/TLD/authoritative 여러 왕복이 필요할 수 있다.
  • 한 daemon이 여러 역할을 할 수 있다. Software process 이름만 보고 recursive인지 authoritative인지 단정하면 AA/RD/RA와 zone 설정을 놓친다.

3. 아키텍처 그림과 요청 흐름

① Application
t0 · getaddrinfo("api.example.com")
↓ library/API call
② Stub resolver
hosts·NSS·search rule 확인 → QNAME/QTYPE, RD=1
↓ configured recursive resolver로 query
③ Recursive resolver
cache hit면 즉시 응답 · miss면 in-flight state 생성
↓ iterative query · referral을 따라감
④ Root → TLD
root: .com NS referral → TLD: example.com NS referral
↓ child authoritative server 선택
⑤ Authoritative server
local zone에서 AA answer 또는 authoritative negative response
↺ RRset + TTL · cache 저장 · final response
⑥ Stub → Application
tN · address 목록 또는 resolver error

번호별 요청·응답·상태 변화

  1. Application은 보통 DNS packet이 아니라 resolver API를 호출한다. Stub은 hostname, address family, search suffix 정책을 실제 QNAME/QTYPE으로 바꾼다.
  2. Stub의 RD=1은 “최종 결과까지 찾아달라”는 요청이다. Server가 RA=1을 보내야 recursive service가 가능함을 나타내지만, 정책상 특정 client는 REFUSED될 수 있다.
  3. Recursive resolver는 cache key인 name·type·class와 만료 시각을 확인한다. Miss면 request state, 후보 NS, retry/deadline, outstanding query를 소유한다.
  4. Root와 TLD는 보통 최종 A record를 주지 않고 더 가까운 zone의 NS referral을 준다. Resolver가 그 referral과 glue를 이용해 다음 authoritative server를 고른다.
  5. Authoritative server는 local zone 데이터로 answer한다. AA는 “이 zone에 권한이 있다”는 출처 성격이지, IP의 service가 살아 있거나 data가 운영 의도와 일치한다는 보증은 아니다.
  6. Recursive resolver는 받은 RRset을 TTL 범위에서 cache하고 stub에 최종 response를 돌려준다. Application은 여러 주소 중 연결 전략을 선택하며 그때부터 route/TCP/TLS path가 시작된다.

4. CS 수준 내부 동작

Recursive resolver의 작은 분산 시스템

내부 상태소유권·불변식·trade-off
CacheRRset과 expiry를 저장한다. Authoritative data보다 cache가 우선해서는 안 되며, TTL 전 재사용은 latency와 upstream load를 줄이는 대신 변경 반영을 늦춘다.
In-flight request동일 QNAME/QTYPE 동시 miss를 하나로 합치면 query storm을 줄인다. 하지만 slow authority 하나가 많은 waiter latency를 묶을 수 있어 deadline과 queue limit이 필요하다.
Delegation state현재 가장 가까운 NS RRset과 주소, 시도 이력, RTT를 관리한다. 잘못된 delegation·lame server에서도 무한 query하지 않도록 work를 bound해야 한다.
Retry/deadlineUDP loss와 dead server를 구분하기 어렵다. 다른 authoritative replica를 시도하되 과도한 병렬·retry가 overload를 증폭하지 않도록 전체 budget을 둔다.
Validation/policyDNSSEC validation, local zone, blocklist, split view가 final response를 바꿀 수 있다. “authoritative가 준 값”과 “client가 받은 값” 사이에 정책 경계가 존재한다.

관측안전한 해석
rd raClient가 recursion을 원했고 응답 server가 recursive capability를 광고했다. Cache hit인지 실제 iterative lookup을 했는지는 이 bit만으로 모른다.

SERVFAILResolver가 final answer를 만들지 못한 임시 실패 범주. Timeout, DNSSEC validation, lame delegation 등 추가 증거가 필요하다.

5. 실무 설계 판단과 best practice

  • Authoritative와 public recursion을 분리한다. 역할·capacity·공격 표면이 다르다. Recursive service는 신뢰한 client에 제한해 open resolver와 amplification 악용을 막는다.
  • Application에 public resolver IP를 hard-code하지 않는다. OS/container의 관리된 resolver 설정을 쓰고, 필요한 경우 두 개 이상의 독립 endpoint와 명확한 timeout budget을 둔다.
  • Cache hit ratio만 보지 않는다. Query rate, p50/p99 latency, RCODE, timeout, upstream별 실패, cache eviction, validation failure를 함께 본다.
  • Cold와 warm path를 따로 측정한다. Warm cache benchmark만으로 authoritative 장애와 delegation latency를 가리지 않는다.
  • 변경 전에 packet·header를 보존한다. dig +comments +stats로 server, flags, RCODE, answer, query time을 남기고 나서 cache flush나 failover를 판단한다.
  • DNS log의 개인정보를 통제한다. QNAME은 사용자·내부 service 정보를 드러낼 수 있으므로 sampling, redaction, 접근권한과 보존기간을 정한다.
Anti-pattern: dig 한 번 성공했다고 “DNS 정상”, 또는 NXDOMAIN 한 번을 보고 “record 없음”으로 확정하지 않는다. 어느 resolver에, 어떤 QNAME/QTYPE으로, recursion·cache·view가 어떤 상태였는지를 같이 기록한다.

6. 장애 대응 표

상황: 일부 host에서만 api.example.com 이름 해석이 간헐적으로 2초 지연되거나 SERVFAIL이다.

순서실행 내용
증상영향 host·AZ·resolver·QTYPE, RCODE, p50/p99, 최초 시각, cache cold/warm 여부를 분리한다. TCP 연결 실패와 DNS resolution 시간을 섞지 않는다.
먼저 수집할 증거/지표/etc/resolv.conf, 실제 QNAME, dig +comments +stats, RD/RA/AA·RCODE, resolver별 latency/timeout/cache 지표, UDP/TCP 53 capture, authoritative health와 delegation을 변경 전에 저장한다.
가능한 가설특정 recursive replica 과부하, packet loss, cache miss storm, lame delegation, authoritative 일부 replica 불일치, DNSSEC validation failure, search suffix로 잘못된 QNAME, split view 차이.
안전한 첫 조치문제 resolver replica를 client rotation에서 drain하고 정상 replica로 제한된 traffic을 옮긴다. 동시에 authoritative와 packet 증거를 보존하고 retry rate를 제한한다.
Rollback/복구직전 정상 resolver/zone/delegation 설정으로 한 shard부터 되돌리고 RCODE·latency·cache refill을 확인한 뒤 확대한다. TTL 때문에 남는 cache window를 계산한다.
하지 말아야 할 조치전체 fleet 동시 cache flush, authoritative 전부 restart, timeout·retry 무제한 확대, 증거 없이 public DNS로 hard-code, TTL 즉시 효과를 가정하지 않는다.

예상 관찰: Answer는 172.28.0.20이다. Docker engine과 network mode에 따라 dig의 SERVER가 랩 DNS 172.28.0.10#53으로 직접 보이거나, 이를 upstream으로 사용하는 Docker embedded resolver 127.0.0.11#53로 보일 수 있다. getent는 application이 쓰는 OS resolver path, dig는 DNS protocol header를 직접 관찰하는 도구라는 차이를 기록한다.

2단계 · 역할과 header bit 비교 (7분)

docker compose -f labs/basic-network-observability/docker-compose.yml exec client dig @172.28.0.10 api.lab A +comments
docker compose -f labs/basic-network-observability/docker-compose.yml exec client dig @172.28.0.10 api.lab A +norecurse +comments

예상 관찰: 첫 query에는 RD가 요청되고, 두 번째는 RD 없이도 local host-record answer를 받는다. 이 dnsmasq는 한 process에서 client-facing resolver와 locally served data 역할을 함께 하므로 “server 한 대 = 역할 하나”라고 단정하지 않는다.

3단계 · DNS packet timeline (7분)

터미널 A:

docker compose -f labs/basic-network-observability/docker-compose.yml exec client tcpdump -ni eth0 -tttt -nn -c 2 'port 53'

터미널 B:

docker compose -f labs/basic-network-observability/docker-compose.yml exec client dig @172.28.0.10 api.lab A +tries=1 +time=1

예상 관찰: Client source ephemeral port에서 destination UDP 53으로 query가 나가고 같은 transaction에 response가 돌아온다. Packet 왕복과 dig query time을 timestamp로 연결한다.

4단계 · 실패 주입: 응답 없는 resolver (4분)

docker compose -f labs/basic-network-observability/docker-compose.yml exec client dig @172.28.0.99 api.lab A +tries=1 +time=1

예상 관찰: DNS response 자체가 없으므로 RCODE가 아니라 client-side timeout을 본다. SERVFAIL은 server가 보낸 DNS response이고 timeout은 response 미관측이라는 failure boundary 차이가 핵심이다.

  • Capture가 비면 client namespace의 eth0와 BPF port 53을 확인하고 DNS cache 때문에 query가 생략됐는지 본다.

8. 놓치기 쉬운 함정

  • Recursive query와 iterative lookup을 혼동하지 않는다. Stub은 보통 recursor에 RD=1로 묻고, recursor는 authority들에게 non-recursive query를 보내 referral을 따라간다.
  • Authoritative server가 domain 전체를 아는 것은 아니다. 위임받은 zone 경계만 책임지고 child delegation 아래는 referral을 줄 수 있다.
  • AA가 신뢰성·보안을 보장하지 않는다. 잘못 배포된 authoritative data도 AA로 올 수 있고, authenticity는 DNSSEC validation 같은 별도 경계다.
  • DNS server와 resolver라는 제품명에 속지 않는다. BIND, Unbound, dnsmasq, cloud service는 설정에 따라 여러 역할을 조합할 수 있다.
  • 검색 suffix가 QNAME을 바꾼다. 사용자가 api를 입력해도 stub은 api.corp.example. 등 여러 질문을 순차 생성할 수 있다.
  • Container의 resolv.conf가 upstream을 그대로 보여준다고 가정하지 않는다. Docker embedded resolver 같은 local forwarding layer가 앞에 서면 실제 upstream은 engine 설정 뒤에 숨을 수 있다.
  • DNS 성공은 connection 성공이 아니다. Address를 얻은 뒤 route, ARP/NDP, TCP/QUIC, TLS, LB, application failure window가 새로 시작된다.

9. 대기업 기술 면접 질문

  1. “브라우저에 URL을 입력했을 때 DNS answer까지의 흐름을 설명하세요.”
    좋은 답변 구조: browser/OS cache 가정 → stub의 QNAME/QTYPE → recursive cache hit/miss → root/TLD referral → authoritative answer → TTL/cache → 주소 선택 → DNS 이후 network path.
  2. “Authoritative DNS와 recursive DNS를 왜 분리합니까?”
    좋은 답변 구조: source-of-truth와 client resolution 책임 → traffic/capacity 특성 → cache·state 차이 → open resolver·DDoS 보안 → 장애 격리 → 비용과 운영 복잡도 trade-off.
  3. “일부 AZ에서만 DNS p99가 2초입니다. 어떻게 진단합니까?”
    좋은 답변 구조: 영향 QNAME/QTYPE·resolver mapping → cold/warm·RCODE·timeout 수치 → packet timestamp → recursor upstream/cache/queue → authoritative replica/delegation → 안전한 drain → rollback·대안.

10. 회상·확인 문제와 채점 기준

어제 내용 회상 3문제

  1. Localhost TCP path에서 남는 kernel state와 빠지는 link state를 각각 말하라.
  2. Container A의 localhost가 Container B service를 가리키지 않는 이유는?
  3. Localhost health와 LB health를 함께 운영해야 하는 이유는?

짧은 정답: ① socket/TCP/IP queue는 남고 ARP·frame·router hop은 빠진다. ② 서로 다른 network namespace와 loopback/socket table이기 때문이다. ③ process-local과 실제 remote serving path라는 다른 failure boundary를 검증한다. 상태 소유자와 반례까지 말하면 만점.

오늘 내용 확인 3문제

  1. Stub, recursive resolver, authoritative server의 책임을 한 문장씩 구분하라.
  2. RD=1, RA=1, AA=1은 각각 무엇을 뜻하며 무엇을 보장하지 않는가?
  3. SERVFAIL과 timeout은 관측 가능한 failure boundary가 어떻게 다른가?

짧은 정답: ① Stub은 위임, recursor는 최종 resolution/cache, authority는 local zone 원본 응답. ② recursion 요청·제공 가능·authoritative 출처를 뜻하지만 cache miss path, data 정확성, service 도달은 보장하지 않는다. ③ SERVFAIL은 DNS response를 받았고 timeout은 response를 받지 못했다. 정의 1점, 내부 흐름 1점, 미보장·대안 1점으로 문항당 3점.
