PROXY · LB · NAT · CLOUD NETWORK · WEEK 5 / DAY 31

SNAT/DNAT, conntrack, ephemeral port

주소 변환을 tuple·state·reverse path로 추적한다 · 개념 70분 + 실습 35분

한 줄 요약
SNAT는 주로 나가는 packet의 source IP:port를, DNAT는 들어오는 packet의 destination IP:port를 바꾼다. 첫 packet에서 만든 conntrack/NAT mapping이 reply packet을 역변환하므로 양방향 packet이 같은 state owner를 지나야 한다. Ephemeral port 고갈은 application host뿐 아니라 NAT public IP·destination 조합에서도 발생한다.

1. 선수 용어 사전

NAT / NAPTNetwork Address Translation은 IP 주소를 바꾸는 기능, NAPT는 IP와 TCP/UDP port까지 함께 매핑해 여러 내부 endpoint가 적은 외부 IP를 공유하게 한다.
SNATSource NAT. Egress packet의 source tuple을 바꾼다. 외부 server는 원 client가 아니라 NAT public IP:port를 peer로 본다.
DNATDestination NAT. Public VIP:port로 온 packet을 내부 server IP:port로 바꾼다. Port forwarding과 container published port가 대표 사례다.
TuplePacket/flow를 식별하는 field 묶음. 보통 protocol + source IP:port + destination IP:port의 5-tuple을 말한다.
ConntrackConnection tracking. Kernel이나 network appliance가 original/reply 방향 tuple, NAT mapping, timeout, 관찰 상태를 저장하는 table/subsystem이다.
Ephemeral portClient가 outbound socket을 열 때 OS가 임시로 고르는 local source port. NAT가 다시 고르는 external port와 같을 수도, 다를 수도 있다.
Mapping / filteringMapping은 내부 tuple을 외부 tuple로 바꾸는 규칙, filtering은 어떤 외부 source의 inbound packet을 그 mapping으로 허용할지 정하는 정책이다.
Idle timeout일정 시간 packet이 없을 때 state를 만료시키는 시간. Application connection은 살아 있다고 믿어도 중간 NAT mapping은 사라질 수 있다.
Asymmetric routingRequest와 reply가 다른 경로·stateful device를 지나는 현상. Reply 쪽 NAT/conntrack에 mapping이 없으면 drop 또는 잘못된 tuple이 된다.
Hairpin NAT같은 NAT 내부 host가 다른 내부 service의 external address를 사용했을 때 packet을 NAT가 내부로 되돌려 전달하는 동작.
Port preservation충돌이 없으면 내부 source port를 external port로 유지하려는 동작. 보장으로 단정하면 안 되며 충돌·구현에 따라 다른 port가 배정된다.
ChecksumHeader/payload 손상을 검출하는 값. NAT가 IP·port를 바꾸면 IP/TCP/UDP checksum도 일관되게 조정해야 한다.

2. 왜 중요한가

NAT는 “private IP를 public IP로 바꾼다”보다 훨씬 많은 state를 만든다. 두 host에서 같은 connection을 보더라도 주소와 port가 다르고, 중간 table이 가득 차거나 먼저 만료되면 application log만으로 원인을 찾기 어렵다.

  • 가용성: Conntrack table full, NAT port allocation failure, asymmetric reply는 server가 정상이어도 connect timeout/reset을 만든다.
  • 성능: 짧은 connection·공격적 retry·connection pool 미사용은 allocation churn과 state 수를 늘린다.
  • 정확성: Server log의 source IP는 NAT/LB일 수 있어 user identity나 unique client 수와 같지 않다.
  • 보안: NAT는 주소 변환이지 firewall이나 인증이 아니다. Mapping과 filtering policy를 구분해야 한다.
  • 면접: 좋은 답변은 before/after tuple, original/reply direction, state owner, timeout과 capacity 단위를 수치로 설명한다.

  1. Client: DNS 결과에 connect하면 kernel이 local address·ephemeral port를 골라 socket tuple을 만든다. Port만이 아니라 source address 선택과 route도 capacity에 영향을 준다.
  2. SNAT: 첫 packet에서 external IP:port를 배정하고 original/reply tuple mapping을 기록한다. 이후 packet은 같은 mapping을 따라야 한다.
  3. DNAT: Public destination을 내부 endpoint로 바꾸지만 client source는 앞선 SNAT 주소로 보인다. 실제 시스템에서는 LB proxy가 connection을 종료할 수도 있어 NAT와 구분한다.
  4. Application: Accept한 socket의 peer는 직전 network hop이 만든 tuple이다. HTTP header의 client IP는 별도 trust 문제다.
  5. Reply: Reverse translation은 새 규칙을 추론하는 과정이 아니라 기존 state lookup이다. 다른 stateful node로 가면 mapping miss가 발생한다.
  6. 완료: Application close, TCP FIN/RST, idle timeout, device policy는 서로 다른 시점에 state를 지운다. 한쪽만 먼저 지우면 stale connection이 된다.
핵심 불변식: Translation 뒤에도 protocol의 양방향 의미가 보존되어야 한다. Forward packet과 reply packet이 동일 mapping을 사용하고 checksum·timeout·filter state가 일관되어야 원 endpoint socket까지 돌아간다.

4. CS 수준 내부 동작

Conntrack은 TCP state machine과 같지 않다

Conntrack은 packet을 original/reply 방향으로 분류하고 protocol별 관찰 상태·timeout·NAT extension을 관리한다. TCP의 정확한 endpoint state는 각 host kernel이 소유한다. 중간 장비가 ESTABLISHED로 분류했다는 사실은 application이 accept·read·commit했다는 뜻이 아니다.

소유 상태무엇을 증명하고 무엇은 증명하지 않는가
Client socketLocal/remote tuple, send/receive queue, TCP sequence를 소유한다. 중간 NAT mapping 존재는 모른다.
Conntrack/NAT양방향 tuple과 translation·timeout을 소유한다. Application business commit은 모른다.
Server socketTranslated peer와 local endpoint를 본다. NAT 전 source는 network metadata 없이는 복원하지 못한다.

Port capacity는 단순히 65,535가 아니다

Host ephemeral range를 R, usable source IP 수를 A, 특정 destination·protocol에 필요한 동시 mapping을 C라 하면 보수적 1차 예산은 A×R이고 C/(A×R)를 utilization로 본다. 하지만 예약 port, TIME_WAIT/idle state, implementation의 mapping reuse/port-overlap, destination 분산, allocator collision 때문에 실제 capacity는 달라진다.

예를 들어 usable port가 28,000개이고 NAT IP가 2개라면 특정 hot destination에 보수적으로 약 56,000 tuple budget이 있다. Peak 40,000 active + 초당 2,000개 churn이 30초 남으면 60,000 state가 추가될 수 있어 위험하다. Retry는 실패당 새 connection을 만들면 이 churn을 곱한다.

Mapping과 filtering은 독립 축이다

같은 내부 IP:port를 다른 destination에서도 같은 external mapping으로 재사용하는가와, 외부 어느 endpoint의 packet을 허용하는가는 별개다. “Cone/symmetric NAT” 한 단어보다 endpoint-independent/address-dependent/address-and-port-dependent mapping·filtering을 나눠 말하는 편이 정확하다.

Failure window와 timestamp

t0 socket bind, t1 mapping allocate, t2 SYN forwarded, t3 reply hit, t4 app response, t5 mapping expire를 기록한다. SYN이 NAT 밖에서 보이지 않으면 route/rule/allocation을, 밖에는 보이나 reply가 없으면 remote path를, reply가 NAT에 도착했으나 안쪽에 없으면 reverse lookup/filter/asymmetry를 의심한다.

7. 35분 실습: Docker DNAT와 source tuple 변화를 증거로 확인

사전 조건: Docker Desktop/Engine과 Compose, 저장소 root. 시작 전에 container direct path와 host published port path에서 API가 볼 source IP:port가 같은지 예측한다. Docker Desktop은 Linux host와 구현 경계가 다를 수 있으므로 관찰 결과를 우선한다.

0단계 · 시작과 주소 확인 (6분)

make doctor
make up
make ps
docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client ip addr show eth0
docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client ip route

예상: Client container의 IP와 default gateway가 보인다. 이것이 client namespace의 source address/route이며 host의 localhost 주소와 다르다.

1단계 · Direct tuple과 ephemeral port 관찰 (8분)

docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client curl -sS http://api:8000/headers

docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client sh -c 'for i in 1 2 3 4 5; do curl -sS http://api:8000/headers; done'

예상: JSON의 client.host는 client container IP이고 client.port는 요청마다 달라질 수 있다. 새 TCP connection마다 local ephemeral port를 새로 고른 증거다.

2단계 · Published port DNAT 경로 비교 (8분)

docker compose -f labs/basic-network-observability/docker-compose.yml port api 8000
curl -sS http://localhost:18000/headers

docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec api tcpdump -ni any -c 6 'tcp port 8000'

예상: Host의 18000이 container 8000으로 publish된다. API가 본 peer는 direct container request와 다를 수 있다. 마지막 tcpdump는 다음 단계 요청과 함께 실행해 translated path의 source/destination tuple을 확인한다.

3단계 · 실패 주입: DNAT backend 중지 (7분)

docker compose -f labs/basic-network-observability/docker-compose.yml stop api
curl -sv --max-time 5 http://localhost:18000/headers
docker compose -f labs/basic-network-observability/docker-compose.yml start api

예상: Public host port 설정이 남아 있어도 backend listener가 없으면 요청은 성공하지 않는다. DNAT rule 존재와 backend readiness는 별도 불변식이다.

4단계 · 복구와 cleanup (6분)

curl -fsS http://localhost:18000/headers >/dev/null
make ps
make down

자주 나는 오류: Host port 충돌이면 make ps와 사용 중 listener를 확인한다. Tcpdump가 계속 기다리면 다른 terminal에서 curl을 실행하고 -c 6 종료를 기다린다. Docker Desktop에서 peer가 VM gateway로 보이는 것은 구현 경계의 증거이지 실패가 아니다. Cleanup 후 container/network가 내려갔는지 확인한다.

8. 놓치기 쉬운 함정

  • NAT와 proxy를 섞지 않는다. NAT는 packet header를 변환하고 proxy는 endpoint가 되어 새 connection을 만들 수 있다.
  • NAT는 firewall이 아니다. Mapping behavior와 inbound filtering policy는 별개다.
  • Host ephemeral port와 NAT external port는 다른 allocator다.
  • 65,535를 곧 capacity로 쓰지 않는다. 예약 범위·destination·protocol·state age·reuse 정책을 포함한다.
  • Conntrack ESTABLISHED는 application 성공이 아니다.
  • Table max만 늘리면 memory·lookup chain·복구 시간이 커질 수 있다.
  • Idle timeout 확대는 stale state와 port 점유를 늘린다.
  • Failover 장비가 config만 공유해도 기존 flow는 끊길 수 있다. Runtime mapping 동기화 여부를 본다.
  • Packet capture 관측점마다 tuple이 다르다. Interface와 NAT 전/후 hook 위치를 표시한다.

9. 대기업 기술 면접 질문

  1. “SNAT packet이 나갔다가 돌아오는 전 과정을 설명하세요.”
    좋은 답변 구조: Client bind/route → pre-NAT 5-tuple → mapping allocation → checksum rewrite → server peer → reply tuple → reverse lookup → socket demux → timeout/asymmetry failure.
  2. “NAT gateway port exhaustion을 어떻게 계산하고 진단합니까?”
    좋은 답변 구조: NAT IP·usable port·destination·protocol 가정 → active+churn×lifetime → allocation metric/conntrack evidence → retry/pool 원인 → rate limit/reuse/capacity canary → rollback.
  3. “DNAT 서비스가 간헐적으로 timeout입니다. 계층별 가설을 세우세요.”
    좋은 답변 구조: DNS/VIP route → listener/rule/filter → mapping/state owner → backend route/bind/health → reply asymmetry → 양방향 pcap/timestamp → safe cohort isolation.

10. 회상·확인 문제와 채점 기준

어제 내용 회상 3문제

  1. L4와 L7 LB의 대표 selection granularity는 무엇인가?
  2. Health check가 green이어도 user request가 실패할 수 있는 이유는?
  3. Source-IP stickiness의 두 가지 실무 문제는?

짧은 정답: ① L4는 flow/connection, L7은 HTTP request/stream 단위가 대표적이다. ② Check는 별도 source·path·protocol·시점의 synthetic control path라 실제 dependency와 queue를 놓칠 수 있다. ③ NAT/proxy가 여러 user를 한 IP로 묶고 hot key가 한 backend를 과부하시킨다.

오늘 내용 확인 3문제

  1. Client, NAT, server가 같은 TCP connection을 서로 다른 tuple로 보는 이유는?
  2. Conntrack state가 있는데도 application 요청이 실패할 수 있는 이유는?
  3. Usable port 28,000개×NAT IP 2개 환경에서 active 40,000, 초당 2,000 churn이 30초 유지되면 왜 위험한가?

짧은 정답: ① NAT가 source/destination IP:port를 rewrite하고 각 endpoint는 자기 관측점의 peer만 보기 때문이다. ② Conntrack은 network flow 관찰 state이지 server accept/read/dependency/commit 성공이 아니기 때문이다. ③ 보수적 56,000 budget에 active 40,000과 잠재 60,000 churn state가 겹쳐 allocation 여유를 넘을 수 있다. 문항당 정의 1점, state/flow 1점, failure·trade-off 1점으로 총 9점이다.
