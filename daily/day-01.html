COMPUTER NETWORKING · WEEK 1 / DAY 01

process, fd, socket, client/server

Process에서 Packet까지 · 예상 학습 30분 + 실습 30분

한 줄 요약
Application은 packet을 직접 보내지 않는다. Process가 file descriptor로 socket을 참조하고 kernel에 byte를 넘기면, kernel이 protocol state·buffer·routing을 적용해 peer socket까지 전달한다. “연결됐다”의 의미는 어느 계층을 말하는지에 따라 다르다.

1. 선수 용어 사전

Program / ProcessProgram은 실행 파일·코드, process는 실행 중인 인스턴스다. Process는 virtual address space, thread, credential, file descriptor table을 가진다.
File descriptor(fd)Process가 kernel object를 참조하는 작은 정수 handle. File뿐 아니라 socket, pipe, device도 fd로 다룬다.
Socket통신 endpoint를 나타내는 kernel object와 API 추상화. Address family, type, protocol, local/remote address, buffer, state를 가진다.
IP addressNetwork layer의 논리 주소. 특정 process를 식별하지 않고 interface, virtual IP, pod, load balancer 등 다양한 대상에 붙을 수 있다.
PortTransport protocol 안에서 endpoint를 식별하는 16bit 번호. TCP 443과 UDP 443은 서로 다른 namespace다.
Client / ServerClient는 먼저 통신을 시작하고 server는 알려진 endpoint에서 기다리는 역할이다. 하나의 process가 상황에 따라 둘 다 될 수 있다.
Listen / AcceptTCP server의 listening socket은 새 연결 요청을 받고, accept는 각 연결을 위한 별도 connected socket fd를 반환한다.
KernelProcess 격리, device, memory, network protocol state를 관리하는 OS 핵심. Application과 NIC 사이의 상태 소유자다.

2. 한 요청의 아키텍처

① Client process
HTTP library → socket fd → write/send
↓ system call · user→kernel boundary
② Client kernel
socket state · send buffer · TCP · route · IP
↓ frame · NIC · switch/router · network
③ Server kernel
NIC → IP/TCP validation → receive buffer → wakeup
↓ read/recv · kernel→user copy/notification
④ Server process
accepted fd → protocol parser → handler → business logic
  1. Client가 hostname을 쓰면 먼저 DNS로 IP 후보를 얻는다. DNS 성공은 해당 port의 TCP 연결 성공을 보장하지 않는다.
  2. socket()이 kernel socket object를 만들고 process에는 이를 가리키는 fd가 생긴다.
  3. connect()는 local ephemeral port를 선택하고 TCP state machine을 시작한다. 성공은 TCP connection 수립이지 TLS/HTTP/application 성공이 아니다.
  4. send()가 성공해도 byte가 peer application에서 처리됐다는 뜻은 아니다. 일반적으로 local send buffer가 data를 받아들였다는 범위다.
  5. Server의 listening socket이 SYN을 처리하고 handshake가 끝난 연결은 accept queue에 들어간다. accept()는 listening fd와 별개의 connected fd를 반환한다.
  6. Server process가 read()로 byte를 받고 protocol parser가 message boundary와 의미를 복원한 뒤에야 application 처리 단계가 시작된다.

3. fd와 socket을 깊게 이해하기

fd는 socket 자체가 아니라 process-local index다. 같은 숫자 7이 서로 다른 process에서 전혀 다른 kernel object를 가리킬 수 있다. fork()나 descriptor passing으로 여러 fd가 같은 open file description/socket을 공유할 수도 있다. 따라서 “fd 10에서 오류”만으로는 incident를 재현할 수 없고 PID, namespace, local/remote tuple, protocol, timestamp가 필요하다.

TCP connection은 흔히 (source IP, source port, destination IP, destination port, protocol)의 5-tuple로 구분한다. NAT나 proxy가 중간에 있으면 관측 위치마다 tuple이 달라진다. Application log의 client IP와 server가 실제 socket peer로 본 IP가 다를 수 있다.

핵심: “IP:port가 process다”라는 표현은 편의적이다. 실제 binding은 network namespace, protocol, local address wildcard, port, socket option, process fd와 연결된다.

4. CS·OS 내부 동작

상태의 소유자

  • Process: fd table, user-space buffer, request deadline, application protocol state.
  • Kernel socket: local/remote address, TCP state, send/receive buffer, sequence/ACK, error state.
  • Routing table: destination prefix에 대해 next hop과 egress interface를 선택하는 control state.
  • NIC/driver: descriptor ring과 frame 송수신, checksum/offload 같은 device path.
  • Server application: 요청을 decode하고 business side effect를 commit했는지 여부.

Blocking, non-blocking, readiness

Blocking read()는 data나 error가 생길 때 thread를 재운다. Non-blocking socket은 준비되지 않았을 때 즉시 EAGAIN을 반환하고, epoll/kqueue 같은 readiness notification과 함께 많은 connection을 적은 thread로 다룬다. Readable은 “완전한 HTTP request가 있다”가 아니라 일부 byte, EOF, error 중 하나일 수 있다.

Buffer와 backpressure

Application이 빠르게 send해도 network/peer가 느리면 kernel send buffer가 찬다. Blocking send는 대기하고 non-blocking send는 partial write/EAGAIN을 낼 수 있다. “send 호출 한 번 = message 한 개”라는 경계는 TCP에 없다. Receiver는 byte stream에서 length/header/delimiter로 framing해야 한다.

성공의 여러 단계

connect 성공TCP peer와 state가 ESTABLISHED. TLS 인증이나 service readiness는 미확정.
send 성공Local kernel이 byte를 수용한 범위. Peer app 처리 미확정.
TCP ACKPeer TCP stack이 sequence 범위를 수신한 범위. Business transaction 미확정.
HTTP 200Application protocol 응답. 비동기 job이나 downstream commit까지 포함하는지는 API contract에 달림.

5. 실무 설계 판단

판단Best practice와 이유
Timeoutconnect, TLS handshake, write, read, 전체 request deadline을 구분한다. 하나의 큰 timeout은 어느 단계가 느린지 숨긴다.
Connection poolprocess/pod 수 × pool max가 downstream max connection을 넘지 않는지 budget을 계산한다. Idle timeout과 keep-alive 불일치도 확인한다.
Binding127.0.0.1, 0.0.0.0, 특정 interface의 노출 범위가 다르다. 개발 환경 설정을 production에 그대로 쓰지 않는다.
RetryTimeout 결과가 불명확할 수 있으므로 idempotency와 deadline, exponential backoff, jitter, retry budget을 함께 둔다.
Observabilityclient DNS/connect/TLS/TTFB 시간, server accept queue, active socket, retransmission, request ID를 같은 timeline에 맞춘다.
SecurityListening address와 firewall만으로 identity가 생기지 않는다. TLS/mTLS, authentication, authorization, secret rotation을 application boundary와 맞춘다.

6. 장애 대응 표

상황: Client에서 API 호출이 timeout되지만 server health check는 정상이다.

증상일부 client만 timeout, connection refused/reset 혼재, p99 증가, server 2xx 지표는 정상.
먼저 수집할 증거/지표Client DNS 결과, source/destination tuple, connect/TLS/read timing, ss -tanp state, listen/accept queue, retransmission, firewall/LB log, server request ID와 access log.
가능한 가설잘못된 port, localhost bind, route/firewall drop, accept queue overflow, connection pool exhaustion, stale DNS, LB unhealthy subset, server handler stall.
안전한 첫 조치한 client와 한 destination IP를 고정해 DNS→TCP→TLS→HTTP 단계별 probe를 실행한다. Retry를 늘리기 전에 request rate와 queue를 확인한다.
Rollback/복구문제 backend를 LB에서 drain하고 known-good config로 rollback한다. Pool/queue 변경은 단계적으로 적용하며 SLO와 downstream load를 관찰한다.
하지 말아야 할 조치원인 확인 없이 모든 timeout과 retry를 늘리지 않는다. Packet capture의 token·개인정보를 무제한 보관하지 않는다. Health check 정상만으로 전체 path 정상이라 단정하지 않는다.

먼저 예측: Server가 0.0.0.0:8000에 listen하면 ss에는 client마다 별도의 ESTABLISHED socket이 생길까?

make doctor
make up
make shell

# client container 안에서
getent hosts api
nc -vz api 8000
curl -v http://api:8000/headers

ss -tanp
# 다른 터미널에서 host 측

nc -vz api 8999
curl -v --connect-timeout 2 http://api:8999/headers

예상 관찰: DNS는 api의 IP를 반환하고 8000은 연결된다. API process에는 listening socket과 connection별 connected socket이 따로 보인다. 8999는 이름 해석과 route가 성공해도 해당 port에 listener가 없어 빠른 refused/RST가 날 수 있다.

추가 관찰: tcpdump -ni any 'tcp port 8000 or tcp port 8999'로 SYN/SYN-ACK/ACK와 RST 차이를 본다. Capture에는 payload와 credential이 포함될 수 있으므로 실습 traffic만 제한한다.

자주 나는 오류: ss: not found면 project image와 README 도구 목록을 확인한다. Host와 container의 localhost는 서로 다른 network namespace다. Proxy를 거치면 source IP와 destination port가 달라질 수 있다.

Cleanup: exit 후 make down. 다른 Docker network나 volume을 광범위하게 삭제하지 않는다.

8. 놓치기 쉬운 함정

  1. localhost = 내 노트북: Container·VM·pod마다 loopback namespace가 다르다.
  2. IP = 물리 장비 하나: VIP, anycast, interface alias, pod IP, NAT 뒤 주소가 될 수 있다.
  3. send 성공 = 처리 성공: Local buffer 수용과 peer business commit을 구분한다.
  4. TCP = message protocol: TCP는 ordered byte stream이며 application framing이 필요하다.
  5. Server process = listening socket 하나: Listener와 accepted connection fd, worker/thread 관계를 구분한다.
  6. Timeout = network 문제: DNS, queue, TLS, application, downstream DB가 모두 timeout으로 보일 수 있다.

9. 대기업 기술 면접 질문

Q1. 브라우저에서 URL을 입력한 뒤 server process까지의 흐름은?

좋은 답변 구조: DNS → route/neighbor → socket/connect → TCP/QUIC → TLS/SNI/ALPN → HTTP → proxy/LB/NAT → server accept/read → handler → response를 말하고, 각 단계의 상태 소유자와 관측 증거·timeout을 붙인다.

Q2. Connection refused와 timeout의 차이는?

좋은 답변 구조: Packet 증거로 refused는 보통 reachable host의 RST/적극 거절, timeout은 응답 부재라고 설명 → firewall drop·route·overload 등 가설 → ICMP/RST가 정책으로 숨겨질 수 있는 edge case → 첫 probe를 제시한다.

Q3. Connection pool 크기를 어떻게 정합니까?

좋은 답변 구조: 대상 capacity와 instance 수 → Little's Law 기반 concurrency ≈ throughput×latency → headroom → queue/deadline → pool 총합과 DB/LB limit → idle/reuse → overload 시 load shedding과 관측 지표를 수치로 방어한다.

  2. IP address와 port는 각각 무엇을 구분하는가?
