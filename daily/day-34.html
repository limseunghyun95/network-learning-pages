1. 선수 용어 사전

Reverse proxyClient 요청을 받아 대신 backend에 새 요청을 보내는 중간 server다. 두 connection의 endpoint이므로 timeout·queue·retry 상태를 소유한다.
Backend / targetProxy나 Load Balancer가 실제 처리를 맡기는 application instance다.
Health checkTarget이 traffic을 받아도 되는지 별도 probe로 판단하는 control loop다. 실제 사용자 요청의 성공과 동일하지 않다.
Timeout특정 단계가 정해진 시간 안에 끝나지 않으면 기다림을 중단하는 정책이다. Connect, read, idle, request deadline은 서로 다른 clock이다.
Deadline전체 작업이 완료돼야 하는 절대 시각 또는 남은 총 시간이다. Hop마다 새 timeout을 시작하는 것보다 end-to-end budget을 보존한다.
503 / 504 / 502503은 service가 처리할 target/capacity가 없음을, 504는 gateway가 upstream을 제때 받지 못했음을, 502는 gateway가 유효한 upstream response를 만들지 못했음을 보통 나타낸다. 제품별 의미를 확인한다.
Passive / active health실제 요청 실패로 상태를 추론하는 방식과 별도 probe를 주기적으로 보내는 방식이다.
NAT mappingOriginal 5-tuple과 변환된 5-tuple, reply 역변환, timeout을 연결하는 state다.
Connection poolProxy가 backend connection을 재사용하도록 보관하는 집합이다. 연결 비용을 줄이지만 stale state와 queue를 만든다.
BackpressureDownstream이 느릴 때 upstream의 유입 속도·동시성·queue를 제한해 overload 전파를 막는 제어다.
Failure window실제 failure 발생부터 probe threshold가 unhealthy로 바뀌고 traffic이 우회될 때까지 실패가 노출되는 구간이다.

2. 왜 중요한가

사용자는 “느리다” 또는 “502다”만 보지만, 실제 원인은 backend CPU, accept queue, proxy read timeout, LB health convergence, NAT idle expiry처럼 서로 다른 계층에 있다. 증거 없이 timeout만 늘리면 느린 실패가 더 오래 자원을 점유한다.

  • 가용성: Health check가 green이어도 실제 endpoint·dependency가 실패할 수 있고, 모든 target이 unhealthy일 때 제품이 fail-open할 수도 있다.
  • 정확성: Client cancel 뒤 backend가 계속 작업하면 사용자는 실패를 봤지만 write는 commit되는 ambiguous success가 생긴다.
  • 성능: Timeout보다 긴 queue와 retry는 Little’s Law에 따라 in-flight state를 쌓아 장애를 증폭한다.
  • 비용: NAT·LB·cross-AZ path와 retry traffic은 같은 business request의 packet 수와 처리량 비용을 늘린다.
  • 면접: 좋은 답변은 status code를 외우지 않고 connection A/B, state transition, budget, health convergence와 안전한 rollback을 그린다.

3. 아키텍처 그림과 요청 흐름

  1. Client budget: DNS·connect·TLS·server wait·body read·retry가 하나의 deadline을 나눠 쓴다.
  2. NAT: 주소만 바꾸는 것이 아니라 reply lookup과 idle timer를 소유한다. Mapping expiry는 application keep-alive보다 짧을 수 있다.
  3. Proxy termination: Connection A와 B는 독립된 sequence number, source port, buffer, timeout을 가진다. A의 원 IP가 B에 자동 보존되는 것은 아니다.
  4. Backend: TCP connect 성공은 process accept/read, thread/async queue, dependency와 commit 성공을 증명하지 않는다.
  5. Timeout: Proxy가 먼저 포기해도 backend 작업을 취소하지 못하면 late response 또는 duplicate side effect가 남는다.
  6. Health convergence: Probe interval×failure threshold만큼 traffic이 이미 나쁜 target으로 갈 수 있다. 반대로 회복도 success threshold만큼 늦다.
  7. 성공 확정: Client가 complete response를 받고, side effect가 있다면 idempotency key로 단일 commit이 확인될 때 business success다.
핵심 불변식: 바깥 deadline > 각 hop timeout + retry backoff여야 하며, 내부 hop은 남은 budget보다 짧아야 한다. Health probe는 실제 traffic과 같은 port·path·dependency 경계를 의도적으로 검사하고, NAT/connection pool의 idle timeout 순서를 알고 있어야 한다.

4. CS 수준 내부 동작

Timeout budget은 중첩된 clock이다

Client deadline이 8초인데 proxy read timeout 10초, backend DB timeout 15초라면 바깥이 먼저 닫혀 내부 작업이 orphan이 된다. 권장 모델은 client deadline 8s > proxy total 7s > backend dependency 5s처럼 바깥에서 안쪽으로 감소시키고 DNS/connect/TLS/queue에 별도 budget을 예약하는 것이다. Retry는 새 8초를 받지 않고 남은 deadline만 사용한다.

Health state machine과 hysteresis

Probe 하나의 실패를 즉시 unhealthy로 바꾸면 transient loss에 흔들린다. 그래서 healthy → suspect → unhealthy → recovering → healthy와 연속 threshold를 둔다. 이 hysteresis는 안정성을 주지만 failure detection과 recovery를 늦춘다. AWS ALB는 interval·timeout·healthy/unhealthy threshold를 각각 관리하며 모든 target이 unhealthy면 fail-open할 수 있다.

Queueing과 retry amplification

Little’s Law L=λW에서 초당 500 request와 평균 4초 체류는 약 2,000 in-flight를 만든다. Client가 한 번 retry하면 arrival rate가 늘고, slow backend의 queue가 더 길어져 timeout이 더 많아지는 positive feedback가 생긴다. Bounded queue, concurrency limit, jittered backoff, retry budget과 circuit breaker가 필요하다.

NAT·pool의 stale connection

Connection pool은 socket을 살아 있다고 생각하지만 NAT/LB는 idle state를 만료했을 수 있다. 다음 write에서 RST나 timeout이 나타난다. AWS NAT gateway는 공식 문서상 idle 350초 이후 mapping을 만료하고 이후 packet에 RST를 보낼 수 있다. Pool max-idle과 keepalive를 가장 짧은 middlebox idle timeout보다 보수적으로 설정한다.

Error code의 owner를 구분한다

같은 502라도 proxy connect refusal, TLS handshake, malformed response가 다르고, 504도 connect timeout·read idle timeout·NACL reply 차단이 다르다. Status code는 결과 label이지 원인 증거가 아니다. Access log의 upstream address/status/time, target reason code, Flow Logs와 packet flags를 같은 request ID·timestamp로 결합한다.

사전 조건: Docker Desktop/Engine과 Compose, 저장소 root, terminal 두 개. 이 랩의 proxy upstream timeout은 Python 코드상 5초다. 각 단계 전에 예상 status·소요 시간·source IP를 적는다.

0단계 · 시작과 baseline (6분)

docker compose -f labs/basic-network-observability/docker-compose.yml \

예상: HTTP 200, X-Lab-Upstream: api:8000. JSON의 client.host는 원 client 172.28.0.50가 아니라 proxy 172.28.0.40다. Proxy가 connection을 terminate하고 B를 새로 만들었기 때문이다.

1단계 · 두 TCP flow packet 관찰 (8분)

Terminal A:

docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec proxy timeout 20 tcpdump -ni eth0 \
  'tcp port 8080 or tcp port 8000'

Terminal B:

docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client curl -fsS http://proxy:8080/api/headers

예상: Proxy eth0에서 client→proxy:8080과 proxy→api:8000의 서로 다른 5-tuple이 보인다. Sequence number와 source port도 독립이다.

2단계 · Proxy read timeout 주입 (9분)

time docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client curl -sv --max-time 8 \
  'http://proxy:8080/api/slow?seconds=7'
time docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client curl -fsS --max-time 8 \
  'http://api:8000/slow?seconds=7'
docker compose -f labs/basic-network-observability/docker-compose.yml \
  logs --tail=30 proxy api

예상: Proxy 경유는 약 5초 뒤 502 JSON으로 끝나고 direct API는 약 7초 뒤 성공한다. 같은 backend라도 proxy timer가 먼저 결과를 소유한다. API log에는 proxy가 닫은 뒤 late write 관련 흔적이 보일 수 있다.

3단계 · Unhealthy backend와 복구 (9분)

docker compose -f labs/basic-network-observability/docker-compose.yml stop api
docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client curl -sv --max-time 4 http://proxy:8080/api/headers
docker compose -f labs/basic-network-observability/docker-compose.yml ps
docker compose -f labs/basic-network-observability/docker-compose.yml start api
until docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec -T client curl -fsS http://api:8000/headers >/dev/null; do sleep 1; done
docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client curl -fsS http://proxy:8080/api/headers

예상: Backend stop 중 proxy는 connect failure를 502로 변환하고, restart/readiness 뒤 성공한다. 이 lab proxy는 active health check가 없어서 request-time에만 실패를 발견한다. 실제 LB의 interval·threshold·drain과 구분한다.

4단계 · Published-port NAT 경계와 cleanup (8분)

# Host terminal에서 실행: 18080이 container 8080으로 변환된다.
curl -sS -D - http://localhost:18080/api/headers
docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec proxy ss -tan
make down

예상: Host는 18080으로 접속하지만 proxy는 8080에서 accept한다. Docker가 published-port DNAT/control state를 소유한다. Proxy가 API에 만든 B의 source는 다시 proxy IP다. Docker Desktop/Engine에 따라 host-side source·NAT 구현은 달라질 수 있으므로 packet evidence를 진실로 삼는다.

자주 나는 오류: 18080 충돌이면 docker compose ps로 owner를 확인하고 임의 process를 종료하지 않는다. Direct slow call이 8초를 넘으면 machine 부하를 확인한다. Stop 뒤 502가 아닌 DNS error여도 backend discovery failure라는 증거다. Cleanup 전에 API를 start해 다른 실습자의 상태를 복구한다.

8. 놓치기 쉬운 함정

  • 502/504는 원인이 아니라 proxy가 본 결과다. Upstream timing과 packet evidence를 본다.
  • Health check 성공은 business dependency 성공이 아니다. 너무 얕아도, 너무 깊어도 문제다.
  • 모든 target unhealthy가 traffic 0을 뜻하지 않을 수 있다. ALB의 fail-open 동작을 설계에 포함한다.
  • Timeout을 늘리면 capacity가 늘지 않는다. In-flight·queue·memory가 더 쌓일 수 있다.
  • Client timeout은 backend cancel을 보장하지 않는다. Deadline propagation과 cancellation support가 필요하다.
  • Retry는 새로운 traffic이다. 멱등성·budget·backoff가 없으면 outage를 증폭한다.
  • Proxy 뒤 source IP는 원 client가 아닐 수 있다. Trusted proxy에서만 전달 header를 수용한다.
  • NAT idle timeout과 pool lifetime을 독립 설정하면 stale socket이 생긴다.
  • Average latency만 보면 tail queue를 놓친다. P95/P99와 timeout/error cohort를 나눈다.

9. 대기업 기술 면접 질문

  1. “Client가 8초에 timeout하고 proxy는 504, backend는 10초 뒤 성공 로그를 남겼습니다. 설명하세요.”
    좋은 답변 구조: connection A/B → 각 timer owner → cancellation 부재 → ambiguous side effect → idempotency/deadline propagation → metric·trace 증거.
  2. “Health check interval과 threshold를 설계하세요.”
    좋은 답변 구조: RTO·false positive 요구 → detection time 계산 → probe cost/path → hysteresis·fail-open → drain/recovery → canary와 alarm.
  3. “배포 뒤 간헐 502와 NAT IdleTimeoutCount가 증가합니다. 어떻게 진단합니까?”
    좋은 답변 구조: timestamp cohort → fresh vs pooled connection → NAT/LB/pool idle order → RST·retransmission → retry amplification → pool max-idle rollback과 장기 대안.

10. 회상·확인 문제와 채점 기준

어제 내용 회상 3문제

  1. Security Group과 NACL의 state·rule evaluation 차이는?
  2. NACL에서 request 443만 허용하면 reply가 실패할 수 있는 이유는?
  3. SG rule 삭제 뒤 기존 connection과 신규 connection이 다를 수 있는 이유는?

짧은 정답: ① SG는 ENI 경계 stateful allow 합집합, NACL은 subnet 경계 stateless first-match allow/deny다. ② Reply destination ephemeral port를 별도 허용해야 한다. ③ Tracked state lifetime 때문에 기존 flow가 계속 허용될 수 있다.

오늘 내용 확인 3문제

  1. Proxy 경유 request에서 TCP connection이 최소 두 개인 이유는?
  2. Health check threshold의 장점과 failure window 비용은?
  3. NAT idle timeout보다 pool max-idle이 길면 어떤 failure가 생기는가?

짧은 정답: ① Proxy가 client connection을 terminate하고 backend에 새 5-tuple로 연결하기 때문이다. ② Transient failure 흔들림을 줄이지만 감지·복구가 늦어 그동안 bad target에 traffic이 갈 수 있다. ③ Pool은 살아 있다고 믿는 mapping-expired socket을 재사용해 RST/timeout을 낸다. 문항당 정의 1점, 내부 흐름 1점, failure·trade-off 1점으로 총 9점이다.
