HTTP · TLS · QUIC · WEEK 4 / DAY 22

HTTP semantics, method/status/header/body

Byte stream 위의 message를 분산 시스템 계약으로 읽기 · 개념 60분 + 실습 35분

한 줄 요약
HTTP message는 method가 “무엇을 요청하는가”, target URI가 “어느 resource인가”, fields가 “조건·표현·routing metadata가 무엇인가”, content가 “어떤 representation 또는 처리 입력인가”, status가 “server가 그 요청을 어떻게 해석한 결과인가”를 합쳐 만든 계약이다. HTTP 200, TCP ACK, business commit은 서로 다른 성공 경계다.

1. 선수 용어 사전

HTTPHypertext Transfer Protocol. Resource에 대한 request와 response의 의미를 정의하는 stateless application-level protocol이다. HTTP/1.1·2·3은 wire 표현이 달라도 core semantics를 공유한다.
ResourceURI로 식별되는 대상 개념. 파일 하나와 동일하지 않다. 주문, 검색 결과, 현재 사용자 상태처럼 server가 의미를 부여한 추상 대상일 수 있다.
Representation특정 시점 resource 상태를 표현한 data와 metadata의 묶음. 같은 resource도 JSON, HTML, gzip, 한국어 등 여러 representation을 가질 수 있다.
MethodTarget resource에 수행하려는 의미. GET은 representation 전송, POST는 resource 고유 처리, PUT은 target 상태 생성·대체 같은 계약을 나타낸다.
SafeClient가 요청한 주된 의미가 server state 변경이 아닌 method 특성. GET·HEAD·OPTIONS·TRACE가 safe로 정의되지만 logging·billing 같은 부수 효과까지 “아무 변화 없음”을 뜻하지 않는다.
Idempotent동일 요청을 한 번 또는 여러 번 의도적으로 적용했을 때 server에 의도된 효과가 같은 성질. PUT·DELETE는 idempotent semantics지만 각 응답·로그·부수 효과가 완전히 동일하다는 뜻은 아니다.
Status codeResponse의 세 자리 결과 분류. 1xx 정보, 2xx 성공, 3xx redirection, 4xx client 쪽 request 문제, 5xx server가 유효한 request 수행에 실패한 계열이지만 개별 의미를 읽어야 한다.
Field / HeaderMessage에 붙는 이름-값 metadata. HTTP/1.1에서는 header line으로 보이고 HTTP/2·3에서는 field section으로 encoding된다. Authorization, Content-Type, Cache-Control처럼 의미가 각자 다르다.
ContentMessage가 전달하는 byte. 흔히 body라고 부르지만 modern HTTP semantics 문서에서는 content로 설명한다. Method·status에 따라 의미나 존재 가능성이 달라진다.
Content-Type보내는 content의 media type과 parameter를 설명한다. application/json이라고 썼다고 JSON이 자동 검증되는 것은 아니다.
AcceptClient가 response로 선호하는 media type을 제시하는 content negotiation field. 보내는 request content의 type을 말하는 Content-Type과 반대 역할이다.
Origin / IntermediaryOrigin server는 target resource의 authoritative response를 만들고, proxy·gateway·cache 같은 intermediary는 request/response를 전달·변환·저장할 수 있다.
FramingMessage와 content 경계를 wire에서 식별하는 규칙. HTTP/1.1의 Content-Length/chunked와 HTTP/2·3 frame은 표현이 다르지만 semantics와 구분해야 한다.

2. 왜 중요한가

HTTP를 “GET은 조회, POST는 생성” 수준에서 멈추면 retry, cache, proxy, API versioning, 보안 사고에서 잘못된 결정을 한다. Method와 status는 구현 편의가 아니라 중간 장비와 client가 자동 행동을 결정하는 shared contract다.

  • 200은 business success 보증이 아니다. GraphQL/error envelope처럼 content 안에 실패를 담는 설계도 있고, 반대로 202는 요청을 받았지만 처리가 끝나지 않았음을 뜻한다.
  • Method는 retry 가능성에 영향을 준다. Idempotent semantics는 자동 재시도 판단의 중요한 입력이지만, 실제 API가 계약을 어기거나 conditional request가 없으면 lost update가 생긴다.
  • Fields는 data path를 바꾼다. Host/:authority는 routing, Authorization은 identity, Accept/Vary는 representation과 cache key, Content-Length는 framing에 영향을 준다.
  • Proxy는 투명한 선이 아니다. Request를 terminate하고 새 upstream connection을 만들며 header를 추가·삭제하고 cache response나 자체 502/503을 만들 수 있다.

  1. Target 결정: Scheme, authority, path, query가 target resource와 routing에 참여한다. Fragment는 일반적으로 HTTP request target으로 전송되지 않는다.
  2. Method semantics: POST content를 origin이 resource 고유 규칙으로 처리한다. “POST=생성”은 흔한 API 관례이지 모든 POST의 표준 의미가 아니다.
  3. Fields 적용: Authorization은 protection space, Content-Type은 보낸 content, Accept는 원하는 response, Idempotency-Key는 별도 application contract를 나타낸다.
  4. Intermediary: Proxy는 hop-by-hop field를 처리하고 routing·cache policy에 따라 origin까지 보내지 않을 수 있다. Via/request ID로 관측 경계를 남긴다.
  5. Origin transaction: TCP ACK는 request byte 수신일 뿐 validation·authorization·DB commit을 보장하지 않는다. Commit과 response write 사이에도 failure window가 있다.
  6. Response 해석: Status, Location, ETag, content를 함께 읽는다. 201은 생성 결과, 202는 accepted-not-complete, 204는 content 없는 성공처럼 개별 semantics가 다르다.
상태 소유권: URI resource state는 origin, cache entry freshness는 cache, transport connection은 각 endpoint/proxy, retry attempt와 deadline은 client, transaction dedup은 application/idempotency store가 소유한다. 이 owner를 섞으면 “응답을 못 받았으니 처리되지 않았다” 같은 위험한 결론이 나온다.

4. CS 수준 내부 동작

Semantics와 wire syntax를 분리하라

HTTP/1.1은 start-line과 textual field line, content framing을 사용한다. HTTP/2는 stream 안의 HEADERS/DATA frame과 HPACK을, HTTP/3는 QUIC stream과 QPACK을 사용한다. 하지만 GET, 404, Content-Type, cache semantics 같은 의미는 RFC 9110을 공유한다. “HTTP header는 항상 줄바꿈된 text”라고 답하면 HTTP/2·3에서 틀린다.

Method matrix: safe와 idempotent는 다르다

MethodSafeIdempotent핵심 의미·함정
GETYesYes현재 선택된 representation 전송. Query URL에 secret을 넣지 않고 GET으로 state change를 설계하지 않는다.
HEADYesYesGET과 같은 header semantics, response content 없음. 구현이 GET metadata와 일치하는지 본다.
POSTNoNoResource 고유 처리. Retry가 필요하면 idempotency key·dedup·status query를 application 계약으로 추가한다.
PUTNoYesTarget resource 상태를 supplied representation으로 생성·대체. If-Match로 lost update를 막는다.
DELETENoYesTarget와 현재 기능의 association 제거 요청. 물리 data 즉시 삭제·모든 후속 응답 동일을 보장하지 않는다.

Status는 category보다 개별 의미가 중요하다

  • 200 OK: Method에 따라 성공 의미와 content가 다르다. GET은 representation, POST는 처리 결과일 수 있다.
  • 201 Created: 하나 이상의 resource가 생성됐고 Location이 primary resource를 가리킬 수 있다.
  • 202 Accepted: 처리를 수락했지만 완료되지 않았다. Job/status resource와 최종 실패 관측이 필요하다.
  • 204 No Content: 성공했지만 response content가 없다. Client가 empty JSON으로 parsing하지 않아야 한다.
  • 304 Not Modified: Conditional GET/HEAD에 선택 representation을 다시 보내지 않는 cache validation 결과이며 일반 3xx redirect가 아니다.
  • 409/412/429: Conflict, precondition failure, rate limit은 각각 다른 retry/사용자 조치가 필요하다.
  • 502/503/504: Gateway upstream error, temporary unavailable, gateway timeout의 owner를 response header·proxy log로 분리한다.

Fields·content·framing의 보안 경계

Content-Length는 media type이 아니라 framing metadata다. Content-Type은 byte 해석, Content-Encoding은 representation coding, Transfer-Encoding은 HTTP/1.1 message transfer coding을 설명한다. Front proxy와 backend가 message length를 다르게 해석하면 request smuggling 위험이 생긴다. Parser가 여러 Content-Length 또는 Transfer-Encoding 조합을 어떻게 거부하는지 engine/version별로 검증한다.

Header에는 Authorization·Cookie·trace baggage 같은 secret과 개인정보가 들어갈 수 있다. 무제한 field size는 memory/CPU 공격, CRLF 처리 오류는 header injection, 신뢰하지 않은 Host/:authority는 cache poisoning·routing 문제를 만들 수 있다. Allowlist, size limit, normalization 후 validation, hop-by-hop 처리와 redaction을 둔다.

6. 장애 대응 표

상황: 배포 후 일부 POST가 중복 생성되고, proxy에는 504가 늘었으며 origin log에는 201이 남아 있다. 일부 client는 empty 204를 JSON parsing error로 기록한다.

순서실행 내용
증상Method·route·status·client version·proxy/upstream status·retry attempt·idempotency key별 중복률과 parsing error, connect/TTFB/total latency를 분리한다.
먼저 수집할 증거/지표Request ID로 edge/proxy/origin log를 join하고 request method/target, redacted fields, content length/type, origin commit/idempotency record, response status/write timestamp, proxy deadline·retry log, client retry와 body parser를 변경 전에 보존한다.
가능한 가설Origin commit 후 response 유실, proxy 504 뒤 client retry, idempotency key 미전파/TTL 부족, POST 자동 retry, 204 content assumption, 202를 완료로 오해, parser/framing 불일치, stale cache를 세운다.
안전한 첫 조치비멱등 자동 retry를 중단·제한하고 idempotency/status query 경로를 사용한다. 문제 client/proxy version을 canary에서 drain하고 transaction reconciliation을 시작한다.
Rollback/복구최근 proxy timeout/retry, status mapping, serializer/parser, cache rule을 known-good으로 원복한다. 신규 중복 중단→미확정 transaction 판정→status/body parsing 회복→504/p99 정상화 순서로 확인한다.
하지 말아야 할 조치모든 5xx 즉시 retry, 504를 미처리로 단정, DB 중복 수동 삭제 전 audit 미보존, timeout 무제한 확대, 모든 응답을 200으로 변환, Content-Length/Transfer-Encoding 검증 비활성화를 하지 않는다.

7. 35분 실습: 같은 TCP 위에서 semantics 분리하기

목표: Docker lab에서 method/status/fields/content를 바꾸며 raw request와 response를 관찰하고, proxy가 만든 upstream metadata와 origin 결과를 구분한다.

사전 조건: Docker Desktop, 저장소 루트, 터미널 2개. 실행 전 GET/HEAD/POST의 response content, 204/503 처리, Content-Type과 Accept의 역할을 예측한다.

0단계 · 시작과 packet 관측 (5분)

make up
docker compose -f labs/basic-network-observability/docker-compose.yml exec client tcpdump -ni eth0 -A -s 0 -c 80 'tcp port 8000 or tcp port 8080'

Capture에는 header/content가 보일 수 있으므로 lab data만 사용한다. 다른 터미널에서 다음 요청을 실행한다.

1단계 · Method와 content (10분)

docker compose -f labs/basic-network-observability/docker-compose.yml exec client curl -sv http://api.lab:8000/headers
docker compose -f labs/basic-network-observability/docker-compose.yml exec client curl -sSI http://api.lab:8000/headers
docker compose -f labs/basic-network-observability/docker-compose.yml exec client curl -sv -X POST -H 'Content-Type: application/json' -H 'Accept: application/json' --data '{"order_id":42}' http://api.lab:8000/orders

예상 관찰: API echo의 method/path/headers가 달라진다. HEAD는 구현이 지원하지 않으면 501 같은 결과를 낼 수 있는데, 이것도 “TCP 성공과 HTTP method 지원은 별개”라는 증거다. Content-Type은 보낸 JSON, Accept는 원하는 response를 설명한다.

2단계 · Status와 성공 경계 (8분)

docker compose -f labs/basic-network-observability/docker-compose.yml exec client sh -lc 'for code in 200 201 202 204 409 429 503; do curl -sS -o /tmp/body -D /tmp/head -w "requested=$code actual=%{http_code} bytes=%{size_download}\n" http://api.lab:8000/status/$code; sed -n "1,5p" /tmp/head; done'

예상 관찰: Lab handler는 status에 관계없이 JSON content를 보낼 수 있어 204처럼 content가 허용되지 않는 status에서 client/server 구현 차이가 드러날 수 있다. “내 framework가 보냈다”가 protocol contract를 자동 보장하지 않음을 설명한다.

3단계 · Proxy가 만든 두 번째 connection (7분)

docker compose -f labs/basic-network-observability/docker-compose.yml exec client curl -sv -H 'X-Request-ID: day22-lab' http://proxy.lab:8080/api/headers
docker compose -f labs/basic-network-observability/docker-compose.yml logs --tail=30 proxy api

예상 관찰: Client→proxy 8080과 proxy→api 8000은 별도 tuple이다. X-Lab-Upstream, echoed Host/headers, 양쪽 log timestamp로 어느 component가 response를 만들었는지 설명한다.

4단계 · 실패 주입과 cleanup (5분)

docker compose -f labs/basic-network-observability/docker-compose.yml exec client curl --max-time 1 -sv 'http://api.lab:8000/slow?seconds=2'
docker compose -f labs/basic-network-observability/docker-compose.yml logs --tail=20 api
make down

예상 관찰: Client는 timeout이어도 origin이 request를 받아 처리했을 수 있다. GET이라 재시도 semantics는 안전하지만 POST side effect였다면 별도 idempotency 계약이 필요하다.

  • Could not resolve host면 lab DNS와 container 상태를 확인한다.
  • HEAD가 501이면 server method implementation 결과이며 network 장애가 아니다.
  • 204 body 관찰은 curl/framework가 protocol에 따라 content를 무시할 수 있어 raw capture와 함께 본다.
  • JSON quote 오류는 shell escaping 문제다. Request capture의 actual content를 확인한다.
  • Cleanup 후 container/network가 내려갔는지 docker compose ... ps로 확인한다.

8. 놓치기 쉬운 함정

  • POST는 반드시 create가 아니다. Resource 고유 처리 method다.
  • Idempotent는 response가 항상 같다는 뜻이 아니다. 의도된 server 효과 기준이다.
  • Safe method도 logging·metering 부수 효과는 있을 수 있다. Client가 state change를 요청하지 않는다는 뜻이다.
  • 200과 business success를 같게 두지 않는다. Status와 domain result 계약을 함께 본다.
  • 202는 완료가 아니다. Job status와 최종 실패 전달 경로가 필요하다.
  • Content-Type과 Accept를 뒤집지 않는다. 전자는 보내는 content, 후자는 원하는 response다.
  • HTTP/2·3 field를 항상 text line이라 설명하지 않는다. Semantics와 wire encoding을 분리한다.
  • GET request content에 application 의미를 기대하지 않는다. Intermediary가 거부할 수 있고 표준상 일반적 의미가 없다.
  • Hop-by-hop field를 무심코 forward하지 않는다. Connection별로 처리해야 한다.
  • Raw URL/header를 metric label로 쓰지 않는다. Secret 노출과 cardinality 폭발을 만든다.
  • Proxy 504가 origin rollback을 뜻하지 않는다. Commit 후 response failure window를 확인한다.

9. 대기업 기술 면접 질문

  1. “Safe와 idempotent method 차이를 retry와 함께 설명하세요.”
    좋은 답변 구조: client-intended semantics 정의 → GET/HEAD safe+idempotent, PUT/DELETE idempotent-not-safe, POST neither → 부수 효과 예외 → timeout failure window → idempotency key/If-Match/status query → retry budget.
  2. “HTTP 200이면 요청이 성공했다고 볼 수 있습니까?”
    좋은 답변 구조: transport/TLS/HTTP/domain/transaction 성공 경계 분리 → method별 200 의미 → error envelope anti-pattern → 201/202/204/409/412 대안 → request ID·transaction state·observability.
  3. “Reverse proxy가 있는 API에서 request smuggling과 timeout 중복 처리를 어떻게 막습니까?”
    좋은 답변 구조: front/back parser·connection 분리 → framing normalization/ambiguous message reject → field limit → proxy deadline와 origin commit failure window → idempotency store → bounded retry → differential tests/rollback.

10. 회상·확인 문제와 채점 기준

어제 내용 회상 3문제

  1. SYN 직후 RST, SYN 재전송 후 무응답, data ACK 뒤 RST는 각각 무엇을 뜻하는가?
  2. CLOSE_WAIT와 TIME_WAIT의 owner와 정상 의미 차이는?
  3. POST 뒤 reset을 무조건 retry하면 안 되는 이유는?

짧은 정답: ① Refused/listener·reject, timeout/drop·route·deadline, established reset/abort·idle timeout. ② CLOSE_WAIT는 local app close 대기, TIME_WAIT는 active closer의 마지막 ACK/old duplicate 안전 state다. ③ TCP ACK와 business commit 경계가 달라 결과 불명확·중복 side effect가 가능하다.

오늘 내용 확인 3문제

  1. PUT이 idempotent지만 동시 수정에서 lost update를 막지 못하는 이유와 보완책은?
  2. Content-Type, Accept, Content-Length의 owner와 역할을 각각 설명하라.
  3. Origin log는 201인데 client가 proxy 504를 받은 경우 어떤 failure window와 안전 조치가 필요한가?

짧은 정답: ① 반복 효과는 같아도 stale representation이 최신 상태를 덮을 수 있어 ETag+If-Match/412가 필요하다. ② Sender가 Content-Type으로 보낸 content를 설명하고 client가 Accept로 원하는 response를 제시하며 sender/framing layer가 Content-Length로 byte 길이를 알린다. ③ Commit 후 response가 deadline 안에 전달되지 않은 결과 불명확 구간이므로 status query/idempotency record로 판정하고 비멱등 blind retry를 막는다. 문항당 semantics 1점, owner/flow 1점, failure trade-off 1점으로 총 9점이다.
