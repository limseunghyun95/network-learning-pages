COMPUTER NETWORKING · WEEK 2 / DAY 10

Cache, TTL, negative caching

DNS를 분산 cache 시스템으로 이해하기 · 예상 학습 45분 + 실습 35분

한 줄 요약
TTL은 “이 시간이 지나면 자동 변경된다”가 아니라 resolver가 특정 positive·negative state를 재사용할 수 있는 상한이다. 긴 TTL은 latency·authority load·outage 내성을 개선하지만 변경·rollback 수렴을 늦추고, 짧은 TTL은 반대 trade-off와 cache stampede 위험을 만든다.

1. 선수 용어 사전

Cache entryQuery 결과와 key, 삽입 시각, expiry를 묶은 resolver state. Positive RRset뿐 아니라 부재와 resolution failure도 entry가 될 수 있다.
TTLTime To Live. RR을 cache해도 되는 초 단위 interval. TTL 0은 현재 transaction에서만 사용하고 cache하지 않는다는 의미다.
Age / remaining TTLCache에 들어온 뒤 지난 시간과 남은 재사용 시간. 보통 remaining = stored TTL - age이며 cache hit가 expiry를 연장하지 않는다.
Positive cacheA·AAAA·CNAME·NS처럼 존재하는 RRset을 저장한 cache.
Negative cache이름 부재(NXDOMAIN)나 type 부재(NODATA)를 저장한 state. Authoritative SOA가 negative TTL 근거를 제공한다.
Failure cacheSERVFAIL, timeout, unreachable, validation failure처럼 유용한 answer를 얻지 못한 resolution failure를 잠시 저장해 반복 폭주를 막는 cache.
Cache hit / miss유효 entry로 응답하면 hit, 없거나 만료되어 upstream resolution이 필요하면 miss다.
Request coalescing같은 key의 동시 miss를 하나의 upstream lookup으로 합치고 여러 waiter가 결과를 공유하는 기법. Singleflight라고도 부른다.
Cache stampedeHot entry가 만료되는 순간 다수 request가 동시에 upstream으로 몰리는 현상. Authority와 resolver queue를 함께 과부하시킬 수 있다.
Serve staleRefresh가 실패했을 때 이미 만료된 cache data를 제한적으로 제공해 availability를 높이는 정책. Freshness와 장애 내성의 명시적 trade-off다.

2. 왜 중요한가

DNS rollout에서 “TTL을 60초로 바꿨으니 1분 뒤 전부 새 IP”라는 말은 대개 틀리다. 이미 어제 3600초 TTL로 cache한 resolver는 그 entry의 남은 TTL을 계속 사용한다. 새 TTL은 다음 refresh로 받아들인 entry부터 적용된다.

  • TTL은 consistency window다. 정상 cache 동작에서도 여러 resolver가 old/new RRset을 동시에 제공하는 시간이 존재한다.
  • TTL은 capacity knob다. 짧게 할수록 authority QPS, network packet, recursive CPU·queue가 늘어난다.
  • Negative TTL도 배포 상태다. 실수로 NXDOMAIN을 낸 뒤 record를 생성해도 negative cache가 만료될 때까지 일부 client는 계속 부재를 본다.
  • Failure caching은 retry storm을 제어한다. 모든 authority가 실패할 때 매 client query를 그대로 재시도하면 DNS 자체가 복구 불능으로 악화될 수 있다.

3. 아키텍처 그림과 cache 상태 흐름

① Query <name,type,class>
t0 · client → recursive resolver
↓ cache lookup
② Fresh hit
now < expiry → remaining TTL을 줄여 즉시 response
또는 miss/expired ↓
③ In-flight singleflight
첫 request만 upstream · 나머지는 bounded wait queue
↓ iterative resolution / refresh
④ Authority result
Positive RRset · NXDOMAIN/NODATA+SOA · resolution failure
↓ key별 TTL·local clamp·expiry 저장
⑤ Response + cache state
fresh data, negative answer, failure response 또는 policy상 stale data
↺ expiry 후 refresh · 성공 시 replace, 실패 시 backoff
  1. Resolver는 cache key와 현재 monotonic time을 비교한다. Wall clock 보정이 생겨도 expiry가 역행하지 않도록 monotonic clock 사용이 안전하다.
  2. Fresh hit는 authority packet을 만들지 않는다. 응답 TTL은 저장 당시 값이 아니라 보통 경과 시간만큼 줄어든 값이다.
  3. Miss가 몰리면 request coalescing으로 한 upstream lookup을 공유한다. Waiter 수·deadline을 제한하지 않으면 slow authority가 resolver memory와 latency를 묶는다.
  4. Positive answer는 RRset TTL, NXDOMAIN/NODATA는 SOA 기반 negative TTL, resolution failure는 resolver policy와 RFC 9520 범위에 따라 별도 expiry를 갖는다.
  5. Refresh 실패 시 serve-stale을 지원하는 resolver는 최근 good data를 제한적으로 반환할 수 있다. 이는 구현·설정 차이가 크므로 “TTL 만료 즉시 절대 사용 불가”라고 운영 현실을 단정하지 않는다.

4. CS 수준 내부 동작

세 cache의 key와 expiry

종류Key · expiry · failure window
Positive RRset<name,type,class>. Authority TTL과 resolver max/min clamp를 적용한다. TTL 0은 현재 transaction 밖에서 cache하지 않는다.
NXDOMAIN<QNAME,QCLASS>. SOA TTL과 SOA.MINIMUM 중 작은 값이 negative TTL 근거다. 이름 부재라 여러 QTYPE에 영향을 준다.
NODATA<QNAME,QTYPE,QCLASS>. 해당 type 부재만 cache한다.
Resolution failure구현에 따라 query tuple, server IP, transport 등을 key로 삼는다. RFC 9520은 최소 1초, 최대 5분 범위와 persistent failure backoff를 요구·권고한다.
Stale retentionFresh expiry와 별도 timer다. 만료 data를 memory에 더 보존하지만 refresh 실패·정책 조건에서만 제공하며 TTL 0 data는 stale 후보가 될 수 없다.

수치로 보는 TTL trade-off

Client 10,000개가 한 이름을 30초마다 조회하면 cache가 없을 때 약 333 QPS다. 이들이 하나의 shared resolver를 쓰고 TTL 300초인 RRset을 완전히 공유한다고 단순화하면 authority refresh는 key당 약 0.0033 QPS다. 대신 cutover 후 그 resolver는 남은 TTL 동안 old answer를 줄 수 있다. 실제 QPS는 resolver 수, cache eviction, prefetch, ECS/view, type 수와 retry에 따라 증가한다.
  • 불변식: Cache hit는 authority의 현재 값을 재확인한 사건이 아니다. “지금도 원본이 같다”가 아니라 “아직 재사용 허용 시간 안”이라는 뜻이다.
  • 성공 확정: Resolver가 fresh answer를 저장하면 그 lookup은 완료되지만 application 연결은 아직 시작 전이다.
  • 비용: TTL을 300초에서 30초로 줄이면 단순 모델의 authority refresh QPS는 최대 10배가 될 수 있다. Capacity test 없이 낮추지 않는다.

5. 실무 설계 판단과 best practice

판단권장 기준과 이유
TTL 선택변경 빈도, 허용 stale window, authority capacity, outage 시 cache 보호, rollback RTO를 수치로 놓고 선택한다. 모든 record에 동일 TTL을 쓰지 않는다.
Cutover 준비기존 긴 TTL을 먼저 낮춘 뒤 최소 그 기존 TTL만큼 기다린다. 그 다음 target 변경, canary 확인, 안정화 후 TTL을 복원한다.
Negative TTL동적 service provisioning이 잦다면 실수·race의 복구 RTO를 고려해 관리한다. 너무 짧으면 typo·bot query가 authority load를 키운다.
Stampede 방지Request coalescing, prefetch, bounded jitter, queue/deadline, authority replica를 함께 쓴다. Jitter는 TTL 의미를 무제한 연장하지 않게 구현한다.
Serve stale읽기 endpoint처럼 old IP가 안전한 경우 availability를 높인다. 폐기·보안 차단 대상 IP에는 stale이 위험할 수 있어 record별 정책과 최대 stale age를 둔다.
관측Cache hit/miss, entry age, eviction, coalesced waiter, refresh latency, stale served, RCODE·failure cache hit, authority QPS를 resolver/version별로 본다.
Anti-pattern: 장애 때 전체 fleet의 DNS cache를 동시에 flush하지 않는다. Authority로 miss storm을 보내고 old/new 상태 증거도 지운다. 영향 key·resolver를 좁히고 capacity·rollback을 확인한 canary flush만 고려한다.

상황: API DNS cutover 5분 뒤에도 약 30% client가 old IP로 연결하고, 새로 만든 hostname은 일부 resolver에서 NXDOMAIN이다.

순서실행 내용
증상Resolver·region·QTYPE별 old/new 비율, NXDOMAIN 비율, 최초 query/변경 시각, old target traffic과 error를 분리한다.

가능한 가설Old long-TTL entry 잔존, TTL 하향 대기 누락, negative cache 잔존, resolver min/max clamp, serve-stale, split view, CNAME link별 다른 expiry.

하지 말아야 할 조치Old endpoint 즉시 종료, TTL을 0으로 연속 변경, 전체 cache flush, authoritative 전부 restart, query retry 무제한 확대, 현재 zone TTL만 보고 과거 entry를 무시하지 않는다.

7. 35분 two-tier cache 실습

목표: Local authority와 caching forwarder를 분리해 remaining TTL 감소와 “record를 만든 뒤에도 NXDOMAIN cache가 남는” 현상을 재현한다.

사전 조건: Docker Desktop, 터미널 3개, 이 저장소. Port 5353/5354와 documentation address만 사용하며 host DNS는 변경하지 않는다.

8. 놓치기 쉬운 함정

  • TTL은 refresh 주기가 아니다. Query가 없으면 expiry 때 자동 refresh하지 않을 수 있고 prefetch 구현은 반대로 만료 전에 refresh할 수 있다.
  • Authoritative TTL과 client 관측 TTL이 같지 않을 수 있다. Recursive·OS·browser·application cache가 각자 clamp와 cache를 둘 수 있다.
  • TTL을 낮추는 순간 기존 cache가 짧아지지 않는다. Old TTL window를 기다리는 rollout 단계가 반드시 필요하다.
  • NXDOMAIN/NODATA와 resolution failure를 같은 negative로 뭉치지 않는다. 전자는 유용한 부재 응답, 후자는 answer를 얻지 못한 실패이며 key·expiry가 다르다.
  • Serve stale은 공짜 availability가 아니다. 폐기된 endpoint·보안 차단·schema incompatibility를 되살릴 위험이 있다.
  • Cache hit ratio가 높아도 안전하지 않을 수 있다. 오래된 wrong answer를 빠르게 제공해도 hit이며, age·RCODE·endpoint SLO를 함께 봐야 한다.

9. 대기업 기술 면접 질문

  1. “DNS TTL을 1시간에서 1분으로 낮추면 어떤 일이 생깁니까?”
    좋은 답변 구조: 기존 cache 비소급 → authority QPS 수치 → recursive CPU/queue → consistency/rollback window → stampede/coalescing → resolver clamp·prefetch → 단계적 rollout.
  2. “Record를 만들었는데 일부 사용자는 계속 NXDOMAIN입니다. 진단하세요.”
    좋은 답변 구조: QNAME/QTYPE/view → authority current answer → recursive SOA/remaining negative TTL → NXDOMAIN key → resolver별 cache → safe canary flush → 최대 회복 시각.
  3. “Serve-stale 정책을 설계하세요.”
    좋은 답변 구조: availability requirement → data 안전성 분류 → refresh-first·timeout → max stale age → TTL 0 제외 → security/retired endpoint risk → metrics/alert → disable·rollback 조건.

10. 회상·확인 문제와 채점 기준

어제 내용 회상 3문제

  1. A와 AAAA가 독립 RRset이라는 사실이 장애 범위를 어떻게 나누는가?
  2. CNAME owner가 다른 일반 data와 공존하면 안 되는 이유는?
  3. NXDOMAIN과 NODATA의 cache key 차이는?

짧은 정답: ① IPv4/IPv6 응답·path를 별도 진단한다. ② Resolver가 alias target으로 일관되게 query를 재시작하기 위한 불변식이다. ③ NXDOMAIN은 name/class, NODATA는 name/type/class다. 상태와 실무 영향까지 말하면 만점.

오늘 내용 확인 3문제

  1. TTL 3600을 60으로 바꾼 직후 기존 resolver entry가 60초 안에 만료되지 않는 이유는?
  2. Positive, negative, resolution-failure cache의 expiry 근거는 어떻게 다른가?
  3. TTL을 짧게 할 때 생기는 capacity 위험과 완화책은?

짧은 정답: ① 기존 entry는 저장 당시 TTL과 age로 expiry가 정해졌고 새 TTL은 다음 refresh부터 적용된다. ② RR TTL, SOA 기반 negative TTL, resolver failure-cache policy다. ③ Miss·authority QPS·stampede가 늘며 coalescing, prefetch/jitter, queue/deadline, capacity로 완화한다. 정의 1점, 흐름 1점, trade-off 1점으로 문항당 3점.
