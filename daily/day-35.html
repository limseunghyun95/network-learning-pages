회상: source IP가 바뀌는 지점 표시

Week 5 전체를 peer address·forwarded identity·state owner로 다시 그린다 · 회상 55분 + 실습 35분

한 줄 요약
“원래 client IP”는 packet에 영원히 붙어 다니는 신분증이 아니다. NAT는 network tuple을 바꾸고, L7 proxy는 연결을 끝낸 뒤 새 연결을 만들며, forwarded header는 신뢰 가능한 ingress가 관리할 때만 identity evidence가 된다.

1. 선수 용어 사전

Source IP현재 packet의 IP header에 기록된 송신 주소다. Hop과 변환 경계를 지나며 달라질 수 있다.
Peer addressSocket이 직접 연결된 반대 endpoint의 network address다. Application이 accept() 뒤 보는 주소는 이 peer다.
Original clientRequest chain을 처음 시작한 주체다. 현재 peer와 같을 수도, 여러 proxy 앞의 다른 주소일 수도 있다.
5-tupleSource IP·source port·destination IP·destination port·protocol 조합. Connection과 NAT mapping을 구분하는 기본 열쇠다.
SNAT / DNATSource 또는 destination address/port를 바꾸는 translation이다. Reply 역변환을 위한 state가 필요하다.
TerminationProxy/LB가 client connection의 endpoint가 되는 것. Upstream에는 독립된 sequence number와 source port로 새 connection을 만든다.
PreservationL4 data path가 target까지 original source IP를 유지하는 기능이다. Target type·protocol·topology 제한을 확인해야 한다.
X-Forwarded-ForHTTP proxy chain이 client address 정보를 전달하는 header다. 누구나 임의 입력할 수 있어 trusted proxy가 sanitize·append한 구간만 믿는다.
PROXY protocolTCP 앞부분에 원 source/destination metadata를 전달하는 별도 protocol이다. 양 endpoint가 명시적으로 지원해야 한다.
Trust boundary그 밖의 입력을 검증 없이 신뢰하지 않는 경계다. Client IP header 해석 정책은 ingress trust boundary의 일부다.
Trace/request IDIP가 바뀌어도 여러 hop의 log를 같은 요청으로 결합하는 식별자다. 인증 identity 자체는 아니다.

2. 왜 중요한가

Rate limit, allowlist, 감사 log, abuse 대응을 source IP 하나에 의존하면 NAT·proxy·IPv6·shared egress 때문에 잘못된 사용자를 차단하거나 공격자가 header를 위조할 수 있다. 먼저 “누가 관찰했고 어느 경계에서 생성된 값인가”를 묻는다.

  • 보안: Public client가 보낸 X-Forwarded-For를 그대로 믿으면 IP allowlist와 audit를 우회할 수 있다.
  • 운영: 수천 client가 하나의 NAT EIP로 보이면 destination 기준 per-IP limit이 정상 traffic을 함께 차단한다.
  • 진단: Backend log의 source가 proxy라 해도 packet loss 지점은 client↔proxy 또는 proxy↔backend 중 어디든 될 수 있다.
  • 설계: Client IP preservation은 편하지만 return path·hairpin·target type·port allocation 제약과 trade-off가 있다.
  • 면접: 좋은 답변은 “XFF로 원 IP를 본다”에서 끝나지 않고 spoofing 방지, trusted hop 계산, tuple 변화와 대안을 설명한다.

  1. Client: Private source는 local socket의 진실이지만 인터넷 destination이 그대로 보는 값은 아니다.
  2. NAT: Source address와 port를 바꾸고 original/reply tuple을 mapping한다. Application payload에 원 IP를 자동 기록하지 않는다.
  3. L4 LB: Packet/flow 수준 전달이지만 client IP preservation은 제품·target type·protocol 설정에 따라 달라진다.
  4. L7 proxy: Connection A를 끝내고 B를 새로 만들어 target peer는 proxy가 된다. 원 address는 trusted header나 PROXY protocol 같은 별도 channel이 필요하다.
  5. Application: Peer address와 forwarded chain을 따로 log한다. 인증 사용자·device identity를 IP와 동일시하지 않는다.
  6. Egress: Backend가 다른 service를 호출하면 새로운 client가 되며 NAT·pool state도 새로 생긴다.
  7. 성공 확정: Reply가 모든 state owner를 역순 통과하고 client가 complete response를 읽어야 network/application 결과가 연결된다.
Week 5 복원 불변식: 각 hop마다 before/after 5-tuple, connection termination 여부, forwarded metadata의 작성자, return path, timeout·health·policy owner를 한 줄씩 기록한다. “원 IP 보존”은 packet source 보존인지 application metadata 보존인지 먼저 구분한다.

4. CS 수준 내부 동작

주소는 identity가 아니라 routing locator다

IP address는 packet을 endpoint까지 전달하기 위한 locator다. DHCP, mobile network, NAT, VPN, dual-stack 전환으로 바뀌고 여러 사용자가 공유한다. Authentication에는 TLS certificate, token, workload identity를 쓰고 IP는 risk signal·routing policy로 제한적으로 사용한다.

NAT state와 port multiplexing

여러 private flow가 하나의 public IP를 공유하려면 NAT는 source port까지 배정한다. Mapping key와 timeout이 충돌 없이 reply를 original socket으로 돌린다. 같은 destination으로 connection이 몰리면 public IP가 남아도 port allocation이 병목일 수 있다.

Proxy chain과 right-to-left trust

X-Forwarded-For: client, proxy1, proxy2를 무조건 왼쪽부터 믿지 않는다. Public ingress가 기존 header를 remove/normalize하고 자기 관찰 값을 append해야 한다. Application은 알려진 trusted proxy 수 또는 CIDR만큼 오른쪽에서 제거한 뒤 남는 address를 사용한다. Chain 길이와 proxy topology가 어긋나면 spoofing 또는 오인식이 생긴다.

L4 preservation과 return-path 제약

Target이 original source를 직접 보면 response가 같은 LB data path로 돌아와야 connection state와 정책이 맞는다. Direct server return, asymmetric route, hairpin, target type에 따라 preservation이 제한될 수 있다. 따라서 “L4니까 항상 원 IP”는 틀린 답이다.

관찰 지점과 timestamp

Packet capture의 source, socket peer, proxy access log의 remote address, forwarded header, application user ID는 서로 다른 관찰이다. NTP/PTP clock 품질과 request ID가 없으면 같은 사건을 정렬하기 어렵다. 최소한 ingress timestamp, upstream connect/response time, backend receive time을 함께 남긴다.

이중 로깅Socket peer와 sanitized original-client 값을 별도 field로 남긴다. Raw chain은 접근 제한과 보존 기간을 둔다.

예상: API의 peer는 proxy 172.28.0.40으로 바뀐다. Lab proxy가 client connection을 끝내고 새 upstream connection을 만들기 때문이다.

2단계 · 위조 header와 trust boundary (7분)

docker compose -f labs/basic-network-observability/docker-compose.yml \

예상: 현재 lab proxy는 XFF를 sanitize하지 않아 API가 가짜 값을 그대로 echo한다. 그래서 public client가 쓴 header를 authorization에 사용하면 안 된다. 실무 ingress는 remove/append 정책과 trusted-hop 검증을 가져야 한다.

3단계 · 두 5-tuple packet 증거 (8분)

Terminal A:

docker compose -f labs/basic-network-observability/docker-compose.yml \

  'tcp port 8080 or tcp port 8000'

Terminal B:

docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client curl -fsS http://proxy:8080/api/headers

예상: client→proxy:8080과 proxy→api:8000가 서로 다른 source IP·port·sequence space를 가진다.

4단계 · Published-port 변환과 cleanup (7분)

# Host terminal: destination 18080이 proxy container 8080으로 매핑된다.
curl -sS -D - http://localhost:18080/api/headers
docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec proxy ss -tan
make down

예상: Host가 18080으로 요청해도 proxy는 8080에서 accept하고 API peer는 여전히 proxy다. Docker Desktop/Engine이 host-side NAT·forwarding을 구현하는 방식은 환경에 따라 다르므로 capture 결과로 확인한다.

자주 나는 오류: Docker가 꺼져 있으면 make doctor에서 중단한다. 18080 충돌은 docker compose ps로 확인한다. Tcpdump가 비면 capture를 먼저 시작하고 새 connection을 만든다. Cleanup은 다른 process를 종료하지 않고 make down만 사용한다.

8. 놓치기 쉬운 함정

  • Backend peer IP와 original client IP는 같은 field가 아니다.
  • XFF의 왼쪽 첫 값이 항상 진실은 아니다. Client가 미리 넣을 수 있다.
  • L4 LB가 항상 source를 보존하지 않는다. Target type·protocol·setting을 확인한다.
  • SG는 HTTP header를 평가하지 않는다. 실제 network peer 또는 SG reference를 본다.
  • NAT public IP 하나가 사용자 한 명을 뜻하지 않는다. CGNAT·enterprise egress를 고려한다.
  • Forwarded metadata가 있어도 return packet의 route state를 대신하지 않는다.
  • Proxy가 원 IP를 전달해도 인증된 identity는 아니다.
  • IPv6→IPv4 translation과 dual-stack은 address family별로 관찰이 달라진다.
  • IP log는 개인정보·보안 데이터다. 최소 수집과 접근 통제가 필요하다.

9. 대기업 기술 면접 질문

  1. “NAT, L4 LB, L7 proxy를 지날 때 backend가 보는 source IP를 설명하세요.”
    좋은 답변 구조: 초기 5-tuple → 각 변환/termination → preservation 조건 → forwarded metadata → return state → 실제 packet/log 검증.
  2. “X-Forwarded-For로 IP allowlist를 구현해도 됩니까?”
    좋은 답변 구조: threat model → public spoofing → ingress sanitize·trusted hops → peer와 header 이중 log → mTLS/token 대안 → privacy.
  3. “한 NAT EIP 뒤 고객들이 rate limit에 함께 걸립니다. 설계를 고치세요.”
    좋은 답변 구조: shared-IP evidence → authenticated tenant key → per-key/global budget → abuse fallback → distributed counter trade-off → rollout·rollback.

10. 회상·확인 문제와 채점 기준

어제 내용 회상 3문제

  1. Proxy 경유 request에 TCP connection이 최소 두 개인 이유는?
  2. Health threshold가 주는 안정성과 비용은?
  3. NAT idle timeout보다 pool max-idle이 길면 어떤 failure가 생기는가?

짧은 정답: ① Proxy가 A를 terminate하고 B를 새로 만든다. ② Transient failure 흔들림을 줄이지만 감지·복구 failure window가 늘어난다. ③ Expired mapping의 stale socket 재사용으로 RST/timeout이 난다.

오늘 내용 확인 3문제

  1. NAT와 L7 proxy의 source IP 변화가 근본적으로 다른 점은?
  2. XFF chain에서 믿을 수 있는 client address를 정하려면 무엇이 필요한가?
  3. Source IP를 사용자 identity로 쓰면 안 되는 세 가지 이유는?

짧은 정답: ① NAT는 같은 flow의 header tuple을 변환하고, L7 proxy는 connection을 종료해 새 flow를 만든다. ② Ingress sanitize 정책, trusted proxy 목록/개수, append 방향과 topology가 필요하다. ③ NAT 공유, address 변경, spoofable forwarded header이며 인증 token/certificate가 더 적합하다. 문항당 정의 1점, 내부 흐름 1점, failure·trade-off 1점으로 총 9점이다.
