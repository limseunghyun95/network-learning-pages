회상: localhost와 remote path 비교

Process에서 packet까지 Week 1 통합 복습 · 예상 학습 35분 + 실습 35분

한 줄 요약
localhost도 socket·TCP/IP kernel state와 queue를 사용하지만, 목적지가 자기 network namespace의 local address이므로 packet은 물리 network로 나가지 않는다. Remote 요청은 route·neighbor·frame·중간 hop·return path라는 추가 상태를 통과한다. “같은 URL 요청”의 실패 범위가 달라지는 이유가 여기에 있다.

1. 선수 용어 사전

localhost“현재 host 자신”을 가리키도록 관례적으로 쓰는 hostname. 이름이므로 먼저 127.0.0.1 또는 ::1 같은 주소로 해석되어야 한다.
Loopback address자기 node로 되돌아오는 특수 목적지. IPv4는 127.0.0.0/8, IPv6는 ::1/128이 대표적이며 외부 link로 전달하면 안 된다.
Loopback interfaceLinux에서 보통 lo로 보이는 가상 interface. 물리 cable이 아니라 같은 kernel network stack 안에서 local traffic을 전달하는 관측 지점이다.
Local routeDestination이 이 namespace 자신에게 속하므로 local input으로 배달하라는 route type. Linux의 local table(ID 255)은 main table보다 먼저 조회되는 기본 규칙을 가진다.
Bind addressServer socket이 어느 local address에서 연결을 받을지 정하는 값. 127.0.0.1, 특정 interface IP, wildcard 0.0.0.0은 접근 범위가 다르다.
Network namespaceInterface, route, firewall, port와 socket view를 격리한 kernel 공간. Container의 localhost는 host나 다른 container가 아니라 그 container의 namespace다.
Wildcard bind0.0.0.0처럼 해당 address family의 사용 가능한 local interface에서 받겠다는 bind. “모든 Internet에서 허용” 자체가 아니라 listener 범위이며 firewall·route는 별도다.
Failure boundary증거로 성공과 실패를 가를 수 있는 경계. 예: SYN이 server capture에 도착했다면 그 지점까지의 forward path는 성공했다.

2. 왜 중요한가

“서버 안에서 curl localhost는 되는데 외부에서는 안 됩니다”는 실무에서 매우 강한 증거다. Application process가 살아 있고 loopback listener까지는 성공했다는 뜻이지만, remote bind, container namespace, service discovery, route, firewall, LB health와 return path는 아직 검증되지 않았다.

  • Localhost 성공은 축소된 data path의 성공이다. ARP/NDP, switch, router, NAT, LB가 빠지므로 remote 성공을 대신할 수 없다.
  • Localhost 실패도 application만의 문제는 아니다. IPv4/IPv6 해석 차이, bind family, namespace, port, local firewall, accept queue가 원인일 수 있다.
  • Health check 위치가 의미를 바꾼다. Process 내부, loopback, Pod IP, Service/LB endpoint는 서로 다른 failure boundary를 검증한다.
  • 보안 경계로 착각하면 위험하다. Loopback-only admin endpoint도 SSRF나 같은 namespace의 침해 process에서는 접근될 수 있다.

번호별 상태 변화

  1. 이름: localhost 자체는 IP가 아니다. Resolver가 IPv6 ::1을 먼저 반환하는데 server가 IPv4에만 bind했다면 첫 시도는 refused가 될 수 있다.
  2. Route: Linux는 우선순위가 높은 local table에서 local destination을 찾는다. Remote destination은 보통 main table에서 connected/default route와 LPM을 거친다.
  3. Data path: Loopback도 TCP state machine과 send/receive queue를 거치지만 Ethernet frame, next-hop MAC, router TTL 감소는 없다. Remote는 각 hop의 독립 queue와 MTU·firewall·NAT 상태가 추가된다.
  4. Listener match: Destination address·port·protocol과 namespace가 listener bind 범위에 맞아야 한다. 127.0.0.1:8000 listener는 다른 host나 다른 container의 172.28.0.x:8000 요청을 받지 않는다.
  5. 성공 확정: connect() 성공은 transport 연결, write() 성공은 보통 local send buffer 수용이다. Application 처리 성공은 protocol response·commit 의미까지 확인해야 한다.

4. CS 수준 내부 동작

Week 1 상태 소유권 지도

상태소유자 · localhost와 remote의 차이
Process / fdProcess의 fd table이 socket kernel object를 참조한다. 두 path 모두 동일하며 application은 보통 packet을 직접 만들지 않는다.
TCP socketKernel이 5-tuple, state, sequence, retransmission, queue를 소유한다. Loopback도 TCP를 쓰면 handshake와 ACK 의미가 남는다.
IP routeLocalhost는 local route/local delivery, remote는 policy·LPM으로 egress와 next hop을 정한다.
Neighbor / MACLoopback에는 ARP/NDP와 Ethernet destination이 필요 없다. Remote on-link는 peer MAC, off-link는 gateway MAC을 해석한다.
Frame / switchLocalhost는 physical frame을 만들지 않는다. Remote frame은 link마다 새 source/destination MAC으로 바뀌며 IP destination은 보통 유지된다.
TTL / returnLoopback은 router hop이 없다. Remote는 forwarding hop마다 TTL/hop limit과 egress queue를 거치며 response는 별도 route lookup을 한다.

불변식과 성공 경계

  • Loopback 범위 불변식: IPv4 127/8과 IPv6 ::1 destination은 node 밖으로 전달되어서는 안 된다. Capture가 physical NIC에서 이를 본다면 잘못된 구성이나 관측 해석을 의심한다.
  • Namespace 불변식: Socket은 자신이 속한 network namespace의 address·port 공간에서만 listener와 match된다.
  • TCP ACK 경계: ACK는 peer TCP가 byte 범위를 수신했다는 transport 증거이지, peer application의 처리·DB commit 증거가 아니다.
  • Locality는 latency만의 문제가 아니다. Localhost는 failure component를 제거한다. 따라서 local과 remote latency 숫자를 직접 비교해 application 성능 결론을 내리면 queue·copy·network 비용을 섞게 된다.

5. 실무 설계 판단과 best practice

판단권장 기준과 이유
Bind 범위Local-only admin service는 loopback에 bind하되 인증도 둔다. Remote service는 필요한 interface/IP에만 bind하고 firewall·network policy를 별도 적용한다. 연결이 안 된다고 무조건 0.0.0.0으로 넓히지 않는다.
Health checkProcess liveness는 local, 실제 serving readiness는 Pod/interface IP, 사용자 경로는 Service/LB probe로 계층화한다. 하나의 localhost probe로 모두 대체하지 않는다.
Container 연결Docker Compose service끼리는 service name과 service port를 쓴다. Kubernetes의 같은 Pod container는 network namespace를 공유해 localhost가 가능하지만 Pod 밖에서는 Pod/Service 주소가 필요하다.
IPv4/IPv6localhost의 A/AAAA 순서와 bind family를 명시적으로 시험한다. IPv6 wildcard ::가 IPv4-mapped 연결까지 받는지는 OS와 bindv6only 설정에 따라 달라질 수 있어 검증 없이 단정하지 않는다.
관측ss로 bind·namespace를 확인하고 localhost는 lo, remote는 실제 egress interface에서 capture한다. 양쪽 모두 numeric 출력과 timestamp를 사용한다.
Anti-pattern: “내 컴퓨터에서 localhost로 되니 배포 환경도 정상”이라고 결론 내리지 않는다. 같은 hostname이라도 namespace, address family, bind, proxy/LB 경로가 다르므로 검증한 failure boundary를 답변에 명시한다.

7. 35분 비교 실습

목표: 같은 API를 API namespace의 localhost와 client namespace의 remote 주소로 호출하고, route·listener·packet 관측 지점이 어떻게 달라지는지 증명한다.

사전 조건: Docker Desktop, 터미널 2개, 이 저장소. 아래 명령은 저장소 root에서 실행한다.

0단계 · 먼저 예측 (3분)

  1. API container에서 127.0.0.1:8000을 호출하면 어느 interface에 packet이 보일까?
  2. Client container의 localhost:8000은 왜 API를 뜻하지 않을까?
  3. Client에서 api:8000을 호출하면 destination MAC은 API인가 gateway인가?

1단계 · 환경과 두 route 확인 (7분)

make up
docker compose -f labs/basic-network-observability/docker-compose.yml exec client getent ahosts localhost
docker compose -f labs/basic-network-observability/docker-compose.yml exec api ip route get 127.0.0.1
docker compose -f labs/basic-network-observability/docker-compose.yml exec client ip route get 172.28.0.20
docker compose -f labs/basic-network-observability/docker-compose.yml exec api ss -lntp

예상 관찰: Local route는 dev lo와 local source를, remote route는 client의 eth0 src 172.28.0.50을 선택한다. API listener의 0.0.0.0:8000은 loopback과 API interface 모두에서 IPv4 연결을 받을 수 있다.

2단계 · localhost capture (8분)

터미널 A:

docker compose -f labs/basic-network-observability/docker-compose.yml exec api tcpdump -ni lo -tttt -nn -c 12 'tcp port 8000'

터미널 B:

docker compose -f labs/basic-network-observability/docker-compose.yml exec api curl -sS -v http://127.0.0.1:8000/health

예상 관찰: lo에서 127.0.0.1 양쪽 endpoint의 SYN → SYN-ACK → ACK와 HTTP data가 보인다. ARP와 Ethernet gateway는 없다. TCP state machine을 건너뛴 것이 아니라 link 밖으로 나가지 않은 것이다.

3단계 · remote capture와 namespace 실패 (9분)

터미널 A에서 client의 eth0 capture를 시작하고 터미널 B에서 두 요청을 비교한다.

docker compose -f labs/basic-network-observability/docker-compose.yml exec client tcpdump -ni eth0 -tttt -nn -c 12 'arp or (tcp port 8000)'

docker compose -f labs/basic-network-observability/docker-compose.yml exec client curl --connect-timeout 2 http://127.0.0.1:8000/health
docker compose -f labs/basic-network-observability/docker-compose.yml exec client curl -sS -v http://api:8000/health

예상 관찰: Client localhost 요청은 client namespace 안에서 빠르게 refused되고 eth0에 나타나지 않는다. Service name 요청은 172.28.0.50 → 172.28.0.20 SYN과 response가 보인다. 두 container는 같은 /24이므로 destination 자체의 MAC을 사용하고 router gateway는 거치지 않는다.

4단계 · 실패 주입: loopback-only bind (5분)

터미널 A: client namespace에 loopback-only 임시 server를 연다.

docker compose -f labs/basic-network-observability/docker-compose.yml exec client python3 -m http.server 9000 --bind 127.0.0.1

터미널 B:

docker compose -f labs/basic-network-observability/docker-compose.yml exec client curl -I http://127.0.0.1:9000
docker compose -f labs/basic-network-observability/docker-compose.yml exec api curl --connect-timeout 2 http://172.28.0.50:9000

예상 관찰: 같은 client namespace의 loopback 요청은 성공하지만 API namespace에서 client IP로 들어오는 요청은 listener match가 없어 refused된다. 이것이 bind address가 만드는 명시적 접근 경계다.

오류 해결과 cleanup (3분)

  • IPv6 ::1이 먼저 선택되면 URL에 127.0.0.1을 명시해 address family를 분리한다.
  • Capture가 비면 namespace와 interface를 다시 확인한다. API localhost는 API의 lo, client remote 요청은 client의 eth0다.
  • 9000 port가 사용 중이면 ss -lntp로 owner를 확인하고 다른 임의 port를 고른다.
터미널 A에서 Control-C로 임시 server 종료

8. 놓치기 쉬운 함정

  • Localhost는 host 전체가 아니라 namespace 자신이다. Docker container마다 다르지만 Kubernetes의 같은 Pod container들은 일반적으로 network namespace를 공유한다.
  • 0.0.0.0은 목적지 주소가 아니다. Server bind의 wildcard 표현이며 client가 접속할 실제 address로 사용하지 않는다.
  • Loopback이라고 zero-copy를 보장하지 않는다. Kernel path, socket buffer, protocol 처리 비용은 남고 OS 구현에 따라 최적화가 다르다.
  • Localhost latency로 production network SLO를 추정하지 않는다. DNS, queue, MTU, NAT/LB, congestion, cross-AZ RTT가 모두 빠져 있다.
  • Loopback-only는 완전한 보안이 아니다. SSRF가 local admin endpoint를 호출하거나 같은 namespace의 process가 접근할 수 있어 application 인증·권한이 필요하다.
  • TCP 성공과 업무 성공을 혼동하지 않는다. ACK, connect 성공, HTTP 200, DB commit은 각각 다른 owner와 확정 시점을 가진다.

9. 대기업 기술 면접 질문

  1. “Localhost 요청은 network를 타지 않는다고 말해도 됩니까?”
    좋은 답변 구조: ‘외부 link는 안 탄다’로 범위 한정 → name resolution → local route/lo → socket·TCP state·queue → 빠지는 ARP/frame/router → namespace와 OS 구현 예외.
  2. “서버 내부 localhost health check는 성공하지만 LB는 unhealthy입니다. 진단하세요.”
    좋은 답변 구조: 각 probe의 failure boundary → bind/listener → target IP·port·path → route/firewall → 양 끝 SYN/RST와 access log → 안전한 drain/rollback → localhost-only 검사의 한계.
  3. “Sidecar와 application의 통신 주소·health check를 설계하세요.”
    좋은 답변 구조: 프로세스/namespace 배치 가정 → loopback vs Pod/interface IP → IPv4/IPv6 → authentication와 SSRF → liveness/readiness/user-path 분리 → latency·failure isolation trade-off → 대안과 검증 계획.

10. 회상·확인 문제와 채점 기준

어제 내용 회상 3문제

  1. ip route show와 ip route get은 각각 어떤 질문에 답하는가?
  2. Client capture의 SYN → RST와 SYN 반복·무응답은 failure boundary가 어떻게 다른가?
  3. ss에 LISTEN이 보일 때 증명되는 것과 아직 미증명인 것은?

짧은 정답: ① route 목록과 특정 조건의 실제 kernel 결정. ② RST는 거절 응답이 왕복했지만 무응답은 forward/return drop 범위가 남는다. ③ bind/listen 준비는 증명하지만 route·firewall·accept·application 처리는 미증명. 도구의 관측 위치와 blind spot까지 말하면 만점.

오늘 내용 확인 3문제

  1. Localhost TCP 요청에서 남는 계층과 빠지는 계층을 각각 두 개 이상 말하라.
  2. Container A의 localhost로 Container B service에 접속할 수 없는 일반적 이유는?
  3. Localhost health, interface-IP health, LB health를 왜 분리해야 하는가?

짧은 정답: ① socket/TCP/IP/local queue는 남고 ARP·Ethernet link·router hop은 빠진다. ② 각 container가 다른 network namespace와 loopback/socket table을 갖기 때문이다. ③ 각각 process-local, remote bind/path, 사용자 경로라는 다른 failure boundary를 검증한다. 정의 1점, 상태 흐름 1점, 반례·trade-off 1점으로 문항당 3점.

Week 1 최종 60초 답변

“Process는 fd로 kernel socket을 참조하고 byte를 쓴다. Kernel은 transport segment, IP packet, link frame으로 캡슐화한다. Destination이 local이면 local table과 loopback으로 같은 namespace의 listener에 배달되어 ARP와 physical frame이 필요 없다. Remote면 LPM으로 route와 source·next hop을 고르고, ARP/NDP로 on-link peer 또는 gateway MAC을 알아내 frame을 보낸다. Router마다 frame은 바뀌고 TTL은 감소하며 response는 독립 return route를 탄다. 진단할 때는 ip addr/route, ss, 양 끝 tcpdump의 5-tuple·state·queue·timestamp로 성공 경계를 좁힌다.”
