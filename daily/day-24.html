HTTP/2 stream, multiplexing, flow control

한 TCP 위의 독립 stream과 공유 병목을 frame·window·queue로 추적하기 · 개념 65분 + 실습 30분

한 줄 요약
HTTP/2는 request/response마다 stream ID를 붙이고 HEADERS·DATA frame을 한 TCP connection에 섞어 보내 HTTP/1.1의 response 순서 HOL을 줄인다. 그러나 stream window·connection window·TCP sequence라는 세 공유 제약과 endpoint queue가 남으므로 “한 connection이면 무조건 빠르다”가 아니라 어느 state가 막혔는지 구분해야 한다.

1. 선수 용어 사전

Binary framingHTTP semantics를 고정된 binary frame header와 payload로 표현하는 방식. Text header line을 단순히 압축한 것이 아니라 message 경계를 frame으로 명시한다.
FrameHTTP/2의 최소 통신 단위. 모든 frame은 9-octet header를 가지며 Length, Type, Flags, 31-bit Stream Identifier와 payload로 구성된다.
Stream한 connection 안에서 특정 request/response 교환에 속하는 양방향 frame 흐름. Stream ID로 구분되며 각각 독립적인 state machine과 flow-control window가 있다.
Multiplexing여러 stream의 frame을 같은 connection byte stream에 interleave하는 것. Stream 1의 DATA 일부 뒤에 stream 3 HEADERS, stream 5 DATA를 보낼 수 있다.
HEADERS / DATAHEADERS는 method/status와 fields를 담은 field block, DATA는 HTTP content byte를 운반한다. END_STREAM flag는 해당 sender 방향의 stream 종료를 뜻한다.
HPACKHTTP/2 field compression. Static/dynamic table과 Huffman coding을 사용해 반복 fields 크기를 줄인다. Connection 전체의 compression context가 state이므로 민감 field와 memory limit을 고려한다.
Flow controlReceiver가 DATA를 얼마나 더 받을 수 있는지 window로 제한하는 hop-by-hop backpressure. TCP flow control과 별개이며 stream 단위와 connection 단위가 동시에 적용된다.
WINDOW_UPDATEReceiver가 소비한 capacity를 sender에게 다시 허용하는 frame. Stream ID 0이면 connection window, 특정 ID면 해당 stream window를 증가시킨다.
SETTINGSPeer 동작 parameter를 알리는 connection-level frame. 최대 동시 stream, 초기 stream window, 최대 frame size, field table size 등을 조정한다.
RST_STREAM / GOAWAYRST_STREAM은 개별 stream을 즉시 끝내고, GOAWAY는 connection에서 새 stream 수락을 중단하며 마지막으로 처리했을 가능성이 있는 stream ID를 전달한다.
ALPNTLS handshake에서 application protocol을 협상하는 확장. HTTPS HTTP/2는 ALPN identifier h2로 선택된다.

2. 왜 중요한가

HTTP/2는 “HTTP/1.1보다 최신”이라는 버전 암기 문제가 아니다. 동시 request를 여러 TCP connection으로 분산하던 구조를 한 connection의 여러 stream으로 바꾸면서 resource owner와 failure blast radius도 바뀐다.

  • Latency: 작은 response가 느린 큰 response의 application 순서를 추월할 수 있어 HTTP/1.1 pipelining HOL을 줄인다.
  • Capacity: Connection·TLS handshake·fd 수는 줄지만 한 connection에 더 많은 request와 memory/queue가 집중된다.
  • Backpressure: Stream 하나를 읽지 않는 consumer와 connection 전체를 늦게 읽는 consumer는 영향 범위가 다르다. Window와 application buffer를 함께 봐야 한다.
  • Failure scope: RST_STREAM은 한 요청만 끊지만 TCP reset, GOAWAY 처리 실패, HPACK connection error는 여러 in-flight stream에 영향을 준다.

  1. 협상: HTTPS client가 ALPN으로 h2를 제안·선택한 뒤 양 endpoint가 connection preface와 SETTINGS를 교환한다. 설정 적용과 ACK도 state transition이다.
  2. Stream 생성: Client가 새 request HEADERS를 보내며 홀수 stream ID 1, 3, 5를 증가시킨다. SETTINGS_MAX_CONCURRENT_STREAMS를 넘으면 새 stream을 기다려야 한다.
  3. Interleave: Server는 s1이 끝나기 전에 s3 response frame을 보내 s3를 완료할 수 있다. Response 전체 순서가 아니라 각 stream 내부 frame 순서만 지킨다.
  4. Flow control: DATA 전송 가능량은 min(stream window, connection window)에 제한된다. HEADERS 같은 control frame은 DATA flow-control 대상이 아니다.
  5. 종료: END_STREAM은 한 방향을 half-closed로 만들고 양쪽 종료 뒤 closed가 된다. Client cancel은 RST_STREAM으로 해당 stream resource를 회수한다.
  6. Drain: GOAWAY의 last-stream-id보다 큰 client stream은 server가 처리하지 않았다고 볼 수 있는 범위지만, 그 이하 stream의 business 결과는 response·idempotency state로 판정한다.
불변식: Stream ID 0은 connection control에 예약된다. 한 stream 안의 frames는 protocol state에 맞아야 하지만 서로 다른 stream의 frames는 interleave될 수 있다. 다만 모든 frame byte는 결국 하나의 TCP sequence space를 지나므로 packet loss 시 connection 전체의 application delivery가 잠시 멈출 수 있다.

4. CS 수준 내부 동작

Stream state machine과 error scope

대표 상태는 idle → open → half-closed(local/remote) → closed다. HEADERS와 END_STREAM, RST_STREAM이 전이를 만든다. 잘못된 frame이 한 stream에만 국한되면 stream error로 RST_STREAM을 보낼 수 있지만, frame size·compression state·connection flow-control 같은 공통 불변식 위반은 connection error가 되어 GOAWAY 뒤 모든 stream이 영향을 받는다.

Flow-control 산술과 BDP

DATA를 D byte 보내면 sender가 보는 stream window와 connection window가 모두 D만큼 감소한다. Receiver가 application consumption 또는 buffer 정책에 따라 WINDOW_UPDATE를 보내면 다시 증가한다. 예를 들어 RTT 50ms, path 200Mbps면 bandwidth-delay product는 약 1.25MB다. 유효 window가 64KiB 근처로 묶이면 손실이 없어도 대략 64KiB / 0.05s ≈ 1.3MB/s 수준으로 제한될 수 있다. Window를 크게 하면 throughput 여유는 늘지만 stream 수 × buffer memory와 slow consumer 위험도 커진다.

RFC 기본 초기 flow-control window는 65,535 octets다. SETTINGS_INITIAL_WINDOW_SIZE는 새·기존 stream의 초기 window에 영향을 주지만 connection window를 직접 키우지는 않는다. Connection window는 stream ID 0 WINDOW_UPDATE로 별도 증가시켜야 한다. Window 최대는 231-1이며 overflow는 protocol error다.

세 종류 HOL을 구분하라

  • HTTP/1.1 application HOL: 앞 response가 끝나야 뒤 response를 보냄. HTTP/2 multiplexing이 줄인다.
  • HTTP/2 connection-window HOL: Connection DATA window가 0이면 window update 전 모든 stream DATA가 멈춘다. Reader scheduling과 buffer 정책 문제다.
  • TCP transport HOL: 앞 sequence byte 손실 시 뒤 frame byte도 kernel이 순서대로 전달해야 한다. HTTP/2가 해결하지 못하며 다음 Day의 QUIC은 stream별 loss recovery로 이 범위를 줄인다.

7. 30분 실습: 한 connection의 stream 1·3·5 관찰

사전 조건: HTTP/2 기능이 포함된 curl과 인터넷 연결. RFC Editor만 사용한다. 실행 전 “TCP connection은 몇 개인가?”, “Stream ID는 어떤 수열인가?”, “응답 완료 순서는 요청 입력 순서와 같아야 하는가?”를 적는다.

0단계 · 기능과 ALPN 확인 (5분)

curl -V
curl --http2 -sS -o /dev/null -w 'version=%{http_version} code=%{http_code} remote=%{remote_ip}\n' https://www.rfc-editor.org/

예상: Features에 HTTP2가 있고 version=2, code=200이 보인다. 실패하면 curl build의 HTTP2 지원, proxy의 protocol downgrade, TLS trust와 DNS를 먼저 확인한다.

1단계 · 세 stream multiplexing (10분)

curl --http2 --parallel --parallel-max 3 -sS \
  -o /dev/null -o /dev/null -o /dev/null -v \
  https://www.rfc-editor.org/rfc/rfc9113.html \
  https://www.rfc-editor.org/rfc/rfc9110.html \
  https://www.rfc-editor.org/rfc/rfc7541.html 2>&1 | \
  grep -E 'ALPN|using HTTP/2|Re-using|OPENED stream|HTTP/2 200'

예상 관찰: ALPN이 h2를 선택하고 한 host connection을 reuse하면서 client stream 1·3·5를 연다. 세 response의 200 출력 순서는 scheduling과 크기에 따라 달라질 수 있다.

2단계 · Timing과 connection 재사용 (7분)

curl --http2 --parallel --parallel-max 3 -sS \
  -o /dev/null -o /dev/null -o /dev/null \
  -w 'url=%{url_effective} conn=%{num_connects} http=%{http_version} start=%{time_starttransfer} total=%{time_total}\n' \
  https://www.rfc-editor.org/rfc/rfc9113.html \
  https://www.rfc-editor.org/rfc/rfc9110.html \
  https://www.rfc-editor.org/rfc/rfc7541.html

첫 transfer의 num_connects가 새 connection을 만들고 다른 transfer는 reuse할 수 있다. 값은 proxy·DNS·curl version에 따라 달라질 수 있으므로 verbose의 connection/stream 증거와 함께 판정한다.

3단계 · 실패 주입: 짧은 deadline (5분)

curl --http2 --parallel --parallel-max 3 --max-time 0.01 -sS \
  -o /dev/null -o /dev/null -o /dev/null -v \
  https://www.rfc-editor.org/rfc/rfc9113.html \
  https://www.rfc-editor.org/rfc/rfc9110.html \
  https://www.rfc-editor.org/rfc/rfc7541.html

예상: 환경에 따라 하나 이상이 timeout/cancel된다. 이 결과는 server 처리 실패 증거가 아니다. GET은 semantics상 retry 후보지만 deadline budget 안에서 backoff해야 하며 POST라면 idempotency와 처리 범위를 확인한다.

4단계 · Cleanup과 기록 (3분)

파일을 저장하지 않았으므로 별도 cleanup은 없다. Terminal trace에 ALPN, connection 수, stream ID, 완료 순서, timeout exit code를 적고 각각 TLS·HTTP/2·application 성공 경계로 분류한다. --parallel이 없으면 curl을 갱신하거나 각 URL을 순차 실행해 HTTP/1.1과 비교한다.

8. 놓치기 쉬운 함정

  • HTTP/2는 semantics를 바꾸지 않는다. GET, POST, status, cache, idempotency 의미는 HTTP 공통이고 wire 표현만 frame/pseudo-header로 달라진다.
  • 한 stream이 느려도 항상 독립적인 것은 아니다. Connection window, TCP loss, event loop, HPACK state, server worker를 공유한다.
  • Flow control은 rate limit이 아니다. Receiver buffer 보호용 byte credit이며 request 수·business quota는 별도 제어가 필요하다.
  • SETTINGS_INITIAL_WINDOW_SIZE는 connection window 설정이 아니다. Stream window와 connection WINDOW_UPDATE를 분리한다.
  • WINDOW_UPDATE는 처리 완료 ACK가 아니다. Receiver가 buffer capacity를 돌려줬다는 transport-adjacent 신호이지 business commit 증거가 아니다.
  • TCP retransmission 하나가 여러 stream latency를 흔들 수 있다. Packet capture의 sequence gap과 모든 stream timestamp를 조인한다.
  • Proxy는 HTTP/2를 end-to-end 그대로 전달하지 않을 수 있다. Front h2를 terminate하고 backend HTTP/1.1 connection pool로 변환할 수 있다.
  • Header compression에도 한계가 필요하다. Field block size·dynamic table memory와 sensitive field indexing 정책을 둔다.
  • Priority는 보장 계약이 아니다. Peer가 hint를 무시할 수 있고 RFC/구현 세대에 따라 scheduling이 다르다.

9. 대기업 기술 면접 질문

  1. “HTTP/2가 HTTP/1.1 HOL을 해결했다고 말해도 됩니까?”
    좋은 답변 구조: HTTP/1.1 response-order HOL 정의 → stream ID와 frame interleave → stream/connection window 공유 → TCP sequence HOL 잔존 → packet loss·RTT 수치 → bounded multi-connection 또는 HTTP/3 대안.
  2. “200Mbps, RTT 50ms 환경에서 HTTP/2 window를 어떻게 잡겠습니까?”
    좋은 답변 구조: BDP 약 1.25MB 계산 → stream 크기·concurrency·consumer rate → stream/connection window 구분 → update threshold → memory budget과 slow consumer trade-off → window-zero·throughput 지표로 검증.
  3. “배포 중 GOAWAY를 받은 client의 retry 정책을 설계하세요.”
    좋은 답변 구조: last-stream-id와 처리 범위 → 새 stream은 새 connection → 이하 stream의 response/business 상태 확인 → safe/idempotent/idempotency key → retry budget·jitter → server drain·transaction reconciliation.

10. 회상·확인 문제와 채점 기준

어제 내용 회상 3문제

  1. HTTP/1.1 persistent connection 재사용 전에 response body를 끝까지 읽어야 하는 이유는?
  2. Pipelining의 response HOL과 TCP HOL은 어떻게 다른가?
  3. Idle connection에 POST를 쓴 직후 RST가 오면 왜 blind retry하면 안 되는가?

짧은 정답: ① Message 끝과 다음 시작을 확정해 clean socket만 pool에 반납하기 위해서다. ② 전자는 request 순서대로 response를 보내야 하는 application 제약, 후자는 손실된 앞 sequence byte 복구 전 뒤 byte를 전달하지 못하는 transport 제약이다. ③ Origin 도달·commit 여부가 불명확해 중복 side effect가 가능하다.

오늘 내용 확인 3문제

  1. Stream 1 DATA를 16KiB 보내면 어떤 두 HTTP/2 window가 줄어드는가?
  2. Stream window는 남았는데 connection window가 0이면 어떤 일이 생기는가?
  3. RST_STREAM과 GOAWAY의 failure scope와 retry 판단 차이는?

짧은 정답: ① Stream 1 outbound window와 connection outbound window가 모두 DATA payload만큼 감소한다. ② 모든 stream의 DATA 전송이 connection WINDOW_UPDATE까지 멈추지만 control frame은 별도 규칙으로 진행할 수 있다. ③ RST_STREAM은 개별 stream 종료, GOAWAY는 connection drain과 last-stream-id 처리 범위를 알리므로 method·처리 범위·idempotency를 함께 본다. 문항당 정의 1점, state/flow 1점, 장애·trade-off 1점으로 총 9점이다.
