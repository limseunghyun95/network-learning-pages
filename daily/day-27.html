DNS→TCP→TLS→HTTP를 하나의 timestamp로 복원 · 개념 55분 + 실습 40분

한 줄 요약
curl -v --trace-time의 event와 --write-out의 누적 milestone을 결합하면 DNS, connect, TLS, first byte를 분리할 수 있다. 인증서 오류는 “암호화가 안 됨” 하나가 아니라 trust path, 유효기간, reference identity와 SAN의 일치, SNI routing 중 어느 불변식이 깨졌는지 증거로 좁혀야 한다.

1. 선수 용어 사전

Verbose / trace-v는 connection과 protocol 대화를 사람이 읽기 좋게 보여준다. Trace는 더 자세한 송수신 기록이다. 둘 다 credential·cookie·body가 노출될 수 있어 공유 전 redaction이 필요하다.
TimestampEvent가 관측된 시각. --trace-time은 curl의 verbose/trace 각 줄 앞에 시간을 붙인다. Packet capture·server log와 clock 기준이 다를 수 있다.
Milestone시작점부터 특정 단계 완료까지의 누적 시간. time_namelookup, time_connect, time_appconnect, time_starttransfer가 예다.
Phase duration인접 milestone 차이로 근사한 구간 시간. 새 direct connection이라면 TCP≈connect−DNS, TLS≈appconnect−connect지만 proxy·Happy Eyeballs·reuse가 있으면 해석이 달라진다.
Reference identityClient가 접속하려고 의도한 service 이름. URL의 hostname이나 명시적 설정에서 온다. DNS가 돌려준 IP와 동일 개념이 아니다.
Presented identityServer certificate의 subjectAltName에 표현된 DNS-ID/IP-ID 등. Client가 reference identity와 규칙에 따라 비교한다.
Trust anchorClient trust store에서 신뢰의 시작점이 되는 CA certificate. Chain의 서명이 수학적으로 맞아도 신뢰 anchor에 닿지 않으면 검증 실패다.
SANSubject Alternative Name. 현대 TLS service identity의 typed identifier 위치다. 자유 형식 Common Name만 보고 hostname을 인증하면 안 된다.
SNI / ALPNSNI는 ClientHello에서 원하는 server name을 알려 certificate/virtual host 선택을 돕고, ALPN은 h2·http/1.1 같은 상위 protocol을 협상한다.
Exit codeProcess가 shell에 돌려주는 결과 코드. HTTP 500과 curl exit 0이 함께 가능하고, TLS verification 실패는 HTTP response 전에 non-zero가 될 수 있다.
Deadline / timeoutDeadline은 전체 작업이 끝나야 하는 절대 경계, timeout은 특정 대기 한도다. Connect timeout만 설정해도 DNS·TLS·response 전체가 보호되는 것은 아니다.
Failure window어느 성공 경계 뒤, 어느 성공 경계 전에 실패했는지 나타내는 구간. 예: TCP 성공 뒤 certificate verify 전 실패.

2. 왜 중요한가

“curl이 느리다”와 “SSL error다”는 증상이지 원인이 아니다. 대규모 서비스에서는 같은 URL도 resolver cache, IPv4/IPv6 race, proxy, connection reuse, edge certificate rollout, client trust store 때문에 서로 다른 path를 지난다.

  • 장애 범위: DNS가 0.8초인지, TCP가 timeout인지, TLS verification이 실패했는지, server TTFB가 늦는지에 따라 owner와 안전한 조치가 완전히 다르다.
  • 보안: -k/--insecure로 성공했다고 원인이 해결된 것이 아니다. 그 실험은 “verification 계층이 blocker”라는 증거일 뿐 production 해법이 아니다.
  • 면접: 좋은 답변은 도구 이름보다 timeline, 상태 owner, 불변식, 반증 가능한 가설, rollback을 연결한다.
  • 실무: Retry 전에 request가 server/application에 도달했는지 모르면 중복 write를 만들 수 있다. Failure window를 알아야 idempotency 전략을 고른다.

  1. Control path: URL, proxy environment, DNS answer, route, SNI, trust store, ALPN이 실제 data path와 parser를 선택한다. Command에 기록하지 않으면 재현성이 사라진다.
  2. TCP 경계: Connect 완료는 peer process나 TLS identity를 보장하지 않는다. SYN-ACK을 보낸 지점이 LB일 수도 있다.
  3. TLS 경계: Client는 certificate path와 time policy를 검증하고 reference identity가 SAN의 typed identity와 일치하는지 확인한다. SNI로 certificate를 골랐다는 것과 hostname 검증 통과는 별도다.
  4. Failure window: Verification 실패라면 TCP는 성공했지만 authenticated channel은 만들어지지 않았고 정상 client는 HTTP request를 보내지 않는다. 따라서 application log 부재가 자연스럽다.
  5. HTTP 경계: First byte까지의 시간에는 proxy/LB queue, upstream pool 대기, application CPU/DB가 섞인다. Curl 하나만으로 server 내부 시간을 단정하지 않는다.
  6. 완료 경계: Body 수신과 curl exit 0도 business transaction의 durable commit을 직접 증명하지 않는다. Request ID와 application/database evidence가 필요하다.
핵심 불변식: Authenticated TLS channel이 성립하려면 유효한 chain이 local trust anchor에 닿고, certificate validity/policy가 맞으며, reference identity가 presented SAN identity와 일치하고, handshake transcript 검증이 끝나야 한다. 하나라도 실패하면 HTTP로 넘어가지 않는다.

각 값은 curl 시작부터 누적된 application-level 관측이다. Packet timestamp와 직접 같지 않다. Curl log, packet capture, edge access log, application trace를 request ID·5-tuple·timestamp tolerance로 join해야 queue 위치를 더 정확히 찾을 수 있다.

Certificate verification은 세 축이다

  • Path: Leaf→intermediate→trust anchor의 signature와 constraints가 유효한가. 자체서명 leaf를 기본 trust store가 모르면 unknown CA다.
  • Time/policy: Client clock이 validity interval 안이고 key usage·algorithm 정책을 만족하는가. Clock drift는 certificate 교체만으로 고쳐지지 않는다.
  • Identity: URL에서 얻은 reference DNS name/IP가 SAN의 같은 typed identifier와 일치하는가. DNS name용 certificate를 IP URL에 쓴다고 자동 일치하지 않는다.

SNI, DNS, Host는 같은 이름처럼 보여도 owner가 다르다

--resolve는 curl 내부의 hostname→IP 선택을 고정하지만 URL hostname은 유지한다. 그래서 SNI, TLS reference identity, HTTP Host/:authority는 wrong.example로 두고 packet destination만 127.0.0.1로 만들 수 있다. 반대로 IP URL은 reference identity도 IP가 되어 DNS SAN certificate와 mismatch가 난다.

Timeout과 retry의 상태기계

DNS/connect/TLS/request의 남은 budget을 하나의 end-to-end deadline 아래 둔다. Certificate mismatch처럼 deterministic한 policy failure는 같은 endpoint에 즉시 retry해도 고쳐지지 않는다. Timeout 뒤에는 server가 request를 받았을 가능성을 failure window로 판단하고, write라면 idempotency key와 status lookup 없이 맹목 재시도하지 않는다.

7. 40분 실습: public timing + local certificate failure

사전 조건: macOS/Linux shell, curl, openssl, loopback port 18443. Corporate proxy를 피하려고 local 명령에 --noproxy '*'를 사용한다. 실행 전 각 단계의 exit code와 HTTP request 도달 여부를 예측한다.

0단계 · 도구와 public baseline (7분)

curl -V
curl -v --trace-time --max-time 10 -o /dev/null \
  -w 'ip=%{remote_ip} code=%{http_code} http=%{http_version}\ndns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} pre=%{time_pretransfer} first=%{time_starttransfer} total=%{time_total}\n' \
  https://www.rfc-editor.org/

예상: DNS address, TCP 연결, TLS backend/verification, ALPN과 HTTP response가 시간순으로 보인다. Milestone은 누적값이다. Trace에 cookie/token이 있으면 저장·공유하지 않는다.

1단계 · 격리된 자체서명 server 준비 (8분)

LAB_DIR=$(mktemp -d /tmp/network-day27.XXXXXX)
openssl req -x509 -newkey rsa:2048 -nodes -days 1 \
  -keyout "$LAB_DIR/key.pem" -out "$LAB_DIR/cert.pem" \
  -subj '/CN=wrong.example' \
  -addext 'subjectAltName=DNS:wrong.example'

openssl s_server -quiet -accept 18443 \
  -cert "$LAB_DIR/cert.pem" -key "$LAB_DIR/key.pem" -www \
  >"$LAB_DIR/server.log" 2>&1 &
LAB_PID=$!
sleep 1

Private key는 임시 directory 밖으로 복사하지 않는다. -addext 미지원이면 local OpenSSL/LibreSSL help를 확인하고 SAN config 방식으로 대체한다.

2단계 · 실패 주입 A: unknown CA (7분)

curl -v --trace-time --noproxy '*' --max-time 5 \
  https://wrong.example:18443/ \
  --resolve wrong.example:18443:127.0.0.1
printf 'exit=%s\n' "$?"

예상: TCP와 TLS bytes 교환은 시작되지만 local trust store가 self-signed leaf를 trust anchor로 받아들이지 않아 non-zero로 끝난다. 정상 curl은 HTTP request를 보내지 않는다.

3단계 · 실패 주입 B: trust 성공, identity 실패 (8분)

curl -v --trace-time --noproxy '*' --max-time 5 \
  --cacert "$LAB_DIR/cert.pem" \
  https://127.0.0.1:18443/
printf 'exit=%s\n' "$?"

예상: 이제 signing certificate는 명시적으로 trust했지만 reference identity는 IP 127.0.0.1이고 certificate SAN은 DNS wrong.example라 hostname/IP mismatch가 난다. Path trust와 service identity가 별도임을 증명한다.

4단계 · 두 불변식을 만족시켜 성공 (6분)

curl -v --trace-time --noproxy '*' --max-time 5 \
  --cacert "$LAB_DIR/cert.pem" \
  --resolve wrong.example:18443:127.0.0.1 \
  https://wrong.example:18443/ -o /dev/null \
  -w 'code=%{http_code} connect=%{time_connect} tls=%{time_appconnect} total=%{time_total}\n'

예상: Local trust와 SAN identity가 모두 맞아 TLS가 끝나고 HTTP 200이 온다. --resolve는 destination IP만 고정하면서 URL hostname/SNI/reference identity를 유지한다.

5단계 · cleanup과 사후 확인 (4분)

kill "$LAB_PID"
wait "$LAB_PID" 2>/dev/null || true
rm -f "$LAB_DIR/key.pem" "$LAB_DIR/cert.pem" "$LAB_DIR/server.log"
rmdir "$LAB_DIR"

자주 나는 오류: 18443 사용 중이면 다른 high port로 command 전체를 바꾼다. Proxy error면 --noproxy '*'가 적용됐는지 본다. Connection refused면 server process/log부터 확인한다. Exit 60의 문구는 TLS backend마다 다를 수 있어 exact string보다 trust/identity failure phase를 기록한다.

8. 놓치기 쉬운 함정

  • --trace-time만으로 packet timestamp가 되지 않는다. Curl process가 본 event 시각이며 kernel queue와 server 내부 queue는 별도다.
  • Milestone은 구간 시간이 아니라 누적 시간이다. 차를 계산하되 reuse·proxy·redirect·Happy Eyeballs 전제를 함께 적는다.
  • HTTP status와 curl exit code는 다른 축이다. HTTP 500도 정상 transport라 exit 0일 수 있고 TLS failure는 status 자체가 없다.
  • CN만 맞는 certificate를 현대 hostname 검증의 정답으로 보지 않는다. Typed SAN identity를 확인한다.
  • --resolve는 /etc/hosts 영구 변경이 아니다. 해당 curl process의 address 선택만 바꾸며 URL hostname 의미는 유지한다.
  • SNI가 맞아도 SAN mismatch일 수 있다. Server certificate 선택과 client identity 검증은 다른 state transition이다.
  • -k 성공은 안전한 성공이 아니다. On-path attacker도 통과시키므로 production health check에 넣지 않는다.
  • Verbose log에는 secret이 섞일 수 있다. Authorization, Cookie, query, response body와 internal hostname을 redaction한다.
  • Client clock을 빼먹지 않는다. Not-yet-valid/expired가 server rollout이 아니라 clock drift일 수 있다.

9. 대기업 기술 면접 질문

  1. “HTTPS 요청이 2초 걸립니다. curl 하나로 어디까지 분해하고 무엇은 단정하지 않겠습니까?”
    좋은 답변 구조: version/proxy/reuse 전제 → 누적 DNS/connect/appconnect/pretransfer/starttransfer/total → 차이 계산 → verbose event와 remote IP/ALPN → server 내부 queue는 trace/request ID로 보완 → 반복 표본/p99.
  2. “-k에서는 성공하고 정상 curl은 hostname mismatch입니다. 원인과 복구는?”
    좋은 답변 구조: encryption과 authentication 분리 → URL reference identity·SNI·served SAN/fingerprint 증거 → default cert/SNI route/잘못된 endpoint 가설 → 올바른 cert/route canary → 검증 우회 금지 → edge 전체 fresh handshake 확인.
  3. “Certificate rotation을 다중 region에서 무중단으로 운영하고 실패를 진단하세요.”
    좋은 답변 구조: termination/key owner → issuance와 old/new overlap → chain/SAN/notAfter/fingerprint external probe → region canary → connection reuse/drain → rollback artifact → client trust/clock/engine 차이와 success SLO.

10. 회상·확인 문제와 채점 기준

어제 내용 회상 3문제

  1. QUIC에서 lost packet과 lost stream data를 왜 같은 식별자로 재전송하지 않는가?
  2. 한 stream의 loss가 다른 stream delivery를 막지 않아도 함께 느려질 수 있는 공유 상태는?
  3. Alt-Svc 광고와 실제 HTTP/3 협상 성공은 왜 다른 증거인가?

짧은 정답: ① Packet number는 ACK/loss timeline이고 stream offset은 application byte 위치라 lost 정보가 새 PN에 재구성된다. ② Congestion window, connection flow-control, CPU/NIC queue, QPACK dependency다. ③ 광고는 시도 가능한 alternative control data일 뿐 client capability·UDP path·handshake·negotiated version을 보장하지 않는다.

오늘 내용 확인 3문제

  1. time_appconnect − time_connect를 TLS 시간으로 부를 때 명시할 전제 세 가지는?
  2. 자체서명 certificate를 --cacert로 trust한 뒤에도 IP URL에서 실패하는 이유는?
  3. Certificate 오류 incident에서 application log가 없을 때 어떤 failure window를 먼저 검증할 것인가?
