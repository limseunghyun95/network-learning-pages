COMPUTER NETWORKING · WEEK 3 / DAY 15

3-way handshake, sequence, ACK

세 packet을 두 kernel의 state machine으로 읽기 · 예상 학습 50분 + 실습 35분

한 줄 요약
TCP 3-way handshake는 “연결 요청·수락·확인”이라는 인사말이 아니라, 양쪽 kernel이 서로의 Initial Sequence Number(ISN), 왕복 도달 가능성, TCP option, 5-tuple state를 맞춰 byte stream을 시작하는 분산 상태 전이다. SYN과 FIN은 data가 없어도 sequence space 1칸을 소비하며, ACK number는 “마지막으로 받은 번호”가 아니라 다음에 기대하는 sequence number다.

1. 선수 용어 사전

TCPTransmission Control Protocol. Application에 신뢰성 있는 양방향 ordered byte stream을 제공하는 transport protocol이다. Message 경계를 보존하지 않고 byte 순서와 재전송 상태를 kernel이 관리한다.
SegmentTCP header와 선택적 data로 이루어진 transport 단위. IP packet 안에 실리며 sequence·ACK·flag·window·option을 담는다.
SYN / ACK / RSTSYN은 sequence number 동기화, ACK flag는 acknowledgment field가 유효함, RST는 해당 connection state를 reset함을 뜻하는 TCP control bit다.
Sequence number이 segment의 첫 data byte가 byte stream에서 차지하는 32-bit 번호. SYN이 있으면 field는 ISN이고 첫 data byte는 ISN+1부터 시작한다.
ISNInitial Sequence Number. Connection 방향별 sequence space의 시작점이다. 예측하기 어려운 선택은 오래된 segment 혼동과 blind injection 위험을 줄인다.
Cumulative ACKACK=N은 N-1까지의 연속 byte를 받았고 N을 다음으로 기대한다는 뜻이다. 뒤쪽 segment가 먼저 와도 중간 gap이 남으면 cumulative ACK는 전진하지 않는다.
5-tupleProtocol, source IP·port, destination IP·port 조합. Kernel, NAT, stateful firewall, L4 LB가 flow state를 구분할 때 핵심 식별자로 쓴다.
TCBTransmission Control Block. Sequence, window, timer, retransmission, state 등 한 TCP connection의 kernel 상태를 가리키는 논리적 개념이다. 실제 자료구조는 OS마다 다르다.
SYN backlog / accept queue일반적인 Linux 설명에서 SYN backlog는 아직 handshake가 끝나지 않은 요청, accept queue는 handshake가 끝났지만 application이 아직 accept()하지 않은 connection을 보관한다. 정확한 구조·한도·overflow 동작은 OS/버전에 따라 다르다.
RTT / RTORTT는 packet과 응답의 왕복 관측 시간, RTO는 ACK가 오지 않을 때 retransmission을 시작하는 timer다. Handshake도 loss 시 SYN·SYN-ACK를 재전송한다.

2. 왜 중요한가

“TCP 연결이 됐다”는 말은 failure boundary를 좁히지만 application 성공을 뜻하지 않는다. Client의 connect()가 성공했어도 server process는 아직 accept()하지 않았을 수 있고, TLS certificate·HTTP routing·DB commit은 전혀 시작되지 않았을 수 있다.

  • Refused와 timeout은 packet 증거가 다르다. SYN 뒤 RST가 왕복하면 목적지 kernel 또는 middlebox가 명시적으로 거절한 것이고, SYN 반복·무응답이면 forward/return path와 listener 상태를 더 분리해야 한다.
  • Handshake latency는 최소 한 RTT를 포함한다. 새 connection을 매 요청마다 만들면 DNS·TCP·TLS 비용이 tail latency와 CPU에 누적된다.
  • Queue가 사용자 증상을 바꾼다. Application thread가 멈춰도 kernel이 handshake를 끝내 accept queue에 넣을 수 있어 connect는 성공하지만 HTTP는 timeout일 수 있다.
  • 중간 장비도 state를 만든다. NAT·conntrack·LB는 SYN에서 mapping/backend를 선택하고 양방향 packet이 같은 flow state를 통과해야 한다.

4. CS 수준 내부 동작

왜 두 번이 아니라 세 번인가

양쪽은 서로 다른 sequence space를 가진다. 첫 SYN으로 client→server 방향 ISN을 전달하고, SYN-ACK로 그 수신을 확인하면서 server→client 방향 ISN을 전달한다. 마지막 ACK가 server ISN 수신을 확인한다. Server가 final ACK를 받기 전에는 client가 SYN-ACK를 실제로 받았는지 확정할 수 없으므로 half-open state가 남는다.

Sequence space 불변식

항목정확한 의미
32-bit moduloSequence number는 2³² 뒤 wrap한다. 단순 정수 대소 비교가 아니라 현재 window 안의 modulo arithmetic으로 앞뒤를 판단한다.
SYN / FIN각각 sequence space 1을 소비한다. 그래서 data가 0 byte인 SYN도 ACK는 ISN+1이다.
Pure ACKPayload·SYN·FIN이 없는 ACK는 sequence space를 소비하지 않는다. 같은 seq로 여러 ACK를 보낼 수 있다.
Cumulative ACKACK=N은 N 이전까지 gap 없이 받았다는 transport 상태다. Application이 read()했는지, transaction을 commit했는지는 포함하지 않는다.
Relative displaytcpdump·Wireshark는 가독성을 위해 첫 sequence를 0으로 정규화할 수 있다. tcpdump -S는 absolute number를 보여준다.

Option 협상과 queue

  • MSS: 각 endpoint가 상대에게 자신이 받을 TCP payload의 최대 크기를 알린다. 방향별 값이며 path MTU 전체를 보장하지 않는다.
  • Window Scale: 16-bit window field를 더 큰 receive window로 확장하는 배율을 SYN에서 협상한다. 연결 중간에 새로 켤 수 없다.
  • SACK Permitted: 선택적 ACK 사용 가능 여부를 SYN에 알린다. 실제 SACK block은 loss가 생긴 뒤 ACK option에 실린다.
  • Timestamp: RTT 측정과 PAWS 등에 쓰이는 option이다. 지원·정책은 stack마다 다르며 packet에서 실제 협상을 확인한다.
  • SYN cookie: SYN flood나 backlog 압력에서 server가 일부 state를 ISN에 encode해 final ACK 때 복원하는 방어다. 항상 켜지는 정상 경로로 가정하거나 backlog 문제의 근본 해결책으로만 보지 않는다.
Control path와 data path: SYN은 route·NAT/LB·firewall·server listener state를 만들고 option을 협상하는 control 성격이 강하지만 같은 packet data path를 통과한다. Handshake 완료 후 application byte도 동일 5-tuple로 흐른다. LB가 SYN과 이후 packet을 다른 backend로 보내면 backend들이 connection state를 공유하지 않는 한 reset/timeout이 생길 수 있다.

5. 실무 설계 판단과 best practice

판단권장 기준과 이유
Timeout 분리connect timeout을 DNS·TLS·request/read timeout과 분리한다. 하나의 큰 timeout은 어느 state에서 시간을 썼는지 숨기고 queue 점유를 늘린다.
Connection reuse요청마다 handshake하지 말고 bounded pool·keep-alive를 사용한다. 단, max-age·idle timeout·endpoint drain을 두어 오래된 DNS/LB destination과 불량 socket을 영구 재사용하지 않는다.
Backlog tuning먼저 SYN rate, SYN-RECV, accept queue, listen overflow/drop, accept latency, CPU를 함께 본다. 숫자만 크게 늘리면 memory·tail latency를 키우고 느린 consumer를 감춘다.
LB/NAT5-tuple, idle timeout, backend selection, source-IP 보존 여부를 문서화한다. Handshake와 data packet이 같은 stateful path를 지나도록 symmetry를 검증한다.
RetryConnect 실패 retry는 전체 deadline·retry budget 안에서 exponential backoff+jitter로 제한한다. 장애 중 즉시 다중 retry는 SYN storm과 ephemeral port·conntrack 압력을 만든다.
관측Client와 server 양쪽의 timestamp, 5-tuple, flags, seq/ack, retransmission, socket state, queue, listener counter를 같은 timeline으로 맞춘다.
보안Ingress source validation, SYN flood protection, rate limit, capacity 격리를 계층화한다. ISN이나 TCP connection 자체는 peer identity·암호화·authorization을 제공하지 않으므로 TLS와 application 인증이 필요하다.
Anti-pattern: ESTABLISHED socket 수만 보고 service 정상이라 결론 내리거나, SYN backlog와 accept queue를 같은 숫자로 뭉개거나, connect timeout을 늘려 overload를 해결하려 하지 않는다.

8. 놓치기 쉬운 함정

  • ACK를 application 확인으로 번역하지 않는다. Peer TCP receive state의 확인이며 process read·처리·commit은 별도다.
  • SYN의 payload length 0만 보고 sequence를 소비하지 않는다고 생각하지 않는다. SYN과 FIN은 각각 한 칸을 쓴다.
  • tcpdump의 0,1을 실제 ISN으로 오해하지 않는다. Relative sequence display인지 -S absolute인지 표시한다.
  • LISTEN socket 하나와 established child socket을 같은 객체로 보지 않는다. 한 listener가 여러 remote 4-tuple의 child state를 만든다.
  • SYN backlog와 accept queue overflow를 같은 원인으로 단정하지 않는다. Kernel/버전별 counter와 application accept latency를 함께 본다.
  • Handshake 성공으로 MTU path를 전부 검증했다고 보지 않는다. 작은 SYN은 통과하지만 큰 TLS/application segment는 PMTU black hole에서 멈출 수 있다.
  • NAT 뒤 client의 source port를 server capture와 그대로 비교하지 않는다. 양쪽 capture의 translated tuple과 conntrack mapping을 연결한다.
  • 항상 정확히 세 packet만 존재한다고 단정하지 않는다. Loss retransmission, simultaneous open, TCP Fast Open, middlebox proxy 때문에 capture 형태가 달라질 수 있다.

9. 대기업 기술 면접 질문

  1. “3-way handshake가 왜 필요한지 sequence number로 설명하세요.”
    좋은 답변 구조: 양방향 byte stream 요구 → 두 독립 ISN → x/y 수치 packet 3개 → SYN의 +1 → final ACK가 증명하는 것 → half-open과 loss → simultaneous open/TFO 예외.
  2. “Connect는 성공하지만 API가 timeout입니다. 어디까지 성공한 겁니까?”
    좋은 답변 구조: DNS/address 가정 → route/NAT/LB → SYN/SYN-ACK/ACK와 client ESTABLISHED → server accept queue 가능성 → accept/read/TLS/HTTP/DB 미확정 → pcap·ss·queue·log 증거 → safe drain/rollback.
  3. “초당 5만 새 연결에서 SYN-RECV와 p99가 증가합니다. 설계와 대응은?”
    좋은 답변 구조: new connection rate·RTT·backlog·memory 수치 가정 → SYN/accept queue 구분 → CPU/softirq/LB/conntrack → reuse·pool·keep-alive → SYN cookie/rate limit trade-off → retry budget → SLO와 부하 테스트.

짧은 정답: ① seq=901, ack=5001. ② Client byte stream의 2400까지 gap 없이 server TCP가 받았음을 확정하지만 application read·처리·commit은 미확정이다. ③ 전자는 대체로 SYN-RECEIVED half-open, 후자는 handshake가 끝난 ESTABLISHED지만 아직 application이 accept하지 않은 state다. 문항당 숫자/정의 1점, owner/state transition 1점, 장애·예외 1점으로 총 9점이다.
