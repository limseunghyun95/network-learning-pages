PROXY · LB · NAT · CLOUD NETWORK · WEEK 5 / DAY 29

forward/reverse proxy와 connection termination

한 요청이 여러 socket·queue·trust 경계로 갈라지는 과정 · 개념 65분 + 실습 35분

한 줄 요약
Forward proxy는 client가 선택해 외부로 나가는 요청을 대신하고, reverse proxy는 client에게 origin처럼 보이며 내부 backend를 대신한다. 둘 다 message를 이해하면 client↔proxy와 proxy↔origin은 서로 다른 connection이므로 5-tuple, TLS key, protocol version, pool, queue, timeout, retry와 성공 시점을 따로 추적해야 한다.

1. 선수 용어 사전

IntermediaryUser agent와 origin 사이에서 request/response를 전달·변환하는 중간 구성요소. Proxy, gateway(reverse proxy), tunnel이 대표 형태다.
Forward proxyClient 설정이 선택하는 대리자. Egress policy, filtering, cache, audit를 위해 client 대신 여러 origin에 연결한다.
Reverse proxy / gatewayClient 쪽에서는 origin처럼 응답하고 내부에서는 backend를 선택해 요청을 전달하는 대리자. TLS termination, routing, load balancing, WAF에 쓰인다.
Tunnel / CONNECT두 connection 사이 byte를 blind relay하는 방식. HTTP CONNECT 성공은 tunnel 준비를 뜻하며 그 안의 origin TLS handshake 성공을 뜻하지 않는다.
Downstream / upstreamProxy 기준 client 쪽 connection을 downstream, origin/backend 쪽을 upstream이라 부른다. Request 방향은 origin 쪽으로 진행한다.
TerminationTCP/QUIC/TLS/HTTP connection state를 끝내고 그 protocol의 endpoint가 되는 것. TLS termination은 plaintext와 private-key 경계도 만든다.
Connection poolProxy가 backend connection을 생성·재사용하는 저장소. Client connection과 1:1이 아니며 max size, idle timeout, wait queue가 필요하다.
Hop-by-hop field현재 두 peer의 connection에만 의미가 있는 HTTP field. Intermediary는 Connection이 지목한 field와 알려진 connection-specific field를 다음 hop으로 그대로 넘기지 않는다.
Forwarded / X-Forwarded-*Proxy 앞의 source, host, scheme 정보를 전달하는 metadata. Client도 위조할 수 있으므로 신뢰 proxy가 경계에서 제거·재작성한 값만 정책에 사용한다.
ViaHTTP message를 전달한 intermediary와 받은 protocol version을 기록해 loop 방지와 capability 진단에 쓰는 field.
BackpressureDownstream 유입이 upstream 처리량을 넘을 때 queue/stream/connection limit, pause, rejection으로 부하를 상류에 전달하는 제어.
Failure window어느 hop의 어느 성공 뒤에 실패했는지 나타내는 범위. Downstream HTTP 502는 front connection 성공과 upstream 실패가 동시에 가능함을 뜻한다.

2. 왜 중요한가

Proxy가 들어오면 “한 요청, 한 connection”이라는 직관이 깨진다. Client가 keep-alive로 proxy에 붙어 있어도 proxy는 다른 backend connection을 고르거나 새로 만들 수 있고, front는 HTTP/2인데 upstream은 HTTP/1.1일 수 있다.

  • 성능: Client RTT보다 pool wait·backend connect·TLS handshake·queue가 p99를 지배할 수 있다.
  • 정확성: Proxy retry가 application retry와 겹치면 한 request가 backend에 여러 번 도달한다.
  • 보안: Client-supplied X-Forwarded-For를 신뢰하면 IP allowlist·audit·rate limit을 우회할 수 있다.
  • 장애: Proxy 502/504는 application bug 하나가 아니라 DNS, route, pool, connect, TLS, timeout, protocol parse failure의 합성 결과다.
  • 면접: 좋은 답변은 proxy 종류보다 connection graph, owner, 성공 경계, retry/timeout budget과 source identity를 설명한다.

  1. 선택: Forward proxy는 client/organization이 선택하고, reverse proxy는 service operator가 DNS/VIP로 배치한다. Transparent interception은 client가 선택한 HTTP proxy와 다르다.
  2. Forward HTTP: Plain HTTP proxy는 absolute URI를 읽어 origin에 새 connection을 만든다. Proxy authentication과 egress policy가 이 hop에 적용된다.
  3. CONNECT tunnel: Forward proxy가 target까지 TCP 연결 후 200을 주면 byte tunnel이 열린다. Origin TLS는 그 안에서 client와 reverse proxy 사이에 별도로 수행된다. TLS inspection proxy라면 tunnel이 아니라 새 TLS endpoint가 되어 trust 경계가 달라진다.
  4. Reverse L7: Reverse proxy는 client request를 parse하고 route/header/policy를 바꿀 수 있다. Downstream HTTP/2 stream을 upstream HTTP/1.1 request로 변환할 수도 있다.
  5. Pool: Upstream connection은 여러 client request가 시간상 공유하거나 한 client의 병렬 request가 여러 connection으로 갈 수 있다. Pool wait와 connect time을 분리 측정한다.
  6. 응답: Upstream connect/refused/TLS/timeout을 reverse proxy가 502 또는 504로 변환할 수 있다. Client가 본 status는 error origin의 위치를 직접 증명하지 않는다.
핵심 불변식: Message-aware intermediary를 지날 때마다 incoming connection과 outgoing connection은 별도 state다. 한 hop의 TLS/ACK/keep-alive 성공을 다음 hop 성공으로 전이시키지 말고, request identity와 deadline만 명시적으로 전달한다.

Hop-by-hop field와 protocol translation

Connection이 지목한 field와 Keep-Alive, Proxy-Connection, Transfer-Encoding 같은 connection-specific metadata를 그대로 다음 hop에 넘기면 framing confusion과 request smuggling 위험이 생긴다. Intermediary는 incoming message를 자신의 parser로 완결성 있게 읽고 hop field를 제거한 뒤 outgoing protocol에 맞게 새 message를 만든다.

HTTP version도 hop마다 다를 수 있다. Client↔proxy가 H2이고 proxy↔origin이 H1이면 H2 stream reset을 upstream TCP close로 mapping하거나 response framing을 재구성해야 한다. 이 변환 과정이 failure scope와 retry 가능성을 바꾼다.

Source identity는 packet과 header에서 다르게 보인다

  • Socket peer: Origin이 보는 source IP는 보통 reverse proxy의 upstream IP다. 이것은 kernel이 확인한 직전 peer다.
  • Forwarded metadata: 원 client IP/scheme/host는 HTTP field로 전달할 수 있지만 cryptographic fact가 아니다.
  • Trust algorithm: Public client가 보낸 기존 X-Forwarded-*를 경계 proxy에서 제거하고, 직접 관측한 peer 값을 새로 기록한다. App은 allowlist된 proxy hop 수/주소만 신뢰한다.
  • Privacy: Forwarded chain은 내부 topology와 개인 IP를 노출할 수 있어 최소 정보·보존 기간·redaction을 설계한다.

Pool, queue, deadline의 수학

Pool 크기가 C, 평균 upstream service time이 W초면 안정적인 처리율 상한은 대략 C/W request/s이고, 도착률이 이를 지속 초과하면 queue가 자란다. Little's Law L=λW로 queue 대기와 동시 request를 연결한다. 무제한 pool은 backend/NAT ephemeral port를 고갈시키고 무제한 queue는 timeout 직전의 쓸모없는 작업을 쌓는다.

Caller deadline에서 DNS/front/pool/connect/TLS/upstream response/response write budget을 차감한다. Proxy가 caller보다 긴 timeout으로 backend 작업을 계속하면 client는 이미 retry해 duplicate load가 된다.

Retry의 모호한 성공 창

Upstream connect 전에 실패하면 request가 app에 도달하지 않았을 가능성이 높지만, body 전송 후 response 전에 timeout이면 app commit 여부가 모호하다. Proxy가 POST를 자동 retry하려면 method 이름만 보지 말고 replayability, body buffering, idempotency key, backend transaction status를 확인해야 한다.

7. 35분 실습: 두 TCP connection과 502 failure window 관찰

사전 조건: Docker Desktop/Engine과 Compose, 저장소 root. Lab은 client→proxy:8080→api:8000 reverse proxy path를 사용한다. 실행 전 direct와 proxy 경유 시 API가 보게 될 socket peer, Host, path, failure status를 예측한다.

0단계 · 시작과 상태 확인 (5분)

make doctor
make up
make ps

예상: client, dns, api, web, proxy가 실행된다. 기존 환경에 충돌이 있으면 무작정 port를 바꾸지 말고 docker compose 상태와 사용 중 network부터 확인한다.

1단계 · Direct와 reverse proxy 경유 비교 (8분)

docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client curl -sS http://api:8000/headers

docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client curl -sv http://proxy:8080/api/headers

예상: Proxy response에는 X-Lab-Upstream: api:8000이 있고 API가 받은 path는 /headers로 바뀐다. API의 socket peer는 direct에서는 client, 경유에서는 proxy다. Proxy가 넣은 X-Lab-Proxy와 X-Forwarded-Host도 확인한다.

2단계 · 두 connection을 packet으로 분리 (8분)

# 터미널 A: proxy namespace의 client-side 8080과 upstream 8000 관찰
docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec proxy tcpdump -ni eth0 'tcp port 8080 or tcp port 8000'

# 터미널 B
docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client curl -sS http://proxy:8080/api/headers >/dev/null

예상: client↔proxy:8080과 proxy ephemeral port↔api:8000 traffic이 별도 5-tuple로 보인다. 관찰 후 터미널 A에서 Ctrl-C한다. Packet ACK와 HTTP response/commit을 같은 성공으로 부르지 않는다.

3단계 · 실패 주입: upstream만 중지 (8분)

docker compose -f labs/basic-network-observability/docker-compose.yml stop api

docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client curl -sv --max-time 7 http://proxy:8080/api/headers

docker compose -f labs/basic-network-observability/docker-compose.yml start api

예상: Client→proxy connection과 HTTP request는 성공하지만 proxy→api connect가 실패해 proxy가 JSON body와 502를 합성한다. 이는 “502를 받았으니 app가 502를 보냈다”가 틀릴 수 있음을 증명한다.

4단계 · 복구·cleanup (6분)

docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client curl -fsS http://proxy:8080/api/headers >/dev/null
make down

자주 나는 오류: Permission denied이면 Docker daemon/사용자 권한을 확인한다. proxy에서 tcpdump가 없으면 image build 상태를 확인한다. 502가 아니라 connection refused면 client가 proxy가 아닌 api에 직접 붙었는지 URL을 본다. API 재시작 직후 race가 나면 readiness를 확인하고 bounded 재시도한다.

8. 놓치기 쉬운 함정

  • Forward와 reverse는 packet 방향 이름이 아니다. 누가 proxy를 선택하고 누구를 대신해 보이는지가 기준이다.
  • CONNECT 200은 origin HTTPS 200이 아니다. Tunnel 생성 뒤 TLS와 HTTP가 남아 있다.
  • Client IP header는 packet source가 아니다. Trusted boundary가 재작성하지 않으면 client 입력일 뿐이다.
  • 한 request가 한 socket만 쓰지 않는다. Message-aware proxy마다 connection과 queue가 새로 생긴다.
  • Front H2가 upstream H2를 뜻하지 않는다. Protocol translation과 stream→connection failure mapping을 확인한다.
  • 502/504의 생성자를 찾는다. Via/Server/header, proxy access/error log, request ID로 어느 hop이 status를 만들었는지 본다.
  • Pool reuse는 공짜가 아니다. Stale idle socket, max lifetime, DNS change, cert rotation과 drain 정책이 필요하다.
  • Timeout을 크게 하면 capacity가 늘지 않는다. Queue residence와 concurrent state가 늘어 overload recovery를 늦춘다.
  • Proxy retry와 SDK retry를 곱하지 않는다. 2회×3회는 최대 6 backend attempt가 될 수 있다.

9. 대기업 기술 면접 질문

  1. “Forward proxy, reverse proxy, tunnel을 connection 관점으로 비교하세요.”
    좋은 답변 구조: 선택 주체/client visibility → absolute-form/CONNECT/gateway → incoming/outgoing socket → TLS termination 여부 → readable metadata → policy/cache/use case → trust·failure boundary.
  2. “Reverse proxy에서 간헐적 502가 납니다. 15분 진단을 설계하세요.”
    좋은 답변 구조: status generator와 request ID → route/backend cohort → pool pending/idle/active → fresh connect DNS/TCP/TLS/ALPN → stale socket/timeout 가설 → 정상 pool canary → retry 축소·rollback·baseline.
  3. “원 client IP를 안전하게 application까지 전달하세요.”
    좋은 답변 구조: Socket peer와 header 구분 → edge가 untrusted chain 제거 → 직접 관측값으로 Forwarded 재작성 → trusted proxy allowlist/hop count → inter-proxy TLS/mTLS → privacy/redaction → spoof test.

10. 회상·확인 문제와 채점 기준

어제 내용 회상 3문제

  1. TLS termination 뒤 upstream에 자동으로 이어지지 않는 세 보안 속성은?
  2. HTTP/2와 HTTP/3에서 한 stream loss의 다른 영향은 무엇이며 어떤 shared state는 남는가?
  3. Transport ACK, HTTP response, DB commit을 왜 분리해야 하는가?

짧은 정답: ① 기밀성·무결성·peer 인증은 새 connection에서 다시 구성해야 한다. ② H2는 TCP sequence gap이 모든 stream delivery를 막을 수 있고 H3는 stream별 복구하지만 cwnd·connection flow/QPACK은 공유한다. ③ 각각 peer transport 수신, application 응답, durable transaction으로 owner와 failure window가 다르다.

오늘 내용 확인 3문제

  1. Client→reverse proxy→app 요청에 최소 몇 connection이 있고 각 owner/state는 무엇인가?
  2. Forwarded/X-Forwarded-For를 authorization에 안전하게 쓰기 위한 조건은?
  3. Proxy가 POST body를 보낸 뒤 upstream timeout이 났을 때 즉시 retry하면 안 되는 이유와 대안은?

짧은 정답: ① 최소 downstream과 upstream 두 개이며 각각 5-tuple, protocol/TLS, buffer/timeout과 pool state가 독립이다. ② Public 입력을 경계에서 제거하고 trusted proxy가 직접 관측값으로 재작성하며 app은 allowlist된 hop만 해석한다. ③ App commit 여부가 모호해 중복 write가 가능하므로 idempotency key, dedup, status 조회, bounded policy가 필요하다. 문항당 정의 1점, state/flow 1점, failure·trade-off 1점으로 총 9점이다.
