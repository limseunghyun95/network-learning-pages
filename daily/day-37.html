RESILIENCE PATTERN · WEEK 6 / DAY 37

deadline propagation과 cancellation

남은 시간과 “더는 결과가 필요 없다”는 신호를 request tree 전체로 전달한다 · 이론 55분 + 실습 35분

한 줄 요약
Deadline은 전체 요청이 쓸 수 있는 단 하나의 시간 예산이고, cancellation은 그 결과를 더 이상 기다리지 않는다는 제어 신호다. 각 hop은 이미 소비한 시간을 빼고 더 짧은 child budget을 만들며, 취소를 socket·worker·DB까지 협력적으로 전파해야 한다.

1. 선수 용어 사전

Deadline이 시각 이후에는 caller가 결과를 기다리지 않겠다는 절대 종료점이다. Timeout duration을 request 시작 시각에 더해 만들 수 있다.
Remaining budget현재 시점부터 deadline까지 남은 시간이다. remaining = deadline − now − reserve로 계산하며 0 이하면 새 downstream 호출을 시작하지 않는다.
PropagationDeadline·trace 같은 request-scoped context를 function, thread, process, service 경계를 넘어 다음 작업에 전달하는 과정이다.
CancellationCaller가 더는 결과를 원하지 않음을 알리는 제어 신호다. Deadline 만료, 사용자 중단, parent 실패, I/O 오류로 시작될 수 있다.
Cooperative cancellationRuntime이 worker를 강제로 죽이는 대신 작업 코드가 취소 신호를 확인하고 안전한 지점에서 종료·정리하는 방식이다.
Cancellation pointLoop 반복, queue 대기, outbound RPC, DB query처럼 취소 신호를 확인하고 빠져나올 수 있는 지점이다.
Parent / child contextParent request에서 파생된 작업 관계다. Parent 취소는 모든 child에 퍼지고, child deadline은 parent보다 길어지면 안 된다.
Fan-out한 request가 여러 downstream을 병렬 호출하는 구조다. 가장 느린 sibling, quorum 조건, 부분 실패와 취소 범위를 정해야 한다.
Reserve / guard bandDownstream 결과를 serialize하고 client로 돌려보낼 시간을 남겨 두는 여유 예산이다.
Commit pointDB transaction이나 외부 결제가 되돌리기 어려운 상태로 확정되는 경계다. 취소가 도착한 시점과 commit 전후를 구분해야 한다.
Orphan workCaller는 포기했지만 server·worker·DB가 계속 수행하는 무주인 작업이다. CPU·lock·connection을 낭비해 overload를 키운다.
Cancellation cause사용자 취소, deadline 초과, parent 실패처럼 왜 취소됐는지를 나타내는 이유다. 단순 “cancelled”보다 진단과 retry 판단에 유용하다.

2. 왜 중요한가

Frontend가 2초 뒤 포기하는데 backend가 30초 timeout으로 DB query를 계속하면 사용자는 실패를 보지만 system은 성공 가능성이 없는 일에 자원을 쓴다. Traffic이 몰리면 orphan work가 새 request를 막고, timeout과 retry가 더 늘어나는 positive feedback loop가 된다.

  • Latency SLO: Hop마다 새 timeout을 시작하지 않고 처음 받은 end-to-end budget 안에서 끝낸다.
  • 자원 회수: Socket만 닫지 말고 queue entry, goroutine/thread, DB query, downstream RPC를 함께 취소한다.
  • 정확성: Commit 이후 취소는 rollback 명령이 아니다. 결과 저장·조회·idempotency 전략이 필요하다.
  • 보안: 외부 client가 보낸 지나치게 짧거나 긴 deadline metadata를 그대로 믿으면 resource exhaustion이나 실패 유도가 가능하다.
  • 면접: “Context를 전달한다”를 넘어 clock skew, reserve, fan-out, cancellation race, commit boundary까지 설명해야 실무 수준이다.

  1. Client: Root deadline과 cancel 권한을 만든다. Deadline 만료 전이라도 사용자가 화면을 떠나면 cancel할 수 있다.
  2. Ingress: 외부 deadline을 신뢰하지 않고 service 최소·최대 범위로 clamp한다. Trace ID와 deadline은 목적이 다른 context다.
  3. Service A: 이미 쓴 500ms와 response reserve를 빼고 B·C child budget을 만든다. Child가 parent보다 길어지지 않는 것이 불변식이다.
  4. Fan-out: “모두 필요”, “하나만 필요”, quorum 중 성공 조건을 먼저 정한다. 조건을 만족하면 불필요한 sibling을 취소한다.
  5. DB: Driver가 context-aware query cancellation을 지원해야 한다. Handler가 return해도 DB query가 자동 종료된다고 가정하지 않는다.
  6. Cancel: Data response와 별도의 control path로 전파된다. Transport signal 도착은 application worker가 실제로 멈췄다는 확인이 아니다.
  7. 성공 확정: Commit 전에는 취소·rollback할 수 있지만 commit 뒤에는 결과 상태를 durable store에 남겨 조회 가능하게 해야 한다.
핵심 불변식: child deadline ≤ parent deadline − response reserve. 각 hop은 deadline을 연장하지 않고, cancel 수신 뒤 새 side effect를 시작하지 않으며, 종료 시 timer·queue slot·socket·DB handle을 정확히 한 번 해제한다.

4. CS 수준 내부 동작

절대 시각보다 남은 duration

Host A의 09:00:02와 Host B의 09:00:02는 clock skew 때문에 같지 않을 수 있다. gRPC는 전파할 때 deadline을 이미 소비한 시간을 뺀 timeout duration으로 바꾸어 skew 영향을 줄인다. 각 process 안의 경과 시간은 monotonic clock으로 재고, 분산 trace 상관관계는 wall clock과 skew를 함께 본다.

Context tree와 happens-before

Parent cancel은 child의 done signal을 닫고, worker는 select/poll 지점에서 이를 관찰한다. Signal 발생과 worker 종료 사이에는 지연이 있다. Shared result를 쓰는 작업은 “성공 publish”와 “cancel publish” 중 하나만 state를 terminal로 바꾸도록 compare-and-swap, mutex, future completion 같은 동기화가 필요하다.

Timer heap, resource leak, cancel function

Deadline context는 runtime timer와 parent→child reference를 가진다. 작업이 일찍 끝났는데 cancel/release 함수를 호출하지 않으면 deadline까지 timer와 child reference가 남을 수 있다. Go 공식 문서는 모든 control-flow path에서 CancelFunc 호출을 요구하며 static analysis도 이를 검사한다.

Transport cancel과 application cancel

HTTP/2 RST_STREAM, gRPC cancel, TCP close는 peer에게 관심 종료를 알리는 수단이다. 하지만 CPU loop, blocking library, 외부 API, DB engine을 강제 중단하지 않는다. Handler가 cancellation point를 두고 사용 중인 client·driver도 신호를 받을 수 있어야 end-to-end cancellation이 된다.

Commit race와 exactly-once 착각

Cancel이 DB commit 직전/직후에 도착할 수 있다. Transaction rollback이 성공하면 “미적용”을 말할 수 있지만 commit 뒤 response가 유실되면 caller는 결과를 모른다. Idempotency key, operation status table, outbox처럼 durable state로 이 모호성을 해소한다.

Detach는 예외이지 기본이 아니다

Audit·outbox publish처럼 request 이후 반드시 끝내야 하는 작업을 parent cancellation에서 분리할 수 있다. 단순 background thread로 떼지 말고 durable queue에 넘기고 새 deadline, owner, retry policy를 부여한다. Go의 WithoutCancel 같은 API를 무심코 쓰면 무한 orphan work가 된다.

5. 실무 설계 판단과 best practice

판단권장 기준과 이유
Ingress clampExternal deadline/timeout header는 인증된 protocol 규칙으로 parse하고 service min/max 범위로 제한한다. 음수·overflow·무한 값을 거부한다.
Single budgetHop마다 새 2초 timeout을 만들지 않는다. 최초 deadline에서 elapsed와 serialization/network reserve를 빼 child timeout을 정한다.
Start gate남은 예산이 예상 최소 실행시간+reserve보다 작으면 downstream을 시작하지 않고 빠르게 budget-exhausted를 반환한다.
Cancellation pointLong loop·queue wait·I/O 전후에 신호를 확인하고, context-aware RPC/DB API를 사용한다. Poll 간격이 실제 cancel latency 상한을 만든다.
Fan-out policyAll/quorum/first-success 요구사항을 명시하고 성공 조건 뒤 sibling을 취소한다. Partial result 허용 여부와 비용을 API 계약에 넣는다.

Version/engine 차이: gRPC deadline 자동 전파와 outgoing RPC 자동 취소 여부는 언어 구현별로 다르다. gRPC 공식 문서는 Java·Go는 deadline 전파가 기본이고 C++은 명시 설정이 필요할 수 있다고 설명한다. Envoy의 route timeout, per-try timeout, stream idle timeout도 서로 다른 timer이므로 실제 release 문서를 확인한다.

7. 35분 실습: 전달된 metadata와 실제 취소를 구분

사전 조건: Docker Desktop/Engine과 Compose, 저장소 root, terminal 두 개. 각 단계 전에 “client가 멈추면 proxy와 API도 즉시 멈출까?”를 예측한다. 이 lab은 의도적으로 cancellation을 전파하지 않아 orphan work를 관찰하게 한다.

예상: Proxy→API 호출이 약 1초에 HTTP 200으로 끝난다. 이것이 failure injection 전 기준선이다.

1단계 · Client cancellation과 orphan work (10분)

Terminal A:

docker compose -f labs/basic-network-observability/docker-compose.yml \
  logs -f --since=10s api proxy

Terminal B:

time docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client curl --max-time 2 -v \
  'http://proxy:8080/api/slow?seconds=4'

예상: Client는 약 2초에 종료하지만 API는 4초 sleep을 계속한다. 이후 proxy 또는 API log에 closed peer/BrokenPipe 계열 오류가 보일 수 있다. Socket close만으로 application 작업이 즉시 중단되지 않는 증거다.

2단계 · Header 전달은 enforcement가 아니다 (7분)

docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client curl -fsS \
  -H 'X-Request-Timeout-Ms: 1500' \
  http://proxy:8080/api/headers

예상: API JSON에 header가 그대로 보인다. 하지만 현재 API는 값을 parse·clamp·timer로 연결하지 않으므로 이것은 metadata propagation일 뿐 deadline enforcement가 아니다. Public header를 곧바로 신뢰하면 안 된다.

3단계 · Remaining budget 산술 (7분)

docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client python -c '
import time
budget = 3.0
reserve = 0.2
start = time.monotonic()
time.sleep(0.8)
elapsed = time.monotonic() - start
remaining = max(0.0, budget - elapsed - reserve)
print(f"original={budget:.1f}s elapsed={elapsed:.3f}s reserve={reserve:.1f}s child_max={remaining:.3f}s")
'

예상: Child가 쓸 수 있는 시간은 약 2.0초다. Service가 매 hop마다 새 3초를 주면 3-hop chain이 사용자 budget을 크게 초과한다.

4단계 · 증거 정리와 cleanup (5분)

docker compose -f labs/basic-network-observability/docker-compose.yml \
  logs --since=5m --timestamps api proxy
make down

관찰 표에 기록: Client stop, proxy error/finish, API finish의 timestamp와 차이를 적고 “cancel signal 전달 여부 / handler 확인 여부 / 실제 stop latency”를 구분한다. 자주 나는 오류: Docker가 꺼져 있으면 make doctor에서 중단한다. Log에 오류가 없어도 API가 4초 뒤 완료했다면 orphan work 증거다. time 출력은 host shell 구현에 따라 형식이 다를 수 있다. Cleanup은 다른 container를 삭제하지 않고 make down만 사용한다.

8. 놓치기 쉬운 함정

  • Deadline을 hop마다 초기화하면 안 된다. End-to-end budget이 아니라 N×timeout이 된다.
  • 절대 timestamp를 다른 host에 그대로 믿지 않는다. Clock skew를 피해 elapsed를 뺀 duration으로 전달한다.
  • Context 전달과 취소 준수는 다르다. Library와 handler가 신호를 실제로 확인해야 한다.
  • TCP disconnect는 DB query cancellation이 아니다.
  • CancelFunc는 실패 경로뿐 아니라 성공 경로에서도 호출한다. Timer/reference leak을 막는다.
  • Fan-out 하나가 성공해도 나머지 sibling을 방치하지 않는다.
  • Deadline exceeded와 user cancelled를 같은 원인으로 집계하지 않는다.
  • Commit 뒤 cancellation을 rollback으로 오해하지 않는다.
  • 외부 deadline header와 trace baggage를 무제한 신뢰·전파하지 않는다.
  • Background detach에는 새 owner·deadline·durable queue가 필요하다.

9. 대기업 기술 면접 질문

  1. “Client 2초 deadline을 4개 microservice에 어떻게 전파하겠습니까?”
    좋은 답변 구조: 사용자 SLO → root deadline → elapsed·reserve 산술 → duration 전파와 clamp → child≤parent 불변식 → trace metric → language/runtime 차이.
  2. “Client가 취소했는데 DB query가 계속 실행됩니다. 어디를 고치겠습니까?”
    좋은 답변 구조: transport cancel과 handler stop 분리 → context tree → cancellation point → driver cancel 지원 → query ID 증거 → cleanup·rollback → canary.
  3. “결제 commit과 cancellation이 경쟁하면 exactly-once를 어떻게 보장합니까?”
    좋은 답변 구조: failure window → commit point → ambiguous result → idempotency key·operation table·outbox → 결과 조회/보상 → blind retry 금지.

10. 회상·확인 문제와 채점 기준

어제 내용 회상 3문제

  1. Connect timeout과 request timeout의 clock 범위는 어떻게 다른가?
  2. Small write 성공이 remote 처리 성공을 뜻하지 않는 이유는?
  3. Timeout 뒤 mutation이 ambiguous할 때 필요한 두 가지 장치는?

짧은 정답: ① Connect는 connection 준비 구간, request timeout은 DNS부터 body·retry까지 전체 상한이다. ② Byte가 local send buffer에만 복사됐을 수 있다. ③ Idempotency key와 durable result 조회/operation status다.

오늘 내용 확인 3문제

  1. Child deadline이 parent보다 길면 어떤 불변식과 비용이 깨지는가?
  2. Cancellation 신호를 보냈는데도 handler가 계속 실행될 수 있는 이유는?
  3. 반드시 끝내야 하는 post-request 작업을 안전하게 분리하는 방법은?

짧은 정답: ① End-to-end budget과 자원 회수 시점이 깨져 orphan work가 생긴다. ② 취소는 협력적이며 handler·blocking library·DB driver가 신호를 확인해야 하기 때문이다. ③ Durable queue/outbox로 넘기고 새 owner·deadline·retry·관측성을 부여한다. 문항당 정의 1점, 내부 흐름 1점, failure·trade-off 1점으로 총 9점이다.
