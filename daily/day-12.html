COMPUTER NETWORKING · WEEK 2 / DAY 12

Split-horizon, search domain, service discovery

“같은 이름인데 왜 다른 IP인가?”를 namespace부터 socket까지 추적하기 · 예상 학습 50분 + 실습 35분

한 줄 요약
Application이 입력한 orders는 아직 DNS QNAME이 아니다. Stub resolver가 search list·ndots·trailing dot 정책으로 후보 이름을 만들고, 선택된 resolver/view가 client context에 맞는 answer를 반환한다. Service discovery는 그 answer를 endpoint·port·metadata로 바꾸지만 실제 성공은 새 socket이 올바른 target에 연결되고 application protocol이 응답해야 확정된다.

1. 선수 용어 사전

FQDNFully Qualified Domain Name. DNS root까지 지정한 완전한 이름이다. Text 표현의 마지막 점은 root label을 뜻해 orders.example.com.처럼 search suffix를 붙이지 않게 한다.
Short nameorders처럼 namespace가 생략된 이름. Local context 없이는 전역에서 하나로 해석되지 않으며 search policy가 실제 query 후보를 만든다.
Search domain/listShort/relative name 뒤에 순서대로 붙여 볼 suffix 목록. DHCP, VPN, kubelet, OS 설정 등이 제공하며 순서 자체가 routing·보안 정책이다.
ndots이름에 점이 몇 개 있어야 absolute 후보를 먼저 시도할지 정하는 resolver option. 구체적 순서와 default는 libc·OS·runtime마다 다르며 RFC 공통 불변식이 아니다.
Split DNS / view같은 zone/name에 query source·destination·type 같은 속성별로 다른 answer를 제공하는 구성. RFC 9499는 효과를 정의하지만 view 구현 자체는 표준 DNS 기능이 아니며 제품별 차이가 있다.
Namespace이름이 유일하고 유효한 범위. Kubernetes namespace, corporate internal zone, public zone은 서로 다른 이름 문맥을 만든다.
Service discovery“어떤 service instance가 어디에서 어떤 port·속성으로 제공되는가?”를 찾는 과정. 단순 A lookup보다 endpoint set, port, priority/weight, metadata와 변화 감지가 포함될 수 있다.
PTR / SRV / TXTDNS-SD에서 PTR은 instance 목록, SRV는 priority·weight·port·target, TXT는 작은 key/value metadata를 제공한다. Target address는 다시 A/AAAA로 해석한다.
Endpoint readinessEndpoint가 새 요청을 받을 준비가 됐다는 control-plane 상태. DNS record 존재, port listen, application healthy는 서로 다른 성공 경계다.

2. 왜 중요한가

개발 PC에서는 db가 되고 production에서는 안 되거나, VPN 안팎에서 같은 FQDN이 다른 IP를 돌려주는 문제는 “DNS가 랜덤하다”가 아니다. Client가 만든 QNAME 후보, 보낸 resolver, 적용된 view가 다르기 때문이다.

  • Short name은 숨은 dependency다. Search list가 바뀌면 application config를 바꾸지 않아도 전혀 다른 FQDN과 trust domain으로 연결될 수 있다.
  • Split DNS는 policy routing이다. 내부 client는 private IP, 외부 client는 public IP를 받을 수 있지만 cache/view 경계를 잘못 공유하면 내부 이름 누출이나 잘못된 endpoint 연결이 생긴다.
  • Discovery와 연결은 다른 state machine이다. DNS가 endpoint를 찾았어도 route, NetworkPolicy, port, TLS certificate, application readiness가 실패할 수 있다.
  • Search expansion은 query amplification이다. Suffix 수 × A/AAAA × retry × upstream 계층만큼 DNS QPS와 tail latency가 늘 수 있다.

3. 아키텍처 그림과 이름→endpoint 흐름

① Application: getaddrinfo("orders")
logical name · deadline t0
↓ stub resolver policy
② Candidate QNAME 생성
orders.payments.svc.cluster.local. → orders.svc.cluster.local. → orders.
↓ UDP/TCP query + source/resolver context
③ Resolver route / authoritative view
inside·outside·tenant·namespace policy로 zone과 answer 선택
↓ A/AAAA 또는 PTR→SRV/TXT→A/AAAA
④ Discovery result
endpoint set + port + metadata + TTL · cache state
↓ endpoint selection + route/ARP·ND
⑤ TCP/QUIC socket → TLS → application
connect queue · SNI/certificate · health · response timestamp
  1. t0: Application은 short name과 전체 request deadline을 소유한다. Resolver 호출 timeout이 deadline과 분리되면 DNS만 기다리다 상위 요청이 이미 취소될 수 있다.
  2. Candidate 생성: Stub은 search list와 ndots로 실제 QNAME 순서를 정한다. Trailing dot이 있는 FQDN은 search expansion을 막는 가장 명확한 입력이다.
  3. View 선택: Resolver/authoritative가 source IP 같은 query attribute로 answer를 결정한다. NAT·VPN·forwarder 때문에 authoritative가 보는 source는 application host와 다를 수 있다.
  4. Discovery: DNS-SD라면 PTR로 instance를 열거하고 SRV/TXT로 port·target·metadata를 얻은 뒤 target의 A/AAAA를 조회한다. Kubernetes Service DNS는 제품 convention이며 RFC 6763 browsing 전체와 동일하다고 가정하지 않는다.
  5. 성공 확정: DNS는 endpoint 후보를 반환하면 끝이지만 user request는 socket connect, TLS identity, application response까지 가야 성공이다. 기존 connection pool은 DNS TTL이 끝나도 old endpoint 연결을 계속 재사용할 수 있다.

4. CS 수준 내부 동작

State owner와 failure window

OwnerState · 불변식 · 실패 창
DHCP/VPN/kubeletNameserver, search list, ndots를 client namespace에 주입한다. Rogue/잘못된 suffix는 short name을 공격자나 다른 tenant domain으로 redirect할 수 있다.
Stub/runtimeCandidate 순서, A/AAAA parallelism, retry와 negative result를 관리한다. glibc, musl, Go, JVM, browser가 OS 설정을 소비하는 방식은 같지 않다.
Split resolver/viewQuery context→zone/answer mapping과 cache를 소유한다. View가 다른 answer를 shared cache key 하나에 섞으면 cross-view contamination이 된다.
Discovery control planeService registry·Kubernetes Service/EndpointSlice→DNS record를 reconcile한다. Readiness 변경부터 record 반영까지 eventual-consistency window가 있다.
Client data planeTTL cache, endpoint 선택, connection pool, retry를 소유한다. DNS에서 제거된 endpoint도 cached address와 existing connection 때문에 traffic을 받을 수 있다.

Query amplification을 수치로 보기

Search suffix 3개와 absolute 후보 1개가 있고 application이 A와 AAAA를 모두 조회한다면 cache miss 한 번이 최대 4 후보 × 2 QTYPE = 8 logical DNS queries가 될 수 있다. 각 후보가 2회 retry하고 recursive가 여러 authority를 방문하면 packet 수는 더 커진다. ndots:5 환경의 api.example.com처럼 점이 5개보다 적은 이름은 구현에 따라 search 후보가 absolute보다 먼저 시도돼 불필요한 NXDOMAIN과 latency를 만들 수 있다.
  • Security invariant: DNSSEC은 “질의한 FQDN의 data가 검증됐다”를 보장할 수 있지만, rogue DHCP가 애초에 다른 search suffix를 선택하게 한 문제까지 자동 해결하지 않는다.
  • SRV invariant: 낮은 priority를 먼저 사용하고 같은 priority 안에서 weight를 해석해야 한다. 배열의 첫 항목 고정 선택은 hot endpoint를 만든다.
  • TLS invariant: 발견된 target IP/host와 사용자가 의도한 logical service identity를 구분해 SNI와 certificate hostname을 검증한다.

5. 실무 설계 판단과 best practice

판단권장 기준과 이유
이름 선택배포 config, certificate, cross-namespace·cross-trust 호출은 FQDN을 사용한다. Short name은 관리된 local namespace에서만 쓰고 expansion 결과를 테스트한다.
Search 정책Suffix 수와 순서를 최소화하고 명시적으로 배포한다. ndots 변경 전 QPS·NXDOMAIN·latency를 runtime별로 측정하며 DHCP가 수동 DNS 설정을 덮지 않게 한다.
Split DNSZone ownership, view match 조건, forward route, cache namespace, DNSSEC 정책을 문서화한다. Inside/outside/VPN/IPv4/IPv6에서 같은 test matrix를 자동화한다.
Discovery schemaA/AAAA만 필요한지, SRV priority·weight·port와 TXT version까지 필요한지 client capability로 정한다. TXT를 secret 저장소나 큰 config blob으로 쓰지 않는다.
LifecycleReady 전 publish 금지, drain→record 제거→TTL/negative cache→connection pool max lifetime 순으로 old endpoint traffic의 상한을 계산한다.
ObservabilityOriginal input, expanded QNAME, search index, selected resolver/view, answer/TTL, registry revision, chosen endpoint, connect/TLS/app timing을 같은 request trace와 timestamp로 연결한다.
Anti-pattern: “내부 DNS니까 안전하다”며 같은 FQDN의 public/private record를 사람 손으로 따로 관리하지 않는다. Ownership·reconciliation·diff check가 없으면 view drift와 certificate·rollback 불일치가 누적된다.

6. 장애 대응 표

상황: checkout은 같은 namespace에서 되지만 다른 namespace와 VPN 밖에서는 NXDOMAIN 또는 public IP를 반환하고, 일부 client는 private IP 연결 timeout이다.

순서실행 내용
증상Client namespace·VPN·subnet·runtime별 original name, 실제 QNAME, resolver IP, answer, RCODE, chosen endpoint와 connect result를 분리한다.
먼저 수집할 증거/지표/etc/resolv.conf·OS DNS config, ndots/search order, dig +search question, FQDN direct query, inside/outside authoritative answer, resolver logs/cache, Service·EndpointSlice readiness, TTL, route/flow log, pool connection age와 timestamp를 저장한다.
가능한 가설잘못된 search suffix/namespace, trailing dot 차이, VPN DNS route 누락, NAT 때문에 잘못된 view match, shared cache leakage, split zone drift, stale/negative cache, EndpointSlice publish 지연, old pooled connection.
안전한 첫 조치영향 client 하나에서 intended FQDN을 direct query하고 올바른 resolver를 명시해 비교한다. Config는 canary에 FQDN으로 고정하고 wrong-view traffic을 차단하기 전 endpoint capacity와 rollback을 확인한다.
Rollback/복구최근 VPN/search/view/CoreDNS 변경을 known-good으로 되돌리고 두 view record를 reconcile한다. TTL·pool lifetime 동안 old/new endpoint를 병행하고 QNAME·answer·connect 성공률로 수렴을 확인한다.
하지 말아야 할 조치전체 cache flush, search suffix 무작정 추가, public/private zone 동시 수동 편집, DNSSEC/TLS 검증 해제, 모든 Pod restart, retry 무제한 확대, DNS 성공만 보고 NetworkPolicy·port·readiness 조사를 끝내지 않는다.

7. 35분 두 DNS view·search·SRV 실습

목표: 같은 FQDN이 resolver view별로 다른 endpoint가 되고, short name이 search suffix로 확장되며, SRV port를 무시하면 연결이 실패하는 과정을 재현한다.

사전 조건: Docker Desktop과 이 저장소. 기존 lab의 documentation network만 사용하며 host DNS 설정은 바꾸지 않는다. 터미널 3개를 연다.

8. 놓치기 쉬운 함정

  • Split DNS와 Geo DNS를 같은 말로 쓰지 않는다. 둘 다 다른 answer를 줄 수 있지만 match input, trust boundary, 목적이 다르다.
  • Authoritative가 application source IP를 본다고 가정하지 않는다. Recursive resolver, forwarder, NAT가 source context를 바꾼다.
  • ndots:5를 Kubernetes의 영원한 불변식으로 외우지 않는다. Cluster/runtime/config에 따라 다르며 Pod의 실제 /etc/resolv.conf를 본다.
  • Search NXDOMAIN을 service 부재로 단정하지 않는다. Intended FQDN을 direct query해 namespace expansion 문제와 record 부재를 분리한다.
  • SRV weight를 load balancer health check로 오해하지 않는다. Weight는 selection hint이며 현재 endpoint health를 보증하지 않는다.
  • Headless Service endpoint set을 connection-level load balancing으로 오해하지 않는다. Client cache와 pool 때문에 한 endpoint에 오래 고정될 수 있다.
  • TXT에 secret을 넣지 않는다. DNS metadata는 cache·log·packet capture에 넓게 노출될 수 있다.

9. 대기업 기술 면접 질문

  1. “같은 도메인이 회사 안팎에서 다른 IP를 주는 구조를 설계하세요.”
    좋은 답변 구조: 요구사항·trust boundary → query source/forward path → split zone/view/cache ownership → private/public TLS·route → TTL/rollback → leak·drift test → observability.
  2. “Kubernetes에서 short service name이 느립니다. 왜일까요?”
    좋은 답변 구조: Pod resolv.conf·ndots → candidate QNAME 수 × A/AAAA × retry 계산 → NXDOMAIN/cache/CoreDNS QPS → FQDN canary → suffix/ndots/runtime trade-off.
  3. “DNS 기반 service discovery의 endpoint lifecycle을 설명하세요.”
    좋은 답변 구조: registry/readiness → DNS reconcile → PTR/SRV/TXT/A·AAAA → TTL/cache → selection → socket/TLS/app → drain/pool lifetime → failure·rollback.

10. 회상·확인 문제와 채점 기준

어제 내용 회상 3문제

  1. EDNS UDP payload size가 path 전달을 보장하지 않는 이유는?
  2. TC=1 이후 TCP DNS message 경계는 어떻게 복원하는가?
  3. 작은 A는 되는데 DNSKEY만 실패할 때 첫 두 실험은?

짧은 정답: ① 광고 size와 PMTU·fragment/middlebox 정책이 다르다. ② 2-octet length prefix만큼 byte stream을 모은다. ③ +ignore +bufsize=512로 TC를 보고 +tcp로 TCP 53을 독립 검증한다.

오늘 내용 확인 3문제

  1. orders가 실제 DNS packet의 QNAME이 되기 전에 어떤 state가 개입하는가?
  2. DNSSEC이 rogue search suffix redirect를 자동으로 막지 못하는 이유는?
  3. Discovery에서 endpoint가 제거된 뒤에도 traffic이 남는 네 가지 window는?

짧은 정답: ① Stub/runtime의 search list·ndots·trailing-dot policy다. ② 공격자가 선택시킨 다른 FQDN도 정당하게 signed될 수 있기 때문이다. ③ Control-plane reconcile, DNS TTL/cache, client endpoint cache, existing connection pool/drain window다. 정의 1점, state 흐름 1점, 장애·trade-off 1점으로 문항당 3점.
