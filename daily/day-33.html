state owner·rule evaluation·return traffic·failure window를 packet 단위로 추적한다 · 개념 75분 + 실습 35분

한 줄 요약
Security Group은 ENI/resource 경계의 stateful allow-list이고, Network ACL은 subnet 경계의 stateless ordered allow/deny-list다. 요청과 응답이 각 경계에서 어떤 규칙과 connection state로 허용되는지 양방향으로 증명해야 한다.

1. 선수 용어 사전

FirewallPacket 또는 connection metadata를 규칙과 비교해 통과·차단을 결정하는 경계다. 암호화나 사용자 인증을 자동 제공하지 않는다.
5-tupleSource IP·source port·destination IP·destination port·protocol의 조합이다. TCP/UDP flow를 구분하는 기본 열쇠다.
Ingress / egress경계 안으로 들어오는 방향과 밖으로 나가는 방향이다. 같은 packet도 어느 경계를 기준으로 보느냐에 따라 이름이 달라진다.
Stateful첫 flow의 상태를 기억하고 그 응답을 기존 connection의 일부로 판단한다. AWS Security Group은 connection tracking을 사용한다.
Stateless각 방향의 packet을 독립적으로 평가한다. Request를 허용해도 reply 방향 규칙이 없으면 응답은 차단된다.
Security GroupAWS의 virtual firewall. ENI를 통해 resource에 적용되며 allow 규칙만 갖고 모든 규칙을 합산 평가한다.
NACLNetwork Access Control List. Subnet과 연결되며 inbound/outbound 규칙을 번호가 낮은 순서로 평가해 첫 match의 allow/deny를 적용한다.
ENIElastic Network Interface. IP·MAC·Security Group이 연결되는 가상 network interface다.
Implicit deny허용 규칙에 match하지 않은 traffic을 기본 차단하는 원칙이다. “규칙이 없다”는 “허용”이 아니다.
Ephemeral portClient OS가 connection마다 임시로 고르는 source port다. Stateless ACL의 reply 규칙은 이 범위를 고려해야 하며 실제 범위는 OS 설정에서 확인한다.
Control/Data plane규칙을 생성·배포하는 관리 경로와 실제 packet을 평가하는 실행 경로다. API 성공과 모든 packet의 즉시 동일 동작은 구분한다.

2. 왜 중요한가

“방화벽을 열었다”는 말만으로는 부족하다. 어느 경계, 어느 방향, 어느 protocol·port·identity, 신규 flow인지 기존 tracked flow인지가 빠지면 장애와 노출을 동시에 만들 수 있다.

  • 가용성: NACL reply ephemeral port 누락은 server가 정상이어도 client timeout을 만든다.
  • 보안: 넓은 CIDR 허용은 임시 복구처럼 보여도 lateral movement와 internet exposure의 영구 경로가 된다.
  • 정확성: Security Group rule 삭제 뒤 tracked connection은 즉시 끊기지 않을 수 있다. 신규·기존 flow를 나눠 검증해야 한다.
  • 용량: Stateful firewall의 conntrack table은 유한하다. Long-idle connection과 retry storm은 규칙이 맞아도 신규 flow drop을 만든다.
  • 면접: 좋은 답변은 “SG는 stateful” 암기에서 끝나지 않고 상태 소유자, rule evaluation, reply path, 관찰 증거와 rollback을 연결한다.

3. 아키텍처 그림과 요청 흐름

단계CLIENT → SUBNET/NACL → MIDDLEBOX → NACL/SUBNET → APP상태·판정 소유자
① resolveDNS → destination IP
socket source port 선택		Resolver·client kernel
② SG outClient ENI SG egress allow?
신규 connection state 후보		Source ENI SG·conntrack
③ NACL outSource subnet outbound
낮은 번호부터 첫 match		Source subnet NACL
④ middleRoute → NAT/LB/firewall
tuple rewrite·termination 가능		각 middlebox state
⑤ NACL inDestination subnet inbound
source·destination port 평가		Destination subnet NACL
⑥ SG inApp ENI SG ingress allow?
SYN이 listen queue로 이동		Destination ENI SG·kernel
⑦ replyAPP → SG state allow → NACL explicit allow
역방향으로 client queue 도착		SG tracked state + 양쪽 NACL
  1. DNS·socket: Client는 destination IP와 ephemeral source port를 정한다. 아직 어떤 firewall도 application 성공을 보장하지 않는다.
  2. Source SG: 신규 egress가 allow rule에 match하면 5-tuple 기반 state가 추적될 수 있다.
  3. Source NACL: Stateless이므로 이 outbound packet 자체를 rule number 순서로 평가한다.
  4. Middlebox: NAT는 tuple을 바꾸고, proxy/LB는 connection을 종료해 새 upstream flow를 만든다. 따라서 다음 경계가 보는 source가 달라질 수 있다.
  5. Destination NACL·SG: NACL은 subnet ingress를, SG는 ENI ingress를 평가한다. 둘 중 하나라도 차단하면 socket까지 도달하지 않는다.
  6. Reply: SG는 tracked response를 자동 허용하지만 NACL은 outbound와 반대편 inbound에 explicit rule이 필요하다.
  7. 성공 확정: TCP handshake는 network success일 뿐이다. TLS, HTTP response, downstream commit은 별도 owner와 timestamp로 확인한다.
핵심 불변식: Forward와 reply가 동일한 stateful owner가 이해할 수 있는 path를 지나고, 모든 stateless 경계에서 각 방향 tuple이 명시적으로 허용되며, 최종 socket이 listen·queue capacity를 가져야 한다.

4. CS 수준 내부 동작

Rule evaluation은 자료구조 문제다

Security Group은 여러 allow rule의 합집합으로 판단하므로 순서가 없다. NACL은 rule number가 작은 것부터 first match를 적용하므로 100 DENY가 200 ALLOW를 가릴 수 있다. 구현은 prefix lookup, protocol/port interval, direction metadata를 최적화하지만 운영자는 최종 판정 의미를 기준으로 사고해야 한다.

Connection tracking과 state transition

TCP의 SYN → SYN-ACK → ACK → ESTABLISHED → FIN/RST 상태와 firewall의 tracked state는 관련 있지만 동일한 객체는 아니다. AWS SG는 traffic의 connection state를 이용해 reply를 허용하고 instance별 tracking allowance를 가진다. State가 남아 있는 동안 rule 변경이 기존 flow를 즉시 끊지 않을 수 있으며, allowance가 고갈되면 신규 packet이 drop될 수 있다. conntrack_allowance_available와 신규 connection failure를 함께 본다.

Stateless reply와 ephemeral range

Client 10.0.1.10:53124가 server 10.0.2.20:443에 접속하면 reply destination은 53124다. Destination subnet NACL outbound와 client subnet NACL inbound가 이 reply tuple을 허용해야 한다. 무조건 1024–65535를 복사하기보다 client OS·NAT·LB의 실제 source-port 범위와 protocol을 확인해 최소 범위를 설계한다.

Identity와 address의 경계

SG reference는 “그 SG를 가진 resource에서 온 traffic”을 network policy source로 표현하는 수단이지 사용자·process identity 인증이 아니다. Proxy/NAT를 지나면 observed source가 바뀔 수 있고, peering·Transit Gateway·middlebox 경로에서는 reference semantics와 원 IP 보존 조건을 공식 문서로 확인해야 한다.

Control-plane change의 failure window

Rule API 성공은 desired policy가 접수되었다는 뜻이다. 기존 tracked flow, data-plane propagation, connection pool reuse 때문에 신규 connection과 기존 connection이 잠시 다르게 보일 수 있다. 변경 전후 request timestamp, source ENI, 5-tuple과 fresh connection probe가 필요하다.

5. 실무 설계 판단과 best practice

판단권장 기준과 이유
경계 역할SG는 workload 단위 최소 권한, NACL은 subnet-wide guardrail·긴급 deny처럼 목적을 분리한다. 같은 정책을 중복 복사하면 drift와 진단 비용이 커진다.
SG-to-SGApp ingress는 가능하면 LB SG를 source로 참조한다. 넓은 subnet CIDR보다 topology 변경에 강하지만 application authentication은 별도로 유지한다.
Rule 번호NACL 번호를 100, 200처럼 간격 두고 관리한다. Emergency deny를 어디에 넣을지와 first-match 결과를 code review에서 계산한다.
Reply 설계Forward만 보지 말고 source-port 범위, NAT/LB tuple 변화, 양쪽 NACL reverse rule을 sequence diagram으로 검증한다.
IPv4/IPv60.0.0.0/0과 ::/0은 별도다. Dual-stack 도입 시 한 protocol family만 보호하거나 허용하는 drift를 점검한다.
관찰 가능성VPC Flow Logs의 ENI·src/dst·ports·action·timestamp를 application trace와 연결한다. Flow Logs는 payload도, application 성공도, 모든 packet의 실시간 기록도 아니다.
변경 배포IaC diff → static analyzer → canary SG/subnet → fresh/established probe → metric gate → 확대 순서로 배포하고 직전 rule set을 rollback artifact로 보존한다.
관리 접근SSH/RDP를 internet 전체에 열지 말고 SSM·bastion·VPN·짧은 승인과 MFA를 사용한다. Break-glass rule은 TTL·owner·audit를 갖는다.
Version/engine 차이: AWS SG/NACL, Linux nftables/iptables, Kubernetes NetworkPolicy, managed firewall은 state model·hook 위치·default action·rule priority가 다르다. “stateful firewall”이라는 한 단어만으로 동작을 이식하지 말고 현재 provider/engine 공식 문서와 runtime counter를 확인한다.

7. 35분 실습: Linux stateless rule과 packet counter로 경계 재현

사전 조건: Docker Desktop/Engine과 Compose, 저장소 root. 실습은 client container의 NET_ADMIN만 사용한다. 실행 전 “destination 8000/TCP REJECT를 넣으면 curl은 timeout일까 즉시 실패일까?”를 먼저 예측한다.

0단계 · 시작과 baseline (6분)

make doctor
make up
make ps
docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client curl -fsS http://api:8000/headers

예상: DNS→TCP→HTTP가 성공한다. 실패 시 규칙을 추가하지 말고 먼저 make ps와 service log를 고친다.

1단계 · 도구 설치와 rule 전 상태 (7분)

docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client apk add --no-cache iptables
API_IP=$(docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec -T client getent hosts api | awk 'NR==1{print $1}')
echo "$API_IP"
docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client iptables -nvL OUTPUT --line-numbers

예상: API IP가 출력되고 OUTPUT chain에 오늘의 REJECT rule은 없다. Package 설치가 막히면 실습을 중단하고 host/network policy를 확인한다.

2단계 · 실패 주입과 counter 증거 (10분)

docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client iptables -I OUTPUT 1 -p tcp -d "$API_IP" --dport 8000 \
  -m comment --comment day33-lab -j REJECT
docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client curl -sv --max-time 4 http://api:8000/headers
docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client iptables -nvL OUTPUT --line-numbers

예상: REJECT이므로 신규 curl이 빠르게 실패하고 rule packet counter가 증가한다. DROP이면 timeout까지 기다리므로 사용자 체감과 retry amplification이 달라진다.

3단계 · 정확한 rollback과 복구 (6분)

docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client iptables -D OUTPUT -p tcp -d "$API_IP" --dport 8000 \
  -m comment --comment day33-lab -j REJECT
docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client curl -fsS http://api:8000/headers

예상: 추가한 정확한 rule만 사라지고 fresh connection이 다시 성공한다. Chain 전체 flush는 다른 사용자의 정책까지 제거할 수 있어 금지한다.

4단계 · 오류 처리와 cleanup (6분)

# 이전 실행 rule이 남았을 때만 exact match로 삭제한다.
docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client iptables -D OUTPUT -p tcp -d "$API_IP" --dport 8000 \
  -m comment --comment day33-lab -j REJECT 2>/dev/null || true
make down

자주 나는 오류: Operation not permitted이면 client의 NET_ADMIN과 container 재생성을 확인한다. Bad rule은 이미 rollback되었을 수 있다. API_IP가 비면 DNS부터 고친다. 실습 rule은 Linux host firewall 모델이며 AWS SG/NACL semantics와 동일하다고 간주하지 않는다.

8. 놓치기 쉬운 함정

  • SG에는 explicit deny가 없다. 차단이 필요하면 allow 제거 또는 다른 통제 계층을 설계한다.
  • 여러 SG 규칙은 합집합이다. 한 SG에서 좁혀도 다른 SG가 넓게 허용할 수 있다.
  • NACL은 first match다. 규칙 목록에 ALLOW가 있다는 사실보다 먼저 match하는 번호가 중요하다.
  • SG rule 삭제가 tracked flow를 즉시 끊는다고 단정하지 않는다. Fresh connection을 별도 시험한다.
  • SG reference는 사용자 인증이 아니다. TLS identity·application authorization을 대체하지 않는다.
  • Proxy/LB/NAT 뒤 source가 바뀔 수 있다. 실제 경계가 보는 tuple로 rule을 작성한다.
  • Flow Logs는 지연되어 나타날 수 있고 payload를 담지 않는다. Packet capture와 application trace를 함께 쓴다.
  • IPv4 rule은 IPv6를 제어하지 않는다. Dual-stack policy를 각각 리뷰한다.
  • Rule 이름·tag는 enforcement가 아니다. 실제 association과 effective rule이 진실이다.

9. 대기업 기술 면접 질문

  1. “Security Group과 NACL을 비교하고 request/reply를 설명하세요.”
    좋은 답변 구조: 적용 경계 → allow/deny와 rule evaluation → state owner → forward/reply tuple → ephemeral port → failure window → 관찰 방법.
  2. “SG rule을 제거했는데 기존 SSH는 유지되고 신규 SSH만 실패합니다. 왜인가요?”
    좋은 답변 구조: tracked/untracked 가정 → connection state lifetime → fresh vs established cohort → Flow Logs·conntrack metric → 즉시 차단 요구 시 NACL 등 대안과 위험.
  3. “3-tier VPC의 최소 권한 정책과 안전한 변경 절차를 설계하세요.”
    좋은 답변 구조: LB→app→DB dependency와 수치 가정 → SG-to-SG → subnet guardrail → IPv4/IPv6 → canary·fresh probe·rollback → audit·drift 탐지.

10. 회상·확인 문제와 채점 기준

어제 내용 회상 3문제

  1. Longest prefix match에서 /24와 /0가 모두 일치하면 무엇이 선택되는가?
  2. Private subnet의 internet egress에 private route 외에 필요한 두 state owner는?
  3. Flow Log ACCEPT가 HTTP 성공을 보장하지 않는 이유는?

짧은 정답: ① 더 구체적인 /24. ② NAT mapping과 NAT public subnet의 IGW route/reply path. ③ Network 경계 통과의 증거일 뿐 TCP queue, TLS, HTTP, downstream commit을 증명하지 않기 때문이다.

오늘 내용 확인 3문제

  1. SG가 inbound request를 허용했을 때 reply egress rule이 없어도 응답 가능한 이유는?
  2. NACL에서 request 443만 허용하고 reply가 실패하는 이유와 고칠 tuple은?
  3. Rule 변경 직후 기존 connection과 신규 connection의 결과가 다를 때 어떤 증거를 모을까?

짧은 정답: ① SG connection tracking이 허용된 flow의 응답을 stateful하게 허용한다. ② NACL은 stateless라 server outbound→client ephemeral port와 반대 subnet inbound를 명시해야 한다. ③ 두 cohort의 timestamp·5-tuple·Flow Logs·packet flags·effective rules·conntrack allowance를 비교한다. 문항당 정의 1점, 내부 흐름 1점, failure·trade-off 1점으로 총 9점이다.
