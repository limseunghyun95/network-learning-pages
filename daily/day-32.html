PROXY · LB · NAT · CLOUD NETWORK · WEEK 5 / DAY 32

VPC/subnet/route table/NAT gateway

논리 네트워크를 packet path·state owner·AZ 장애·비용으로 해부한다 · 개념 75분 + 실습 35분

한 줄 요약
VPC는 격리된 논리 주소 공간, subnet은 한 Availability Zone 안의 CIDR 구간, route table은 목적지 prefix를 target에 연결하는 control-plane 규칙이다. Private subnet의 인터넷 egress는 보통 private route → 같은 AZ NAT gateway → public route → internet gateway의 두 route table과 stateful NAT를 모두 통과해야 한다.

1. 선수 용어 사전

VPCVirtual Private Cloud. Cloud provider의 물리망 위에 만든 tenant별 논리 네트워크다. CIDR, route, gateway, policy 객체가 data path를 제어한다.
CIDR주소와 prefix length로 범위를 표현하는 방식이다. 10.20.1.0/24는 앞 24bit가 network prefix라는 뜻이다.
SubnetVPC CIDR의 겹치지 않는 일부 주소 구간이다. AWS에서는 subnet 하나가 하나의 Availability Zone에 속한다.
Availability ZoneRegion 안의 독립 장애 영역이다. 물리 위치 이름이 아니라 실패 상관관계를 낮추기 위한 배치 경계로 이해한다.
Route table목적지 prefix와 next target의 목록이다. AWS subnet은 한 시점에 하나의 route table과 연결되고 여러 subnet은 같은 table을 공유할 수 있다.
Longest prefix match목적지와 일치하는 route 중 prefix length가 가장 긴, 즉 가장 구체적인 route를 고르는 규칙이다. /24는 겹치는 /0보다 우선한다.
Target / next hop선택된 route가 packet을 넘길 논리 객체다. local, NAT gateway, internet gateway, network interface, peering 등이 될 수 있다.
Internet gatewayVPC와 인터넷 사이의 관리형 gateway다. Route만 있다고 모든 instance가 인터넷에 나가는 것은 아니며 public address와 policy도 맞아야 한다.
NAT gatewayPrivate source가 외부로 connection을 시작하도록 source address/port를 변환하고 reply state를 유지하는 관리형 middlebox다.
Public/private subnetAWS 문맥에서 public subnet은 internet gateway로 직접 향하는 route가 있고, private subnet은 직접 route가 없다. 이름 tag가 성질을 만들지 않는다.
Data plane실제 packet을 lookup·rewrite·forward하는 실행 경로다. Control plane 변경이 data plane 전체에 반영되기까지 짧은 convergence window가 있을 수 있다.
Flow logInterface/VPC traffic의 tuple, bytes, accept/reject 같은 metadata 기록이다. Payload나 application 성공을 증명하지는 않는다.

2. 왜 중요한가

Cloud network 장애는 “서버가 살아 있다”와 “요청이 도달한다” 사이의 control-plane 객체 하나만 틀려도 발생한다. Route, NAT, internet gateway, policy, DNS를 한 덩어리로 보면 안전한 복구가 어렵다.

  • 가용성: 하나의 NAT gateway를 여러 AZ가 공유하면 그 NAT의 AZ 장애가 다른 AZ의 egress까지 끊을 수 있다.
  • 정확성: Route table은 응답의 대칭성과 NAT state owner까지 자동 보장하지 않는다. 양방향 path를 따로 그려야 한다.
  • 성능·용량: NAT gateway는 bandwidth, packets per second, destination별 port allocation이라는 서로 다른 병목을 가진다.
  • 비용: Cross-AZ path, NAT 처리량, internet egress 비용은 아키텍처 선택과 직접 연결된다. Gateway endpoint 등 우회 경로가 더 안전하고 저렴할 수 있다.
  • 면접: 좋은 답변은 “public/private” 라벨이 아니라 route association, longest prefix match, target state, source translation과 failure domain을 설명한다.

  1. DNS: 목적지 IP를 얻지만 어느 route가 선택될지는 아직 결정하지 않는다.
  2. Private route lookup: 모든 일치 route 중 longest prefix match로 target을 고른다. Endpoint나 firewall appliance로 향하는 더 구체적인 route가 있으면 default NAT route보다 우선한다.
  3. NAT: 첫 packet에서 mapping과 port state를 만들고 source tuple을 바꾼다. 이 시점이 “외부에서 보이는 source”의 경계다.
  4. Public route lookup: NAT가 있는 subnet도 internet gateway로 향하는 route가 필요하다. Private table만 고쳐서는 충분하지 않다.
  5. Reply: Reply는 기존 mapping을 찾아야 하므로 NAT AZ와 state owner가 경로의 불변식이다.
  6. 성공 확정: Flow log ACCEPT나 SYN-ACK은 network 단계의 증거일 뿐이다. TLS/HTTP와 business commit은 뒤의 별도 성공 조건이다.
핵심 불변식: Source subnet이 의도한 route table과 연결되고, 선택 target이 Available이며, NAT와 public subnet의 다음 route가 유효하고, reply가 동일 NAT state로 돌아와야 한다. 이 중 하나라도 깨지면 application은 정상이어도 egress는 실패한다.

4. CS 수준 내부 동작

주소 공간과 격리

VPC의 private CIDR는 인터넷 전역에서 유일하지 않다. 격리는 주소 자체가 아니라 provider의 virtual routing/forwarding context, tenant identifier, encapsulation과 policy가 만든다. 두 VPC가 같은 10.0.0.0/16을 써도 독립적으로 동작하지만 peering·VPN·합병 시 overlap 때문에 route를 명확히 만들 수 없다.

Longest prefix match와 control-plane convergence

Route lookup을 단순화하면 destination IP와 각 prefix를 bitwise 비교하고 가장 긴 match를 선택한다. 10.20.0.0/16 → local, 10.20.2.0/24 → appliance, 0.0.0.0/0 → NAT가 있으면 10.20.2.7은 /24로 간다. Route 변경 API 성공은 control plane이 요청을 수락했다는 뜻이며, 기존 flow와 모든 data-plane replica가 즉시 같은 결과를 보장한다는 뜻은 아니다. 변경 전후의 짧은 failure window를 canary로 관찰한다.

Subnet은 broadcast LAN과 동일하지 않다

전통 Ethernet subnet에서는 ARP/ND와 broadcast domain을 떠올리지만 cloud VPC는 provider가 neighbor resolution과 forwarding을 가상화한다. “같은 subnet이면 switch 하나에서 broadcast”라고 단정하면 틀린다. 중요한 것은 source interface, destination address, subnet association, local route와 provider data plane이다.

NAT capacity model

AWS 공식 문서의 현재 수치에 따르면 NAT gateway는 각 IPv4 address마다 unique destination(IP, port, protocol)당 최대 55,000 simultaneous connection을 지원한다. 이를 모든 destination을 합친 무한 capacity로 오해하면 안 된다. required state ≈ active + connection_rate × state_lifetime로 hot destination별 peak를 계산하고 ErrorPortAllocation, IdleTimeoutCount, packets/bytes/drop과 retry rate를 함께 본다.

Data path와 비용 path

Private-A가 NAT-B를 쓰면 packet이 AZ 경계를 왕복할 수 있다. 이는 NAT-AZ 장애 상관관계와 cross-AZ data transfer 비용을 만든다. Object storage가 VPC endpoint를 지원한다면 NAT를 거치지 않는 더 구체적인 endpoint route로 state·비용·internet exposure를 줄일 수 있다. 다만 DNS, endpoint policy와 route association이 새 control plane이 된다.

7. 35분 실습: route 선택과 blackhole 실패를 namespace에서 재현

사전 조건: Docker Desktop/Engine과 Compose, 저장소 root. Client container에는 NET_ADMIN capability가 있다. 실행 전에 api의 IP와 default route 중 어느 route가 선택될지 예측한다.

0단계 · 시작과 control plane 확인 (6분)

make doctor
make up
make ps
docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client ip -4 addr show eth0
docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client ip route

예상: Connected prefix와 default gateway가 보인다. 이 table이 cloud subnet route table의 축소 모델이다.

1단계 · 실제 lookup 증거 (7분)

API_IP=$(docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec -T client getent hosts api | awk 'NR==1{print $1}')
echo "$API_IP"
docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client ip route get "$API_IP"
docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client curl -fsS http://api:8000/headers

예상: API destination에는 connected route가 default보다 구체적이므로 직접 interface가 선택되고 HTTP 200이 온다.

2단계 · 실패 주입: /32 blackhole (8분)

docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client ip route add blackhole "$API_IP/32"
docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client ip route get "$API_IP"
docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client curl -sv --max-time 4 http://api:8000/headers

예상: 더 구체적인 /32 blackhole이 connected prefix보다 우선해 즉시 unreachable/timeout이 난다. DNS와 API process는 정상이어도 route만으로 실패한다.

3단계 · rollback과 관찰 (8분)

docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client ip route del blackhole "$API_IP/32"
docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client ip route get "$API_IP"
docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client curl -fsS http://api:8000/headers

예상: Route 삭제 직후 connected route가 다시 선택되고 fresh connection이 성공한다. 이것이 작은 blast radius의 route rollback이다.

4단계 · 오류 처리와 cleanup (6분)

# add가 File exists라면 먼저 정확한 /32만 삭제한다.
docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client ip route del blackhole "$API_IP/32" 2>/dev/null || true
make down

자주 나는 오류: Operation not permitted이면 compose의 client NET_ADMIN 설정과 container 재생성을 확인한다. API_IP가 비어 있으면 make up 후 DNS를 확인한다. Cleanup은 broad route flush가 아니라 실습에서 추가한 정확한 /32만 삭제한다.

8. 놓치기 쉬운 함정

  • Subnet 이름이 public/private를 결정하지 않는다. 실제 route target과 public address 조건을 본다.
  • Route는 양방향 connection을 자동 보장하지 않는다. Reply path와 stateful middlebox를 별도로 확인한다.
  • Default route만 보면 안 된다. 더 구체적인 route가 항상 우선한다.
  • NAT gateway를 public subnet에 두는 것만으로 끝나지 않는다. Public table의 IGW route도 필요하다.
  • NAT는 inbound publish나 보안 인증 기능이 아니다.
  • Single NAT는 비용은 줄여도 AZ failure domain과 cross-AZ 비용을 키울 수 있다.
  • Flow log ACCEPT는 TLS/HTTP/DB commit 성공이 아니다.
  • Route API 성공과 즉시 전역 수렴은 같은 약속이 아니다. Canary와 timestamp가 필요하다.
  • IPv4 0.0.0.0/0는 IPv6 ::/0를 포함하지 않는다.

9. 대기업 기술 면접 질문

  1. “Private subnet의 request가 인터넷 API에 도달하는 전체 경로를 설명하세요.”
    좋은 답변 구조: DNS → source ENI/subnet → longest prefix route → same-AZ NAT mapping → public subnet route → IGW → reply state → socket → TLS/HTTP 성공 조건.
  2. “NAT gateway를 AZ마다 둘지 하나만 둘지 설계하세요.”
    좋은 답변 구조: RTO/가용성 요구 → traffic/connection 수치 → AZ 장애 상관관계 → cross-AZ/NAT 비용 → endpoint 대안 → metric·canary·rollback.
  3. “Route 변경 후 특정 destination만 timeout입니다. 어떻게 진단합니까?”
    좋은 답변 구조: source cohort·timestamp → 모든 matching prefix → longest match/target state → forward/reply flow log → NAT allocation/policy → safe one-subnet rollback → 대안.

10. 회상·확인 문제와 채점 기준

어제 내용 회상 3문제

  1. SNAT의 forward tuple과 reply 역변환에 필요한 핵심 state는 무엇인가?
  2. Conntrack ESTABLISHED가 application 성공을 증명하지 못하는 이유는?
  3. NAT port exhaustion을 active connection만으로 계산하면 놓치는 항은?

짧은 정답: ① Original/reply tuple과 NAT mapping·timeout이다. ② 중간 network state이며 server accept/read와 business commit은 endpoint/application 소유이기 때문이다. ③ Connection creation rate×state lifetime의 churn, retry, destination별 hot spot을 놓친다.

오늘 내용 확인 3문제

  1. /0 → NAT와 /24 → appliance가 모두 일치하면 어느 route가 선택되며 왜인가?
  2. Private-A가 NAT-B 하나를 공유할 때 생기는 가용성·비용 위험은?
  3. Flow log ACCEPT인데 curl이 실패할 수 있는 세 가지 후속 지점을 말하라.

짧은 정답: ① 더 긴 /24가 longest prefix match로 선택된다. ② NAT-B AZ 장애가 A egress도 끊고 cross-AZ 왕복·비용을 만든다. ③ NAT reverse state/port, TCP queue·timeout, TLS 인증/HTTP/application dependency 중 세 가지를 들 수 있다. 문항당 정의 1점, 내부 흐름 1점, failure·trade-off 1점으로 총 9점이다.
