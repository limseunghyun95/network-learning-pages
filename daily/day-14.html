회상: DNS 변경 rollout 계획

TTL에서 connection drain까지 Week 2 통합 복습 · 예상 학습 50분 + 실습 35분

한 줄 요약
DNS cutover는 record 한 줄을 바꾸는 일이 아니다. 기존 RRset의 남은 TTL, negative cache, 권한 서버 복제, resolver별 cache·serve-stale 정책, client cache, 기존 socket·connection pool이 서로 다른 시각에 끝나는 분산 상태 전이다. 성공은 새 IP가 한 번 조회된 때가 아니라 새·구 endpoint가 공존하는 failure window를 관측하고 rollback 가능한 상태로 종료한 때다.

1. 선수 용어 사전

Rollout / cutoverRollout은 변경을 작은 범위부터 단계적으로 확장하는 과정, cutover는 traffic의 주 대상을 old에서 new로 전환하는 사건이다. DNS 수정 시각 하나가 rollout 전체는 아니다.
TTLTime To Live. Resolver가 RRset을 다시 권한 서버에 묻지 않고 재사용할 수 있는 시간 예산이다. 이미 cache된 값의 남은 TTL은 나중에 권한 서버에서 TTL을 낮춰도 즉시 줄지 않는다.
Positive / negative cachePositive cache는 존재하는 RRset, negative cache는 NXDOMAIN 또는 NODATA 같은 부재 결과를 저장한다. 새 hostname을 record 생성 전에 조회하면 부재가 먼저 cache될 수 있다.
SOA / serialSOA는 zone의 관리 정보 RR이고 serial은 zone version을 나타낸다. 여러 authoritative server가 같은 serial과 intended RRset을 제공하는지 확인해야 한다.
Convergence여러 복제본·cache·client가 의도한 상태에 수렴하는 과정. “전 세계에 복사되는 DNS 전파” 한 단계가 아니라 owner마다 만료와 refresh 조건이 다르다.
Serve staleFresh TTL이 끝난 data라도 authoritative 장애 시 resolver 정책이 제한적으로 과거 answer를 제공하는 복원력 기능. Fresh cache와 별도의 기간·조건을 가진다.
Canary전체 traffic 전에 작은 resolver·region·client 집합으로 변경을 검증하는 표본. DNS answer뿐 아니라 connect·TLS·HTTP와 업무 SLO까지 확인한다.
Connection drainOld endpoint에 새 연결은 줄이되 기존 연결·in-flight request가 안전하게 끝날 시간을 주는 절차. DNS가 new IP를 반환해도 keep-alive pool은 old socket을 계속 쓸 수 있다.
Rollback window문제가 생겼을 때 old endpoint와 설정으로 안전하게 돌아갈 수 있도록 양쪽 호환성·capacity·관측을 유지하는 기간. DNS rollback도 새 answer TTL 때문에 즉시 완료되지 않는다.

2. 왜 중요한가

“TTL을 60초로 바꿨으니 1분 뒤 모두 new IP를 본다”는 운영 사고의 전형적인 출발점이다. T-5분에 TTL을 60으로 낮췄더라도 어떤 resolver가 T-6분에 old TTL 3600으로 cache했다면 그 entry는 최대 54분 더 유효할 수 있다. 권한 서버의 현재 TTL과 cache entry의 남은 TTL은 다른 상태다.

  • DNS 성공은 endpoint 성공이 아니다. Route·ARP/NDP·TCP·TLS·HTTP·application readiness가 뒤에 남는다.
  • Old와 new가 동시에 정상이어야 한다. Cache와 connection pool 때문에 양쪽 traffic은 일정 기간 필연적으로 공존한다.
  • 부재도 state다. 새 이름을 늦게 만들면 NXDOMAIN이 positive record보다 오래 관측될 수 있다.
  • Rollback도 또 하나의 rollout이다. New answer를 이미 cache한 client를 즉시 old로 되돌릴 수 없으므로 new endpoint도 복구 과정 동안 살아 있어야 한다.

3. 아키텍처 그림과 rollout 흐름

④ Resolver / client state

  1. 사전 하향: 새 TTL이 아니라 변경 전 old TTL만큼 기다려야 과거 cache entry의 상한이 끝난다. Resolver별 remaining TTL 표본을 저장한다.
  2. Canary: DNS를 우회해 new IP에 연결하되 TLS SNI와 HTTP Host는 production hostname으로 유지해 인증서·virtual host를 함께 시험한다.
  3. Cutover: Control plane의 “저장 성공”과 모든 authoritative replica의 answer/serial 수렴을 분리한다. 이때가 resolver cache 만료의 시작점이지 완료점이 아니다.
  4. Mixed window: Resolver는 entry별 남은 TTL, negative cache, stale 정책을 소유한다. Client/runtime이 별도 cache를 두면 DNS TTL보다 길 수도 있다.
  5. Data path: New IP를 받았어도 기존 keep-alive, HTTP/2, gRPC connection은 old endpoint에 남는다. DNS·connect·TLS·HTTP timestamp를 분리한다.
  6. 종료: “내 dig가 new”가 아니라 권한 서버 수렴, resolver 표본, old/new endpoint SLO, old connection age, rollback capacity라는 exit criteria를 만족해야 한다.

4. CS 수준 내부 동작

상태 소유권과 success boundary

상태 소유자불변식 · 성공이 확정되는 시점
DNS control plane원하는 RRset과 serial을 저장한다. API 200은 authoritative data path 반영 완료를 증명하지 않는다.
Authoritative replicas각 NS가 intended RRset·TTL·SOA serial을 AA=1로 답할 때 authority 수렴을 확인한다. Resolver cache는 아직 별개다.
Recursive resolverCache key와 expiry를 소유한다. Fresh entry는 권한 서버의 최신 변경보다 과거여도 TTL 동안 유효하다.
Stub / runtimeSearch expansion, resolver 선택, application-local cache를 소유한다. dig 결과가 JVM·browser·sidecar 결과와 같다는 보장은 없다.
Kernel / proxy pool이미 만들어진 5-tuple socket과 idle/max-age/in-flight state를 소유한다. DNS 재조회 없이 old endpoint를 계속 사용할 수 있다.
ApplicationHTTP 성공, 업무 처리, DB commit의 의미를 소유한다. TCP connect 성공만으로 rollout 성공을 확정하지 않는다.

시간 예산을 수식으로 방어하기

Old endpoint 안전 종료 시각의 보수적 하한
Tremove-old ≥ Tcutover + max(authority 수렴, cutover 시점 최대 remaining positive/negative TTL, client cache 상한, serve-stale 정책 window, connection max-age/drain grace, 관측 지연) + safety margin

수치 예시: 기존 TTL 3600초를 T-24h에 60초로 낮추고 old TTL 소진을 확인했다. Cutover 후 authority 수렴 90초, resolver remaining TTL 60초, runtime cache 300초, connection max-age 900초, 관측 지연 120초라면 max는 900초다. Safety margin 300초를 더해 old endpoint는 적어도 T0+20분까지 capacity와 호환성을 유지한다. Serve-stale이 장애 조건에서 1시간 가능하다면 그 정책을 별도 위험으로 포함하거나 old endpoint 종료 전 stale 제공을 통제해야 한다.

  • TTL은 push timer가 아니다. Cache entry가 언제 채워졌는지에 따라 만료 시각이 다르다.
  • CNAME chain은 한 덩어리가 아니다. CNAME RRset과 최종 A/AAAA RRset은 각각 cache되고 TTL도 다를 수 있다.
  • NXDOMAIN과 NODATA 범위는 다르다. 새 record를 만들기 전 negative answer가 관측됐는지와 SOA 기반 negative TTL을 확인한다.
  • Failure cache는 보호 장치다. SERVFAIL·timeout 때 무제한 retry하면 resolver와 authority QPS를 증폭시킨다.

5. 실무 설계 판단과 best practice

판단권장 기준과 이유
TTL 하향 시점적어도 기존 TTL과 권한 복제 지연보다 먼저 낮춘다. 현재 새 TTL만 보고 준비 완료로 판단하지 말고 여러 resolver의 remaining TTL을 표본 확인한다.
새 이름 출시Client 배포보다 record를 먼저 만들고 권한·recursive 양쪽에서 검증한다. 선조회로 NXDOMAIN이 cache될 가능성을 deployment 순서에 포함한다.
Canary 단위Resolver/region/runtime별 표본을 고른다. Public resolver 하나의 결과를 전체 사용자 대표로 취급하지 않는다.
양쪽 호환성Old/new가 같은 schema·TLS identity·session semantics를 지원하고 각각 예상 혼합 traffic을 감당하게 한다. Stateful migration은 DNS보다 data compatibility가 먼저다.
관측authoritative serial/RRset, resolver RCODE·answer·TTL·latency, endpoint별 connect/TLS/HTTP, connection age, business SLO를 같은 timeline에 둔다.
Rollback trigger“오류가 많아 보임”이 아니라 new endpoint error budget, latency, saturation, DNS SERVFAIL/NXDOMAIN 비율의 수치 threshold와 결정권자를 사전에 정한다.
TTL 복원안정화와 rollback window 종료 후 평시 TTL로 복원한다. 낮은 TTL을 영구 유지하면 authority QPS·latency·장애 의존성이 커질 수 있다.
Anti-pattern: 전체 resolver cache flush, TTL=0 남발, old endpoint 즉시 종료, DNSSEC 검증 해제, public resolver 하나만 확인, rollback 때 다시 record만 원복하는 방식은 증거를 없애거나 혼합 상태의 피해를 키운다.

6. 장애 대응 표

상황: DNS cutover 5분 뒤 일부 region은 new IP, 일부는 old IP, 일부 runtime은 NXDOMAIN이며 new endpoint 5xx와 old endpoint connection이 동시에 남아 있다.

순서실행 내용
증상Region/resolver/runtime/QTYPE별 old·new·NXDOMAIN·SERVFAIL 비율과 endpoint별 connect/TLS/HTTP/business error를 분리한다.
먼저 수집할 증거/지표모든 authoritative NS의 AA answer·TTL·SOA serial, resolver별 raw dig와 remaining TTL, SOA negative TTL, stale/failure-cache log, client resolver 설정, old/new connection age·pool·SLO, 변경 audit timestamp를 저장한다.
가능한 가설TTL 사전 하향 대기 누락, NS serial drift, split view 오배포, pre-created NXDOMAIN, stale serve, CNAME chain TTL 차이, runtime cache, connection pool reuse, new capacity/TLS/readiness 문제다.
안전한 첫 조치추가 확대를 멈추고 old/new endpoint를 모두 유지한다. 정상 resolver·region canary에서 DNS→connect→TLS→HTTP를 재검증하고 new traffic을 가역적으로 줄이며 retry를 bounded backoff로 제한한다.
Rollback/복구Known-good RRset/view/serial로 원복하되 new endpoint도 rollback TTL·pool window 동안 유지한다. Authority 수렴→resolver remaining TTL 감소→old SLO 회복→new connection drain 순으로 확인한다.
하지 말아야 할 조치전체 cache flush·resolver 재시작, TTL 0, old/new 중 한쪽 즉시 종료, 무제한 retry, DNSSEC 해제, pcap 무제한 수집, “전파가 덜 됨”으로 모든 가설을 뭉뚱그리지 않는다.

7. 35분 재현 실습: authority=new, recursive=old

목표: 로컬 authoritative DNS와 recursive cache를 분리해 cutover 직후 두 resolver가 서로 다른 정답을 동시에 제공하는 정상적인 mixed-answer window를 관찰하고 종료 조건을 계산한다.

사전 조건: Docker Desktop과 이 저장소. 터미널 2개를 사용하며 저장소 root에서 실행한다. 실습은 container의 /tmp만 사용한다.

0단계 · 먼저 예측 (3분)

  1. Recursive가 old IP를 30초 TTL로 cache한 뒤 authority를 new IP로 바꾸면 첫 recursive answer는 무엇일까?
  2. Authority direct query가 new여도 recursive old가 장애 증거일까?
  3. DNS TTL이 끝나기 전에 old HTTP endpoint를 끄면 어떤 client가 실패할까?

1단계 · 두 DNS 계층 시작 (8분)

make up
docker compose -f labs/basic-network-observability/docker-compose.yml exec client sh -lc "printf '%s\n' 'port=5354' 'listen-address=127.0.0.1' 'bind-interfaces' 'no-resolv' 'no-hosts' 'local=/rollout.test/' 'host-record=api.rollout.test,172.28.0.20' 'local-ttl=30' > /tmp/day14-auth.conf; dnsmasq --conf-file=/tmp/day14-auth.conf --pid-file=/tmp/day14-auth.pid"
docker compose -f labs/basic-network-observability/docker-compose.yml exec client sh -lc "printf '%s\n' 'port=5353' 'listen-address=127.0.0.1' 'bind-interfaces' 'no-resolv' 'no-hosts' 'server=127.0.0.1#5354' 'cache-size=100' > /tmp/day14-rec.conf; dnsmasq --conf-file=/tmp/day14-rec.conf --pid-file=/tmp/day14-rec.pid"

예상 관찰: 5354는 권한 역할, 5353은 이를 upstream으로 쓰는 cache 역할이다. 실제 production의 전체 DNSSEC·replication을 복제하지 않고 cache state transition만 격리한다.

2단계 · Old answer를 cache (5분)

docker compose -f labs/basic-network-observability/docker-compose.yml exec client dig @127.0.0.1 -p 5354 api.rollout.test A +noall +answer +comments
docker compose -f labs/basic-network-observability/docker-compose.yml exec client dig @127.0.0.1 -p 5353 api.rollout.test A +noall +answer +comments
docker compose -f labs/basic-network-observability/docker-compose.yml exec client curl -sS http://172.28.0.20:8000/health

예상 관찰: 두 DNS가 172.28.0.20과 약 30초 TTL을 반환하고 recursive가 RRset을 cache한다. 마지막 요청은 old endpoint readiness를 확인한다.

3단계 · 실패 주입: TTL 중간에 cutover (10분)

docker compose -f labs/basic-network-observability/docker-compose.yml exec client sh -lc "kill \$(cat /tmp/day14-auth.pid); sed -i 's/172.28.0.20/172.28.0.30/' /tmp/day14-auth.conf; dnsmasq --conf-file=/tmp/day14-auth.conf --pid-file=/tmp/day14-auth.pid"
docker compose -f labs/basic-network-observability/docker-compose.yml exec client dig @127.0.0.1 -p 5354 api.rollout.test A +noall +answer +comments
docker compose -f labs/basic-network-observability/docker-compose.yml exec client dig @127.0.0.1 -p 5353 api.rollout.test A +noall +answer +comments
docker compose -f labs/basic-network-observability/docker-compose.yml exec client curl -sS http://172.28.0.30:8080/health

예상 관찰: Authority 5354는 new 172.28.0.30, recursive 5353은 TTL이 남은 동안 old 172.28.0.20을 답한다. 두 answer는 각자 상태에 비추어 정상이다. 약 31초 뒤 recursive를 다시 조회하면 new로 refresh된다. Web endpoint의 health path가 구현과 다르면 curl -I http://172.28.0.30:8080/으로 readiness를 확인한다.

4단계 · Runbook과 cleanup (9분)

다음 열로 1페이지 표를 만든다: phase | owner | expected old/new/negative state | evidence | wait bound | rollback action | exit criteria. TTL 30초, runtime cache 60초, connection max-age 120초, 관측 지연 30초, safety 30초라면 old 종료 하한을 계산한다. 답은 max(30,60,120,30)+30=150초다.

docker compose -f labs/basic-network-observability/docker-compose.yml exec client sh -lc "test ! -f /tmp/day14-rec.pid || kill \$(cat /tmp/day14-rec.pid); test ! -f /tmp/day14-auth.pid || kill \$(cat /tmp/day14-auth.pid); rm -f /tmp/day14-rec.conf /tmp/day14-auth.conf /tmp/day14-rec.pid /tmp/day14-auth.pid"
make down
  • dnsmasq: failed to create listening socket: 이전 실습 process가 남았는지 PID를 확인하고 cleanup 후 재시도한다.
  • Recursive가 바로 new: 첫 recursive query로 old를 cache하지 않았거나 30초가 이미 지났다. cleanup 후 단계 순서를 지킨다.
  • New HTTP health 실패: 이는 DNS와 별도 data-path 실패다. IP·port·path와 container 상태를 확인하고 rollout 종료를 선언하지 않는다.
  • sed -i 차이: 이 명령은 Alpine container 내부에서 실행된다. Host macOS의 BSD sed와 혼동하지 않는다.

8. 놓치기 쉬운 함정

  • 권한 서버의 현재 TTL과 이미 cache된 remaining TTL을 혼동하지 않는다.
  • 낮은 TTL이 정확히 지켜진다고 절대 단정하지 않는다. Runtime·proxy·resolver가 별도 cache 최소/최대 정책을 가질 수 있어 실측이 필요하다.
  • A만 바꾸고 AAAA를 잊지 않는다. Dual-stack client는 IPv6 경로로 계속 old 또는 broken endpoint를 선택할 수 있다.
  • CNAME만 보고 최종 A/AAAA TTL을 놓치지 않는다. Chain의 각 RRset은 독립 state다.
  • 새 hostname의 NXDOMAIN 선조회를 무시하지 않는다. 부재 cache가 끝나기 전까지 record 생성 후에도 일부 client는 실패한다.
  • DNS 결과 비율을 traffic 비율로 착각하지 않는다. Client 수·QPS·connection reuse가 달라 answer 표본과 실제 request 분포는 다르다.
  • Old connection 0을 DNS만으로 기다리지 않는다. Pool max-age, idle timeout, graceful drain과 long-lived stream을 별도로 통제한다.
  • Rollback을 즉시 스위치로 표현하지 않는다. Old와 new answer·socket이 다시 공존하므로 양쪽을 유지해야 한다.

9. 대기업 기술 면접 질문

  1. “TTL 1시간인 서비스를 5분 내 안전하게 새 IP로 전환하세요.”
    좋은 답변 구조: 5분 요구가 기존 cache와 모순인지 확인 → 사전 TTL 하향과 old TTL 대기 → new endpoint compatibility/capacity → authority canary → mixed window → pool drain → 수치 exit criteria → DNS 이외 LB/weighted 대안.
  2. “DNS를 원복했는데 왜 장애가 계속됩니까?”
    좋은 답변 구조: rollback도 cache되는 새 state → authority serial → resolver positive/negative/stale → runtime cache → old/new connection pool → endpoint별 SLO → remaining TTL과 max-age 기반 복구 시간.
  3. “DNS rollout runbook을 설계하고 실패 주입까지 설명하세요.”
    좋은 답변 구조: 요구사항·RTO/SLO·QPS 가정 → owner/불변식 지도 → T-24h/T0/T+ phase → authoritative/recursive/client/pool evidence → NXDOMAIN·stale·NS drift·new 5xx 주입 → rollback trigger → postmortem과 TTL 복원.

10. 회상·확인 문제와 채점 기준

어제 내용 회상 3문제

  1. dig +trace 성공과 production recursive resolver 성공은 왜 같은 증거가 아닌가?
  2. NXDOMAIN, SERVFAIL, timeout은 packet과 cache 관점에서 무엇이 다른가?
  3. TC=1을 받은 뒤 DNS success는 언제 확정되는가?

짧은 정답: ① Trace는 client가 delegation path를 직접 따라가며 recursive의 cache·policy·view를 복제하지 않는다. ② NXDOMAIN은 유용한 부재 응답이라 negative cache 가능, SERVFAIL은 해석 실패 응답, timeout은 deadline 안에 응답을 못 받은 상태다. ③ TCP fallback 등으로 complete message를 받고 question/RCODE/validation을 통과한 때다.

오늘 내용 확인 3문제

  1. TTL 3600을 cutover 5분 전에 60으로 낮추면 왜 1분 전환을 보장하지 못하는가?
  2. Authoritative=new, recursive=old가 동시에 정상일 수 있는 조건은?
  3. Old endpoint 종료 시각에 DNS TTL 외에 포함할 상태 세 가지는?

짧은 정답: ① 과거 3600으로 cache된 entry의 remaining TTL은 권한 TTL 변경으로 줄지 않는다. ② Recursive의 old cache가 fresh TTL 안에 있고 authority는 cutover를 반영한 경우다. ③ Client/runtime cache, serve-stale window, connection max-age·drain grace, authority 수렴·관측 지연 중 세 가지다. 문항당 정의 1점, owner/state transition 1점, 수치·장애·trade-off 1점으로 총 9점이다.

Week 2 최종 90초 답변

“DNS 변경은 control plane write, authoritative replica, recursive positive·negative·stale cache, stub/runtime cache, connection pool이 각자 수렴하는 분산 상태 전이다. 먼저 기존 TTL보다 일찍 target TTL을 낮추고 old entry 소진을 표본 확인한다. New endpoint를 IP direct+SNI/Host로 검증한 뒤 authoritative RRset과 SOA serial을 cutover하고 resolver·region·QTYPE별 answer/TTL/RCODE를 본다. 동시에 old/new의 connect·TLS·HTTP·business SLO와 connection age를 추적한다. Old 종료 시각은 remaining TTL, client cache, stale 정책, pool max-age, 관측 지연의 max에 safety margin을 더해 정한다. 문제가 나면 확대를 멈추고 양쪽 endpoint를 유지한 채 known-good RRset으로 원복하며 rollback TTL과 pool window가 끝날 때까지 양쪽을 운영한다.”
