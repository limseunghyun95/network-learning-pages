PROXY · LB · NAT · CLOUD NETWORK · WEEK 5 / DAY 30

L4/L7 LB, health check, stickiness

선택 단위·건강 상태·affinity의 소유자를 분리한다 · 개념 65분 + 실습 35분

한 줄 요약
L4 LB는 주로 flow의 IP·port 같은 transport 정보로 connection의 backend를 고르고, L7 LB는 종료한 HTTP connection 안에서 request·stream별로 backend를 고를 수 있다. Health check는 실제 요청과 다른 synthetic control path이고, stickiness는 부하 분산보다 affinity를 우선하는 상태이므로 선택 key·유효 기간·장애 시 fallback을 명시해야 한다.

1. 선수 용어 사전

Load balancer여러 backend 후보 중 새 packet·flow·request를 처리할 대상을 선택하는 구성요소. 단순 분산뿐 아니라 장애 격리, capacity 조절, TLS·policy 경계 역할도 한다.
L4 / L7L4는 TCP/UDP transport 정보, L7은 HTTP 같은 application protocol 의미를 가리킨다. 제품 이름이 아니라 실제로 어느 protocol을 parse·terminate하는지가 기준이다.
5-tuplesource IP·source port·destination IP·destination port·protocol. L4 flow를 구별하는 대표 key이며 구현에 따라 일부 field나 다른 salt가 추가될 수 있다.
VIP / backendVIP는 client가 접속하는 virtual IP, backend는 실제 처리를 맡는 server endpoint다. VIP가 살아 있어도 모든 backend가 건강하다는 뜻은 아니다.
Active health checkLB가 주기적으로 TCP connect, HTTP request, gRPC call 등을 보내 건강 상태를 직접 측정하는 synthetic traffic.
Passive check실제 user traffic의 connect failure, reset, 5xx, latency를 관찰해 backend를 outlier로 판단하는 방식.
Readiness / livenessReadiness는 지금 새 traffic을 받아도 되는지, liveness는 process를 재시작할 만큼 복구 불가능한지를 묻는다. 같은 endpoint로 섞으면 장애를 키울 수 있다.
Healthy threshold연속 몇 번 성공해야 healthy로 복귀하는지 정하는 값. Unhealthy threshold와 함께 flapping을 줄이는 hysteresis를 만든다.
Stickiness / affinity같은 client/session/key를 같은 backend로 보내려는 규칙. Cookie, source IP, consistent hash key, LB state table로 구현한다.
Consistent hashingBackend 집합이 바뀔 때 key 전체가 재배치되지 않도록 이동 범위를 줄이는 hash 계열 기법. 균등 분산과 최소 이동은 별도 검증해야 한다.
Drain / deregistration delay새 선택에서는 제외하되 기존 connection·request가 제한 시간 안에 끝나도록 기다리는 전이 상태.
Control path / data pathControl path는 discovery·health·weight·membership을 갱신하고, data path는 실제 packet/request를 전달한다. 둘의 갱신 지연이 failure window를 만든다.

2. 왜 중요한가

LB 장애는 “서버 몇 대에 나눠 준다”로는 설명되지 않는다. 선택 단위가 connection인지 request인지, health state를 누가 언제 갱신하는지, sticky key가 어느 backend set을 전제로 하는지에 따라 증상과 복구가 달라진다.

  • 가용성: 너무 느린 health check는 실패 backend로 계속 보내고, 너무 민감한 check는 일시적 지연에 healthy backend를 모두 제거한다.
  • 성능: Round robin은 request 비용이 균일하다는 가정이 있고, least-connections도 HTTP/2 stream 수나 backend queue를 모르면 실제 부하를 오판한다.
  • 정확성: Sticky backend에 session state를 두면 장애·scale-in 때 session이 사라지고 hot key가 한 server를 과부하시킬 수 있다.
  • 보안: L7 LB는 TLS plaintext와 cookie/header를 보므로 key·PII·로그 redaction 경계를 소유한다.
  • 면접: 좋은 답변은 알고리즘 이름보다 key, granularity, state owner, convergence time, failure fallback과 관측 지표를 연결한다.

  1. Membership: Service discovery가 endpoint를 추가해도 모든 LB node가 동시에 알지는 않는다. Health check가 통과하기 전 ready set과 configured set은 다를 수 있다.
  2. 도달: DNS·route 성공은 VIP listener 도달만 말한다. Backend selection과 application readiness는 이후 단계다.
  3. L4 선택: 보통 새 flow의 첫 packet에서 hash/table로 backend를 정하고 같은 flow를 고정한다. Packet마다 round robin하면 TCP reorder와 path disruption을 만들 수 있다.
  4. L7 선택: LB가 TLS/HTTP endpoint가 되므로 동일 downstream HTTP/2 connection의 서로 다른 stream을 서로 다른 backend connection에 전달할 수 있다.
  5. Affinity: Sticky key는 후보 set이 그대로일 때만 안정적이다. Backend 제거 시 cookie mapping이 무효가 되거나 hash가 재배치된다.
  6. Feedback: 실제 traffic 실패는 passive health로 control state를 바꿀 수 있다. 이 feedback이 너무 공격적이면 장애 시 traffic이 남은 backend로 몰리는 load concentration을 만든다.
핵심 불변식: 선택 결과는 그 시점의 healthy backend set과 selection key에 대한 함수다. Health state가 바뀌면 같은 client라도 결과가 달라질 수 있으며, 기존 connection의 backend와 새 request의 backend는 별도로 추적해야 한다.

4. CS 수준 내부 동작

선택 granularity가 state machine을 결정한다

단위선택 key·state·trade-off
PacketECMP/LAG가 header hash로 path를 고른다. Flow-stable hash가 일반적이며 next-hop set 변화는 flow remapping을 일으킨다.
Flow/connection5-tuple→backend mapping, conntrack/NAT/timeout을 소유한다. Long-lived connection 하나가 backend load를 오래 고정할 수 있다.
Request/streamHost/path/header/cookie와 healthy set으로 선택한다. 더 정교하지만 parse·TLS·pool·queue 비용과 retry ambiguity를 소유한다.

알고리즘은 측정값의 의미보다 정확하지 않다

  • Round robin: 단순하고 state가 작지만 request cost와 connection length가 균일하다는 가정이 있다.
  • Least connections: Active connection 수를 proxy로 쓰지만 H2의 한 connection에 수백 stream이 있으면 work를 과소평가할 수 있다.
  • Weighted: 이질적인 capacity를 반영하지만 weight 변경과 in-flight work 사이의 지연을 고려해야 한다.
  • Hash: Key affinity를 주지만 skewed tenant/key가 hot backend를 만든다. Modulo-N은 backend 수 변화 때 대규모 remapping이 생길 수 있다.
  • Power of two choices: 임의 두 후보의 load를 비교해 작은 쪽을 고르면 full scan 없이 tail load를 줄일 수 있지만 metric 신선도가 필요하다.

Health check도 분산 시스템이다

Interval이 I, timeout이 T, 연속 실패 threshold가 F라면 최악의 감지 시간은 대략 scheduler jitter를 제외하고 I×F+T 범위가 될 수 있다. 그 뒤 control state 전파와 기존 connection drain 시간이 더해진다. 복귀는 success threshold를 따로 둬 flapping을 막는다.

TCP connect check는 listener만 증명하고, HTTP shallow check는 handler만 증명한다. 반대로 모든 DB·queue dependency를 readiness에 넣으면 공유 dependency의 작은 흔들림이 모든 backend를 동시에 제거한다. “새 traffic을 받아 처리할 최소 능력”을 검증하되 dependency failure를 별도 degraded state와 application SLO로 관측한다.

Stickiness는 숨은 distributed state다

Cookie 방식은 mapping state를 client에 둘 수 있고, table 방식은 LB memory와 replica synchronization을 요구한다. Source-IP affinity는 NAT/기업 proxy 뒤 다수 사용자를 한 key로 뭉친다. Stateless service가 가능하면 session은 공유 store/token으로 옮기고 affinity를 optimization으로 낮추는 편이 장애 복구에 유리하다.

7. 35분 실습: L4 health와 L7 readiness의 차이·hash remapping 관찰

사전 조건: Docker Desktop/Engine과 Compose, 저장소 root. 실행 전에 “TCP connect가 성공하지만 HTTP 503인 backend를 LB가 healthy로 봐도 되는가?”와 backend 수가 3→2가 될 때 modulo hash key가 얼마나 이동할지 예측한다.

0단계 · 시작과 baseline (5분)

make doctor
make up
make ps

예상: client, dns, api, web, proxy가 실행되고 api:8000이 listen한다. 여기까지는 process/listener와 network path의 일부만 증명한다.

1단계 · L4 connect check와 L7 response 비교 (8분)

docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client nc -vz api 8000

docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client curl -sv http://api:8000/status/503

예상: TCP connect는 성공하지만 HTTP는 503이다. Connect-only check가 application readiness를 과대평가할 수 있음을 보여준다. 반대로 503 endpoint 하나만으로 process liveness 실패를 선언해서도 안 된다.

2단계 · 실제 proxy path와 backend 증거 (7분)

docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client curl -sS -D - http://proxy:8080/api/headers

docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client curl -sS -D - http://proxy:8080/web/plain

예상: X-Lab-Upstream이 api:8000과 web:8080을 구분한다. L7 path가 backend selection key가 될 수 있고, client가 본 하나의 proxy endpoint 뒤에 서로 다른 upstream connection이 있음을 확인한다.

3단계 · 실패 주입과 control-state 지연 생각하기 (7분)

docker compose -f labs/basic-network-observability/docker-compose.yml stop api

docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client sh -c 'nc -vz -w 2 api 8000; true'

docker compose -f labs/basic-network-observability/docker-compose.yml \
  exec client curl -sv --max-time 7 http://proxy:8080/api/headers

예상: Direct connect는 실패하고 proxy는 upstream 실패를 502로 합성한다. 실제 LB라면 마지막 성공 check부터 unhealthy threshold·state 전파까지 일부 request가 실패 backend를 선택할 수 있다.

4단계 · Modulo hash remapping과 cleanup (8분)

for key in alice bob carol dave erin frank; do
  h=$(printf '%s' "$key" | cksum | awk '{print $1}')
  printf '%-6s N=3:%s N=2:%s\n' "$key" "$((h % 3))" "$((h % 2))"
done

docker compose -f labs/basic-network-observability/docker-compose.yml start api
make down

예상: Backend 수만 바꿨는데 많은 key의 index가 이동한다. 이것이 local session/cache miss와 재로그인을 만들 수 있다. 자주 나는 오류: nc가 오래 기다리면 -w 2를 확인하고, proxy가 502가 아니면 api를 실제로 stop했는지 make ps로 본다. Docker 권한 오류는 daemon/context를 확인한다.

8. 놓치기 쉬운 함정

  • L4가 반드시 pass-through는 아니다. Connection proxy/NAT 형태면 L4에서도 양쪽 connection state를 소유할 수 있다.
  • L7 LB는 connection마다 한 backend가 아니다. HTTP/2 stream·HTTP request별 재선택이 가능하다.
  • Healthy는 binary truth가 아니다. 특정 관측자·시점·endpoint·threshold의 결과다.
  • Health path가 너무 얕으면 false positive, 너무 깊으면 correlated false negative가 난다.
  • Source-IP affinity는 user affinity가 아니다. NAT·mobile carrier·proxy가 많은 user를 하나로 묶는다.
  • Least connections는 least work가 아니다. Stream 수, request cost, backend queue가 다를 수 있다.
  • Scale-in은 capacity만 줄이지 않는다. Hash ring·cookie mapping·long-lived flow를 재배치한다.
  • Passive ejection은 positive feedback이 될 수 있다. 일부 제거→남은 곳 과부하→추가 제거 순환을 제한한다.
  • Retry는 LB selection과 곱해진다. 다른 backend 선택이 duplicate side effect를 없애지 않는다.

9. 대기업 기술 면접 질문

  1. “L4와 L7 load balancer의 차이를 packet부터 application까지 설명하세요.”
    좋은 답변 구조: 요구 protocol·source preservation → selection granularity/key → termination과 connection graph → health/data path → TLS·observability → 비용·failure scope → 계층화 대안.
  2. “서버는 정상인데 health check만 실패합니다. 어떻게 설계·진단합니까?”
    좋은 답변 구조: 정상의 정의 → check source DNS/route/TLS/Host/path/auth → timestamp·threshold·state age → 실제 user path 비교 → safe drain/canary → rollback → shallow/deep check trade-off.
  3. “Sticky session이 필요한 서비스를 10배 scale-out하세요.”
    좋은 답변 구조: session owner·key cardinality → cookie/IP/table/hash 비교 → hot key·NAT → backend set 변화/remapping → external session store/token → drain·TTL·fallback → migration metric.

10. 회상·확인 문제와 채점 기준

어제 내용 회상 3문제

  1. Forward proxy와 reverse proxy를 누가 선택하고 누구 대신 보이는가?
  2. Message-aware proxy를 지날 때 connection state가 어떻게 분리되는가?
  3. Client가 보낸 X-Forwarded-For를 그대로 신뢰하면 안 되는 이유는?

짧은 정답: ① Forward는 client/조직이 선택하고 reverse는 service operator가 origin처럼 배치한다. ② Downstream/upstream 5-tuple·TLS·pool·queue·timeout은 독립이다. ③ Header는 client가 위조할 수 있어 trusted edge가 제거·재작성한 hop만 신뢰해야 한다.

오늘 내용 확인 3문제

  1. 같은 HTTP/2 downstream connection의 request가 다른 backend로 갈 수 있는 이유는?
  2. Interval 5초, timeout 2초, 실패 threshold 3이면 감지 지연을 어떻게 추정하고 무엇을 더해야 하는가?
  3. Source-IP stickiness가 hot backend를 만드는 두 상황과 대안은?

짧은 정답: ① L7 LB가 stream/request를 parse해 upstream pool에서 개별 선택하기 때문이다. ② 대략 최대 5×3+2초에 scheduler jitter, control 전파, drain을 더한다. ③ NAT/proxy 뒤 다수 user와 skewed IP traffic이며 signed cookie/tenant key, consistent hash, session externalization을 검토한다. 문항당 정의 1점, state/flow 1점, failure·trade-off 1점으로 총 9점이다.
