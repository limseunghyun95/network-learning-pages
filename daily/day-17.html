COMPUTER NETWORKING · WEEK 3 / DAY 17

receive window와 flow control

느린 consumer가 sender까지 멈추는 backpressure 경로 · 예상 학습 55분 + 실습 35분

한 줄 요약
TCP flow control은 receiver가 ACK의 advertised receive window(rwnd)로 “ACK number부터 몇 byte를 더 받을 수 있는가”를 알리고 sender가 그 오른쪽 경계를 넘지 않게 하는 hop-to-hop feedback이다. Application이 늦게 읽으면 receive buffer가 차고 rwnd가 줄어 zero window가 될 수 있으며, 이 backpressure는 send buffer·thread·connection pool·upstream queue까지 전파된다.

1. 선수 용어 사전

Flow control빠른 sender가 느린 receiver의 memory를 넘치게 하지 않도록 receiver capacity를 feedback하는 제어다. Network 전체 혼잡을 다루는 congestion control과 목적·상태 소유자가 다르다.
Receive bufferReceiver kernel이 아직 application에 전달하지 못한 byte와 out-of-order byte 등을 보관하는 per-socket memory. 정확한 accounting과 autotuning은 OS·버전에 따라 다르다.
Send bufferSender kernel이 아직 전송하지 못했거나 ACK되지 않은 application byte를 보관하는 per-socket memory. write() 성공은 peer 수신 완료가 아니라 이 buffer에 맡겼다는 뜻일 수 있다.
rwndReceive window. Receiver가 TCP Window field로 광고한 수신 허용 범위다. ACK=N, rwnd=W이면 N부터 N+W-1까지 받을 의사가 있다는 뜻이다.
cwndCongestion window. Sender가 network 혼잡을 피하려고 자체적으로 제한하는 in-flight 양이다. Receiver가 보내는 값이 아니라 sender congestion-control 상태다.
In-flight data보냈지만 아직 cumulative/SACK 증거로 확인되지 않은 network상의 byte. 단순히 send buffer 전체와 같지 않다.
Sliding windowACK가 전진하고 새 window가 광고될 때 sender가 보낼 수 있는 sequence 범위의 왼쪽·오른쪽 경계가 이동하는 방식이다.
Window Scale16-bit Window field의 약 64KiB 한계를 넘기기 위해 SYN에서 방향별 shift count를 협상하는 TCP option. 실제 window는 field를 협상된 만큼 왼쪽 shift해 해석한다.
Zero windowReceiver가 현재 새 data를 받을 공간이 없다고 win=0을 광고한 상태다. Connection 종료가 아니라 일시 정지 신호다.
Persist / window probeZero-window 뒤 window update가 유실되어 양쪽이 영원히 기다리는 deadlock을 피하려 sender가 작은 probe를 주기적으로 보내 receiver의 현재 window를 다시 확인하는 메커니즘이다.
BackpressureDownstream이 처리할 수 없을 때 upstream의 생산 속도를 늦추는 압력. TCP rwnd는 connection 한 구간의 backpressure이고 application queue·stream demand·rate limit은 더 위 계층의 별도 장치다.
BDPBandwidth-Delay Product. 대역폭×RTT로, path를 계속 채우는 데 필요한 대략적인 in-flight data 양이다. Window가 BDP보다 작으면 loss가 없어도 link를 다 쓰지 못한다.

2. 왜 중요한가

“Network는 멀쩡한데 upload가 멈췄다”는 현상은 receiver application이 socket을 읽지 않아 생긴 정상적인 flow control일 수 있다. 반대로 rwnd가 충분한데 전송이 느리면 congestion, sender application, pacing, loss, CPU를 찾아야 한다. 둘을 분리하면 엉뚱한 MTU·timeout 변경을 피한다.

  • Memory safety: Receiver는 무한히 빠른 sender의 byte를 모두 저장할 수 없다. rwnd는 sequence-space 경계로 수신 memory를 보호한다.
  • Throughput: 1Gbps, RTT 100ms path의 BDP는 약 12.5MB다. Window가 65,535B에 묶이면 이상적 상한도 약 5.24Mbps여서 Window Scale이 필요하다.
  • 장애 위치: Zero window는 packet drop이 아니라 “receiver TCP가 공간 부족을 광고했다”는 증거다. 왜 application이 읽지 못했는지는 CPU, GC, lock, disk/DB, downstream queue에서 찾아야 한다.
  • 분산 시스템: Proxy가 양쪽 TCP를 terminate하면 backend의 zero window가 곧바로 client rwnd가 되지 않는다. Proxy buffer가 먼저 차고 난 뒤 client-side read를 늦추는 별도 backpressure 경로가 형성된다.

  1. Receiver가 경계를 소유한다. ACK field는 다음 기대 sequence, Window field는 그 지점부터 받을 octet 수다. Sender가 임의로 늘릴 수 없다.
  2. Sender는 두 제약을 동시에 지킨다. Receiver 용량 rwnd와 network 용량 cwnd 중 작은 범위에서 이미 in-flight인 양을 빼고 새 전송 가능량을 구한다.
  3. Application stall이 packet에 드러난다. Receiver kernel이 byte를 정상 수신·ACK했어도 application이 읽지 않으면 free space가 줄어 win=0이 된다.
  4. Window update도 유실될 수 있다. 그래서 zero-window sender는 persist/probe로 현재 window를 다시 묻는다. Probe는 장애를 고치는 data flood가 아니다.
  5. Backpressure가 위로 이동한다. Sender send buffer가 차면 blocking write는 잠들고 nonblocking write는 EAGAIN을 낼 수 있다. Runtime queue와 request pool이 무제한이면 그곳에서 memory가 대신 터진다.
성공 경계: ACK가 전진하면 receiver TCP가 byte를 연속 수신했다. Window가 다시 열리면 receiver가 buffer 공간을 제공한다. 둘 다 application의 business 처리 완료를 뜻하지 않는다. Flow control의 불변식은 sender가 receiver가 광고한 sequence-space 오른쪽 경계를 넘지 않는 것이다.

4. CS 수준 내부 동작

Window는 buffer 크기와 같지만은 않다

개념적으로 available receive space가 rwnd의 기반이지만 OS는 metadata, out-of-order queue, memory pressure, autotuning, application의 low-water mark를 함께 고려한다. 따라서 SO_RCVBUF=1MB라고 매 ACK가 정확히 1MB window를 광고한다고 단정하면 안 된다. Packet의 Window field와 scale, ss -tinm의 socket memory를 함께 본다.

상태Owner와 의미
RCV.NXTReceiver TCP가 다음으로 기대하는 sequence. Receive window의 왼쪽 경계이자 ACK number의 기반이다.
RCV.WNDReceiver가 수신할 수 있는 octet 수. 오른쪽 경계는 개념적으로 RCV.NXT+RCV.WND다.
SND.UNASender가 아직 ACK받지 못한 가장 오래된 sequence. ACK 전진 시 send buffer를 회수할 기준이다.
SND.NXTSender가 다음에 전송할 sequence. 광고 window와 congestion 경계를 넘지 않아야 한다.
SND.WNDSender가 마지막으로 유효하게 받아들인 peer advertised window. 오래되거나 재정렬된 window update를 함부로 적용하지 않도록 ACK/sequence 문맥을 사용한다.

16-bit Window와 Window Scale

TCP header의 Window field는 16-bit unsigned 값이라 scale이 없으면 최대 65,535다. RFC 7323 Window Scale option은 SYN에서 방향별 shift count를 협상하며 최대 shift는 14다. 예를 들어 field 32,768과 shift 8이면 effective window는 32,768×256=8,388,608B다. SYN·SYN-ACK 자체의 Window field는 scale하지 않고, option이 성공적으로 교환된 뒤 후속 segment에 적용한다.

Scale은 buffer를 만들어 주지 않는다. 큰 BDP path의 표현 범위를 넓힐 뿐이며 실제 window는 memory·autotuning·application read 속도에 의해 달라진다. SYN에서 option이 빠지면 connection 중간에 새로 켤 수 없으므로 middlebox option stripping도 성능 원인이 된다.

rwnd와 cwnd를 수치로 분리하기

단순화하면 새로 보낼 수 있는 양은 max(0, min(rwnd,cwnd)-bytes_in_flight)다. 예를 들어 rwnd=256KB, cwnd=64KB, in-flight=48KB면 congestion limit 때문에 약 16KB만 더 보낼 수 있다. 반대로 rwnd=32KB, cwnd=1MB, in-flight=24KB면 receiver limit 때문에 약 8KB다. 실제 stack은 SACK, retransmission, pacing, offload, application send queue를 더 고려한다.

관측우선 가설
rwnd 작음, cwnd 큼Receiver buffer/application read가 병목인 flow-control limited 상태.
rwnd 큼, cwnd 작음Slow start, loss, ECN, congestion algorithm 등 network feedback가 제한.
둘 다 큼, 전송 없음Sender application 미생산, send buffer/lock, pacing, scheduler, protocol-level credit를 확인.
win=0 반복Receiver app stall·작은 buffer·downstream block. Probe가 보이면 TCP는 살아 있을 수 있다.

Silly Window Syndrome와 작은 update

Receiver가 몇 byte씩 window를 열고 sender가 그때마다 tiny segment를 보내면 header·interrupt·ACK 비용이 폭증한다. Receiver는 의미 있는 공간이 생길 때까지 작은 window 광고를 억제하고, sender는 작은 data 전송을 합치는 전략을 사용할 수 있다. 하지만 latency-sensitive traffic, TCP_NODELAY, delayed ACK, Nagle 상호작용은 workload에 따라 trade-off가 달라 일괄 설정하지 않는다.

Data path와 control path

Receive buffer 소비는 application data path지만 그 결과가 ACK Window field라는 control feedback으로 반대 방향에 전달된다. NAT/LB는 보통 window 값을 바꾸지 않고 전달하지만 TCP proxy는 자체 receive/send buffer와 두 독립 window를 만든다. HTTP/2·QUIC처럼 application/transport 위에 stream-level flow control이 추가되면 connection window가 열려 있어도 특정 stream credit가 0이라 멈출 수 있다.

5. 실무 설계 판단과 best practice

판단권장 기준과 이유
Buffer sizingBandwidth·RTT·connection 수·memory budget을 함께 계산한다. Per-socket 16MB를 10만 connection에 허용하면 이론상 1.6TB다. OS autotuning 상·하한과 cgroup/container memory를 포함한다.
Read loopSocket read thread에서 긴 CPU 작업·blocking DB call을 하지 말고 bounded queue로 넘긴다. Queue가 찼을 때 read를 늦춰 의도적으로 TCP backpressure를 전달하되 timeout/cancellation 정책을 둔다.
Nonblocking writeEAGAIN을 busy loop로 재시도하지 않고 event readiness와 deadline을 사용한다. Application user-space queue를 무제한으로 키워 kernel backpressure를 숨기지 않는다.
Proxy/LBFront/back socket buffer, request/response buffering, high/low watermark, per-connection limit을 문서화한다. Backend stall 때 proxy memory가 먼저 차는 failure window를 부하 테스트한다.
Pool/queueFlow-control stall connection이 pool slot을 점유하는 시간을 제한한다. Bounded concurrency, queue deadline, bulkhead로 한 slow consumer가 전체 worker를 잡지 못하게 한다.
ObservabilityZero-window count·duration, advertised window, send/receive queue, socket memory, blocked write time, app queue depth, event-loop lag, downstream latency를 같은 connection/timestamp로 묶는다.
SecuritySlow-read/slow-write peer가 buffer와 connection을 오래 점유할 수 있다. Header/body deadline, minimum progress, per-client connection·memory quota, load shedding을 계층화한다.
Version 확인Buffer autotuning, max window, memory pressure, ss 필드 의미는 kernel마다 다르다. RFC의 wire invariant와 특정 OS 구현값을 구분하고 canary에서 packet·socket telemetry로 검증한다.
Anti-pattern: Zero window를 보자마자 receive buffer만 크게 늘리거나, blocking write를 별도 unbounded thread에 숨기거나, proxy buffering을 무제한으로 켜지 않는다. 병목을 뒤로 미루며 memory·tail latency·failure blast radius를 키울 뿐이다.

6. 장애 대응 표

상황: Upload request의 throughput이 0에 가까워지고 client write가 30초씩 block된다. Loss와 retransmission은 낮지만 일부 flow에서 TCP zero window가 반복된다.

순서실행 내용
증상Endpoint·backend·AZ·payload size·connection age별 throughput, blocked write time, request deadline, zero-window duration, active connection·pool occupancy를 분리한다.
먼저 수집할 증거/지표양 끝 pcap의 ACK/window/scale/probe, ss -tinm의 send-q·recv-q·skmem·cwnd·rtt, receiver thread dump·event-loop lag·CPU/GC, app queue, disk/DB/downstream latency, proxy front/back buffer를 변경 전에 저장한다.
가능한 가설Receiver app 미읽기, event loop blocking, bounded queue 포화, downstream DB/disk stall, 작은 고정 SO_RCVBUF, container memory pressure, proxy buffering 한계, Window Scale 미협상, 반대 방향 capture 해석 오류를 세운다.
안전한 첫 조치문제 backend를 소량 drain하고 신규 대용량 upload concurrency를 제한한다. 느린 downstream 호출을 canary에서 격리하고, receiver read loop가 다시 돌도록 가역적인 부하 완화·worker 복구를 적용한다.
Rollback/복구최근 buffer/watermark/event-loop/proxy 설정과 배포를 known-good으로 원복한다. recv-q 감소→window update→sender write 재개→pool 회수→request SLO 회복 순서를 확인하고 traffic을 단계적으로 복귀한다.
하지 말아야 할 조치전 fleet buffer 무제한 확대, 모든 socket 강제 종료, retry·timeout 동시 확대, evidence 전 proxy 우회, zero-window probe를 공격으로 단정, sender pcap만 보고 receiver application 원인을 확정하지 않는다.

7. 35분 실습: 느린 reader와 zero window 관찰

목표: 작은 receive buffer를 가진 server가 12초간 읽지 않도록 만들어 client sendall()이 block되는 과정, ACK window 감소·zero window·window update와 socket queue를 연결한다.

  2. win=0 직전 server recv-q와 client send-q를 기록한다.
  3. Window update 뒤 client가 재개되는 timestamp와 server read 시작 시점을 맞춘다.

8. 놓치기 쉬운 함정

  • Window field를 그대로 byte로 읽지 않는다. SYN에서 협상된 방향별 Window Scale을 적용해야 한다.
  • SYN의 Window field는 scale하지 않는다. SYN의 option은 후속 segment 해석에 쓸 shift count를 협상한다.
  • Zero window는 connection dead가 아니다. ACK·probe가 오갈 수 있고 application이 읽으면 다시 열린다.
  • Receive window와 congestion window를 섞지 않는다. rwnd는 receiver capacity, cwnd는 sender의 network feedback 상태다.
  • Receive buffer를 application queue로 보지 않는다. Kernel socket memory와 runtime/user-space queue는 서로 다른 owner·limit·metric을 갖는다.
  • ACK를 처리 완료로 번역하지 않는다. Byte가 kernel에 도착했을 뿐 DB commit·파일 flush·consumer 처리 완료는 별도다.
  • 큰 buffer가 항상 빠르지 않다. BDP를 채우는 데 도움 되지만 connection 수가 많으면 memory와 queueing delay, 장애 체류 시간을 키운다.
  • Proxy 환경에서 client pcap 하나로 backend를 단정하지 않는다. 두 TCP connection의 window·queue를 각각 관측한다.
  • Application-level flow control을 생략하지 않는다. HTTP/2 stream, gRPC demand, Kafka fetch, file pipeline queue는 TCP window만으로 공정성·business capacity를 표현하지 못한다.

9. 대기업 기술 면접 질문

  1. “ACK=10001, Window field=32768, scale=7입니다. Sender가 이해할 수신 범위를 설명하세요.”
    좋은 답변 구조: Window field unsigned 16-bit → effective rwnd=4,194,304B → 왼쪽 10001, 오른쪽 exclusive 4,204,305 → 이미 in-flight와 cwnd를 함께 제한 → SYN field 예외·방향별 scale.
  2. “Loss는 낮은데 upload가 멈추고 zero window가 보입니다. 어디부터 진단합니까?”
    좋은 답변 구조: receiver가 광고 주체임을 명시 → 양 끝 pcap scale/ACK → recv-q·skmem → app read loop·CPU/GC/lock → downstream DB/disk → proxy 두 connection → safe drain·concurrency 제한 → buffer 확대 trade-off.
  3. “1Gbps, RTT 100ms 서비스의 socket buffer를 어떻게 정합니까?”
    좋은 답변 구조: BDP 12.5MB 계산 → Window Scale 필요 → connection 수·memory 총량 → autotuning 상한 → workload payload/RTT 분포 → cwnd·loss도 별도 → 부하 테스트와 zero-window/throughput/SLO로 검증.

10. 회상·확인 문제와 채점 기준

어제 내용 회상 3문제

  1. 첫 RTT가 100ms일 때 RFC 6298 기준 SRTT·RTTVAR·계산 RTO는?
  2. ACK=2001, SACK=3001:4001이 말하는 gap은?
  3. TCP retransmission과 application retry의 성공 경계가 다른 이유는?

짧은 정답: ① 100ms, 50ms, 계산 300ms이며 baseline 1초 하한을 구분한다. ② 2001:3001이 비었고 3001:4001은 선택 수신됐다. ③ TCP는 한 connection의 byte stream을 복구하지만 retry는 transaction 결과가 불명확한 새 request를 만들 수 있어 idempotency가 필요하다.

오늘 내용 확인 3문제

  1. rwnd=256KB, cwnd=64KB, in-flight=48KB일 때 단순화한 새 전송 가능량은?
  2. ACK=5001, win=0은 무엇을 확정하고 무엇을 확정하지 않는가?
  3. Proxy의 backend-side rwnd가 0이 되었을 때 client-side가 즉시 같은 win=0이 아닐 수 있는 이유는?

짧은 정답: ① min(256,64)-48=16KB. ② 5000까지 연속 수신했고 현재 5001부터 새 byte 공간이 없음을 알리지만 application 처리 완료나 connection 종료는 뜻하지 않는다. ③ Proxy가 두 TCP를 terminate하고 자체 buffer를 소유하므로 backend stall을 먼저 흡수한 뒤 buffer watermark에서 client read를 늦춘다. 문항당 수치/정의 1점, owner·state 1점, 장애·trade-off 1점으로 총 9점이다.
