COMPUTER NETWORKING · WEEK 3 / DAY 16

retransmission, RTT/RTO, duplicate ACK

손실을 추측하는 TCP의 두 시계와 ACK 증거 · 예상 학습 55분 + 실습 35분

한 줄 요약
TCP는 packet이 사라졌다는 직접 통지를 받는 대신 RTO timer, duplicate ACK, SACK, 시간 기반 RACK이라는 불완전한 증거로 loss를 추론한다. 재전송은 byte stream의 빈칸을 메우지만 latency 비용과 congestion window 감소를 만들며, 그 위의 application retry까지 겹치면 중복 처리와 retry storm이 된다.

1. 선수 용어 사전

LossSender가 보낸 TCP segment가 receiver까지 도착하지 않거나, receiver의 ACK가 돌아오지 않은 상태다. TCP sender는 둘을 직접 구별하지 못하고 ACK 관측으로 추론한다.
RetransmissionACK되지 않았다고 판단한 byte 범위를 다시 보내는 것. 같은 application byte가 새 TCP segment 경계로 나뉘어 전송될 수 있어 “같은 packet 복사”와 정확히 같지는 않다.
RTTRound-Trip Time. Data를 보낸 시점부터 그 byte를 확인하는 ACK가 돌아올 때까지의 왕복 관측 시간이다. 전파·queue·처리 지연이 모두 섞인다.
SRTT / RTTVARSmoothed RTT는 최근 RTT의 완만한 평균, RTT variation은 흔들림의 추정치다. 평균만 쓰면 순간 queue 증가에 timer가 너무 빨리 만료되므로 둘을 함께 쓴다.
RTORetransmission Timeout. ACK를 기다릴 최대 시간이 아니라, 미확인 data의 재전송 timer가 만료되는 기준이다. Timeout마다 backoff되어 같은 속도로 계속 두드리지 않는다.
Out-of-order뒤 sequence 범위가 앞의 빈칸보다 먼저 도착한 상태다. 실제 loss뿐 아니라 multipath·queue·NIC 처리 순서 때문에 생길 수 있다.
Duplicate ACKCumulative ACK number가 전진하지 않은 채 같은 다음 기대 번호를 반복 알리는 ACK. 뒤 data가 도착했지만 중간 gap이 남았다는 단서가 될 수 있다.
SACKSelective Acknowledgment. Cumulative ACK 뒤쪽에서 이미 받은 byte block을 option으로 알려 sender가 실제 빈 구간을 더 정확히 고르게 한다.
Fast retransmitRTO 만료를 기다리지 않고 duplicate ACK 등의 증거로 loss를 추론해 재전송하는 절차. 고전적인 기준은 세 개의 duplicate ACK다.
RACK / TLPRACK은 전송 시간 순서로 loss를 판단하는 현대적 알고리즘이고, Tail Loss Probe는 흐름 끝의 loss를 작은 probe로 드러내 긴 RTO 대기를 줄인다.
Spurious retransmission원본 segment가 늦게 살아 있었는데 sender가 loss로 오판해 불필요하게 다시 보낸 경우다. Reordering과 너무 공격적인 timer가 원인이 될 수 있다.

2. 왜 중요한가

Application에는 “느린 요청” 하나로 보이지만 kernel 안에서는 queue 증가, ACK 정체, loss 추론, 재전송, congestion window 감소가 연쇄적으로 일어난다. 이 경계를 모르면 timeout을 무작정 늘리거나 application retry를 추가해 장애를 증폭시킨다.

  • Loss는 latency를 계단식으로 올린다. Duplicate ACK가 충분하면 빠르게 복구하지만 tail segment 하나만 잃으면 ACK 증거가 부족해 timer 또는 TLP까지 기다릴 수 있다.
  • Loss와 congestion은 같은 말이 아니다. 무선 간섭·NIC ring·방화벽 drop도 loss를 만들지만 고전 TCP는 loss를 congestion 신호로 취급해 전송률을 낮춘다.
  • Transport 재전송은 application 중복을 막지 않는다. TCP는 같은 connection의 byte 전달을 복구하지만 client가 request timeout 뒤 새 요청을 보내면 server의 첫 실행 성공 여부는 별도다.
  • 관측 위치가 사실을 바꾼다. GSO/GRO, checksum offload, NAT, proxy 때문에 host capture의 segment 수와 wire의 packet 수가 다를 수 있다.

3. 아키텍처 그림과 요청 흐름

  1. 전송: Application의 write()가 성공해도 byte는 sender kernel send buffer의 소유다. SND.UNA는 가장 오래된 미확인 byte, SND.NXT는 다음 전송 byte를 가리킨다.
  2. 손실: Router queue, NIC, virtual switch, NAT/conntrack, firewall 등 어디서든 drop될 수 있다. Sender는 drop 이벤트 자체가 아니라 돌아오는 ACK와 시간만 본다.
  3. 증거: Receiver는 뒤쪽 byte를 받았지만 gap 때문에 cumulative ACK 2001을 반복한다. SACK은 3001:4001을 이미 보관했다는 추가 정보를 준다.
  4. 복구: 충분한 ACK 또는 RACK의 시간 증거가 있으면 RTO 전 재전송한다. 증거가 부족하면 RTO가 만료되고 sender는 backoff와 congestion response를 수행한다.
  5. 성공 경계: ACK 4001은 receiver TCP가 4000까지 연속 수신했음을 뜻한다. Receiver application의 read(), HTTP 처리, DB commit은 확정하지 않는다.
상태 소유권: Sender kernel은 send buffer·RTT estimator·RTO timer·SACK scoreboard·cwnd를, receiver kernel은 receive buffer·gap·cumulative ACK를 소유한다. Proxy/LB가 TCP를 terminate하면 client↔proxy와 proxy↔backend는 서로 다른 두 TCP state machine이므로 한쪽 ACK가 반대쪽 application 성공을 증명하지 않는다.

4. CS 수준 내부 동작

RTO는 평균이 아니라 평균 + 불확실성이다

RFC 6298의 기준 계산에서 첫 RTT 표본이 R이면 SRTT=R, RTTVAR=R/2, RTO=SRTT+max(G,4×RTTVAR)다. G는 clock granularity다. 이후 표본에는 α=1/8, β=1/4를 사용하며 RTTVAR를 이전 SRTT로 먼저 갱신한다.

표본계산
첫 RTT 100msSRTT=100ms, RTTVAR=50ms, 계산값 RTO=300ms
다음 RTT 140msRTTVAR=0.75×50+0.25×40=47.5ms, SRTT=0.875×100+0.125×140=105ms, 계산값 RTO=295ms

RFC 6298 baseline은 측정 전 1초 초기 RTO를 권고하고 계산값이 1초보다 작으면 1초로 올릴 수 있도록 규정한다. 실제 OS는 표준이 허용하는 개선, 더 정밀한 timer, RACK 등을 조합하므로 운영 환경의 exact minimum과 알고리즘은 stack·version·socket telemetry로 확인한다.

Karn의 모호성: 어느 전송의 ACK인가

원본을 t0에, 재전송을 t1에 보낸 뒤 ACK가 t2에 오면 t2-t0인지 t2-t1인지 알 수 없다. 모호한 표본을 SRTT에 넣으면 RTO가 왜곡된다. RFC 6298의 Karn 규칙은 재전송된 segment의 RTT 표본을 피하고 timeout 때 RTO를 지수적으로 backoff한다. Timestamp처럼 전송을 구분할 충분한 정보가 있는 경우 구현이 모호성을 줄일 수 있지만 packet과 stack 동작을 확인해야 한다.

Duplicate ACK, SACK, RACK은 서로 다른 증거다

  • Duplicate ACK: RFC 5681은 outstanding data가 있고, ACK number가 전진하지 않으며, window가 변하지 않고, control bit가 없는 등의 조건으로 duplicate ACK를 설명한다. 세 개는 고전 fast retransmit threshold지만 reordering에서도 생긴다.
  • SACK: Receiver가 받은 비연속 block을 알려 “무엇이 도착했는가”를 보강한다. Cumulative ACK 자체는 여전히 가장 앞 gap에서 멈춘다.
  • RACK: 더 늦게 보낸 packet이 ACK된 뒤 충분한 시간 차가 지난 앞 packet을 loss로 표시한다. Packet count보다 시간 순서를 사용해 reordering과 tail loss 복구를 개선한다.
  • TLP: 흐름 끝에는 뒤 segment가 없어 duplicate ACK가 적다. Probe를 보내 ACK clock을 다시 움직여 full RTO 전에 loss를 드러낸다.

재전송과 congestion control의 결합

TCP의 신뢰성은 공짜가 아니다. Timeout은 ACK clock이 무너졌다는 강한 신호라 전송을 크게 줄이고 RTO를 backoff한다. Fast retransmit/fast recovery는 일부 data가 계속 흐른다는 증거를 이용해 더 빠르게 회복하지만 cwnd와 ssthresh를 조정한다. 불변식은 network에 허용된 양보다 많은 unacknowledged data를 무제한 밀어 넣지 않는 것이다. Receiver의 advertised window가 제한하는 flow control과 network 혼잡을 제한하는 congestion control은 다른 경계이며 실제 전송 가능량은 둘 중 작은 쪽에 묶인다.

5. 실무 설계 판단과 best practice

판단권장 기준과 이유
Deadline budgetDNS·connect·TLS·request/read·queue를 전체 deadline 안에 배분한다. TCP RTO보다 짧은 application timeout은 kernel 복구 전에 request를 버릴 수 있고, 지나치게 긴 timeout은 실패한 work와 pool을 붙잡는다.
Retry ownerClient SDK, proxy, service 중 한 계층이 전체 retry budget을 소유하게 한다. 각 계층 3회는 한 요청을 최대 27회로 증폭할 수 있다. Backoff+jitter, max attempts, retry-after, budget을 둔다.
IdempotencyPOST/결제처럼 side effect가 있으면 idempotency key와 server deduplication, 처리 상태 조회를 설계한다. TCP ACK는 business transaction 결과가 아니다.
Pool과 connection ageBounded pool, idle timeout, max-age, health/drain을 둔다. 하나의 손상된 connection에 재사용 요청이 몰리거나 NAT/LB idle timeout 뒤 half-dead socket을 영구 재사용하지 않게 한다.
증거 묶음Retransmission rate만 보지 말고 RTT 분포, RTO, SACK/reordering, cwnd, bytes-in-flight, queue drop, NIC error, conntrack, request p99를 같은 5-tuple·timestamp로 묶는다.
Capture 위치Client host, server host, LB 앞뒤 중 최소 두 지점을 비교한다. GSO/GRO/TSO/LRO와 checksum offload가 capture를 어떻게 바꾸는지 기록하고 가능하면 wire 또는 switch mirror 증거를 보강한다.
Version/engineRACK·TLP·SACK 기본값, RTO minimum, congestion algorithm은 OS/kernel/cloud proxy마다 다를 수 있다. 이름만으로 추정하지 말고 version, sysctl/socket option, packet trace를 배포 산출물에 남긴다.
Anti-pattern: “duplicate ACK가 많으니 server CPU 문제”, “retransmission이 있으니 무조건 network congestion”, “timeout이면 안전하게 retry”처럼 단일 지표를 원인·안전성으로 바로 번역하지 않는다. ACK loss, reordering, capture artifact, receiver stall, middlebox 정책을 반증해야 한다.

6. 장애 대응 표

상황: API p99가 200ms에서 4초로 튀고 client에서 TCP retransmission과 timeout retry가 동시에 증가했다.

순서실행 내용
증상Region/AZ/client version/backend/IPv4·IPv6/connection age별 p50·p95·p99, timeout·reset, retry amplification, retransmission 비율과 시작 시점을 분리한다.
먼저 수집할 증거/지표양 끝 pcap의 seq/ACK/SACK/timestamp, ss -tin의 rtt·rto·cwnd·retrans, NIC/interface drop, qdisc·softnet, switch/LB drop, conntrack, socket send/receive queue, application deadline·retry log를 변경 전에 보존한다.
가능한 가설Path congestion, microburst queue drop, NIC/ring overflow, reordering에 의한 spurious retransmit, ACK return-path loss, receiver CPU/receive-window stall, MTU black hole, NAT/LB state expiry, connection pool의 오래된 socket, 배포 후 retry storm을 병렬로 세운다.
안전한 첫 조치Retry budget과 concurrency를 먼저 제한하고 문제 AZ/backend를 소량 drain한다. 정상/비정상 flow 한 쌍의 양방향 capture로 실제 gap 위치를 찾고, 여유 capacity가 확인된 path로 canary 우회한다.
Rollback/복구최근 qdisc/MTU/LB/kernel/client timeout 변경을 known-good으로 한 항목씩 원복한다. retrans·RTO·queue drop·request p99·retry amplification이 함께 회복되는지 보고 traffic을 단계적으로 복귀한다.
하지 말아야 할 조치Timeout과 retry를 동시에 확대, 모든 connection 강제 종료, firewall 전체 해제, MTU를 전 fleet에 즉시 변경, 한쪽 pcap의 “TCP Retransmission” 표시만으로 loss 지점을 확정, 증거 수집 전 전 장비 restart를 하지 않는다.

7. 35분 실습: loss를 주입하고 ACK·timer·socket state 연결

목표: Baseline RTT를 기록한 뒤 client egress에 delay/loss를 주입하고 tcpdump의 sequence gap, duplicate ACK/SACK, ss -tin의 rtt·rto·cwnd·retrans를 하나의 timeline으로 설명한다.

사전 조건: Docker Desktop과 이 저장소. 실습 network는 격리된 bridge이고 client container에 NET_ADMIN이 있다. 저장소 root에서 실행하며 각 단계 전에 예상 결과를 한 줄 적는다.

0단계 · 예측 (3분)

  1. RTT가 80ms 늘면 request time과 RTO 추정치는 어느 방향으로 변할까?
  2. Client egress loss는 request data뿐 아니라 server response에 대한 ACK도 잃게 할 수 있다. 어느 방향에서 재전송이 보일까?
  3. 20% random loss에서 매 실행마다 duplicate ACK가 정확히 세 번 보인다고 보장할 수 있을까?

1단계 · Baseline (7분)

make up
docker compose -f labs/basic-network-observability/docker-compose.yml exec client curl -sS -o /dev/null -w 'total=%{time_total}s\n' http://172.28.0.20:8000/headers
docker compose -f labs/basic-network-observability/docker-compose.yml exec client ss -tin dst 172.28.0.20

예상 관찰: Local bridge의 짧은 RTT와 retrans 0에 가까운 값을 본다. ss 출력은 connection이 너무 빨리 닫히면 비어 있을 수 있으므로 다음 loop 중에 다시 관찰한다.

2단계 · Capture와 실패 주입 (15분)

터미널 A:

docker compose -f labs/basic-network-observability/docker-compose.yml exec client tcpdump -ni eth0 -tttt -nn -S -c 100 'host 172.28.0.20 and tcp port 8000'

터미널 B:

docker compose -f labs/basic-network-observability/docker-compose.yml exec client tc qdisc replace dev eth0 root netem delay 80ms loss 20%
docker compose -f labs/basic-network-observability/docker-compose.yml exec client sh -lc 'for i in $(seq 1 20); do curl --max-time 3 -sS http://172.28.0.20:8000/headers >/dev/null || echo request-$i-failed; done'

터미널 C 또는 loop 실행 중 B:

docker compose -f labs/basic-network-observability/docker-compose.yml exec client ss -tin dst 172.28.0.20

예상 관찰: 매 실행의 random 결과는 다르다. Seq gap 뒤 같은 ACK number, SACK block 또는 RTO 뒤 동일 byte 범위 전송을 찾는다. ss에서 RTT 상승과 retrans 변화를 찾아 packet timestamp와 맞춘다. Duplicate ACK가 적어도 RTO/TLP로 복구될 수 있으며 이것은 실패가 아니라 tail loss의 핵심 관찰이다.

3단계 · 증거 해석 (5분)

  1. 재전송 byte 범위와 최초 전송 timestamp를 표시하고 시간 차를 계산한다.
  2. 그 전에 같은 cumulative ACK, SACK, 뒤 packet ACK가 있었는지 확인해 fast loss detection인지 timeout 계열인지 분류한다.
  3. Request 실패가 있으면 TCP가 끝내 복구하지 못했는지, curl --max-time 3 deadline이 먼저 끝났는지 구분한다.

자주 나는 오류와 해결 · cleanup (5분)

  • tc: Operation not supported면 Docker Desktop kernel의 sch_netem 지원과 container capability를 확인한다. 지원되지 않으면 host 전체 설정을 바꾸지 말고 실습 환경을 재생성한다.
  • qdisc already exists면 replace를 사용한다. 설정은 tc qdisc show dev eth0로 증명한다.
  • 재전송이 안 보이면 loop 수를 늘리기 전 capture filter·qdisc 적용을 확인한다. Random loss라 한 번의 실행으로 결론 내리지 않는다.
  • Checksum incorrect는 offload 전 capture artifact일 수 있다. 상대 host 수신과 양방향 capture로 반증한다.
docker compose -f labs/basic-network-observability/docker-compose.yml exec client sh -lc 'tc qdisc del dev eth0 root 2>/dev/null || true'
docker compose -f labs/basic-network-observability/docker-compose.yml exec client tc qdisc show dev eth0
make down

Cleanup 확인: netem이 보이지 않고 lab container/network가 내려갔는지 확인한다. 장애 주입을 남긴 채 다른 테스트를 시작하지 않는다.

8. 놓치기 쉬운 함정

  • TCP 재전송은 packet identity가 아니라 byte 범위의 재전달이다. MSS, coalescing, SACK 상태에 따라 segment 경계가 달라질 수 있다.
  • Duplicate ACK 하나를 loss로 확정하지 않는다. Reordering, window update, ACK compression, capture 중복 여부를 조건과 함께 본다.
  • ACK loss도 sender에게는 data loss처럼 보일 수 있다. Receiver가 이미 byte를 받았어도 ACK가 사라지면 불필요한 재전송이 생긴다.
  • RTO와 application timeout을 같은 timer로 보지 않는다. 서로 다른 owner가 독립적으로 만료되며 application이 먼저 포기해도 kernel은 socket close 정책에 따라 상태를 처리한다.
  • Retransmission 비율만 평균내지 않는다. 특정 AZ, long-lived connection, packet size, IPv6, tail latency와 상관관계를 본다.
  • Offload된 host capture의 giant segment를 wire packet으로 세지 않는다. Capture point와 GSO/GRO/TSO/LRO 설정을 기록한다.
  • Proxy가 있으면 한 연결이 아니다. Front-side ACK와 back-side ACK의 sequence space, RTT, RTO, congestion state는 독립이다.
  • Retry 성공을 원인 해결로 착각하지 않는다. Retry는 사용자 성공률을 잠시 올리면서 downstream 부하와 중복 side effect를 키울 수 있다.

9. 대기업 기술 면접 질문

  1. “Seq 2001:3001이 유실되고 3001:5001이 도착했습니다. Receiver와 sender 상태를 숫자로 설명하세요.”
    좋은 답변 구조: ordered byte stream 불변식 → cumulative ACK=2001 → out-of-order queue/SACK block → duplicate ACK 또는 RACK 증거 → 2001:3001 재전송 → ACK=5001 → send buffer 해제 → reordering 오판 가능성.
  2. “RTO와 fast retransmit은 언제 다르게 동작하며 tail latency에 어떤 영향을 줍니까?”
    좋은 답변 구조: RTT/SRTT/RTTVAR 수치 가정 → 뒤 data가 만드는 duplicate ACK → fast path → tail loss의 증거 부족 → TLP/RACK/RTO → backoff·cwnd trade-off → stack/version 검증 방법.
  3. “TCP가 신뢰성을 보장하는데 왜 API retry가 필요하고, 왜 위험합니까?”
    좋은 답변 구조: TCP byte 전달과 request/transaction 성공 경계 → deadline·connection reset failure window → 응답 유실 후 server commit 사례 → idempotency key/dedup → single retry owner·budget·jitter → overload와 retry storm 대안.

10. 회상·확인 문제와 채점 기준

어제 내용 회상 3문제

  1. Client SYN seq=x, server SYN-ACK seq=y, ack=x+1일 때 final ACK의 seq/ack는?
  2. connect() 성공이 server application의 accept()·HTTP 처리를 확정하지 않는 이유는?
  3. SYN backlog와 accept queue가 각각 소유하는 대표 state는?

짧은 정답: ① seq=x+1, ack=y+1. ② Client kernel의 ESTABLISHED와 server kernel의 handshake 완료만 확인하며 application scheduling/read/commit은 별도다. ③ 전자는 대체로 SYN-RECEIVED, 후자는 handshake가 끝났으나 아직 accept되지 않은 ESTABLISHED connection이다.

오늘 내용 확인 3문제

  1. 첫 RTT가 100ms이고 G가 무시 가능하면 SRTT, RTTVAR, 계산 RTO는?
  2. ACK=2001, SACK=3001:4001은 받은 범위와 gap을 어떻게 말하는가?
  3. TCP 재전송과 application retry가 각각 보장하려는 대상과 중복 위험은?

짧은 정답: ① 100ms, 50ms, 300ms이며 RFC 6298 baseline의 1초 하한 적용을 별도로 언급해야 만점이다. ② 2000까지 연속 수신, 3001:4001도 선택 수신했지만 2001:3001이 gap이다. ③ TCP는 한 connection의 byte stream을 복구하고 application retry는 request 성공을 다시 시도한다. 첫 요청의 처리 결과가 불명확하면 중복 side effect가 생기므로 idempotency와 retry budget이 필요하다. 문항당 숫자/정의 1점, owner·state 1점, 장애·trade-off 1점으로 총 9점이다.
