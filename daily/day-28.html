HTTP · TLS · QUIC · WEEK 4 / DAY 28 · REVIEW

회상: 암호화·인증·무결성 경계

“HTTPS니까 안전”을 hop·state·owner 단위로 해체 · 개념 60분 + 실습 35분

한 줄 요약
암호화는 내용을 숨기고, 무결성은 변경을 탐지하며, 인증은 상대 identity를 검증한다. TLS는 이 속성을 한 TLS connection의 두 endpoint 사이에 제공할 뿐 DNS·LB 뒤 upstream·application authorization·database commit까지 자동 확장하지 않는다. 따라서 termination마다 새로운 trust와 failure 경계를 그려야 한다.

1. 선수 용어 사전

Confidentiality기밀성. 허가되지 않은 관찰자가 data 내용을 알기 어렵게 하는 속성. TLS도 packet 길이·시점·IP 같은 모든 metadata를 숨기지는 않는다.
Integrity무결성. 전송 중 data가 바뀌면 수신자가 탐지할 수 있는 속성. TCP checksum은 우발 오류용이지 공격자에 대한 cryptographic integrity가 아니다.
Authentication인증. 상대가 주장한 identity를 증거로 확인하는 절차. Server certificate path와 hostname 검증은 server authentication의 일부다.
Authorization인가. 인증된 주체가 어떤 resource/action을 수행할 수 있는지 결정한다. TLS server 인증이 사용자에게 결제 권한을 주지는 않는다.
Endpoint / hopEndpoint는 security protocol이 끝나는 주체, hop은 두 인접 endpoint 사이 구간이다. Client→LB와 LB→app은 별도 connection·key·certificate·timeout을 가진다.
TLS terminationTLS record를 복호화해 plaintext를 얻는 지점. 이 지점은 private key, peer identity, log/redaction, 다음 hop 보호의 owner가 된다.
Trust boundary다른 권한·위협·운영 owner로 넘어가는 경계. Network segment 이름이 아니라 “누가 plaintext·key·정책을 제어하는가”로 그린다.
AEADAuthenticated Encryption with Associated Data. 암호화와 변조 탐지를 함께 제공하며 record header 일부를 associated data로 묶는다.
Certificate pathLeaf에서 intermediate CA를 거쳐 local trust anchor까지 이어지는 서명·constraint 검증 경로. Name match와는 별도 축이다.
SNI / ALPNSNI는 TLS server name/certificate route 선택, ALPN은 HTTP/2·HTTP/1.1 같은 상위 protocol 선택에 쓰는 handshake control data다.
Reliability손실·중복·순서를 다뤄 application에 ordered bytes/stream을 제공하는 속성. TCP/QUIC reliability와 TLS security는 서로 대체하지 않는다.
Success boundary어떤 component가 무엇을 확정한 시점. DNS answer, TCP ACK, TLS Finished, HTTP response, DB commit은 각각 다른 성공이다.

2. 왜 중요한가

“HTTPS를 쓴다”는 말만으로 실제 보안 속성을 알 수 없다. Edge에서 TLS를 끝내고 origin까지 plaintext라면 외부 hop은 보호되지만 내부 hop은 그렇지 않다. Certificate가 유효해도 application authorization이 틀리면 data leak가 발생하고, HTTP 200이어도 durable commit은 실패할 수 있다.

  • Threat model: Passive observer, active on-path attacker, compromised proxy, malicious client, insider는 서로 다른 통제가 필요하다.
  • Incident: TLS handshake failure를 application retry로 덮으면 해결되지 않고 handshake CPU와 queue만 늘어난다.
  • Architecture: Connection pool을 재사용하는 LB는 client connection과 upstream connection을 1:1로 묶지 않는다. Identity·timeout·trace owner도 분리된다.
  • 면접: 대기업 수준 답변은 “TLS가 안전하다”가 아니라 보호 대상, endpoint, key owner, 보장하지 않는 것, failure/rollback을 명시한다.

  1. DNS: IP를 찾는 control path와 service identity 검증을 구분한다. 공격자가 IP를 바꿔도 정상 TLS hostname validation이 통과하지 않으면 authenticated connection은 막힌다.
  2. Transport: TCP sequence/ACK 또는 QUIC stream recovery가 delivery reliability를 만든다. 이것만으로 peer identity나 cryptographic integrity를 얻지 못한다.
  3. Front TLS: Edge가 certificate private key를 소유하고 plaintext를 얻으므로 client가 인증한 peer는 origin app이 아니라 edge termination endpoint일 수 있다.
  4. HTTP policy: TLS 인증 뒤에도 bearer token/session/mTLS identity를 application principal로 mapping하고 resource authorization을 별도로 결정한다.
  5. Upstream: Re-encryption을 하면 새 handshake와 새 trust policy다. Front certificate 성공은 backend certificate·hostname·mTLS 성공을 보장하지 않는다.
  6. Commit: Transport ACK는 peer socket 수신, HTTP status는 application 응답, DB commit은 durable state의 경계다. Timeout retry는 이 차이를 고려해야 한다.
백지 복원 규칙: 모든 화살표마다 ① protocol, ② connection owner, ③ plaintext가 보이는 곳, ④ peer identity 검증 주체, ⑤ key/trust store owner, ⑥ timeout/retry, ⑦ 성공 확정 시점을 적는다. 하나라도 답하지 못하면 “end-to-end secure”라고 단정하지 않는다.

4. CS 수준 내부 동작

보안 속성은 protocol stack마다 다르다

계층제공하는 핵심제공하지 않는 것
IP/EthernetHop 전달, address와 forwarding기본적으로 end-to-end 기밀성·peer 인증 없음
TCPOrdered reliable byte stream, flow/congestion control공격자에 대한 기밀성·identity·cryptographic integrity 없음
TLS 1.3Handshake peer auth/key establishment, protected record의 기밀성·무결성Traffic length/timing 은닉, application 인가, DB commit 보장 없음
HTTPMethod/status/header/content semantics와 routing metadataTLS 없이 자체 기밀성·server identity를 자동 제공하지 않음
ApplicationUser/service authn, authorization, validation, transaction/idempotency아래 hop 보호가 없으면 network plaintext 노출을 막지 못함

TLS handshake가 세 속성을 묶는 방식

ClientHello/ServerHello가 version·cipher·key share를 정하고 transcript가 negotiation을 묶는다. Certificate path와 SAN은 public key를 intended server identity에 연결하고 CertificateVerify는 private-key possession과 transcript signature를 확인한다. Finished는 derived secret과 transcript를 확인한다. 이후 방향별 traffic key와 nonce로 AEAD record를 보호한다.

  • 암호화 key 생성만으로 인증은 아니다. 공격자와도 key agreement는 가능하므로 certificate identity 검증이 필요하다.
  • 인증만으로 application 권한은 아니다. Server가 진짜라고 사용자의 account/action이 허용되는 것은 아니다.
  • 무결성 failure는 복구 가능한 bit error가 아니다. AEAD tag/Finished 검증 실패 시 connection을 종료하고 secret을 폐기해야 한다.

HTTP/1.1, HTTP/2, HTTP/3의 공통점과 차이

버전Framing·multiplexLoss·security 경계
HTTP/1.1Text message framing, keep-alive; pipelining response order 제약TCP byte stream HOL; HTTPS면 별도 TLS connection
HTTP/2Binary frame와 stream multiplex, stream+connection flow control한 TCP sequence gap이 모든 stream delivery를 막을 수 있음; TLS 경계는 connection endpoint
HTTP/3HTTP semantics를 QUIC request/control/QPACK stream에 mappingStream별 loss recovery, shared cwnd/flow state는 남음; QUIC에 TLS 1.3 결합

세 버전은 method/status/header 같은 HTTP semantics를 공유한다. Version을 바꿔도 authentication·authorization·idempotency 요구가 사라지지 않는다. 반대로 transport framing 차이는 queue, failure scope, observability 도구를 바꾼다.

성공 상태는 단조롭게 쌓이지 않을 수 있다

DNS cache가 성공한 뒤 route가 바뀔 수 있고, TLS가 성공한 connection도 idle timeout으로 닫힐 수 있으며, HTTP response가 유실된 뒤 server transaction은 commit됐을 수 있다. 각 component는 자기 state만 안다. Exactly-once를 network ACK로 만들 수 없고 idempotency key·deduplication·transaction status 조회가 필요하다.

5. 실무 설계 판단과 best practice

판단권장 기준과 이유
보안 경계 문서화각 hop의 TLS endpoint, private-key/trust-store owner, plaintext 위치, SNI/SAN, authorization owner를 architecture와 runbook에 적는다.
Edge→origin 보호Network trust만 가정하지 말고 threat model에 따라 TLS/mTLS와 workload identity를 사용한다. Front TLS 성공을 upstream 신뢰로 재사용하지 않는다.
Certificate lifecycleIssuance·rotation·revocation·old/new overlap·rollback을 자동화하고 실제 listener의 chain/SAN/fingerprint/notAfter를 외부 probe한다.
Protocol rolloutH2/H3 negotiation과 fallback을 client/network cohort별 측정한다. Version만 보고 성능 개선을 단정하지 않고 loss·cwnd·flow/QPACK blocking을 함께 본다.
Timeout·retryDNS/connect/TLS/request/pool timeout을 end-to-end deadline 안에 배분한다. Deterministic auth failure는 retry하지 않고 transient failure도 bounded backoff+jitter를 쓴다.
BackpressureConnection/stream/queue limit와 load shedding을 둔다. TLS handshake storm, unlimited H2/H3 streams, unbounded retry가 memory·CPU를 고갈시키지 않게 한다.
ObservabilityRemote IP, SNI/ALPN, TLS version/fingerprint, negotiated HTTP, DNS/connect/TLS/TTFB, pool wait, request ID, app/DB result를 join하되 key/token/body는 redaction한다.
검증 우회-k, trust-all, hostname verification off를 production workaround로 금지한다. 진단 비교를 했다면 scope·duration·결론을 명시한다.
Version/engine 차이: Browser, curl TLS backend, JVM, proxy/LB는 trust store, ALPN, TLS policy, HTTP/3, retry와 error text가 다르다. RFC가 정의한 불변식과 제품의 구현/기본값을 분리하고 target runtime·region·network에서 canary한다.

7. 35분 실습: 보안 경계 백지 복원과 failure drill

사전 조건: curl, openssl, 인터넷 연결. RFC Editor만 호출한다. 실행 전 종이에 Client→DNS→TCP→TLS→HTTP→Edge를 그리고 각 단계의 “보장/미보장/owner”를 먼저 쓴다.

0단계 · 예측표 작성 (5분)

HTTP/1.1과 HTTP/2 각각에 대해 transport, framing, multiplexing, TLS endpoint, loss 영향, 성공 증거를 한 줄씩 적는다. “HTTPS”를 protocol 한 칸으로 쓰지 말고 HTTP와 TLS를 분리한다.

1단계 · 같은 semantics, 다른 framing 협상 (8분)

curl -sS -o /dev/null --http1.1 \
  -w 'forced=h1 negotiated=%{http_version} code=%{http_code} tls=%{time_appconnect}\n' \
  https://www.rfc-editor.org/

curl -sS -o /dev/null --http2 \
  -w 'offered=h2 negotiated=%{http_version} code=%{http_code} tls=%{time_appconnect}\n' \
  https://www.rfc-editor.org/

예상: 둘 다 같은 HTTP status semantics를 쓰지만 negotiated version은 1.1과 2로 갈린다. --http2는 TLS ALPN 협상을 허용하며 build가 HTTP/2를 지원해야 한다.

2단계 · TLS identity와 ALPN 증거 (8분)

printf '' | openssl s_client \
  -connect www.rfc-editor.org:443 \
  -servername www.rfc-editor.org \
  -alpn h2,http/1.1 2>&1 | \
  grep -E 'Protocol|Cipher|ALPN|subject=|issuer=|Verify return code'

예상: Certificate subject/issuer, verify 결과, TLS version/cipher와 ALPN이 보인다. Engine별 출력 형식은 다르다. “Cipher가 있다”와 “hostname identity 검증 완료”를 같은 주장으로 쓰지 않는다.

3단계 · 실패 주입: destination은 같고 SNI/reference identity만 변경 (8분)

curl --noproxy '*' --max-time 8 -v \
  --connect-to wrong.example:443:www.rfc-editor.org:443 \
  https://wrong.example/ -o /dev/null
printf 'exit=%s\n' "$?"

예상: TCP destination은 RFC Editor edge지만 ClientHello SNI와 reference identity는 wrong.example다. Edge 정책에 따라 TLS handshake alert 또는 certificate hostname mismatch로 실패한다. Exact 문구보다 “TCP 성공 뒤, authenticated TLS/HTTP 전”이라는 failure window를 기록한다.

4단계 · 6경계 판정표 완성 (6분)

각 명령에 대해 DNS, TCP, TLS key agreement, certificate identity, ALPN/HTTP, application response를 성공/실패/미관측으로 표시한다. 그다음 “-k로 바꾸지 않고 어디를 복구해야 하는가?”를 SNI route/certificate SAN/trust 관점으로 답한다.

Cleanup과 자주 나는 오류

파일·route·trust store를 바꾸지 않았으므로 cleanup은 없다. HTTP/2 미지원이면 curl -V의 Features를 확인한다. Corporate proxy가 있으면 --noproxy 유무와 proxy certificate를 기록한다. s_client 출력이 다르면 grep 없이 전체 header를 읽되 certificate/private data를 외부에 올리지 않는다. Wrong SNI가 예상과 다른 certificate를 내는 것은 shared edge policy 차이이지 실습 실패가 아니다.

8. 놓치기 쉬운 함정

  • 암호화와 인증은 같은 단어가 아니다. Key agreement 성공 뒤에도 certificate identity가 틀리면 공격자와 안전하게 암호화한 꼴이 될 수 있다.
  • 무결성과 신뢰할 수 있는 내용은 다르다. TLS는 peer가 보낸 bytes의 변조를 막지만 peer가 거짓 data를 보내는 것은 막지 않는다.
  • TLS termination 뒤는 자동으로 보호되지 않는다. Upstream hop마다 새 TLS/mTLS·identity·authorization을 설계한다.
  • HTTP/2 multiplexing이 TCP loss HOL을 없애지 않는다. HTTP/3도 shared congestion/flow/QPACK dependency는 남는다.
  • SNI와 Host/:authority는 시점과 owner가 다르다. SNI는 TLS 선택, Host는 TLS 뒤 HTTP routing이다.
  • Connection reuse는 identity와 principal을 섞을 수 있다. HTTP는 같은 connection의 모든 request가 같은 user라고 가정하지 않는다.
  • 성공 응답과 exactly-once는 다르다. Response loss/retry window는 idempotency와 deduplication으로 다룬다.
  • Observability가 새 유출 경계가 될 수 있다. TLS가 숨긴 token/body를 verbose log에 평문으로 남기지 않는다.
  • “내부망이라 안전”은 통제가 아니다. Plaintext reader, route owner, workload identity와 lateral movement threat를 적는다.

9. 대기업 기술 면접 질문

  1. “HTTPS가 제공하는 것과 제공하지 않는 것을 client→LB→app 구조로 설명하세요.”
    좋은 답변 구조: threat model → front TLS endpoint/private key → confidentiality/integrity/server auth → termination plaintext → upstream 별도 TLS/mTLS → application authz/DB commit 미보장 → logging·rollback.
  2. “HTTP/1.1, HTTP/2, HTTP/3의 framing과 HOL failure scope를 비교하세요.”
    좋은 답변 구조: 공통 HTTP semantics → H1 ordered messages/pipelining → H2 frames/streams over one TCP → TCP loss HOL → H3 QUIC stream offset recovery → shared cwnd/flow/QPACK → negotiation/fallback trade-off.
  3. “특정 tenant만 certificate 오류이고 -k는 성공합니다. 15분 대응을 설계하세요.”
    좋은 답변 구조: SNI/URL/SAN/fingerprint·edge 증거 → TCP/TLS/HTTP success boundary → default cert/partial rollout 가설 → tenant canary route/직전 cert rollback → 검증 우회 금지 → 모든 edge fresh handshake·error budget 확인.

10. 회상·확인 문제와 채점 기준

어제 내용 회상 3문제

  1. time_appconnect − time_connect를 TLS 구간으로 해석할 때 필요한 전제는?
  2. 자체서명 certificate를 trust해도 IP URL에서 hostname mismatch가 난 이유는?
  3. Curl exit 0, HTTP 200, DB commit은 왜 서로 다른 성공 경계인가?

짧은 정답: ① 새 direct connection, proxy/reuse/redirect/IP race와 TLS backend 전제를 적는다. ② Path trust와 reference IP↔presented DNS SAN identity match는 별도 검증이다. ③ 각각 process/transport+protocol, application response, durable state의 owner와 확정 시점이 다르다.

오늘 내용 확인 3문제

  1. 암호화·무결성·인증·인가를 한 문장씩 구분하고 TLS termination 뒤 무엇이 사라지는지 설명하라.
  2. HTTP/2 stream A loss가 B를 막을 수 있지만 HTTP/3에서는 B가 진행할 수 있는 내부 이유는?
  3. “end-to-end TLS” architecture review에서 반드시 물어볼 owner/state 질문 다섯 개를 제시하라.

짧은 정답: ① 내용 은닉, 변조 탐지, peer identity 확인, action 허용 결정이며 termination 뒤 해당 TLS record 보호가 끝나 새 hop 보호가 필요하다. ② H2는 하나의 TCP byte sequence gap을 공유하고 H3는 packet number와 stream offset을 분리해 stream별 delivery를 복구한다. ③ Endpoint/private-key owner, trust store와 peer identity, plaintext 위치, connection pool/timeout, authorization, success/commit 중 다섯 가지. 문항당 정의 1점, state/flow 1점, failure·trade-off 1점으로 총 9점이다.
