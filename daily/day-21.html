회상: refused/timeout/reset packet 차이

오류 문자열을 외우지 않고 packet·socket state·timer로 판정하기 · 복습 45분 + 실습 35분

한 줄 요약
TCP connection refused는 보통 SYN에 대한 즉시 RST처럼 명시적인 거절 증거가 있고, connect timeout은 SYN에 유효한 응답이 없어 timer와 retry budget이 끝난 부재의 결과이며, connection reset은 이미 존재하던 connection을 RST가 비정상 종료한 state transition이다. 다만 firewall·proxy·OS가 오류를 합성할 수 있으므로 문자열이 아니라 관측 위치와 packet을 함께 답한다.

1. 선수 용어 사전

Connection refusedConnect 시도에 목적지 또는 중간 장비가 “이 connection을 받지 않는다”는 오류를 빠르게 반환한 결과. TCP closed port의 RST가 대표적이지만 OS/API가 표시하는 문자열만으로 발신자를 확정하지 않는다.
Connect timeoutSYN-SENT 등 connection establishment가 deadline 안에 완료되지 않은 결과. Packet이 drop됐는지, 응답이 reverse path에서 사라졌는지, route/neighbor 단계인지 추가 증거가 필요하다.
Connection resetTCP RST 처리로 connection state가 즉시 중단돼 application에 오류가 전달된 결과. 정상 EOF를 의미하는 FIN과 다르다.
LISTENServer kernel이 특정 local address/port의 새 SYN을 받을 준비가 된 socket state. Process가 존재해도 올바른 address/port에 LISTEN하지 않으면 connect는 성공하지 않는다.
SYN-SENTActive opener가 SYN을 보낸 뒤 유효한 SYN-ACK 또는 오류를 기다리는 상태. 응답이 없으면 SYN retransmission timer가 작동한다.
Drop / RejectDrop은 packet을 조용히 버려 sender가 timeout으로 추론하게 하고, reject는 RST·ICMP 등 명시적 오류를 돌려 빠르게 실패시킨다. 제품별 action 이름과 packet은 반드시 확인한다.
RSTReset flag. Closed/nonexistent connection, abortive close, invalid state, proxy 정책 등 여러 owner가 만들 수 있다. Source IP만으로 process owner를 단정하지 않는다.
FIN / EOFFIN은 sender 방향에 더 보낼 data가 없다는 정상 종료 signal이고, 앞선 byte를 모두 읽은 application은 EOF를 본다. Reset error와 의미가 다르다.
RTOACK가 없을 때 재전송을 시작하는 TCP timer. Connect timeout은 OS의 여러 SYN 재전송 정책과 application deadline 중 먼저 끝난 경계에서 나타날 수 있다.
Failure window관찰자가 성공/실패를 확정할 수 없는 시간 구간. Reset 전 request가 server application에 전달·commit됐는지는 TCP error 하나로 결정할 수 없다.
Active / Passive openClient의 connect()처럼 connection을 시작하는 것이 active open, server의 listen()/accept()처럼 기다리는 것이 passive open이다.
Observation pointPacket capture나 metric이 실제로 본 위치. Process 앞, host veth, physical NIC, LB 앞·뒤의 결론 범위가 서로 다르다.

2. 왜 중요한가

세 오류는 대응 방향이 다르다. Refused는 destination endpoint/listener와 reject policy를, timeout은 end-to-end 경로의 silent drop·route·deadline을, reset은 established state의 owner·abort·idle timeout·application lifecycle을 우선 조사한다.

  • Refused는 빠른 실패다. 목적지에 도달했다는 강한 단서일 수 있지만 NAT/LB/firewall이 대신 RST를 만들면 실제 backend에는 도달하지 않았다.
  • Timeout은 packet 한 종류가 아니다. “Timeout packet”은 없다. 기대한 event가 deadline까지 관측되지 않아 application/OS timer가 만든 결과다.
  • Reset은 처리 결과를 모호하게 만든다. Response 전에 RST가 왔어도 request side effect가 이미 commit됐을 수 있으므로 retry 안전성은 application protocol이 보장해야 한다.
  • 관측 지점이 다르면 같은 사건이 다르게 보인다. Proxy front connection은 정상 HTTP 503인데 back connection은 reset일 수 있고, client에는 proxy source RST만 보일 수 있다.

  1. ① 이름과 route: 오류가 TCP 단계인지 말하기 전에 destination IP·port와 route를 고정한다. DNS 실패는 세 분류보다 앞 단계다.
  2. ② 첫 SYN: Client capture에 SYN이 없으면 application, socket allocation, route/neighbor, capture filter를 본다. SYN이 있다고 wire 전체 전달이 증명되는 것은 아니다.
  3. ③ 응답 종류: SYN에 RST가 즉시 오면 refused 계열, SYN-ACK가 오면 handshake를 진행한다. 아무 유효 응답이 없으면 재전송과 deadline을 본다.
  4. ④ Established 이후: Data exchange 뒤 RST라면 reset owner와 failure window를 추적한다. FIN이면 정상 EOF 경로이므로 같은 오류로 묶지 않는다.
  5. ⑤ Proxy/LB 경계: Front/back connection은 5-tuple·sequence space·timer가 별개다. Proxy log의 request ID와 upstream error를 join한다.
  6. ⑥ 성공 확정: SYN-ACK는 listener 도달, ACK는 peer TCP 수신, HTTP response는 L7 결과다. Business commit은 transaction state로 확인한다.
면접용 10초 분기: “오류 문자열을 먼저 믿지 않고 pcap에서 첫 SYN과 응답을 봅니다. 즉시 RST면 listener/reject, 무응답+재전송이면 drop/route/deadline, handshake 뒤 RST면 connection owner와 abort/idle timeout을 조사합니다. Proxy가 있으면 앞뒤 connection을 분리합니다.”

4. CS 수준 내부 동작

Refused: CLOSED state의 명시적 응답

목적지 TCP가 SYN의 4-tuple에 대응하는 LISTEN/connection state를 찾지 못하면 규격에 따른 RST를 생성할 수 있다. Client는 유효한 RST를 처리해 SYN-SENT를 종료하고 connect()에 빠르게 오류를 반환한다. 그래서 refused latency가 짧은 경우가 많다. 그러나 host firewall의 reject, Kubernetes/Cloud LB listener, NAT 장비가 RST를 합성할 수도 있어 source IP·TTL·양쪽 capture로 owner를 좁힌다.

Timeout: negative evidence와 여러 timer

Timeout은 peer가 보낸 control bit가 아니다. Sender kernel은 SYN을 보내고 RTO/backoff 정책에 따라 재전송하며, application의 connect timeout이나 전체 deadline이 먼저 끝나면 socket call이 실패한다. Client capture에서 SYN 재전송만 보이면 forward SYN, reverse SYN-ACK, middlebox state 중 어느 것이 사라졌는지 아직 모른다. Server capture·flow log·route/neighbor evidence가 필요하다.

또한 timeout은 connect/read/write/request로 분리한다. Handshake가 완료된 뒤 server processing이 느려 read timeout이 난 것을 connect timeout으로 부르면 route와 firewall을 잘못 고친다. Timestamp로 DNS→connect→TLS→TTFB→total phase를 나눈다.

Reset: sequence-validated state transition

RST는 connection을 비정상 종료하므로 unread receive data, pending send data, application response가 사라질 수 있다. Modern TCP는 blind reset 공격을 줄이기 위해 sequence/window 검증과 challenge ACK 같은 방어를 사용할 수 있다. 정확한 처리와 telemetry는 RFC 9293·RFC 5961, kernel version을 확인한다.

RST 직전의 packet이 중요하다. Closed port SYN-RST는 application data가 없지만, established reset은 request가 peer kernel·application에 도착했을 가능성이 있다. send() 성공이나 TCP ACK만으로 business commit 여부를 결론내리지 않는다.

5. 실무 설계 판단과 best practice

판단권장 기준과 이유
오류 taxonomyDNS, connect-refused, connect-timeout, TLS, read-timeout, EOF, reset, HTTP status를 별도 metric으로 둔다. 하나의 network_error로 합치면 owner가 사라진다.
Endpoint evidence실패 시 resolved IP·port, source IP, route, AZ, proxy/LB hop, socket state와 timestamp를 남긴다. Credential/payload는 최소화한다.
Timeout budgetConnect/read/overall deadline을 구분하고 남은 budget을 downstream에 전파한다. Timeout 증가는 queue·동시성·복구시간을 키울 수 있다.
Retry eligibilityRefused·timeout·reset 모두 무조건 retry하지 않는다. Idempotency, 결과 불명확 여부, remaining deadline, retry budget, jitter/backoff를 함께 본다.
Graceful deployReadiness 제거→신규 connection 차단→in-flight drain→close 순서를 둔다. Listener 선종료나 강제 kill은 refused/reset spike를 만든다.
Pool alignmentClient pool idle/max-age를 LB/NAT/backend timeout과 맞추고 stale connection 검증을 둔다. 재사용 첫 request reset을 줄인다.
SecurityRST source와 sequence validity를 검증하고 capture 접근을 제한한다. Refused를 숨기려고 모든 port를 drop하면 scanner 정보는 줄 수 있지만 운영 복구시간은 늘 수 있다.
Anti-pattern: refused를 DNS 장애라 부르거나, timeout을 server down으로 단정하거나, reset을 모두 retry하거나, RST가 보였다는 이유로 TCP ACK 이후의 business side effect를 없었다고 판단하지 않는다.

6. 장애 대응 표

상황: 배포 직후 일부 client에는 refused, 다른 AZ에는 timeout, 기존 pooled connection에는 reset이 동시에 증가했다.

순서실행 내용
증상오류를 endpoint·AZ·version·신규/재사용 connection·request method별로 분리하고 connect/TTFB/total latency와 발생 시각을 비교한다.
먼저 수집할 증거/지표양끝·proxy pcap의 SYN/SYN-ACK/RST/FIN·seq/ack/timestamp, ss -lntpo/ss -tanpo, route/neighbor, firewall/SG/NACL/LB flow log, listener/readiness, pool age, deploy/drain log, transaction status를 변경 전에 보존한다.
가능한 가설Listener 선종료·wrong bind, firewall reject/drop 차이, route/AZ black hole, LB target drain race, stale pooled connection, backend abort/crash, unread data close, NAT state expiry를 증상별로 매핑한다.
안전한 첫 조치문제 version/AZ 신규 traffic을 drain하고 known-good endpoint로 소량 우회한다. Retry는 idempotent request와 budget 안으로 제한하고 결과 불명확 transaction을 status query로 판정한다.
Rollback/복구최근 listener/readiness/firewall/route/LB timeout/pool 변경을 원복한다. SYN-ACK 회복→RST/refused 감소→pool 재생성→in-flight/transaction 일관성→SLO 순서로 확인한다.
하지 말아야 할 조치모든 timeout 확대, 전 요청 무제한 retry, 증거 전 전 pod 동시 restart, firewall 전체 해제, 한쪽 capture만으로 RST owner 확정, ACK만 보고 side effect 단정, TIME_WAIT 전역 제거를 하지 않는다.

8. 놓치기 쉬운 함정

  • “Timeout packet”은 없다. 기대 event가 timer 안에 없었다는 local 결과다.
  • Refused가 항상 server process RST는 아니다. Firewall/LB/NAT가 reject를 합성할 수 있다.
  • Reset과 FIN을 같은 close로 묶지 않는다. FIN은 정상 EOF, RST는 abort error다.
  • Client SYN 관측만으로 server 도달을 증명하지 않는다. Capture 위치와 qdisc/offload를 본다.
  • Port가 열렸다는 사실과 application healthy를 혼동하지 않는다. SYN-ACK 뒤 HTTP/TLS/app failure가 남는다.
  • Reset 뒤 request 미처리를 단정하지 않는다. Peer ACK·app log·transaction status를 확인한다.
  • ICMP/firewall 오류를 TCP RST로 뭉뚱그리지 않는다. Protocol과 실제 packet type을 기록한다.
  • Proxy 앞뒤를 한 connection으로 그리지 않는다. Tuple·sequence·timeout owner가 둘이다.
  • Retry로 진단 증거를 덮지 않는다. Retry attempt별 새 tuple과 original outcome을 보존한다.
  • Cleanup 없는 failure injection을 남기지 않는다. 다음 실험의 baseline을 오염시킨다.

9. 대기업 기술 면접 질문

  1. “Connection refused와 timeout을 packet 수준에서 비교하세요.”
    좋은 답변 구조: destination IP/port 고정 → SYN 공통 → refused의 즉시 RST와 빠른 state 종료 → timeout의 무응답·SYN retransmission·deadline → reject/drop → listener/route/firewall evidence → proxy 예외.
  2. “POST 전송 뒤 connection reset이면 retry합니까?”
    좋은 답변 구조: connect/send/ACK/app-read/commit failure window → RST 직전 seq/ack → 결과 불명확 → idempotency key·dedup·status query → remaining deadline·bounded jitter retry → 대안과 중복 비용.
  3. “Client pcap에는 SYN이 있는데 server pcap에는 없습니다. 어디가 문제입니까?”
    좋은 답변 구조: capture point/clock/filter 검증 → 두 지점 사이 범위만 주장 → qdisc/veth/NIC/bridge/router/LB counter → NAT tuple mapping → midpoint capture/flow log → safe reroute와 rollback.

10. 회상·확인 문제와 채점 기준

어제 내용 회상 3문제

  1. Client egress에만 80ms delay를 넣었을 때 RTT가 정확히 160ms 증가한다고 단정할 수 없는 이유는?
  2. 같은 sequence range가 두 번 보이면 무엇을 확정할 수 있고 무엇은 확정할 수 없는가?
  3. 5% packet loss와 HTTP request 실패율이 같지 않은 이유는?

짧은 정답: ① 방향·packet 역할·qdisc 통과가 비대칭이고 jitter/processing이 더해진다. ② Retransmission 후보는 말할 수 있지만 최초 loss hop은 양끝/중간 증거 없이 모른다. ③ Packet 단위 확률이며 request당 packet 수·TCP recovery·RTO·deadline이 결과를 바꾼다.

  2. min(cwnd,rwnd)에서 각 window의 owner와 보호 대상은 무엇인가?
  3. CLOSE_WAIT와 TIME_WAIT가 많을 때 owner·수집 증거·첫 조치를 비교하라.

짧은 정답: ① Refused/listener·reject, timeout/drop·route·deadline, reset/abort·idle timeout·process lifecycle. ② cwnd는 sender가 network congestion을, rwnd는 receiver가 receive buffer를 보호한다. ③ CLOSE_WAIT는 local app close 지연이므로 fd/stack/EOF path를, TIME_WAIT는 active close 안전 state이므로 close rate·tuple·port budget을 본다. 문항당 packet/state 1점, owner 1점, 장애·trade-off 1점으로 총 9점이다.
